Bônus: CSS moderno & layout

~6h · a linguagem mudou muito nos últimos 5 anos — provavelmente mais que o React

Grid, container queries, @layer e a cascata em camadas resolveram problemas que antes exigiam gambiarra ou uma lib inteira (clearfix, grid systems de 12 colunas, especificidade em guerra). Esta seção é o CSS que um sênior de front-end deveria saber nomear, não só usar por tentativa e erro.

Munição da sua entrevista · migração pro Tailwind v4

O bloco de Next.js/Tailwind já cobre que a v4 move os tokens de design pra @theme, viram custom properties nativas. Isso conecta direto aqui: os tokens gerados pelo Tailwind existem em runtime como CSS custom property, então dá pra ler ou sobrescrever com JavaScript (tema escuro alternável sem novo build) — algo que um objeto de config compilado em build nunca permitiu.

Por que isso importa: conecta duas seções do guia numa resposta só, o que sempre soa mais senior do que citar fatos soltos.

Responda em voz alta · só depois abra o gabarito
  1. Duas regras têm a mesma especificidade e miram o mesmo elemento. Qual vence?
    ver resposta

    A que aparece depois no CSS (ou é importada por último) — é o último critério de desempate da cascata, depois de origem e especificidade. É por isso que a ordem dos <link> de stylesheet, ou a ordem de import, importa mesmo quando ninguém usa !important.

  2. Por que @layer reset, components, utilities; resolve o problema de um botão de componente perder pra uma regra de reset mais específica?
    ver resposta

    Porque entre camadas diferentes, a especificidade não decide — só a ordem de declaração das camadas decide, e camada declarada depois sempre vence a anterior. Declarando reset antes de components, qualquer regra de componente vence o reset, mesmo com especificidade menor. Dentro da mesma camada, a especificidade normal continua valendo.

  3. Um card precisa virar duas colunas quando tem espaço largo, e uma coluna quando estreito — independente da largura da tela, porque o mesmo card aparece numa sidebar estreita e num conteúdo largo. Media query resolve?
    ver resposta

    Não de forma confiável — media query olha o viewport, não o espaço real disponível pro componente. A ferramenta certa é container query: declara o pai como container-type: inline-size e o filho reage ao espaço daquele pai específico com @container (min-width: …). É o que torna um componente de fato reutilizável em qualquer lugar do layout.

  4. Um elemento com z-index: 9999 aparece atrás de outro com z-index: 1. Causa mais provável?
    ver resposta

    z-index só compara elementos dentro do mesmo contexto de empilhamento. Se um ancestral do elemento de z-index: 9999 criou um novo contexto (por ter opacity < 1, transform, filter, ou position com z-index própria), o 9999 só compete dentro desse contexto — e o contexto inteiro pode estar atrás do outro elemento na pilha externa. Aumentar o número não resolve; é preciso subir na árvore e ver quem criou o contexto.
