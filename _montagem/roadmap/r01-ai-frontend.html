1 · VerO básico, em linguagem simples

Leia isto antes do resto. Cada cartão responde a três perguntas: qual é o problema, como se resolve e o que você diz na entrevista.

1. Streaming: por que a resposta aparece aos pedaços

O problemaUm modelo leva de 5 a 15 segundos para escrever uma resposta inteira. Uma tela parada por 10 segundos parece quebrada.

Como funcionaO servidor manda cada pedaço de texto assim que o modelo o escreve, sem esperar o fim. No navegador, response.body é um fluxo de dados (um stream). Você lê um pedaço de cada vez com getReader() e vai acrescentando o texto na tela.

O detalheO tempo total não muda. O que muda é o tempo até aparecer o primeiro texto, o TTFT (time to first token). É isso que a pessoa sente.

Na entrevista“Streaming não deixa o modelo mais rápido. Ele faz a primeira palavra aparecer em um segundo, em vez de dez.”

2. Os estados da tela

O problemaUm simples “carregando: sim ou não” não descreve uma tela de IA. Ela passa por mais fases, e cada fase mostra uma coisa diferente.

Como funcionaA tela segue esta sequência: idle (parada) → submitted (pedido enviado, nada chegou ainda) → streaming (o texto está chegando) → ready (terminou) ou error (falhou). É o modelo do useChat, o hook mais usado para isso em React.

ExemploEm submitted, mostre “Pensando…” e o botão Parar. Em streaming, o texto crescendo e o mesmo botão. Em error, uma mensagem clara e “Tentar de novo”. O botão Parar usa um AbortController, que cancela o pedido de verdade e não só esconde o texto.

Na entrevista“Eu desenho os estados antes do componente: enviado, chegando, pronto, erro e parado pelo usuário.”

3. Structured output: pedir dados, não texto

O problemaO modelo devolve texto livre, mas o seu componente precisa de dados com formato fixo, por exemplo { summary, options: [...] }.

Como funcionaVocê envia um JSON Schema junto com o pedido. O schema é a descrição do formato: quais campos existem e de que tipo. O modelo responde em JSON seguindo esse formato. Depois, o seu código valida a resposta de novo com Zod, uma biblioteca de validação.

Por que validar duas vezesO schema garante a forma, não o conteúdo. Um campo pode vir vazio, um id pode ser inventado e duas alternativas podem vir marcadas como corretas. Trate a saída do modelo como um formulário que o usuário preencheu: ela pode estar errada.

Na entrevista“O schema garante a forma, e o meu código confere o sentido.”

4. Tool calling: o modelo pede, o seu código faz

O problemaO modelo não sabe o que está no seu banco de dados e não consegue fazer nada fora da conversa.

Como funcionaVocê descreve algumas ferramentas: nome, para que servem e quais argumentos recebem. O modelo responde algo como “quero chamar getOrder com { id: 42 }”. Quem executa é o seu código. O resultado volta para o modelo, que continua a resposta.

CuidadoO modelo não executa nada sozinho. Quem roda é o seu servidor, com as permissões dele. Então valide o argumento e confira se o usuário pode ver aquele pedido, como faria com qualquer formulário.

Não confundaStructured output define o formato da resposta final. Tool calling é um pedido de ação no meio da conversa.

Na entrevista“Se eu só preciso do formato, uso structured output. Se o modelo precisa decidir o que buscar, uso tool calling.”

5. Generative UI: a resposta vira componente

O problemaAlguns resultados ficam ruins em forma de parágrafo, como uma lista de voos, um gráfico ou um pedido para aprovar.

Como funcionaCada ferramenta tem um componente React. Quando o modelo chama showWeather, a tela renderiza <WeatherCard> com os dados que a ferramenta devolveu. O cartão também tem estados: carregando, pronto e erro. O modelo escolhe qual componente aparece, sempre de uma lista fechada que você definiu. Ele nunca gera HTML para a página executar.

Quando não usarSe a resposta tem sempre o mesmo formato, um card fixo preenchido com os dados é mais simples, mais fácil de testar e mais acessível.

Na entrevista“Generative UI é o modelo escolhendo um componente de uma lista fechada. Eu só uso quando o formato da resposta muda de pedido para pedido.”

6. Quando dá errado: erro, retry e aprovação humana

Erro passageiro429 (limite de pedidos estourado), 503 (serviço fora do ar) e queda de rede costumam passar sozinhos. Vale tentar de novo, esperando cada vez mais entre as tentativas (backoff), ou esperando o tempo que a própria API pediu.

Erro permanente400 (pedido mal feito) e 404 (não existe) não melhoram com outra tentativa. Mostre a mensagem e pare.

Prazo de desistênciaA tela nunca fica carregando para sempre. Depois de um tempo, ela diz o que aconteceu e o que a pessoa pode fazer.

Aprovação humanaAntes de uma ação com efeito real (enviar e-mail, apagar, pagar), a IA para e pede confirmação. O nome disso é human-in-the-loop.

AcessibilidadeQuem usa leitor de tela não vê o texto aparecer. Um role="status" (ou aria-live) faz o leitor anunciar que a resposta chegou.

Na entrevista“Eu desenho o caminho de erro junto com o caminho feliz: o que repete, quanto espera, quando desiste e o que a pessoa vê.”

FAZER 1

Os estados de um chat num reducer

20 min · TypeScript

Escreva o tipo State e a função reducer(state, action) de uma tela de chat com IA. As ações são SEND (enviar), CHUNK (chegou um pedaço de texto), DONE (a resposta terminou), FAIL (falhou, com uma mensagem) e STOP (o usuário clicou em Parar).

Regras

  • Não dá para SEND enquanto uma resposta ainda está chegando.
  • STOP no meio guarda o texto que já chegou e marca a resposta como interrompida.
  • Um pedaço que chega depois de parar ou de falhar é ignorado.
  • O tipo não pode permitir estado impossível, como texto em idle ou mensagem de erro em ready.

Pode consultarTypeScript: discriminated unions · MDN: switch · cartão 2 do Ver

dica

Use uma união discriminada: cada estado é um objeto com um campo status e só os campos que fazem sentido nele. Aí o TypeScript não deixa você ler text num estado que não tem texto.

solução comentada

type State =
  | { status: 'idle' }
  | { status: 'submitted' }
  | { status: 'streaming'; text: string }
  | { status: 'ready'; text: string; interrupted: boolean }
  | { status: 'error'; message: string; text: string };

type Action =
  | { type: 'SEND' }
  | { type: 'CHUNK'; text: string }
  | { type: 'DONE' }
  | { type: 'FAIL'; message: string }
  | { type: 'STOP' };

export function reducer(s: State, a: Action): State {
  switch (a.type) {
    case 'SEND':
      // while a response is arriving, a second send is ignored
      return s.status === 'submitted' || s.status === 'streaming' ? s : { status: 'submitted' };
    case 'CHUNK':
      if (s.status === 'submitted') return { status: 'streaming', text: a.text };
      if (s.status === 'streaming') return { status: 'streaming', text: s.text + a.text };
      return s; // late chunk, after a stop or a failure
    case 'DONE':
      if (s.status === 'streaming') return { status: 'ready', text: s.text, interrupted: false };
      if (s.status === 'submitted') return { status: 'ready', text: '', interrupted: false };
      return s;
    case 'FAIL':
      if (s.status !== 'submitted' && s.status !== 'streaming') return s;
      // keep what already arrived: the screen can show the partial text next to the error
      return { status: 'error', message: a.message, text: s.status === 'streaming' ? s.text : '' };
    case 'STOP':
      if (s.status === 'streaming') return { status: 'ready', text: s.text, interrupted: true };
      if (s.status === 'submitted') return { status: 'idle' };
      return s;
  }
}

O que mostrar ao entrevistador: o tipo impede estado impossível (não existe text em idle), o pedaço atrasado não “ressuscita” uma resposta parada, e parar é um estado de verdade, não um detalhe. Na tela real, o STOP também chama abortController.abort() para cancelar o pedido.

Revisar · depois da solução

1 · Explique em voz alta
  1. Por que o State é uma união, e não um objeto só, como { status: string; text?: string; message?: string }?
  2. Por que STOP em submitted volta para idle, mas em streaming vai para ready?
  3. Por que o estado error guarda o texto que já tinha chegado?
respostas
  1. No objeto único, todos os campos são opcionais. Nada impede { status: 'idle', message: 'erro' }, e o código precisa conferir undefined em todo lugar. Na união, cada estado tem só os seus campos, e o TypeScript sabe quais existem depois de um if (s.status === ...).
  2. Em submitted nada chegou ainda, então não existe resposta para guardar: a tela volta ao começo. Em streaming já existe texto, e a regra 2 manda guardá-lo, marcado como interrompido.
  3. Para a pessoa não perder o que já leu. A tela mostra o texto parcial e, abaixo, o aviso de erro com “Tentar de novo”.
2 · Caça ao bug

Esta versão compila sem erro e parece certa. Ela quebra três das quatro regras. Ache os três erros e diga qual regra cada um quebra. (O tipo Action é o mesmo da solução.)


type State =
  | { status: 'idle' }
  | { status: 'submitted' }
  | { status: 'streaming'; text: string }
  | { status: 'ready'; text: string; interrupted: boolean; message?: string }
  | { status: 'error'; message: string; text: string };

export function reducer(s: State, a: Action): State {
  switch (a.type) {
    case 'SEND':
      return { status: 'submitted' };
    case 'CHUNK':
      if (s.status === 'submitted') return { status: 'streaming', text: a.text };
      if (s.status === 'streaming') return { status: 'streaming', text: s.text + a.text };
    case 'DONE':
      return { status: 'ready', text: s.status === 'streaming' ? s.text : '', interrupted: false };
    case 'FAIL':
      if (s.status !== 'submitted' && s.status !== 'streaming') return s;
      return { status: 'error', message: a.message, text: s.status === 'streaming' ? s.text : '' };
    case 'STOP':
      if (s.status === 'streaming') return { status: 'ready', text: s.text, interrupted: true };
      if (s.status === 'submitted') return { status: 'idle' };
      return s;
  }
}
os erros
  1. SEND não olha o estado (regra 1). No meio de uma resposta, um segundo envio volta para submitted e joga fora o texto que estava chegando.
  2. CHUNK não termina com return s (regra 3). Quando o estado não é submitted nem streaming, o código cai no case 'DONE' logo abaixo. Isso se chama fall-through. E o DONE também não confere o estado. Resultado: um pedaço que chega depois de um erro transforma o erro em ready com texto vazio, e a mensagem de erro some.
  3. message? no ready (regra 4). O tipo passa a aceitar “pronto com mensagem de erro”, um estado impossível.

Para o TypeScript achar o erro 2 sozinho, ligue noFallthroughCasesInSwitch no tsconfig.json. Com ela, um case que cai no próximo vira erro de compilação.

3 · Mude um requisito

Agora existe o botão “Tentar de novo”. Ele gera a ação RETRY, que só vale no estado error e recomeça o pedido. O que muda no tipo e no reducer? O que o TypeScript faz se você esquecer uma parte?

o que muda

Duas mudanças. No tipo, mais uma opção: | { type: 'RETRY' }. No reducer, mais um case: se s.status === 'error', devolve { status: 'submitted' }; senão, return s.

Se você mudar o tipo e esquecer o case, o TypeScript reclama que a função nem sempre devolve um State. É a união discriminada trabalhando a seu favor: ela aponta todos os lugares que precisam tratar a ação nova.

Fora do reducer: a tela precisa disparar um fetch novo, com um AbortController novo. O reducer só descreve a tela; quem faz o pedido é o componente.

FAZER 2

Validar a resposta do modelo com Zod

15 min · TypeScript + Zod

O modelo devolve um texto que deveria ser este JSON: { "summary": "...", "options": [{ "letter": "A", "correct": false, "reason": "..." }, ...] }. Escreva parseExplanation(text, answerKey), que devolve os dados validados ou null.

Regras

  • O texto pode nem ser JSON válido.
  • summary e cada reason não podem ser vazios. São de 4 a 5 alternativas, com letras de A a E, sem repetir.
  • Exatamente uma alternativa correta, e ela tem de ser a letra do gabarito (answerKey).

Pode consultarZod: API · MDN: JSON.parse · cartão 3 do Ver

dica

Separe em três portas: JSON.parse dentro de try (o texto é JSON?), safeParse do Zod com refine (a forma e as regras estão certas?) e uma comparação com o gabarito (o sentido está certo?).

solução comentada

import { z } from 'zod';

const Option = z.object({
  letter: z.enum(['A', 'B', 'C', 'D', 'E']),
  correct: z.boolean(),
  reason: z.string().trim().min(1),
});

const Explanation = z
  .object({
    summary: z.string().trim().min(1),
    options: z.array(Option).min(4).max(5),
  })
  .refine((x) => x.options.filter((o) => o.correct).length === 1, 'needs exactly one correct option')
  .refine((x) => new Set(x.options.map((o) => o.letter)).size === x.options.length, 'duplicate letter');

export type Explanation = z.infer;

export function parseExplanation(text: string, answerKey: string): Explanation | null {
  let raw: unknown;
  try {
    raw = JSON.parse(text); // gate 1: is it JSON?
  } catch {
    return null;
  }
  const r = Explanation.safeParse(raw); // gate 2: shape and rules
  if (!r.success) return null;
  const correct = r.data.options.find((o) => o.correct)!;
  return correct.letter === answerKey ? r.data : null; // gate 3: does it match the answer key?
}

O que mostrar ao entrevistador: quando volta null, quem chama refaz o pedido ao modelo (até 3 vezes, como no Gabarita). Isso serve para resposta malformada. Para erro de rede ou de cota, refazer na hora não ajuda: aí entra o retry com espera do cartão 6.

Revisar · depois da solução

1 · Explique em voz alta
  1. Por que o JSON.parse fica dentro de um try?
  2. Por que safeParse, e não parse?
  3. Por que a comparação com o gabarito fica fora do schema?
respostas
  1. Porque ele lança um erro quando o texto não é JSON, e o modelo às vezes responde “Claro! Aqui está:” antes do JSON. Sem o try, a função quebra em vez de devolver null.
  2. parse também lança erro. safeParse devolve { success, data } ou { success, error }, e o código decide o que fazer sem precisar de outro try.
  3. O schema confere a forma, que é igual para toda questão. O gabarito muda de questão para questão e confere o sentido. Separar as três portas deixa claro em qual delas a resposta falhou.
2 · Caça ao bug

Esta versão compila e passa no caso feliz. Ache os três erros. Para cada um, escreva uma resposta do modelo que passa quando não deveria (ou que quebra a função).


const Option = z.object({
  letter: z.string(),
  correct: z.boolean(),
  reason: z.string(),
});

const Explanation = z
  .object({
    summary: z.string().min(1),
    options: z.array(Option).min(4).max(5),
  })
  .refine((x) => x.options.some((o) => o.correct), 'needs a correct option');

export function parseExplanation(text: string, answerKey: string) {
  const r = Explanation.safeParse(JSON.parse(text));
  if (!r.success) return null;
  const correct = r.data.options.find((o) => o.correct)!;
  return correct.letter === answerKey ? r.data : null;
}
os erros
  1. JSON.parse fora do try. Com o texto "Claro! Aqui está", a função lança SyntaxError em vez de devolver null, e quem chama não refaz o pedido.
  2. some aceita duas corretas. Com A e C marcadas como corretas e gabarito A, o find pega a primeira (A) e a resposta passa. A regra pede exatamente uma.
  3. Campos frouxos. letter aceita "F" e letras repetidas; reason aceita ""; e summary aceita " ", porque o min(1) conta os espaços (faltou o trim()).

Repare que a versão com bug fica verde no teste do caso feliz. É por isso que a revisão precisa pensar nas entradas ruins, uma por regra.

3 · Mude um requisito

O modelo passou a mandar o JSON dentro de um bloco de código: ```json ... ```. A função deve aceitar isso. Onde você mexe? E onde você não mexe?

o que muda

Só antes da porta 1: limpe as cercas e depois faça o JSON.parse. Por exemplo, text.trim().replace(/^```(?:json)?\s*/, '').replace(/\s*```$/, '').

O schema e a comparação com o gabarito não mudam. A mudança está na embalagem da resposta, não nas regras. Afrouxar o schema para “aceitar mais coisas” seria o erro clássico.

A solução melhor é na origem: pedir structured output ao modelo (o cartão 3 do Ver). Aí ele devolve só o JSON, sem cerca.

3 · ContarAs suas decisões e onde você já aplicou

É o que você fala na entrevista: por que escolheu cada coisa nos seus projetos e a resposta honesta para o que ainda não fez.

Decisões e tradeoffs: escolha, custo e restrição

Cada cartão responde à mesma pergunta: por que assim, e não de outro jeito? Os quatro primeiros campos são um rascunho feito a partir do código; o último é seu. Antes de ler a pista, diga a sua versão em voz alta. O que mais se cobra em entrevista é a linha “Restrição que forçou”: o que impedia a outra opção.

Streaming: por que o Gabarita gera a explicação antes decisão tomada

Em uma frase: O Gabarita não mostra a explicação aparecendo aos pedaços: gera tudo antes, confere e só então mostra.

Escolha
Gerar a explicação em segundo plano (after()) assim que a questão abre, e mostrá-la pronta, em vez de transmitir token a token.
O que compra
Nenhum render espera a IA, e a validação roda sobre a resposta inteira: a aluna nunca vê um texto que ainda pode ser recusado.
O que custa
Não exercita streaming de tokens nem a interface com os quatro estados e o botão de parar. E só funciona porque a geração (10 a 13 s) termina antes de a aluna responder (30 s a 2 min).
Restrição que forçou
A validação (exatamente uma correta, letras iguais às do banco) só decide com a resposta completa. Numa prova de medicina, um texto errado exibido por poucos segundos já ensina errado.
Quando eu faria diferente
Sua vez.Pista: pense numa tela de chat, em que a pessoa fica olhando a espera. A mesma decisão se mantém?

No mundo realO ChatGPT transmite a resposta aos pedaços porque a pessoa está olhando a tela, esperando. O YouTube gera as legendas automáticas depois do upload e entrega o resultado pronto, porque ninguém está acompanhando palavra por palavra. A pergunta que decide é: tem alguém esperando na frente da tela?

Saída da IA: o schema garante a forma, o código garante o sentido decisão tomada

Em uma frase: O schema garante o formato da resposta. Se ela faz sentido, quem confere é o código, que pede de novo quando ela não passa.

Escolha
Pedir JSON ao modelo e validar a saída no código com Zod, refazendo a chamada até 3 vezes quando a validação recusa. No Ally AI o schema também vai na chamada (responseJsonSchema).
O que compra
Regras de domínio que o schema não alcança passam a ser conferidas por código: exatamente uma alternativa correta, e a correta da IA tem de ser a do gabarito.
O que custa
Chamadas extras de IA (e de cota) quando a saída é recusada, e no Ally AI duas definições do mesmo formato para manter em dia, o JSON Schema e o Zod.
Restrição que forçou

Retry: quando repetir e quanto esperar decisão tomada

Em uma frase: Só repete o que pode dar certo numa nova tentativa, e espera o tempo que a própria API pediu.

Escolha
Repetir só o que é transitório (429, 5xx, rede), esperando o retryDelay que a API mandou, com teto; erro permanente (400, 404) não repete.
O que compra
Não gasta cota em tentativa que não pode dar certo, e respeita o tempo que o próprio provedor pediu.
O que custa
Mais política para manter (classificar o erro, ler o prazo, impor o teto), e no pior caso uma única questão pode levar minutos até desistir.
Restrição que forçou
Backoff fixo gasta as tentativas antes do prazo pedido e falha do mesmo jeito; repetir na hora só aumenta a pressão sobre uma cota que já estourou.
Quando eu faria diferente
Sua vez.Pista: retry automático no servidor ou botão de “tentar de novo” na tela? O que muda para a pessoa?

No mundo realEm 2015, a AWS publicou o artigo “Exponential Backoff and Jitter”, que virou referência: esperas que dobram e um pouco de sorteio, para milhares de clientes não tentarem de novo no mesmo segundo e derrubarem o serviço outra vez. Os SDKs oficiais da OpenAI e da Anthropic já repetem sozinhos os erros 429 e 5xx, com espera crescente.

Você já fez streaming de resposta de LLM em produção? não usei em produção

Em voz alta: Em produção, não, e no Gabarita foi escolha: a validação decide sobre a resposta inteira, e a geração termina antes de a aluna responder, então streaming quase não ajudaria. Eu faria streaming numa tela em que o usuário espera olhando, como um chat: o Route Handler devolve o stream, o cliente lê com getReader() (ou com o useChat do AI SDK), a interface tem os quatro estados e um botão de parar com AbortController, e o re-render é limitado a uma pintura por quadro. Por quê: streaming melhora o tempo até o primeiro token, que é o que o usuário percebe, não o tempo total.

In English: “I haven't shipped LLM streaming to production, and in Gabarita that was deliberate: validation needs the full response. For a chat I would stream from a Route Handler, read it with getReader() or useChat, model the four states, and wire a stop button with AbortController, because streaming improves time to first token, not total time.”

Munição da sua entrevista · “a IA propõe, o código verifica” no Gabarita

A explicação de uma questão de residência médica precisa concordar com o gabarito. Por isso, no Gabarita, a saída do Gemini passa por três portas: Zod garante o formato (ExplicacaoSchema), validarExplicacao confere que as letras são as da questão e que a correta da IA é a do banco, e a chamada é refeita até 3 vezes até passar (src/lib/study/explain.ts). Tudo roda fora do caminho crítico, num after(), com trava atômica no Postgres pra gerar cada explicação uma vez só; o cliente consulta em 3s, 9s e 21s e, aos 23s, mostra uma mensagem clara sem travar o estudo.

E a decisão de design que impressiona: geração antecipada em vez de streaming ali. A validação decide sobre a resposta inteira, e como a aluna leva de 30s a 2min por questão e a geração leva 10-13s, a explicação já está pronta quando ela responde.

Por que isso importa: qualquer um liga um useChat. O que separa sênior é escolher a técnica pelo caso, tratar a saída do modelo como entrada a validar, e desenhar o estado de falha junto com o estado feliz.

4 · ProvarPerguntas abertas e múltipla escolha

Responda em voz alta antes de abrir a resposta. A múltipla escolha, no fim, começa com três questões de aquecimento, só de conceito.

Responda em voz alta · só depois abra o gabarito
  1. Por que o Gabarita não faz streaming da explicação, se streaming “é melhor pra UX”?
    ver resposta

    Porque a validação é sobre a resposta inteira: só no fim dá pra saber se a alternativa que a IA marcou como correta é a do gabarito. Transmitir token a token mostraria à aluna um texto que pode ser recusado e substituído — numa prova de medicina, uma explicação errada que aparece por 5 segundos já ensinou errado.

    E o ganho de streaming (tempo até o primeiro token) quase não existe ali: a geração começa num after() quando a questão abre e termina antes de a aluna responder. Streaming resolve espera percebida; quando a geração antecipada já elimina a espera, ela é a escolha mais simples.

  2. Qual a diferença entre structured output e tool calling, e quando você usaria cada um?
    ver resposta

    Structured output formata a resposta final: você quer que o modelo devolva dado num formato que o código consiga usar (o array de análises do Ally AI, a explicação do Gabarita). Tool calling é o modelo pedindo uma ação no meio da conversa: ele devolve nome + argumentos, o seu código executa, e o resultado volta pra ele continuar.

    Regra prática: se você já sabe quais dados o modelo precisa e só quer o formato, structured output. Se o modelo precisa decidir o que buscar ou fazer (consultar o relatório, filtrar por impacto), tool calling. Os dois combinam: o resultado da ferramenta pode alimentar uma resposta final estruturada.

  3. Num fluxo de tool calling, o modelo “chama” sua função. O que isso significa em termos de segurança?
    ver resposta

    O modelo não executa nada: ele devolve um pedido, e quem executa é o seu código, com as permissões do seu servidor. Então os argumentos são entrada não confiável, igual a um formulário: validar com schema, checar autorização do usuário pro recurso (o id pedido é dele?), e nunca dar à ferramenta mais poder que o necessário.

    Prompt injection é o vetor: um texto de terceiro dentro do contexto (o HTML auditado pelo Ally AI, por exemplo) pode tentar convencer o modelo a pedir uma ferramenta perigosa. Por isso ação sensível pede aprovação humana antes de rodar.

  4. O polling do Gabarita (3s, 9s, 21s, desiste em 23s) é uma boa solução? O que mudaria com SSE ou streaming?
    ver resposta

    Pro caso dele, sim: são no máximo 3 requisições, o intervalo crescente acompanha a distribuição real do tempo de geração, e o prazo de desistência garante que a tela nunca fica em loading eterno. O trade-off é de latência: a explicação pode ficar pronta aos 10s e aparecer no refresh dos 21s.

    Com SSE (ver Semana 4), o servidor avisaria no instante em que a explicação fosse gravada — menos latência, mas uma conexão aberta por aluna, o que pesa em serverless com limite de duração de função. É o trade-off clássico entre polling (simples, sem estado) e push (imediato, com conexão).

  5. Dê dois exemplos de human-in-the-loop nos seus projetos e diga por que um deles foi substituído por verificação automática.
    ver resposta

    No Gabarita: questão extraída de PDF pela IA nasce com needsVerification: true e vai pra fila /verificacao, onde um revisor confirma, rejeita ou edita; e o aluno pode reportar “gabarito errado”, o que prioriza a fila.

    O resumo de diretriz clínica trocou revisão humana por verificação determinística: só é publicado se a citação que a IA propõe existir palavra por palavra no texto da fonte (src/lib/diretrizes/citacao.ts). Quando existe um critério objetivo e barato, o código decide; humano fica pro que exige julgamento.

  6. Qual a diferença entre Generative UI e só renderizar o JSON da IA num card fixo? E quando vale a complexidade?
    ver resposta

    No card fixo, quem decide o componente é você: a IA só preenche dados num lugar previsto (é o que o Gabarita e o Ally AI fazem, e é a escolha certa quando a forma da resposta é sempre a mesma). Na Generative UI, o modelo escolhe, por uma ferramenta, qual componente aparece e com quais dados: a lista filtrada, o gráfico, o cartão de aprovação. O front mantém um mapa “nome da ferramenta → componente” e renderiza a part tool-<nome> pelo estado (carregando, pronto, erro).

    Vale quando a intenção do usuário é aberta e o formato do resultado varia, como num assistente com várias capacidades. Não vale quando a forma é fixa: card fixo é mais simples, mais testável e mais acessível. Os cuidados são o conjunto fechado de componentes (o modelo nunca gera JSX nem HTML para executar), props validadas com Zod, texto como alternativa quando a ferramenta falha, e anúncio de conteúdo que aparece sozinho (aria-live).
