JavaScript & React: os modelos mentais

~8h · base pra tudo que vem depois

Você usa hooks corretamente há anos por instinto. Esta semana é sobre nomear por que eles funcionam assim — call stack, closures, e o que realmente acontece quando o React “re-renderiza”. É a pergunta mais comum de entrevista de pleno e a que mais separa quem só usa de quem entende.

Munição da sua entrevista · src/lib/study/scheduler + fluxo de questão

A tela de questão do Gabarita tem um fluxo selecionar → confirmar → corrigir (D85). Isso é uma máquina de estados simples vivendo em useState: cada clique é uma transição, e o React só re-renderiza a alternativa que muda de estado — não a tela inteira. Numa entrevista, é o gancho perfeito pra falar de reconciliação sem decorar teoria solta: você já implementou.

Por que isso importa: entrevistador pergunta “me conta um componente com estado complicado que você fez” — você já tem um exemplo real, não um TodoList de tutorial.

Responda em voz alta · só depois abra o gabarito
  1. Por que console.log dentro de um setTimeout só roda depois que todo o código síncrono termina, mesmo com delay 0?
    ver resposta

    setTimeout não agenda “rode agora”, ele enfileira um macrotask. O event loop só puxa da fila de tarefas quando a call stack está vazia — então delay 0 significa “o mais cedo possível depois que todo o código síncrono terminar”, não “imediatamente”.

    O detalhe que separa a resposta boa da decorada: Promise.then e queueMicrotask vão pra fila de microtasks, que é drenada inteira ao fim de cada tarefa, antes do próximo macrotask. Por isso um .then criado depois de um setTimeout(…, 0) ainda roda primeiro.

  2. O que é uma closure obsoleta (“stale closure”) e como ela se manifesta num useEffect sem array de dependências correto?
    ver resposta

    Uma função criada durante um render captura as variáveis daquele render (escopo léxico). Se o array de dependências não lista o que ela lê, o React não recria o efeito — e ele continua rodando a versão antiga, enxergando o valor congelado no render em que nasceu.

    Caso clássico: useEffect(() => { const id = setInterval(() => setCount(count + 1), 1000); … }, []). O count ali é sempre 0, então o contador trava em 1. Saídas: incluir a dependência, usar a forma de atualização (setCount(c => c + 1)) que não precisa ler o valor, ou guardar o valor mutável num useRef.

  3. Duas listas de itens são iguais, mas você trocou a key de índice pra id. O que muda no re-render, e por quê?
    ver resposta

    A reconciliação compara os filhos posição a posição, casando por (tipo, key). Com key de índice, inserir ou remover no meio desloca todo mundo: o React acha que o item da posição 2 continua sendo “o item 2” e apenas atualiza as props dele — o DOM e o estado interno (texto digitado num input, foco, animação em curso) ficam grudados na posição, não no dado.

    Com id estável, o React reconhece que é o mesmo elemento em outro lugar: move o nó do DOM e preserva o estado do componente. Bônus: trocar a key de propósito é a forma idiomática de resetar um componente.

  4. Por que você não pode chamar um hook dentro de um if?
    ver resposta

    Porque o React não guarda hooks por nome — guarda por ordem de chamada, numa lista ligada pendurada no fiber daquele componente. O primeiro useState do render é o slot 1, o segundo é o slot 2, e assim por diante.

    Um if (ou um return antecipado, ou um loop de tamanho variável) muda essa ordem entre um render e outro: o valor que era do useState vai parar no slot do useEffect, e você recebe estado trocado ou um erro de “rendered fewer hooks than expected”. Não é convenção de estilo, é consequência direta da estrutura de dados.

Munição da sua entrevista · src/lib/security/csp.ts

Comentário real do seu código, no módulo que monta a CSP:

/**
 * Este módulo é carregado pelo MIDDLEWARE, que roda no runtime edge:
 * nada de `node:crypto` aqui (`createHash` não existe lá).
 * `crypto.getRandomValues` e `btoa` são globais nos dois runtimes.
 */
export function gerarNonce(): string {
  const bytes = new Uint8Array(16);
  crypto.getRandomValues(bytes);
  return btoa(String.fromCharCode(...bytes));
}

Por que isso importa: é um exemplo real e específico de “runtime Edge tem uma API diferente do Node” — a maioria dos candidatos só repete a frase de decoreba. E o motivo de toda rota do Gabarita ser dinâmica (o layout raiz lê headers() pra pegar o nonce) é outro exemplo direto de renderização estática vs. dinâmica na prática, com uma consequência real: página pré-renderizada serviria HTML sem nonce, e a CSP bloquearia o próprio app — tela branca em silêncio.

Responda em voz alta · só depois abra o gabarito
  1. Diferença entre um Server Component e um Client Component — o que cada um NUNCA pode fazer?
    ver resposta

    Server Component nunca pode ter estado ou ciclo de vida (useState, useEffect), registrar event handler (onClick) nem tocar em API de navegador (window, localStorage) — ele roda uma vez, no servidor, e não vai pro bundle do cliente.

    Client Component nunca pode acessar diretamente banco, segredo ou sistema de arquivos: tudo que ele importa é enviado ao navegador, então uma chave de API ali é uma chave vazada.

    Correção que vale ponto: “Client” não quer dizer “só no cliente”. No primeiro request ele também é renderizado no servidor (SSR) e depois hidrata. O que a diretiva marca é a fronteira a partir da qual o código vai também pro bundle.

  2. Você chama headers() ou cookies() num layout raiz. O que isso faz com o resto da árvore de rotas, e por quê?
    ver resposta

    São APIs dinâmicas: o resultado depende do request, então a rota não pode ser pré-renderizada em build nem servida do Full Route Cache. Chamado no layout raiz, isso vale pra toda a árvore abaixo — o app inteiro passa a renderizar por request.

    É exatamente o custo consciente do nonce de CSP no Gabarita, e a resposta honesta é dizer que foi uma troca deliberada: sem isso a página pré-renderizada serviria HTML com um nonce velho e a própria CSP bloquearia o app. Com Cache Components / PPR dá pra isolar a parte dinâmica numa fronteira de Suspense e manter a casca estática.

  3. ISR: o que exatamente é revalidado, e o que os outros usuários veem enquanto isso acontece?
    ver resposta

    Revalida aquela rota gerada (a entrada dela no Full Route Cache), não o app inteiro. O comportamento é stale-while-revalidate: o primeiro request depois do prazo ainda recebe a versão antiga e dispara a regeneração em segundo plano; quem chega depois recebe a nova.

    Ou seja, ninguém fica esperando um build — e se a regeneração falhar, a versão antiga continua sendo servida em vez de virar erro. Vale citar o par de invalidação sob demanda: revalidatePath / revalidateTag, para quando o gatilho é um evento e não o relógio.

  4. Por que o Tailwind v4 não precisa mais escanear seu tailwind.config.js em JS?
    ver resposta

    Porque na v4 a configuração mora no próprio CSS, via @theme: os tokens do design system viram custom properties nativas. O motor (reescrito em Rust) não precisa carregar e avaliar um módulo JavaScript pra descobrir sua paleta e sua escala de espaçamento, e a descoberta dos arquivos de conteúdo passou a ser automática.

    A consequência prática que ninguém menciona em entrevista: os tokens passam a existir em runtime, no navegador. Trocar tema, escopo ou densidade vira CSS puro — algo que um objeto JS compilado em build nunca permitiu.

Responda em voz alta · só depois abra o gabarito
  1. Duas transações leem a mesma linha e uma atualiza. A outra ainda enxerga o valor antigo até fazer commit — por quê, em MVCC?
    ver resposta

    Porque o Postgres não sobrescreve a linha. Um UPDATE escreve uma nova versão da tupla e marca a antiga com o xmax da transação que a substituiu. Cada transação carrega um snapshot (quais txids já estavam commitados quando ela começou) e só enxerga as versões visíveis nesse snapshot.

    Daí o slogan do MVCC: leitor nunca bloqueia escritor, escritor nunca bloqueia leitor. O preço é lixo: tuplas mortas que o autovacuum precisa recolher. Se ele não dá conta, você paga em bloat, índices inchados e, no limite, risco de wraparound de txid.

  2. Você tem um índice em (status, especialidadeId). Uma query filtra só por especialidadeId. O índice ajuda?
    ver resposta

    Pela regra do prefixo mais à esquerda, não do jeito que você quer. A árvore B está ordenada primeiro por status; sem esse campo no filtro, não existe faixa contígua pra percorrer.

    O Postgres pode ainda usar o índice — com status tendo pouquíssimos valores distintos, um bitmap scan ou skip scan às vezes compensa — mas você não deveria contar com isso. O índice confiável é (especialidadeId, status), ou um só de especialidadeId. E a frase que fecha a resposta: “eu não chuto isso, eu rodo EXPLAIN (ANALYZE, BUFFERS) e leio o plano”.

  3. Por que rodar uma migration através de um pooler em transaction mode pode travar ou falhar silenciosamente?
    ver resposta

    Em transaction mode (PgBouncer, o pooler da Neon/Supabase), cada transação pode cair numa conexão de backend diferente — não existe sessão estável. Tudo que é por sessão se perde ou se aplica na conexão errada: prepared statements, SET/search_path, advisory locks de sessão, temp tables.

    Migrations dependem justamente disso: pegam lock, rodam DDL longo, às vezes fora de uma transação (CREATE INDEX CONCURRENTLY). Resultado: trava, estoura timeout ou aplica pela metade. A regra operacional é simples — app pela porta do pooler, migration pela conexão direta.

  4. Dê um cenário real onde você escolheria MySQL em vez de Postgres.
    ver resposta

    Cenários legítimos: a hospedagem ou o produto só suportam MySQL bem (WordPress, boa parte do shared hosting); o time já opera MySQL há anos e sabe fazer failover às 3h da manhã; ou você precisa de sharding horizontal massivo com Vitess/PlanetScale, onde o ecossistema é maduro no MySQL e não no Postgres.

    A resposta madura é dizer que a escolha raramente é técnica pura, é operacional. E aí você lista o que pesa a favor do Postgres quando não há amarra: tipos ricos (JSONB, arrays, ranges), índices GIN/GiST/parciais/por expressão, CTEs e window functions maduras, extensões (pgvector, PostGIS) e — o que mais salva a pele — DDL transacional: uma migration que falha no meio faz rollback em vez de deixar o schema num estado indefinido.

Concorrência: SO, event loop, filas e tempo real

›
~10h · a parte que você disse ter menos base

Não precisa virar especialista em sistemas operacionais. Precisa saber: por que Node é “single-threaded” e mesmo assim não trava; o que uma fila garante e o que ela NÃO garante; e reconhecer uma race condition quando ela morde seu próprio negócio — o que, aliás, já aconteceu no Gabarita.

Responda em voz alta · só depois abra o gabarito
  1. “Node é single-threaded” — o que exatamente roda numa única thread, e o que não?
    ver resposta

    O que roda numa thread só é o seu JavaScript: o event loop e os callbacks. Ponto.

    Não são single-thread: o thread pool da libuv (fs, dns, zlib, cripto pesada — 4 threads por padrão, ajustável por UV_THREADPOOL_SIZE), o I/O de rede (delegado ao kernel via epoll/kqueue, sem thread nenhuma) e o GC/JIT do V8.

    A conclusão que vale a pergunta: concorrência de I/O é altíssima, paralelismo de CPU é zero sem worker_threads ou cluster. Um laço de 2 segundos calculando algo trava todos os usuários daquele processo, não só quem pediu.

  2. Você processa um job duas vezes porque o worker caiu antes de confirmar. Como se proteger disso sem mudar a fila?
    ver resposta

    Você não conserta isso na fila — praticamente toda fila entrega at-least-once de propósito, porque a alternativa (at-most-once) perde job. A proteção mora no consumidor: torne o efeito idempotente.

    Dois caminhos concretos: (1) gravar uma chave de idempotência com UNIQUE na mesma transação do efeito, de modo que a segunda execução esbarre na constraint e vire no-op; (2) desenhar o efeito pra ser naturalmente repetível — UPSERT em vez de INSERT, “definir estado = pago” em vez de “incrementar saldo”.

    Frase de fechamento: exactly-once não existe na entrega; existe no efeito.

  3. Me dá um exemplo de race condition que você já causou ou corrigiu, fora de banco de dados.
    ver resposta

    Exemplos fortes, todos fora de banco:

    Fetch fora de ordem: o usuário digita na busca, dispara uma requisição por tecla, e a resposta do termo antigo chega depois da do novo e sobrescreve a tela. Correção: AbortController ou uma flag de cancelamento no cleanup do efeito.

    Duplo clique no submit: dois cliques rápidos disparam duas Server Actions. Correção: desabilitar o botão via useTransition mais idempotência no servidor — só a UI não basta, porque o cliente não é confiável.

    A resposta boa descreve o sintoma que o usuário viu, não só o nome do problema.

  4. Quando SSE é melhor que WebSocket, e quando é o contrário?
    ver resposta

    SSE ganha quando o fluxo é unidirecional servidor→cliente: notificação, progresso de job, streaming de tokens de LLM, feed ao vivo. É HTTP puro — passa por proxy, CDN e firewall corporativo sem tratamento especial, reconecta sozinho e retoma pelo Last-Event-ID, e você não mantém um protocolo à parte.

    WebSocket ganha com tráfego bidirecional de alta frequência (chat, colaboração em documento, jogo, presença) ou dados binários, onde o overhead de header de cada mensagem HTTP importaria.

    Pegadinha clássica do SSE: em HTTP/1.1 o navegador limita a ~6 conexões por origem, e cada aba com um stream aberto consome uma. Em HTTP/2 isso deixa de doer, porque tudo multiplexa numa conexão só.

  1. Por que JWT “sem estado” dificulta revogar uma sessão antes da expiração?
    ver resposta

    Porque a validação é feita só pela assinatura, sem consultar nada — que é justamente a propriedade que torna o JWT atraente. Revogar exigiria o estado que o design eliminou. Na prática: um cookie vazado vale até expirar, e você não tem botão de desligar.

    Saídas conhecidas: TTL curto + refresh token rotativo (com detecção de reuso); uma denylist consultada a cada request, que reintroduz estado e desfaz metade do argumento; ou o caminho do Gabarita (D107) — um carimbo credenciaisAlteradasEm que já viaja no mesmo select que lê papel e plano, então a checagem sai de graça, sem consulta extra.

    Detalhe que impressiona: não dá pra usar o iat do próprio token, porque o Auth.js reemite o cookie periodicamente e renova o iat — a sessão comprometida escaparia da comparação.

  2. O que é IDOR, e qual o padrão de código que evita — não de UI, de query?
    ver resposta

    IDOR (Insecure Direct Object Reference) é usar um identificador vindo do cliente pra buscar um recurso sem provar que ele pertence a quem pediu: trocar /prova/123 por /prova/124 e ver a prova de outra pessoa.

    O padrão que evita não é esconder o ID (UUID só dificulta, não protege) nem checar na UI. É colocar o dono na cláusula WHERE da mesma consulta que busca o dado: where: { id: sessionId, session: { userId } }. Nunca em duas etapas — buscar e depois comparar em código é o padrão que a próxima função esquece de repetir.

    É literalmente a D109 do seu projeto, e o teste certo é por função, não por tela: guarda de página confirma quem é a pessoa, nunca de quem é o recurso.

  3. CSP com nonce: o que impede um script injetado de rodar mesmo que ele consiga se inserir no HTML?

O atacante que consegue injetar HTML não sabe o nonce: ele não está no HTML anterior, não é previsível e não sobrevive de uma resposta pra outra. O script entra no DOM e simplesmente não roda.

Ele propaga a confiança de um script com nonce para os chunks que ele carrega — necessário porque o Next importa JS dinamicamente — e faz o navegador ignorar allowlists de domínio, que são exatamente a parte da CSP que costuma ser contornável por um endpoint JSONP esquecido num CDN permitido.

  1. Seu worker de geração por IA hoje só roda local, num Docker Compose. Pra virar produção com vários usuários gerando ao mesmo tempo, o que muda pra escalar horizontalmente?
    ver resposta

    Seis mudanças, na ordem em que doem:

    1. Worker vira stateless — nada em memória ou disco local; estado vai pro Postgres ou pra armazenamento de objetos, senão duas réplicas divergem.
    2. A fila precisa suportar N consumidores sem entregar o mesmo job duas vezes: no Postgres isso é SELECT … FOR UPDATE SKIP LOCKED, que é exatamente o que o pg-boss faz por baixo.
    3. Job idempotente + retry com backoff exponencial + DLQ pro que falha sempre.
    4. O gargalo muda de lugar: não é CPU, é a cota da API de IA. Precisa de limite de concorrência por worker e rate limiting global.
    5. Ciclo de vida: health check, e graceful shutdown que termina o job em voo antes de morrer (senão todo deploy gera reprocessamento).
    6. Autoscaling pelo tamanho da fila, não por CPU — worker de IA fica ocioso esperando rede, e a CPU nunca sobe.

  2. Em que ponto “pg-boss sobre Postgres” para de fazer sentido, e o que você trocaria?
    ver resposta

    Para de fazer sentido quando a fila passa a competir com a carga transacional pelo mesmo banco: taxa alta de enqueue/dequeue gera muita tupla morta e pressão de autovacuum bem na tabela mais quente; ou quando você precisa de fan-out (vários consumidores independentes lendo a mesma mensagem), retenção longa com replay, ou latência de entrega abaixo de milissegundos.

    Ordem de grandeza pra citar sem medo: até alguns milhares de jobs por minuto num banco saudável, Postgres é ótimo — e você economiza uma peça de infraestrutura, um ponto de falha e um sistema de permissões.

  3. O Postgres da Vercel/Neon tem réplica de leitura defasada por alguns segundos. Isso fere consistência ou disponibilidade, no vocabulário do CAP?
    ver resposta

  1. O que é a janela de contexto de um LLM, e o que normalmente acontece quando ela estoura no meio de uma tarefa longa?
    ver resposta

    É o teto de tokens que o modelo enxerga numa única chamada — prompt de sistema, histórico, ferramentas e a resposta, tudo somado. Não é memória: é campo de visão. Entre uma chamada e outra o modelo não lembra de nada; quem carrega o histórico é o harness.

    Quando estoura numa tarefa longa, o harness normalmente trunca ou resume o começo — e o começo é onde estavam as instruções e as decisões já tomadas. O sintoma: o agente passa a repetir trabalho já feito, contradiz uma escolha anterior ou “esquece” uma restrição que você deu no início.

    Por isso agentes sérios compactam contexto e mantêm o que é essencial em arquivo — um DECISOES.md vale mais que 200 mensagens de histórico, porque pode ser relido sob demanda em vez de ocupar espaço permanente.

  2. Qual a diferença entre o modelo (o LLM em si) e o harness (o agente que você usou pra codar)?
    ver resposta

    O modelo é, na prática, uma função de texto pra texto. Ele não lê arquivo, não roda comando, não acessa rede e não lembra de nada entre chamadas. Quando ele “usa uma ferramenta”, tudo o que ele faz é emitir um pedido estruturado.

    O harness é o programa em volta: monta o prompt, declara quais ferramentas existem, executa de fato o comando que o modelo pediu, devolve o resultado, controla o loop de parada, gerencia a janela de contexto e aplica permissões.

    A tese que vale dizer em voz alta: boa parte da diferença entre usar IA bem e mal está no harness, não no modelo — mesmo modelo, harness diferente, resultado incomparável.

  3. Por que seu pipeline de geração valida a saída da IA com Zod em vez de confiar direto no JSON que ela devolve?
    ver resposta

    Porque a saída de um LLM é texto plausível, não um contrato. Mesmo com JSON mode ou saída estruturada, a resposta pode vir com campo faltando, um enum inventado, número como string ou uma alternativa a mais do que a questão devia ter.

  1. Qual a diferença prática entre Strategy e Factory? Um exemplo de cada, seu ou não.
    ver resposta

    Strategy é sobre comportamento intercambiável: uma interface, várias implementações, e o chamador troca sem saber qual está usando. Factory é sobre criação: encapsular a decisão de qual objeto instanciar, pra que o chamador não precise conhecer as classes concretas.

    No seu próprio código: AIProvider como interface, com o pipeline chamando provider.gerar() sem saber se é Anthropic ou outro — isso é Strategy. A função que lê a variável de ambiente e devolve o provider certo é a Factory.

    Elas quase sempre andam juntas, e é justamente isso que confunde: a Factory escolhe a Strategy. Uma responde “como o comportamento varia”, a outra “quem decide qual vem”.

  2. Por que “monolito modular primeiro” costuma ser melhor conselho que “já nasce em microsserviços”?
    ver resposta

    Porque microsserviços trocam um problema fácil — chamada de função, que ou funciona ou lança — por vários difíceis: rede não confiável, transação distribuída (adeus ACID, olá saga), versionamento de contrato, deploy coordenado e observabilidade distribuída.

    E você paga esse preço antes de saber onde as fronteiras reais estão. Essa é a parte que decide a resposta: fronteira errada dentro de um monolito é um refactor de uma tarde; fronteira errada entre dois serviços é uma migração com janela de manutenção.

    O conselho do Fowler (MonolithFirst) não é “monolito pra sempre”: é comece modular, com fronteiras internas explícitas, meça onde dói de verdade — escala independente, time independente, isolamento de falha — e extraia só esse pedaço.

  3. O que é bounded context, e por que dois times podem ter uma definição diferente da mesma palavra (“Cliente”, por exemplo)?
    ver resposta

    Bounded context é o limite dentro do qual um modelo e sua linguagem têm um significado único e consistente.

    Dois times divergem sobre “Cliente” porque não estão falando da mesma coisa: em Vendas, Cliente é um lead com funil, origem e probabilidade de fechar; em Faturamento, é um CNPJ com endereço fiscal, regime tributário e limite de crédito. Mesmo nome, conceitos diferentes.

    A tentativa de fazer um modelo canônico de Cliente pra empresa inteira é exatamente o que produz aquela tabela de 80 colunas onde metade é sempre nula e ninguém pode remover nada. A saída do DDD é o contrário: modelos separados por contexto, cada um coerente internamente, e um mapeamento explícito entre eles (context map) na fronteira.

Responda em voz alta · só depois abra o gabarito
  1. Por que TypeScript deixa passar um objeto com campos a mais pra uma função que só espera dois campos, mas reclama se faltar um?
    ver resposta

    Porque o TypeScript é estruturalmente tipado: um tipo é compatível com outro se tem pelo menos o que o outro exige. Campos a mais não atrapalham ninguém (é subtipagem por largura); campo faltando quebra a promessa e por isso é erro.

    A exceção que confunde todo mundo é o excess property check: passar um objeto literal direto — f({ a: 1, b: 2, c: 3 }) — reclama do c. Mas atribua a uma variável antes e o erro some.

    Não é inconsistência: um literal escrito ali na hora, com campo a mais, é quase sempre erro de digitação ou de entendimento da API — vale avisar. Uma variável pode ter vindo de qualquer lugar e ser legitimamente mais rica que o parâmetro.

  2. Quando um genérico com extends é melhor que any ou unknown?
    ver resposta

    Quando você precisa preservar a relação entre entrada e saída. any desliga a checagem e contamina tudo o que toca; unknown é seguro mas apaga a informação — quem chama recebe algo que precisa estreitar de novo.

    O exemplo canônico: function pega<T, K extends keyof T>(obj: T, chave: K): T[K]. Isso devolve exatamente o tipo daquele campo e erra em compilação se a chave não existe. Nem any nem unknown conseguem isso.

    Regra prática que vale citar: um genérico só está ganhando alguma coisa se o parâmetro de tipo aparecer em pelo menos dois lugares (por exemplo entrada e retorno, ou entrada e restrição). Se aparece uma vez só, ele é decoração — troque por unknown.

  3. Por que derivar o tipo do schema Zod é mais seguro que escrever a interface TypeScript separada, do lado?
    ver resposta

    Porque a interface escrita à mão e o schema divergem em silêncio. Alguém adiciona um campo no schema e o tipo continua o antigo; ou pior, o tipo promete um campo que a validação não garante — e aí o TypeScript te dá confiança em runtime que ele não pode sustentar.

    Com z.infer<typeof schema> existe uma fonte de verdade: o schema. Qualquer divergência vira erro de compilação em vez de undefined em produção.

    É o mesmo princípio de derivar tipos do Prisma em vez de redigitar a tabela em TypeScript. Tipo é uma projeção do contrato, nunca uma segunda cópia dele mantida à mão.

  4. Diferença entre Omit<T, K> e Partial<T> — quando usar cada um?
    ver resposta

    Partial<T> mantém todos os campos e torna cada um opcional — o tipo certo pra um update parcial (PATCH), onde o cliente manda só o que mudou.

    Omit<T, K> remove campos inteiros — “o mesmo usuário, mas sem senhaHash” para o que sai numa API, ou “sem id”, porque quem cria não fornece.

    A diferença que importa: Partial enfraquece a garantia (agora tudo pode faltar, e você precisa tratar todo campo como possivelmente ausente); Omit muda a forma do tipo, e o que sobra continua obrigatório.

    Pegadinha pra citar: Omit não distribui sobre union — aplicado a A | B ele colapsa nas propriedades comuns. O idiomático é um helper distributivo: type OmitD<T, K extends keyof any> = T extends any ? Omit<T, K> : never.

/**
 * Dois baldes porque são dois ataques diferentes:
 * - por E-MAIL: força-bruta contra uma conta específica;
 * - por IP: credential stuffing, muitos e-mails testados

Responda em voz alta · só depois abra o gabarito
  1. Diferença entre 401 e 403 — um exemplo de cada no seu próprio backend?
    ver resposta

    401 Unauthorized é, apesar do nome, “não sei quem você é”: credencial ausente, inválida ou expirada. Formalmente deve vir com o header WWW-Authenticate. A ação certa do cliente é autenticar — mandar pro login resolve.

    403 Forbidden é “sei exatamente quem você é, e mesmo assim não pode”. Repetir o login não muda nada.

    No seu backend: request sem cookie de sessão numa Server Action protegida → 401. Usuária autenticada tentando abrir uma StudySession de outra pessoa (D109) → 403.

    Ressalva que vale ponto: em recurso de outro dono, muita gente prefere devolver 404 em vez de 403 — porque 403 confirma que aquele ID existe, e isso já é vazamento de informação (dá pra enumerar).

  2. O que o TLS garante, e o que ele NÃO garante (um site de phishing pode ter certificado válido)?
    ver resposta

    Garante três coisas: confidencialidade (ninguém no caminho lê), integridade (ninguém altera sem que você detecte) e autenticidade do domínio — você está falando com quem controla aquele nome DNS.

    Não garante nada sobre a honestidade do dono do domínio, sobre a segurança do site, sobre como o servidor guarda seus dados, nem sobre o que acontece depois que a conexão termina.

    Por isso banco-seguro-atendimento.com com cadeado verde é phishing perfeitamente válido do ponto de vista do TLS: um certificado DV só prova controle do domínio, sai em segundos e é gratuito. O cadeado nunca significou “site confiável” — significa “canal cifrado até este nome”. Foi por entender isso errado em massa que os navegadores pararam de mostrar “Seguro” ao lado da URL.

  3. Por que confiar cegamente no header X-Forwarded-For pra saber o IP real do cliente é perigoso?
    ver resposta

    Porque é um header — texto arbitrário que o cliente escreve. Qualquer um manda X-Forwarded-For: 1.2.3.4 e, se você lê o primeiro valor sem pensar, contorna rate limit por IP, ban, geolocalização, allowlist e log de auditoria (que passa a apontar pro inocente).

    O correto é confiar apenas no valor acrescentado pelo seu proxy mais externo: contar da direita pra esquerda, pulando exatamente N proxies confiáveis — porque tudo que está à esquerda pode ter sido forjado pelo cliente e simplesmente repassado adiante.

    Melhor ainda: usar o header que a própria plataforma sobrescreve e controla na borda (a Vercel e a Cloudflare fazem isso). Regra geral: header de rede só vale se um componente confiável o escreveu — e você precisa saber qual é esse componente.

  4. O que muda de fato entre HTTP/1.1 e HTTP/2 numa página com 40 recursos (imagens, JS, CSS)?
    ver resposta

    Em HTTP/1.1, cada conexão transporta uma requisição por vez (head-of-line blocking) e o navegador abre ~6 conexões por origem: os 40 recursos entram numa fila de 6 em 6. Foi daí que nasceram os hacks da época — sprites de imagem, concatenação de bundles, inline de CSS crítico e domain sharding.

    Em HTTP/2 tudo multiplexa numa única conexão TCP, com streams paralelos, priorização e compressão de header (HPACK, que importa muito quando 40 requests repetem os mesmos cookies). Os 40 recursos viajam concorrentes — e os hacks de 1.1 viram contraproducentes: um bundle gigante impede cache granular e sharding só multiplica handshakes.

    O que HTTP/2 não resolve: o head-of-line blocking do próprio TCP. Um pacote perdido segura todos os streams, porque o TCP entrega em ordem. É exatamente isso que o HTTP/3 resolve, trocando TCP por QUIC sobre UDP, onde cada stream se recupera sozinho.

 * existe, e só quando o Google confirma email_verified —

  1. OAuth resolve autenticação ou autorização? Por que “login com Google” tecnicamente usa as duas coisas (OAuth + OIDC)?

    OAuth 2.0 é autorização delegada, não autenticação. Ele existe pra dar a um app um token com escopo limitado pra agir em nome do usuário numa API, sem que o usuário entregue a senha. Ele não diz quem o usuário é — tratar access token como prova de identidade é um antipadrão clássico e a origem de várias falhas reais.

    OIDC (OpenID Connect) é a camada fina em cima do OAuth que acrescenta identidade: o escopo openid, o endpoint /userinfo e sobretudo o ID token — um JWT com sub, email, email_verified, iss, aud, nonce.

    “Login com Google” usa os dois porque faz duas coisas: OIDC pra estabelecer quem é, e OAuth pro token que eventualmente acessa uma API do Google (agenda, contatos) em nome dessa pessoa.

  2. Por que seu app só vincula uma conta Google a um usuário que JÁ existe, e só se o e-mail vier verificado?
    ver resposta

    Porque o e-mail é o único elo entre a conta do provedor e a conta local — e ele só é confiável se o provedor afirmar que verificou a posse.

    Exigir que a conta já exista elimina a criação silenciosa de conta por OAuth e o cenário em que alguém “reivindica” um e-mail ainda não cadastrado, deixando uma conta plantada esperando a vítima chegar. Exigir email_verified elimina o takeover direto.

    Em entrevista, o enquadramento certo é assumir a troca: menos conveniência no cadastro, zero risco de sequestro de conta por vínculo automático. É uma decisão de produto defensável — e mostra que você sabe que a alternativa “vincula sempre que o e-mail bater” é o padrão inseguro que muita gente implementa sem perceber.

  3. O que dá errado se você confiar só no e-mail devolvido pelo provedor, sem checar email_verified?
    ver resposta

    Takeover de conta. Alguns provedores permitem cadastrar um endereço sem provar posse dele (foi o caso histórico de vários, e ainda acontece em provedores corporativos e instâncias self-hosted).

    O ataque é direto: o atacante cria no provedor uma conta com o e-mail da vítima, clica em “entrar com esse provedor” no seu app, o seu app faz o match por e-mail — e ele cai dentro da conta da vítima sem nunca tocar na senha dela, sem MFA, sem nada.

    Regra: só faça match por e-mail se vier email_verified: true, e nunca vincule automaticamente contas de provedores diferentes só porque o endereço coincide. Se precisar permitir o vínculo, exija que o usuário esteja autenticado na conta local no momento de vincular — que é exatamente o que o Gabarita faz.

  4. Diferença entre access token e ID token — qual dos dois prova identidade?
    ver resposta

    O ID token prova identidade. É um JWT emitido pelo provedor para o seu app (aud = seu client_id), e você o valida: assinatura contra o JWKS do provedor, iss, aud, exp e o nonce que você mandou. Só depois disso as claims valem alguma coisa.

    O access token é uma credencial de acesso destinada à API do provedor. Pode até ser opaco (sem estrutura legível), você não deveria inspecionar, e ele não fala sobre o seu app — só se repassa em Authorization: Bearer.

    O erro clássico — e o motivo da pergunta — é aceitar um access token como prova de identidade. Como ele não tem aud apontando pro seu app, um token emitido legitimamente pra outro aplicativo seria aceito pelo seu: é o confused deputy. Um app malicioso qualquer, autorizado pela vítima pra ler o perfil dela, passa a conseguir entrar como ela no seu sistema.

Munição da sua entrevista · src/lib/study/scheduler (SM-2)

Você já implementou um algoritmo de verdade, com estado, invariantes e casos de borda — o SM-2, que decide quando cada questão volta a aparecer. Não é um problema de LeetCode, e é justamente por isso que ele funciona bem numa entrevista: é um algoritmo que você escolheu, ajustou e sabe defender.

Ganchos concretos que ele te dá: a fila de revisões vencidas é naturalmente uma fila de prioridade por data (heap); a seleção de questões respeitando cota é um problema de escolha sob restrição; e o crescimento do intervalo por fator de facilidade é uma recorrência — a mesma forma de raciocínio da programação dinâmica.

Por que isso importa: a pergunta “me fala de um algoritmo não trivial que você implementou” costuma receber uma resposta de tutorial. Você tem uma resposta com decisões dentro: por que SM-2 e não FSRS, o que acontece quando a pessoa some por 40 dias, e como você testa um algoritmo cujo efeito só aparece semanas depois.

Como é o processo em vaga estrangeira

O funil típico tem cinco etapas e cada uma elimina por um motivo diferente. 1) Screen com recrutador — 20–30 min, em inglês, sobre seu histórico e expectativa salarial (chegue com um número em USD/EUR já pesquisado no levels.fyi). 2) Online assessment: 1–2 problemas cronometrados no HackerRank ou CodeSignal, sem ninguém assistindo. 3) Entrevista técnica com engenheiro: um algoritmo, com você narrando o raciocínio. 4) “Onsite” (hoje remoto): dois algoritmos, um system design e um comportamental. 5) Negociação e formato de contratação — PJ direto, ou EOR via Deel/Remote/Ontop, que muda imposto, benefício e estável jurídico.

Duas coisas que pegam brasileiro bom de surpresa, e nenhuma delas é técnica. A primeira é o comportamental em inglês no formato STAR: não basta ter as histórias (você tem, estão no DECISOES.md) — elas precisam sair fluidas em inglês, e isso só vem falando em voz alta, gravando e reouvindo. A segunda é a autopromoção direta: dizer “I designed” em vez de “we ended up doing” soa arrogante no Brasil e soa normal lá fora; quem não ajusta isso é lido como quem não liderou nada.

Responda em voz alta · só depois abra o gabarito
  1. Você precisa do k-ésimo maior elemento de um fluxo contínuo de números. Qual estrutura, e por quê?
    ver resposta

    Um min-heap de tamanho k. Você insere cada elemento; quando o heap passa de k, remove o menor. No fim, a raiz é o k-ésimo maior.

    Custo: O(n log k) de tempo e O(k) de memória — e a memória é o ponto. Ordenar tudo seria O(n log n) e, num fluxo, exigiria guardar todos os n elementos, o que pode nem caber. A palavra “fluxo” no enunciado é a pista: ela descarta qualquer solução que precise ver o conjunto inteiro de uma vez.

  2. Qual pista num enunciado indica janela deslizante em vez de dois ponteiros genéricos?
    ver resposta

    A palavra contíguo (subarray, substring) somada a uma condição que se pode manter incrementalmente — soma, contagem de caracteres distintos, máximo.

    A janela funciona porque expandir à direita e encolher à esquerda atualiza o estado em O(1), sem recalcular do zero. Se a condição exige recomputar a janela inteira a cada passo, você só escreveu um O(n²) com nome bonito.

    Dois ponteiros genéricos (um em cada ponta) aparecem em outro contexto: array ordenado, procurando um par que satisfaz algo.

  3. Você travou 40 minutos num problema de DP. O que fazer — e por que essa é uma pergunta sobre método, não sobre o problema?
    ver resposta

    Ler a solução, entender a recorrência (não o código), e reescrever do zero no dia seguinte, sem consultar. Depois de uma semana, de novo.

    O motivo: acima de ~25 minutos travado, você parou de aprender o padrão e passou a testar força de vontade. O que se transfere entre problemas é o reconhecimento do padrão, e reconhecimento vem de exposição repetida e espaçada — exatamente a tese do SM-2 que você implementou. Aplicar seu próprio scheduler ao seu estudo é, inclusive, uma ótima resposta pra “como você aprende coisas novas?”.

  4. Numa entrevista de algoritmo, você enxerga na hora a solução ótima. Deve ir direto pra ela?
    ver resposta

    Não. Diga a força bruta primeiro, em uma frase, com a complexidade dela (“dá pra fazer com dois laços, O(n²); acho que consigo O(n) trocando tempo por memória”) e só então desenvolva a boa.

    Dois motivos práticos: (1) o entrevistador precisa te avaliar em comunicação e análise de trade-off, não só ver o código pronto — e a rubrica dele normalmente tem essa linha; (2) se a sua solução ótima estiver errada, você já deixou uma solução correta na mesa.

    Pular etapa e sair codando é o erro mais comum de quem sabe resolver — e é frequentemente confundido com “decorou a resposta”.

B9

Bônus: arquiteturas de software — o catálogo e a escolha

›
~10h · a seção mais longa do guia · é a conversa que decide vaga de pleno pra cima

O B3 te deu o vocabulário — camadas, DDD, Strategy, repositório. Esta seção é o passo seguinte, e é o que realmente pesa numa entrevista: o catálogo inteiro de estilos, o contexto em que cada um faz sentido, e como se defende uma escolha. A distinção que organiza tudo o que vem abaixo: design é decisão barata de reverter (renomear função, extrair componente, trocar biblioteca de data); arquitetura é o conjunto das decisões caras — onde ficam as fronteiras, quem fala com quem, o que é síncrono, onde o dado mora. Design você refatora numa tarde; arquitetura errada você migra por trimestres.

E a resposta certa quase nunca é um nome de estilo. Ninguém escolhe “microsserviços” porque são microsserviços: escolhe-se escala independente, deploy independente ou isolamento de falha, e paga-se rede, consistência eventual e observabilidade distribuída por isso. Arquitetura é a arte de nomear qual atributo de qualidade você está comprando — latência, disponibilidade, custo, evolutibilidade, segurança, time-to-market — e qual você está vendendo pra pagar a conta. Entrevistador experiente não avalia o desenho: avalia se você sabe dizer o que o seu desenho perdeu.

A mesma pergunta em seis contextos

“Qual arquitetura você usaria?” não tem resposta sem contexto — e devolver o contexto antes de responder é parte da resposta esperada. Seis cenários e o que muda em cada um:

Ctx 1
Produto novo, um a três devs, mercado ainda incerto
Monolito modular sobre um Postgres. O atributo dominante é velocidade de mudança, e nenhum outro chega perto: você ainda não sabe onde ficam as fronteiras do domínio. Invista só em duas coisas — módulos por domínio com import cruzado proibido, e a lógica de negócio fora do framework. Isso mantém aberta a porta de extrair um serviço depois, sem cobrar nada por ela hoje.
Ctx 2
SaaS B2B com clientes que exigem isolamento
A decisão que domina é multi-tenancy, não estilo de serviço. Pool (uma base, tenantId em toda tabela, RLS no Postgres) é barato e escala em número de clientes, mas um bug de autorização vaza dado entre empresas. Silo (uma base por cliente) isola de verdade e vende bem em compliance, ao preço de rodar N migrations e observar N bancos. Híbrido — pool no plano padrão, silo no enterprise — é o que a maioria acaba fazendo, e é uma ótima resposta porque mostra que você viu os dois lados.
Ctx 3
Alto tráfego de leitura, escrita modesta
Não é problema de estilo, é de caminho do dado. Na ordem certa de custo/benefício: cache HTTP e CDN → réplica de leitura → cache de aplicação com stale-while-revalidate → desnormalização/materialização → só então CQRS. Quem começa por CQRS está resolvendo com arquitetura um problema que um Cache-Control resolvia — e passa a conviver com consistência eventual sem precisar.
Ctx 4
Muitos times atrapalhando uns aos outros no mesmo deploy
Aqui a extração de serviço finalmente se paga — e note que o driver é organizacional, não técnico (Lei de Conway trabalhando a favor). O erro clássico é decompor por camada (“serviço de banco”, “serviço de UI”), o que produz o monolito distribuído: toda feature exige deploy coordenado dos três, com a lentidão do monolito somada à fragilidade da rede. Decomponha por capacidade de negócio, com dado privado por serviço.
Ctx 5
Sistema com IA no meio do fluxo
Duas propriedades novas mandam no desenho: a chamada é lenta e cara, e a saída é não determinística. Daí: fila e worker pra tudo que não é conversa em tempo real; streaming (SSE) pro que é; abstração de provedor com fallback, porque a API cai e o preço muda; cache por prompt normalizado; e avaliação automatizada tratada como teste de regressão. RAG é apenas um pipes & filters — extrair, fatiar, indexar, recuperar, reordenar, gerar — e a maior parte dos ganhos vem das etapas antes do modelo.
Ctx 6
Legado que ninguém quer tocar, mas que precisa mudar
O cenário mais provável da sua próxima vaga. A resposta esperada é strangler fig: um roteador na frente, uma rota por vez reescrita atrás, o legado encolhendo até morrer — com uma camada anticorrupção traduzindo o modelo velho pro novo, pra que o legado não contamine o desenho novo. O antipadrão emparelhado é o big bang rewrite: dois anos sem entregar valor, com o legado ganhando features enquanto você reescreve.

Como escolher, sem virar chute nem cerimônia

1
Liste os atributos de qualidade e priorize de verdade
Escreva de três a cinco: latência, disponibilidade, custo, evolutibilidade, segurança, time-to-market. Depois ordene — e é a ordenação que dói, porque é ela que revela o trade-off. Uma lista em que tudo é prioridade é uma lista sem decisão. Quantifique quando der: “p95 abaixo de 300 ms” é requisito; “rápido” é desejo.
2
Escreva as restrições antes das soluções
Tamanho e senioridade do time, prazo, orçamento de infra, stack que já existe, exigência regulatória, se há plantão. Metade das arquiteturas ruins nasce de copiar o desenho de uma empresa com cem engenheiros dedicados — a solução estava certa para as restrições dela.
3
Registre a decisão num ADR
Uma página: contexto, opções consideradas, decisão, consequências (inclusive as ruins), status. O valor real aparece 18 meses depois, quando alguém — provavelmente você — pergunta “por que diabos isso é assim?”. Seu DECISOES.md já é exatamente isso; o nome de mercado é ADR.
4
Prototipe o risco, não o fácil
Se a dúvida é se a fila aguenta o pico, o protótipo é a fila sob carga — não a tela. Walking skeleton: um fluxo fim a fim, fininho, atravessando todas as fronteiras arriscadas. É o que transforma discussão de opinião em medição.
5
Transforme a regra em teste que quebra o CI
Fitness function: se a regra é “lib/ não importa nada de app/”, existe uma regra de ESLint que falha o build quando alguém desobedece. Regra arquitetural que vive só num diagrama tem prazo de validade de um sprint; a que vive no CI dura anos.
6
Desenhe em quatro níveis, não em um
O C4 resolve o problema de todo diagrama de arquitetura ser ilegível: separe contexto (quem usa, com o que conversa), containers (as peças que sobem: web, worker, banco), componentes (dentro de uma peça) e código (raramente vale desenhar). Numa entrevista de system design, comece pelo nível 1 — e só desça quando pedirem.

Antipadrões, com o nome que o entrevistador usa

Monolito distribuído — serviços separados que precisam subir juntos e compartilham banco: você pagou o preço da rede sem receber a independência. Big ball of mud — sem fronteira reconhecível; qualquer coisa chama qualquer coisa. Martelo dourado — a ferramenta da última empresa aplicada a um problema que não é o mesmo. Arquitetura de currículo — Kafka, Kubernetes e microsserviços num produto de duzentos usuários. EDA sem rastreio — eventos por toda parte e ninguém sabe quem consome o quê; acrescentar um campo vira arqueologia. Camada anêmica — quatro camadas cujo único trabalho é copiar objeto de uma pra outra. Saber apontar qual deles você evitou, e como, vale mais numa entrevista do que recitar o catálogo inteiro.

Munição da sua entrevista · o Gabarita descrito como arquitetura

Você não tem “um projeto pessoal”: você tem um sistema com fronteiras defensáveis. Descrito no nível 2 do C4 — containers, que é o desenho que se faz numa entrevista:

[navegador] ──HTTP──▶ [app Next.js]
                          │  app/    → rotas: orquestram, não decidem
                          │  lib/    → domínio: scheduler SM-2, cobrança, auth
                          │  types/  → contratos compartilhados
                          │
              ┌───────────┼──────────────────┐
              ▼           ▼                  ▼
       [PostgreSQL]   [fila no          [provedor de IA]
        MVCC, índices  Postgres]         atrás da interface
                       SKIP LOCKED       AIProvider
                          │
                          ▼
                     [worker de IA]
                      assíncrono, retry, idempotência

As três decisões arquiteturais que esse desenho contém, e que valem ser ditas em voz alta:

1. Monolito modular, deliberadamente. Um deploy, fronteiras internas explícitas, domínio em lib/ sem saber que existe um Next.js por cima. O que isso comprou: uma transação ACID resolve o que numa versão distribuída exigiria saga. O que isso custa: quando o worker de IA precisar escalar sozinho, ele terá que sair — e o caminho está mapeado justamente porque ele já é stateless e consome por fila.

2. Fila sobre Postgres em vez de mais uma peça de infra. SKIP LOCKED dá concorrência entre workers sem broker; o preço é não ter fan-out nem replay, e gerar tupla morta na tabela mais quente. Você conhece o ponto de virada (fan-out, replay, latência sub-milissegundo) — e é saber o ponto de virada que caracteriza a escolha como decisão, e não como acaso.

3. Ports & adapters onde a volatilidade está. AIProvider, Scheduler e Queue são portas: o domínio define a interface, e o provedor de IA é adaptador plugado de fora. Não é hexagonal no projeto inteiro — é hexagonal exatamente nas três fronteiras que mudam, e acesso direto no resto. Essa assimetria é a resposta madura: aplicar o padrão onde ele se paga, e não aplicar onde não se paga.

Por que isso importa: a pergunta “me desenha a arquitetura do seu projeto” recebe, quase sempre, um diagrama de caixas sem uma única decisão dentro. A sua versão tem três decisões, cada uma com o que comprou, o que custou e qual é o gatilho pra mudar — e o DECISOES.md é o ADR que prova que elas foram tomadas no dia, e não inventadas na véspera da entrevista.

Responda em voz alta · só depois abra o gabarito
  1. Um time tem seis serviços que precisam subir juntos a cada release e compartilham o mesmo banco. O que isso é, e por que é pior que o monolito de onde saíram?
    ver resposta

    É um monolito distribuído: as fronteiras foram desenhadas por camada ou por conveniência de repositório, não por capacidade de negócio, e o banco compartilhado amarra tudo de novo — qualquer mudança de esquema atinge os seis.

    É pior que o monolito original por soma, não por escolha: você mantém o deploy acoplado e a impossibilidade de mudar sozinho, e acrescenta latência de rede, falha parcial, transação distribuída, versionamento de contrato e depuração em seis logs. Todo o preço dos microsserviços, nenhum dos benefícios.

    O sinal diagnóstico, dito assim numa entrevista: se dois serviços não conseguem fazer deploy independente, eles são um serviço só — mal empacotado. A saída não é voltar tudo pra um monolito: é dar dado privado a cada serviço (database per service) ou reagrupar os que não tinham razão de estar separados.

  2. Qual a diferença entre event notification e event-carried state transfer? Quando cada um é a escolha certa?
    ver resposta

    Event notification é um evento magro: “pedido 123 foi pago”. Quem consome, se precisar de detalhe, volta e pergunta ao dono do dado. Event-carried state transfer é gordo: o evento carrega o estado necessário (valor, cliente, itens), e o consumidor não precisa perguntar nada.

    O trade-off é acoplamento contra autonomia. O evento magro mantém um único dono da verdade e evita duplicação, mas cria acoplamento temporal na volta — se o produtor estiver fora do ar, o consumidor trava. O evento gordo deixa o consumidor trabalhar sozinho e sobreviver à queda do produtor, ao preço de replicar dado, conviver com cópias desatualizadas e transformar o formato do evento num contrato público difícil de mudar.

    Regra prática: notificação quando os consumidores são poucos e o produtor é confiável; state transfer quando o consumidor precisa de autonomia real — times separados, disponibilidade independente, ou um volume de consultas de volta que sobrecarregaria o produtor.

  3. Você precisa salvar um pedido no banco e publicar um evento de “pedido criado”. Como garantir que não acontece um sem o outro?
    ver resposta

    O problema tem nome: dupla escrita. Banco e broker são dois sistemas, e não existe transação atômica entre eles. Se você commita e o publish falha, o resto do mundo nunca soube; se publica antes e a transação faz rollback, você anunciou um pedido que não existe.

    A resposta canônica é o padrão outbox: na mesma transação que grava o pedido, você insere uma linha numa tabela outbox. Ou as duas coisas acontecem, ou nenhuma — é uma transação só, no mesmo banco. Um processo separado (polling da tabela, ou CDC lendo o WAL) lê o outbox e publica de fato, marcando o que já saiu.

    O que isso te dá é at-least-once: o publicador pode morrer entre publicar e marcar, então o evento sai duas vezes — e por isso o consumidor precisa ser idempotente. Repare que é exatamente a mesma conclusão da sua fila: exactly-once não existe na entrega, existe no efeito. E, no seu caso, a fila já mora no Postgres: enfileirar dentro da transação do domínio é um outbox.

  4. Por que hexagonal e clean architecture são “a mesma coisa”, e qual é o insight único que as duas expressam?
    ver resposta

    O insight é um só: quem define a interface é o domínio, e a dependência aponta pra dentro. Sua regra de negócio não importa o driver do banco; ela declara Repositorio e alguém de fora entrega uma implementação. É inversão de dependência aplicada na fronteira — e é por isso que domínio se testa sem subir infraestrutura.

    Os nomes diferem só na metáfora. Hexagonal (Cockburn) fala em portas e adaptadores e é simétrica: HTTP e banco são adaptadores igualmente externos, um entrando e outro saindo. Onion e Clean (Uncle Bob) desenham círculos concêntricos e nomeiam camadas internas (entidades, casos de uso). O hexágono não tem número obrigatório de lados e as camadas da Clean não precisam ser quatro — discutir isso é discutir desenho, não arquitetura.

    A resposta que soa madura termina no custo: a indireção só se paga onde há volatilidade ou complexidade de domínio. Num CRUD estável, ela produz três arquivos e uma interface pra fazer um INSERT, e quem mantiver aquilo depois vai te xingar com razão. No seu projeto, portas existem em AIProvider, Scheduler e Queue — justamente onde a implementação pode trocar — e não no resto.

  5. Sua empresa vai migrar um sistema legado grande. Qual abordagem você defenderia, e o que mediria pra saber se está dando certo?
    ver resposta

    Strangler fig, não big bang rewrite. Um roteador (proxy, gateway ou middleware) na frente do legado; uma rota ou capacidade por vez reescrita atrás dele; tráfego migrado gradualmente, com rollback sendo uma mudança de rota e não um deploy de emergência. Entre o novo e o velho, uma camada anticorrupção traduzindo o modelo antigo — sem ela, o legado coloniza o desenho novo e você reescreveu a mesma bagunça com sintaxe moderna.

    Por que não o rewrite: durante dois anos você não entrega valor, o legado continua ganhando features (o alvo se move) e o conhecimento que está implícito nos casos de borda do código velho — que ninguém documentou — se perde. Historicamente é o modo mais confiável de matar um projeto.

    O que medir, e é isto que separa a resposta boa da genérica: percentual de tráfego servido pelo caminho novo (a única métrica de progresso que não mente), paridade de comportamento entre os dois caminhos durante o período de shadow, taxa de erro e latência p95 comparadas lado a lado, e quantas rotas ainda restam no legado. Migração sem métrica de progresso vira “está 90% pronto” por seis meses seguidos.

  6. Um recrutador pergunta: “por que você não usou microsserviços no Gabarita?”. Responda em 40 segundos.
    ver resposta

    A armadilha é responder no eixo errado — “é um projeto pequeno” soa como desculpa. Responda no eixo do trade-off: quais atributos eu estava otimizando, e o que microsserviços cobrariam por eles.

    Formato que funciona: “Porque nenhum dos três drivers estava presente. Não há times se atrapalhando no deploy — sou eu. Não há componente com perfil de escala tão diferente que justifique separar: o pedaço mais pesado, que é a geração por IA, eu isolei por fila, o que resolve o mesmo problema sem virar um serviço. E não há requisito de isolamento de falha que uma transação no Postgres não atenda melhor.

    O que eu fiz foi manter as fronteiras: domínio em lib/, worker já stateless, comunicação por fila. Se amanhã a geração por IA precisar de escala e custo próprios, extraí-la é um deploy novo lendo a mesma fila — não uma reescrita. Escolhi a opção reversível: microsserviços cedo demais me custariam saga, observabilidade distribuída e versionamento de contrato antes de eu saber onde as fronteiras reais estão.”

Como contar a história do Gabarita numa entrevista

Você documentou cada decisão difícil no DECISOES.md enquanto ela acontecia — isso é praticamente um roteiro de entrevista pronto. Cada card abaixo é uma decisão real, reescrita no formato Situação / Decisão / Por quê / Resultado. Pratique dizendo em voz alta, não só lendo.

D101

Cota por questão, não por “pode responder?”

Situação
Conta grátis tinha 20 questões de trial. A checagem original era um booleano por questão respondida.
Decisão
Criei cotaRestante(), que devolve um número, e passei a validar o LOTE inteiro (a prova toda) contra ele numa transação, antes de gravar qualquer resposta.
Por quê
Com o booleano, 1 questão de cota liberava a entrega de um simulado de 200 — um erro clássico de checar-e-usar (TOCTOU) na regra de negócio, não no banco.
Resultado
O trial agora recusa lotes acima da cota restante, sem truncar (truncar revelaria o gabarito de tudo) — e questão em branco não gasta cota nem revela resposta.
D104

Um usuário pode ter várias assinaturas no Stripe

Situação
Cancelar e reassinar cria uma linha nova de assinatura no Stripe. Meu schema tinha userId único em Subscription, e o webhook retornava 500 na segunda assinatura.
Decisão
Removi a unicidade e passei a derivar planId do CONJUNTO de assinaturas do usuário, recalculado dentro da própria transação de escrita.
Por quê
Um evento deleted atrasado da assinatura antiga não pode rebaixar quem já tem uma nova ativa — e o Stripe reentrega webhook que falhou, então o bug se repetia pra sempre.
Resultado
Quem cancela e reassina volta a ficar Pro de verdade, e o histórico de assinaturas antigas fica preservado como auditoria.
D107

Trocar a senha precisa derrubar toda sessão aberta

Situação
Sessão é JWT de 30 dias sem rotação. Trocar a senha não invalidava sessões já emitidas — um cookie vazado continuava valendo por até um mês.
Decisão
Adicionei um carimbo (credenciaisAlteradasEm) que entra no token no login e é reconferido contra o banco em toda guarda de rota.
Por quê
Não usei o iat do próprio JWT porque o Auth.js reemite o cookie periodicamente, renovando o iat — uma sessão comprometida escaparia da comparação de tempo.
Resultado
Trocar a senha derruba imediatamente qualquer outra sessão aberta, sem nenhuma consulta extra — o carimbo viaja no mesmo select que já lia papel/plano.
D109

Nem toda tabela por usuário tem uma coluna de dono

Situação
SessionResponse e StudySessionItem não têm userId próprio — dependem de StudySession. Uma varredura de segurança achou uma função vazando dado entre sessões de usuários diferentes.
Decisão
Toda função que recebe (userId, sessionId) prova posse NA MESMA consulta (where: sessionId, session: userId), nunca em duas etapas.
Por quê
Guarda de página confirma quem é a pessoa, nunca de quem é a sessão — se a checagem de posse vivesse só nas páginas, uma Server Action nova herdaria a falha por acidente.
Resultado
Um teste por função (não por tela) trava a invariante pra sempre — a próxima função nasce com o teste, não com a suposição de que “quem chama já confere”.
D111

CSP com nonce por request, montada no middleware

Situação
Precisava de script-src restrito sem liberar unsafe-inline, mas o Next injeta o payload RSC como script inline diferente a cada resposta.
Decisão
Nonce gerado por request no middleware (runtime edge), não hash fixo em config — e todo layout raiz lê headers(), o que torna toda rota dinâmica de propósito.
Por quê
Hash só serve pra script cujo texto é conhecido de antemão. strict-dynamic propaga a confiança do script com nonce pros chunks que ele carrega, exatamente como o Next carrega JS.
Resultado
Dois testes de fumaça (fumaca:csp, fumaca:csrf) travam isso em runtime real, porque um teste unitário isolado passaria verde com a página inteira em branco.
