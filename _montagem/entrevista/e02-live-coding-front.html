E2

Live coding de front em React

~10h, um componente por sessão de 45 min · 8 clássicos de entrevista, com solução testada

Em uma frase: em vaga de front, o código ao vivo mais comum é construir um componente React pequeno, e o que se avalia é o estado bem pensado, os casos de erro e a acessibilidade, não a quantidade de recurso. Os oito exercícios abaixo são os temas que mais aparecem: lista com estado, dados de uma API, busca enquanto digita, formulário, abas, tabela, cronômetro e modal. Todas as soluções foram rodadas com testes (React 19 + Testing Library). Faça o E1 até o nível 2 antes de começar.

1. Como é a etapa

FormatoDe 45 a 60 minutos, num editor online (CodeSandbox, StackBlitz) ou no seu, com a tela compartilhada. Às vezes há uma API pronta; às vezes, um mock com dados.

O que pedem“Faça uma lista de tarefas com filtro”, “busque e mostre os usuários desta API”, “faça um campo de busca que não chame a API a cada tecla”.

O que avaliamSe você pergunta antes de supor, se o estado é o mínimo necessário, se trata carregando, erro e vazio, se o HTML é semântico, e se explica o que faz.

Na entrevista“Primeiro faço o caminho feliz funcionar; depois trato carregando, erro e lista vazia; no fim, teclado e leitor de tela.”

2. Como treinar

Projetonpm create vite@latest treino -- --template react-ts, e um arquivo por exercício. Ou abra um projeto React no StackBlitz.

Cronômetro45 minutos. Passou do tempo? Pare, leia a solução, feche e refaça do zero dois dias depois.

Em voz altaExplique cada decisão enquanto escreve. Grave um dos exercícios e assista: os silêncios longos são o que mais pesa contra.

Teste rápidoNo fim, use o componente só com o teclado (Tab, Enter, setas). É o teste de acessibilidade mais barato que existe.

3. O esqueleto de todo componente

Estado mínimoGuarde só o que não dá para calcular. A lista filtrada, o total e a página atual derivam do estado; não precisam de useState próprio.

Nunca mude o estadoCrie objetos e listas novos ([...lista, item], map, filter). Mudar no lugar não avisa o React, e a tela não atualiza.

Efeito é para o mundo de forauseEffect sincroniza com algo externo (API, timer, evento). E todo efeito que começa algo devolve uma função que limpa.

Os quatro estadosCarregando, erro (com “tentar de novo”), vazio e pronto. O vazio é o mais esquecido.

Na entrevista“Isto não precisa ser estado, eu calculo a partir da lista.” Essa frase mostra mais maturidade em React do que qualquer hook avançado.

    LC 3

    Busca enquanto digita

    40 min · debounce, corrida entre pedidos

    Um campo de busca de países chama GET /api/paises?q=termo. Só busque 300 ms depois que a pessoa parar de digitar. Mostre “Buscando…”, os resultados, “Nenhum país com X” e o erro. Uma resposta atrasada de um termo antigo nunca pode aparecer na tela.

    Pode consultarReact: você talvez não precise de um efeito · o exercício 13 do E1

    dica

    Separe em duas partes: um hook useDebounce(valor, ms) que devolve o valor atrasado, e um efeito que busca quando o termo atrasado muda. Para a corrida, aborte o pedido anterior na limpeza e guarde junto da resposta o termo a que ela pertence.

    solução comentada
    
export function useDebounce(valor: T, ms: number): T {
  const [atrasado, setAtrasado] = useState(valor);
  useEffect(() => {
    const t = setTimeout(() => setAtrasado(valor), ms);
    return () => clearTimeout(t); // digitou de novo antes do prazo: cancela
  }, [valor, ms]);
  return atrasado;
}

async function buscarPaises(termo: string, signal: AbortSignal): Promise {
  const res = await fetch(`/api/paises?q=${encodeURIComponent(termo)}`, { signal });
  if (!res.ok) throw new Error(`HTTP ${res.status}`);
  return res.json();
}

    O que mostrar ao entrevistador: são duas proteções contra a corrida. O abort cancela o pedido velho, e a comparação resposta.termo === termo garante que, mesmo se ele chegar, não aparece.     Explique em voz alta

    Por que encodeURIComponent? E por que o debounce fica num hook separado?

    respostas

    Mude um requisito

    LC 4

    Formulário de cadastro

    40 min · validação, acessibilidade, envio

    Faça um cadastro com e-mail, senha e confirmação. Ao enviar, valide; se houver erro, mostre a mensagem junto do campo e leve o foco ao primeiro campo com erro. Durante o envio, o botão fica desabilitado. Se o envio falhar, avise e deixe tentar de novo.

    Regras

    • E-mail com formato válido. Senha com pelo menos 8 caracteres e um número. Confirmação igual à senha.
    • O leitor de tela precisa ouvir o erro ao chegar no campo.

    Pode consultarMDN: aria-invalid · MDN: aria-describedby · React: input

    dica

    Uma função pura validar(campos) que devolve um objeto de erros é fácil de testar e de explicar. No campo, aria-invalid marca o erro e aria-describedby aponta para o id da mensagem. Um componente Campo evita repetir isso três vezes.

    solução comentada

export function validar(c: Campos): Erros {
  const erros: Erros = {};
  if (!/^[^\s@]+@[^\s@]+\.[^\s@]+$/.test(c.email)) erros.email = 'Digite um e-mail válido.';

  return erros;
}

    Revisar

    Explique em voz alta

    Por que não deixar todas as abas com tabIndex={0}?

    resposta

    Com dez abas, a pessoa no teclado precisaria de dez Tabs para chegar ao conteúdo. O padrão do W3C trata o grupo de abas como um controle só: um Tab para entrar, setas para escolher, um Tab para sair. É o mesmo comportamento de um grupo de rádio.

    Mude um requisito

    o que muda

    Guarde um Set com as abas já abertas e renderize o conteúdo só delas (as nunca abertas ficam vazias). Cada conteúdo é um componente com o seu próprio efeito de busca, como o LC 2. Como os painéis já abertos continuam montados (com hidden), voltar a uma aba não busca de novo.

    LC 6

    40 min · estado derivado, useMemo

    Pode consultarReact: useMemo · MDN: aria-sort · o exercício 8 do E1

    dica

    Cronômetro

    30 min · setInterval, cleanup, useRef

    Faça um cronômetro mm:ss.d com Iniciar/Continuar, Pausar e Zerar. O tempo mostrado não pode atrasar, mesmo depois de vários minutos ou com a aba em segundo plano. Ao sair da tela, nenhum timer fica rodando.

    Pode consultarReact: useRef · MDN: setInterval

    dica

    Não some 100 a cada tick: o navegador não garante o intervalo exato. Guarde o horário em que a contagem começou e calcule Date.now() - inicio a cada tick. Valores que não aparecem na tela (o início, o acumulado) ficam num useRef.

    solução comentada
    
function formatar(ms: number) {
  const totalSeg = Math.floor(ms / 1000);
  const min = String(Math.floor(totalSeg / 60)).padStart(2, '0');
  const seg = String(totalSeg % 60).padStart(2, '0');
  const decimo = Math.floor((ms % 1000) / 100);
  return `${min}:${seg}.${decimo}`;
}

    Caça ao bug

    Esta é a versão que quase todo mundo escreve primeiro. Ache os três problemas.

    
useEffect(() => {
  if (!rodando) return;
  setInterval(() => setDecorrido(decorrido + 100), 100);
}, [rodando]);
    os erros
    1. Closure velha (stale closure). A função do intervalo lembra o decorrido do momento em que foi criada (0). Ela calcula 0 + 100 para sempre, e a tela trava em 00:00.1. Com setDecorrido((d) => d + 100), esse problema some.
    2. Sem limpeza. Pausar não para o intervalo, e cada Iniciar cria mais um. Depois de três pausas, são três intervalos rodando juntos.
    3. Somar 100 a cada tick atrasa. O intervalo não é exato, e navegadores como o Chrome reduzem os timers de abas em segundo plano para no máximo um por segundo. Contando ticks, o cronômetro mostra menos tempo do que passou.
    Mude um requisito

    O cronômetro ganha um botão “Volta”, que registra o tempo atual numa lista, como no app de relógio do celular.

    o que muda

    Um estado novo, voltas: number[]. O botão calcula o tempo atual do mesmo jeito que o intervalo (acumulado.current + Date.now() - inicio.current) e acrescenta à lista. O tempo de cada volta (a diferença para a anterior) é derivado na hora de mostrar, e o Zerar também limpa as voltas.
