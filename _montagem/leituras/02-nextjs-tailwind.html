O curso constrói um dashboard financeiro com App Router. Os capítulos 7 a 12 são o que importa pra entrevista: onde buscar dados, estático vs. dinâmico, streaming, PPR, estado na URL e mutação com Server Actions.

Cap. 7 — Fetching data
  • Server Components podem ser async e buscar dados direto (ORM, SQL, SDK), sem criar uma rota de API só pra isso — o segredo nunca vai pro navegador.
  • Waterfall: await a(); await b(); faz b esperar a sem precisar. Se forem independentes, await Promise.all([a(), b()]).
  • Waterfall às vezes é desejado (b depende do resultado de a) — o erro é ter sem querer.
Cap. 8 — Static and dynamic rendering
  • Estático: renderizado em build (ou ao revalidar) e servido de cache/CDN. Rápido e barato, mas igual pra todo mundo.
  • Dinâmico: renderizado a cada request. Necessário quando depende de quem pede ou do momento: cookies(), headers(), searchParams, dados em tempo real.
  • No modo dinâmico, a página é tão lenta quanto a busca mais lenta — o que motiva o capítulo seguinte.
Cap. 9 — Streaming
  • Streaming quebra a resposta em pedaços: a casca sai na hora e as partes lentas chegam depois, cada uma substituindo seu fallback.
  • loading.tsx = um <Suspense> em volta da página inteira (nível de rota).
  • <Suspense fallback={<Skeleton/>}> em volta de um componente específico dá granularidade: mova a busca de dados pra dentro do componente lento, não a deixe no topo da página.
  • Route groups — pastas entre parênteses, como (overview) — limitam o alcance de um loading.tsx sem mudar a URL.
  • Onde colocar a fronteira: onde faz sentido pro usuário ver chegar junto. Fronteira demais produz efeito pipoca; de menos, espera longa.
Cap. 10 — Partial Prerendering

PPR combina os dois mundos na mesma rota: tudo que é estático é pré-renderizado como casca, e os trechos dinâmicos (envoltos em Suspense) viram “buracos” preenchidos por streaming no request. Na versão atual do Next isso vem pelo modelo de Cache Components (ver o recurso de cache logo abaixo).

Cap. 11 — Search and pagination
  • O estado de busca e página mora na URL (?query=ana&page=2): dá pra compartilhar e favoritar, funciona com SSR e o botão voltar funciona.
  • No cliente: useSearchParams, usePathname e useRouter().replace(...), com debounce pra não disparar uma navegação por tecla.
  • No servidor: a página recebe searchParams e busca os dados já filtrados.
Cap. 12 — Mutating data
// actions.ts
'use server';
export async function criarFatura(formData: FormData) {
  const dados = Schema.parse(Object.fromEntries(formData)); // valide SEMPRE no servidor
  await db.fatura.create({ data: dados });
  revalidatePath('/dashboard/faturas');   // invalida o cache da listagem
  redirect('/dashboard/faturas');
}
// <form action={criarFatura}>…</form>
  • Server Action é uma função que roda no servidor, chamável a partir de um formulário ou de código cliente; o framework cria o endpoint POST.
  • Para editar, passe o id com criarFatura.bind(null, id) — não num campo escondido que o usuário pode alterar sem checagem.
  • Capítulos seguintes: error.tsx (fronteira de erro), notFound(), e validação com useActionState devolvendo erros por campo.
  • Toda Server Action é um endpoint público: autentique e autorize dentro dela, mesmo que a página já esteja protegida.

Por padrão tudo é Server Component. 'use client' marca uma fronteira: daquele arquivo pra baixo (imports), o código também vai pro bundle do navegador. Decore onde fica a fronteira e o que pode atravessá-la.

Como funciona por baixo
  1. No servidor, o React renderiza os Server Components num formato compacto chamado RSC Payload (a árvore renderizada, os lugares onde entram Client Components e as props deles). O Next usa isso mais os Client Components pra pré-renderizar HTML.
  2. No cliente, o HTML aparece logo (ainda sem interatividade); o RSC Payload reconcilia a árvore; o JavaScript hidrata os Client Components.
  3. Navegações seguintes: o RSC Payload é pré-carregado e cacheado, e Client Components renderizam só no cliente, sem HTML do servidor.
A fronteira
  • 'use client' no topo de um arquivo faz dele e de tudo que ele importa parte do bundle cliente. Coloque a diretiva o mais baixo possível: extraia o botão interativo, não marque o layout inteiro.
  • Não dá pra importar um Server Component dentro de um arquivo cliente. Dá pra passar como children ou outra prop — é o interleaving:
// Modal é 'use client'; Carrinho é Server Component
<Modal>
  <Carrinho />   {/* renderizado no servidor, encaixado no slot */}
</Modal>
O que atravessa a fronteira
  • Props de Server → Client precisam ser serializáveis pelo React: primitivos, objetos e arrays simples, Date, Map, Set, Promises. Funções comuns e instâncias de classe não passam — exceto Server Actions, que atravessam como referência.
  • Uma Promise pode ser passada e lida no cliente com use(promise), dentro de Suspense: a busca começa no servidor e o componente cliente espera por ela.
Detalhes que caem em entrevista
  • Context não existe em Server Components. Crie um provider cliente que recebe children e renderize-o o mais fundo possível.
  • Lib de terceiros que usa hooks mas não tem 'use client': reexporte num arquivo seu marcado como cliente.
  • Envenenamento de ambiente: import 'server-only' faz o build falhar se um módulo com segredo for importado no cliente. Só variáveis NEXT_PUBLIC_* vão pro bundle.

No modelo novo (Next 16, cacheComponents: true), nada é cacheado por padrão. Você marca o que pode ser cacheado com 'use cache', define por quanto tempo com cacheLife e como invalidar com cacheTag. O que não é cacheado precisa estar dentro de Suspense.

O modelo mental
  • Antes, o App Router tentava adivinhar o que era estático e havia várias camadas implícitas. O modelo de Cache Components troca isso por opt-in explícito.
  • Dado sem cache que é acessado fora de uma fronteira Suspense gera erro de build — o framework obriga você a decidir: ou cacheia, ou mostra fallback enquanto chega. O resultado é PPR por padrão: casca estática + buracos dinâmicos.
'use cache'
async function listarEspecialidades() {
  'use cache';
  cacheLife('hours');           // perfil: seconds, minutes, hours, days, weeks, max
  cacheTag('especialidades');   // rótulo pra invalidar
  return db.especialidade.findMany();
}
  • Pode ir no topo de um arquivo, de um componente ou de uma função.
  • A chave do cache é derivada dos argumentos e dos valores capturados — por isso eles precisam ser serializáveis.
  • APIs de request (cookies(), headers()) não podem ser lidas dentro de um escopo cacheado: leia fora e passe o valor como argumento (e aí ele vira parte da chave).
  • cacheLife também aceita objeto com stale, revalidate e expire.
Invalidação
  • revalidateTag('especialidades', 'max') — marca como velho e serve o antigo enquanto regenera (stale-while-revalidate). Bom pra webhook e job.
  • updateTag('especialidades') — dentro de Server Action, expira na hora pra quem escreveu ver a própria escrita (read-your-own-writes).
  • revalidatePath continua existindo pra invalidar por rota.
O que isso substitui

Configs de segmento como export const dynamic, revalidate e fetchCache deixam de ser o caminho; unstable_cache vira 'use cache'.

Utilitários trocam “inventar nome de classe e escrever CSS” por “compor classes restritas a um design system”. Na v4 o design system é declarado em CSS com @theme, e cada token vira ao mesmo tempo utilitário e variável CSS.

Styling with utility classes
  • Por que não inline style: utilitário tem restrição de escala (você escolhe entre p-4 e p-6, não inventa 17px), tem estados (hover:, focus-visible:, disabled:), responsividade (md:), dark mode (dark:) e seletores que style="" não alcança.
  • Variantes empilham: dark:md:hover:bg-slate-700.
  • Valores arbitrários quando o design pede exceção: top-[117px], bg-[#316ff6], grid-cols-[1fr_auto].
  • Duplicação se resolve no template (componente React, loop), não criando classes CSS. @apply é exceção, não estratégia.
  • Conflito: se um elemento tem p-2 e p-4, vence quem vem depois no CSS gerado, não na ordem do atributo. Não aplique as duas; escolha uma condicionalmente (ou use um utilitário como tailwind-merge).
Theme variables (@theme)
@import "tailwindcss";

@theme {
  --color-marca-500: oklch(0.62 0.14 160);
  --font-display: "IBM Plex Sans", sans-serif;
  --breakpoint-3xl: 120rem;
}
/* gera bg-marca-500, text-marca-500, font-display, 3xl:…
   e expõe var(--color-marca-500) pra qualquer CSS */
  • Cada namespace gera uma família: --color-*, --font-*, --text-*, --spacing, --breakpoint-*, --radius-*, --shadow-*, --animate-*.
  • Pra substituir a paleta padrão inteira: --color-*: initial; e declare só as suas.
  • Por que @theme e não :root: :root só cria variável; @theme cria variável e utilitário. Precisa estar no topo do arquivo, sem aninhamento.
  • Os tokens existem em runtime: trocar tema ou densidade é redefinir variáveis num seletor.

“Separação de responsabilidades” entre HTML e CSS é ilusão: sempre existe uma dependência. A escolha real é a direção dela — e utility-first escolhe o HTML depender de um CSS reutilizável.

A trajetória em fases
  1. CSS “semântico”: .author-bio com seletores aninhados espelhando a estrutura (.author-bio > h2). O HTML fica “limpo”, mas o CSS agora depende da estrutura do HTML — mudou a marcação, quebrou o estilo.
  2. Desacoplar com BEM (.author-bio__image): menos frágil, mas as classes ainda são nomeadas pelo conteúdo. Quando surge um card de artigo com a mesma cara, você duplica CSS ou usa @extend/mixins.
  3. A virada: o nome pelo conteúdo tornava o HTML reestilizável, mas o CSS não reaproveitável. Nomear pela aparência/função (.media-card) inverte: CSS reaproveitável, HTML precisa mudar pra mudar o visual. Nenhuma das duas é “separação” — são dependências em direções opostas.
  4. Componentes agnósticos + variações: .card, .card--large, .card--muted… as variações explodem, e cada pequena diferença vira uma decisão de nomenclatura.
  5. Utilitários (.text-center, .mb-4) pras pequenas variações, e depois utility-first: construir tudo com utilitários e extrair componente só quando um padrão realmente se repete — no template, não no CSS.
O que se ganha
  • Consistência: uma escala fechada de espaçamento, cor e tipo impede os 37 tons de cinza.
  • Menos decisões: você não inventa nomes nem abre o arquivo CSS pra cada ajuste.
  • CSS para de crescer: feature nova reutiliza classes existentes em vez de adicionar regras.
  • Mudança local: alterar um utilitário num elemento não afeta nada em outro lugar.
Objeções respondidas
  • “É inline style.” Não: inline não tem restrição de escala, estados, media queries nem pseudo-elementos.
  • “HTML fica feio.” É uma troca consciente: a complexidade sai de um CSS global difícil de apagar e vai pra um lugar visível e local. A duplicação se resolve extraindo componente de UI.

Resposta pra “por que não CSS Modules?”: CSS Modules resolve escopo (colisão de nomes), não resolve consistência nem crescimento do CSS; Tailwind resolve os dois com uma escala compartilhada. E dá pra combinar quando precisar.
