Internal package é uma biblioteca cujo código mora no próprio monorepo e é referenciada pelo protocolo de workspace do gerenciador ("@repo/ui": "workspace:*" no pnpm). A decisão que importa é quem compila o pacote — e há três respostas, cada uma com um custo diferente.

As três estratégias
EstratégiaQuem compilaGanhaPerde
Just-in-Timeo bundler da app que consomequase zero configuração: o package.json exporta os .ts direto, sem buildsó funciona se todo consumidor transpila; o Turborepo não tem build pra cachear; não aceita compilerOptions.paths; erro de tipo do pacote aparece em quem consome
Compiledo próprio pacote (normalmente tsc), gerando dist/saída cacheada pelo Turborepo; serve pra consumidor que não transpila TypeScriptmais configuração: opções do compilador, sideEffects, exports com types e default
Publishableo pacote, com a configuração mais rígidapode ir pro registro npm e ser usado fora do monorepoexige ferramenta de versionamento e publicação — a doc recomenda changesets
Como reconhecer qual você tem
  • Se o package.json aponta main/types/exports pra ./src/index.ts e não existe script de build, é Just-in-Time. É o caso do @ally-ai/types.
  • Se aponta pra ./dist/index.js e há um build que gera esse arquivo, é Compiled.
  • O dependsOn: ["^build"] no turbo.json é o que garante que o dist/ do pacote existe antes da app que o consome buildar.
Boas práticas que a página pede
  • Declarar exports explícitos no package.json — é isso que define a fronteira pública do pacote. O que não está em exports não pode ser importado de fora, e é assim que se impõe boundary sem depender de disciplina.
  • Em Compiled, separar types e default em cada entrada de exports.
  • Ter os mesmos scripts de lint e typecheck em todo pacote, pra o Turborepo rodar a mesma task no repo inteiro.

Frase de entrevista: “Comecei com o pacote de tipos Just-in-Time porque é só contrato e os dois consumidores transpilam. Se virasse biblioteca de UI usada por várias apps, eu passaria pra Compiled, pelo cache do build e pra o erro de tipo não vazar pra quem consome.”

Micro frontends são “um estilo de arquitetura em que aplicações de front-end entregáveis de forma independente são compostas num todo maior”. O artigo de Cam Jackson é favorável ao estilo, mas é honesto sobre o preço — e o preço é o que se cobra numa entrevista.

Os quatro benefícios
  • Atualização incremental: trocar um legado aos pedaços em vez de reescrever tudo, e experimentar tecnologia nova num pedaço só.
  • Bases de código menores e desacopladas: menos acoplamento acidental; fluxo de dados e eventos entre partes fica explícito.
  • Deploy independente: cada micro frontend tem seu pipeline; o time decide quando sobe.
  • Times autônomos: organizados por funcionalidade vista pelo usuário, não por camada técnica.
As cinco formas de integrar
AbordagemResumoVeredito do artigo
Composição no servidorserver-side includes montando fragmentos de HTMLpadrão e simples: cada fragmento tem seu pipeline e deploy, e a composição pode ficar num servidor só na frente dos outros. Exige a página montada no servidor
Build-time (pacote npm)cada micro frontend vira dependência do containerdesaconselhado: obriga release em lockstep e reintroduz o acoplamento que se queria evitar

Runtime via Web Componentscustom elements como ponto de entradaalternativa baseada em padrão, com a mesma flexibilidade
Os problemas transversais
  • CSS é global: convenção (BEM), CSS Modules, CSS-in-JS ou shadow DOM — o requisito é um time não quebrar o estilo do outro.
  • Biblioteca compartilhada: deixe o padrão surgir do uso antes de centralizar; comece por primitivas visuais “burras” (botão, ícone, label); nunca regra de negócio; precisa de um responsável cuidando da qualidade.
  • Comunicação entre apps: o mínimo possível — custom events, props/callbacks do container, ou a URL. Contratos dirigidos pelo consumidor no lugar de E2E frágil.
  • Back-end: BFF por micro frontend; autenticação centralizada no container.
Os custos
  • Payload: builds independentes duplicam dependências (o React, por exemplo). Externalizar a dependência comum devolve o acoplamento de build.
  • Ambientes diferentes: desenvolver isolado esconde problema que só aparece integrado.
  • Complexidade operacional: mais repositórios, pipelines e governança — exige maturidade de automação.

Frase de entrevista: “Micro frontend resolve problema de organização, não de código. Com um time só, eu pagaria payload duplicado e governança sem ganhar deploy independente de ninguém.”

Multi-zones são a abordagem de micro frontend do próprio Next: várias aplicações Next no mesmo domínio, cada uma dona de um conjunto de rotas. Pro usuário parece uma app só; pro time, são builds e deploys separados.

A ideia
  • Exemplo da doc: /blog/*, /dashboard/* e /* (o resto) viram três apps. Cada uma fica menor, builda mais rápido e não carrega código que só a outra usa — e pode até usar outro framework.
  • Navegar dentro de uma zona é soft navigation (sem recarregar). Navegar entre zonas é hard navigation: descarrega a página e carrega a outra. Regra prática: páginas visitadas juntas ficam na mesma zona.
Configuração, em três peças
  • Definir a zona: uma app Next normal com assetPrefix (ex.: '/blog-static'), pra o JS e o CSS dela saírem em /blog-static/_next/... sem colidir com os da outra. A zona padrão (o /*) não precisa de prefixo. A partir do Next 15, não é mais preciso o rewrite extra dos assets.
  • Rotear: qualquer proxy HTTP serve, mas a própria app principal pode fazer isso com rewrites apontando /blog, /blog/:path+ e /blog-static/:path+ pro domínio da outra zona. Cada caminho pertence a uma zona só. Rewrite é o recomendado pela latência; proxy (o antigo middleware) é pra decisão dinâmica, como uma feature flag durante migração.
  • Linkar: entre zonas use <a>, não <Link>. O Link tenta prefetch e soft navigation em caminho relativo, e isso não funciona atravessando zonas.
O resto
  • Código compartilhado: as zonas podem estar em qualquer repositório, mas monorepo facilita; entre repositórios, pacote npm público ou privado. Como cada zona sobe numa hora diferente, feature flag ajuda a ligar uma funcionalidade em todas ao mesmo tempo.
  • Server Actions: é preciso liberar o domínio que o usuário vê em experimental.serverActions.allowedOrigins, porque o mesmo domínio serve várias apps.

Frase de entrevista: “Se eu precisasse separar uma área com time próprio, começaria por multi-zone por rota — é o microfrontend mais barato: sem runtime compartilhado, o custo é só a hard navigation na fronteira.”

Nonce é uma string aleatória, única por request, que autoriza só os scripts que a carregam. O efeito colateral arquitetural é grande: com nonce, toda página precisa ser renderizada dinamicamente, porque o nonce só existe quando existe request.

Como o Next aplica o nonce
  1. O proxy (antigo middleware) gera o nonce, monta o header Content-Security-Policy e coloca o nonce também num header próprio (x-nonce) — tanto na requisição quanto na resposta.
  2. Durante a renderização no servidor, o Next lê o header da CSP e extrai o valor de 'nonce-…'.
  3. Ele mesmo aplica o nonce nos scripts do framework, nos bundles da página, nos inline gerados e em <Script nonce>. Pra script de terceiro, leia o nonce com headers() num Server Component.

Página estática é gerada no build, quando não há request nem header — por isso não há como injetar nonce nela. A doc sugere await connection() pra forçar dinâmico quando necessário.

O que se perde, segundo a própria doc
  • Otimização estática e ISR desligados; cada request gera página nova.
  • Página não pode ser cacheada pela CDN sem configuração extra.
  • Partial Prerendering (PPR) é incompatível: o shell estático não tem acesso ao nonce.
  • Consequências: carga inicial mais lenta, mais carga no servidor, custo de hospedagem maior.
  • Quando vale: requisito de segurança que proíbe 'unsafe-inline', dado sensível, compliance.
As alternativas
  • Sem nonce: CSP fixa em headers() do next.config, mas aí o script-src precisa de 'unsafe-inline'.
  • Subresource Integrity (experimental, só App Router): experimental.sri.algorithm gera hash dos scripts no build e põe integrity nas tags. Mantém geração estática e cache de CDN; limitação: não cobre script gerado dinamicamente, e pode mudar ou sair.

Frase de entrevista: “Nonce é uma decisão de arquitetura, não só de segurança: ele troca cache de borda por uma CSP sem 'unsafe-inline'. Eu aceitei esse custo numa app com dado de usuário, e sei que SRI é a saída se precisar de estático.”

Bundle menor carrega mais rápido, executa menos JS, melhora Core Web Vitals e reduz cold start no servidor. O Next já faz code splitting e tree-shaking; este guia é pros casos em que é preciso medir e intervir.

Os três remédios mais comuns
  • Pacote com centenas de exports (ícones, utilitários): experimental.optimizePackageImports faz carregar só o módulo usado. Atenção: vários pacotes já são otimizados por padrão — lucide-react, date-fns, lodash-es, recharts, os ícones do @heroicons/react, react-icons/*, entre outros — e não precisam estar na lista.
  • Trabalho pesado no cliente: biblioteca que só transforma dado em UI (realce de sintaxe, gráfico, parser de markdown) dentro de Client Component vai inteira pro bundle. Se não precisa de API do navegador nem de interação, rode num Server Component e mande só o HTML. O exemplo da doc troca Prism no cliente por Shiki no servidor.
  • Pacote que não deve ser empacotado no servidor: serverExternalPackages tira pacotes específicos do bundling de Server Components e Route Handlers.

Frase de entrevista: “Antes de otimizar eu meço: rodo o analisador, acho o módulo grande e a cadeia de import que o trouxe, e só então escolho entre optimizePackageImports, mover pra Server Component ou lazy loading.”

INP (Interaction to Next Paint) é a Core Web Vital de responsividade: observa todas as interações da visita e reporta a mais lenta. A meta é 200 ms ou menos no p75, separado por tipo de aparelho; acima de 500 ms é ruim.

As três fases de uma interação
FaseVai de…Causa típicaRemédio
Input delayo clique até o handler começarthread principal ocupada — script sendo carregado, parseado, compilado, hidrataçãoreduzir trabalho de inicialização; entender a relação entre avaliação de script e long tasks
Processing durationo handler rodandocallback fazendo trabalho demaisceder a thread com frequência (setTimeout), rodar primeiro só o que afeta a tela e adiar o resto (requestAnimationFrame + setTimeout); evitar layout thrashing (ler estilo logo depois de escrever força layout síncrono)
Presentation delayo fim do handler até o próximo framerenderização grandeDOM menor, content-visibility pro que está fora da tela, menos HTML renderizado por JS no cliente

A soma das três é a latência da interação. O ponto sobre renderização no cliente é direto: HTML que chega por streaming do servidor cede a thread naturalmente; HTML montado por JavaScript bloqueia até terminar.

Como achar a interação lenta
  • Comece pelo campo: um provedor de RUM ou os dados do CrUX (via PageSpeed Insights) dizem qual interação e qual página.
  • Depois o laboratório: reproduza o fluxo e teste as interações durante o carregamento, quando a thread principal está mais ocupada.

Frase de entrevista: “Quando INP piora, eu não chuto useMemo: separo a interação em input delay, processamento e apresentação, e ataco a fase que a medição apontou.”
