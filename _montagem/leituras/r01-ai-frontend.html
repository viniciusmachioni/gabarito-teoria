O useChat é a referência de mercado pra UI de LLM em React: ele junta mensagens, streaming, um status com quatro valores e as ações de parar e regenerar. Mesmo que você nunca use o SDK, é esse o vocabulário que um entrevistador vai usar.

A arquitetura em duas pontas
  • No servidor, um Route Handler recebe as mensagens, chama streamText() com o modelo e devolve o stream já no formato de mensagens de UI (toUIMessageStream() embrulhado em createUIMessageStreamResponse(), nas versões atuais). A chave da API nunca sai do servidor.
  • No cliente, o hook mantém a lista de mensagens e vai atualizando a última à medida que os pedaços chegam. Você só renderiza.
  • Cada mensagem tem parts em vez de um texto único: texto, chamada de ferramenta, resultado de ferramenta, raciocínio, arquivo. É isso que permite renderizar cada tipo de um jeito (a base da Generative UI).

Ações e eventos
  • sendMessage() envia; stop() aborta o stream em andamento; regenerate() refaz a última resposta do assistente.
  • Callbacks onFinish, onError e onData servem pra log, analytics e efeitos de UI.
  • O guia insiste num ponto de segurança: no estado de erro, mostre mensagem genérica ao usuário e não vaze detalhe do servidor.
Performance: throttle
  • Cada pedaço do stream é uma atualização de estado, ou seja, um re-render. A opção throttle (em ms) agrupa essas atualizações. O stream continua sendo processado na hora; só a pintura é espaçada.
  • É o mesmo raciocínio de debounce/throttle do B14: o gargalo é o React renderizar 50 vezes por segundo, não a rede.
Transporte e metadados
  • O transporte padrão é HTTP e aceita headers, body extra e credenciais. Dá pra trocar por um transporte próprio.
  • O servidor pode anexar metadados à mensagem (modelo usado, tokens, timestamps), lidos no cliente em message.metadata. É útil pra mostrar custo ou origem.

Frase de entrevista: “Uma UI de LLM tem pelo menos quatro estados (enviado, transmitindo, pronto, erro) e uma ação que o usuário sempre precisa ter: parar. Eu desenho os quatro antes de escrever o caminho feliz.”

Todo SDK de streaming de IA, no fim, faz isto: response.body é um ReadableStream, e você lê pedaço por pedaço num laço até done. Saber fazer à mão é o que permite depurar quando o SDK não ajuda.

Consumir um fetch como stream
  • response.body já é um ReadableStream. getReader() cria um leitor e trava o stream: só um leitor por vez, até releaseLock().
  • reader.read() devolve uma promessa de { done, value }. O padrão é: ler; se done, parar; processar o pedaço; ler de novo.
const reader = response.body.getReader();
while (true) {
  const { done, value } = await reader.read();
  if (done) break;
  // value é um Uint8Array: decodifique com TextDecoder
}
  • O value vem em bytes. Pra texto de LLM, você decodifica com TextDecoder (ou passa o stream por um TextDecoderStream com pipeThrough).
Iteração assíncrona e cancelamento
  • A forma mais curta é for await (const chunk of response.body).
  • Cancelar é com AbortController: passe o signal pro fetch e chame abort() no clique do botão “parar”. Isso fecha a conexão de verdade, e o servidor pode parar de gerar (e de cobrar token).
  • reader.cancel() descarta o stream e o que estava na fila.
Criar, dividir e encadear
  • O construtor new ReadableStream({ start, pull, cancel }) cria um stream próprio, alimentado com controller.enqueue() e encerrado com controller.close(). É o que um Route Handler faz pra transmitir a resposta do modelo.
  • tee() divide um stream em dois idênticos (ex.: mostrar ao usuário e gravar em cache ao mesmo tempo).
  • pipeThrough() passa por um transform stream; pipeTo() despeja num writable.

Frase de entrevista: “Por baixo do SDK é um ReadableStream: leitor, laço de read(), TextDecoder e um AbortController no botão de parar, porque parar também precisa parar o custo.”

Structured output é pedir que o modelo responda em JSON que obedece a um schema. O Gemini aceita um subconjunto de JSON Schema. Mesmo assim, a própria documentação manda validar a saída na aplicação: o schema garante a forma, não a verdade.

Como pedir
  • Você informa o tipo de mídia JSON e um schema. Os nomes dos campos variam entre a API REST, os SDKs e as versões. No SDK @google/genai que o Ally AI usa, isso fica em config.responseMimeType + config.responseJsonSchema (aiService.ts L102-105).
  • Nos SDKs, o schema pode sair de uma biblioteca de tipos: Pydantic em Python e Zod em JavaScript, convertidos pra JSON Schema. Assim existe uma fonte de verdade só, que é exatamente o que o Ally AI faz à mão com dois schemas espelhados.
O que o schema aceita

  • Nem todo recurso de JSON Schema é aceito, e schema muito grande ou aninhado pode ser rejeitado. Regras como “exatamente uma alternativa correta” ficam no seu código (o refine do Zod no Gabarita).
Streaming de saída estruturada
  • Em streaming, cada pedaço é um JSON parcial: a concatenação forma o objeto final. Dá pra mostrar progresso, mas o objeto só é válido no fim.
Boas práticas que a página lista
  • Use description nos campos pra orientar o modelo.
  • Prefira tipos específicos (enum, integer) a strings genéricas. O Ally AI faz isso com priority: enum ["baixa","media","alta"].
  • Combine prompt claro com schema.
  • Valide os valores na aplicação e trate saída semanticamente errada.
Structured output vs. function calling
  • Structured output formata a resposta final.
  • Function calling é quando o modelo precisa pedir uma ação antes de responder.
  • Nos modelos Gemini 3, os dois podem ser combinados na mesma chamada.

Frase de entrevista: “O schema é contrato de forma; o significado eu valido no código. No Gabarita, uma explicação com o JSON perfeito e a alternativa errada é recusada e refeita.”

Function calling deixa o modelo pedir uma ação: ele devolve o nome da função e os argumentos, o seu código executa e devolve o resultado, e só então o modelo responde ao usuário. O modelo nunca executa nada sozinho.

O ciclo em quatro passos
  1. Declarar as funções: nome, descrição e parâmetros em JSON Schema (type: "object", properties, required).
  2. Chamar o modelo com a mensagem do usuário e as declarações.
  3. Se o modelo decidir usar uma ferramenta, ele devolve uma chamada de função com nome e argumentos. Sua aplicação extrai isso e executa localmente.
  4. Devolver o resultado ao modelo, que gera a resposta final pro usuário.
Padrões avançados
  • Paralelo: várias funções independentes pedidas no mesmo turno (ex.: clima de três cidades).
  • Composicional: o resultado de uma chamada alimenta a próxima (descobrir a localização, depois buscar o clima dela). É o embrião do loop agentic do B2.
Modos
ModoComportamento

Boas práticas (incluindo segurança)
  • Descrições claras de cada função e parâmetro: é com elas que o modelo decide quando chamar.
  • Nomes descritivos e consistentes.
  • Validar os argumentos antes de executar: o modelo pode errar tipo, inventar valor ou ser induzido por prompt injection.
  • Autenticação e autorização em quem a função acessa; validar argumento contra injeção.
  • Tratar falha de execução e devolver um resultado informativo ao modelo, em vez de quebrar a conversa.

Frase de entrevista: “Tool calling é o modelo preenchendo um formulário que o meu código executa. Então eu trato os argumentos como qualquer input de usuário: schema, autorização e menor privilégio.”

Generative UI é deixar o LLM ir além do texto. O modelo chama uma ferramenta, a ferramenta devolve dado tipado, e a interface renderiza um componente React pra aquele resultado, em vez de um parágrafo descrevendo-o.

O fluxo
  1. O modelo recebe o prompt e uma lista de ferramentas, cada uma com descrição, schema de entrada em Zod e uma função execute.
  2. Pelo contexto, ele decide se chama alguma (“como está o tempo em SF?” → displayWeather).
  3. A ferramenta roda no servidor e devolve dado ({ weather, temperature, location }).
  4. Esse dado chega ao cliente como uma part da mensagem, e um componente <Weather /> o renderiza.
Renderizar por tipo e por estado
  • As parts de ferramenta são tipadas pelo nome: tool-displayWeather. Você percorre message.parts e faz um switch no tipo.
  • Cada part de ferramenta tem um estado, e cada estado pede uma UI:
EstadoSignificaRenderize
input-availablea ferramenta foi chamada e está rodandoskeleton do componente
output-availableterminou com sucessoo componente com o dado
output-errora ferramenta falhouerro localizado naquele bloco, sem derrubar a conversa
No servidor
  • O Route Handler chama streamText com o modelo, as instruções, as mensagens convertidas (convertToModelMessages()) e o objeto tools, e devolve o stream de mensagens de UI.
O que isso muda no desenho
  • A ferramenta vira um contrato entre o modelo e o design system: o schema de saída é a prop do componente. Mudar um exige mudar o outro.
  • Cada componente gerado precisa dos mesmos cuidados de qualquer componente: acessível, responsivo, com estado de carregando e de erro. É aqui que Design Engineering (R2) encontra IA.

Frase de entrevista: “Generative UI é o modelo escolhendo qual componente do meu design system mostrar, e com quais dados. O schema da ferramenta é a interface de props.”

Tool approval é human-in-the-loop no nível da ferramenta: antes de executar algo sensível (rodar comando, processar pagamento), o agente para e a UI pede aprovação. Se o usuário nega, a ferramenta não roda, e o modelo segue sabendo disso.

Os quatro desfechos de uma chamada
StatusO que acontece
not-applicableexecuta normalmente, sem metadado de aprovação (padrão)
approvedaprovação automática registrada, executa
deniednegação automática registrada, devolve resultado “negado”
user-approvalemite um pedido de aprovação e espera a resposta
Estática ou dinâmica
  • Estática: um mapa por ferramenta, como { runCommand: 'user-approval' }.
  • Dinâmica: uma função que olha o argumento, por exemplo pagamento acima de 1000 pede aprovação e abaixo passa direto. É o desenho certo na maioria dos casos: pedir aprovação pra tudo treina o usuário a clicar “sim” sem ler.
  • Também dá pra ter uma política única que avalia qualquer chamada pelo nome da ferramenta e pela entrada.
No cliente
  • O pedido chega como uma part de ferramenta com state: 'approval-requested'. A UI mostra o que vai ser feito, com os argumentos legíveis, e dois botões.
  • A resposta volta por addToolApprovalResponse({ id, approved }), do useChat.
  • Na negação, a ferramenta não executa e o modelo recebe a negação. A documentação recomenda instruir o modelo a não tentar de novo o que foi negado.
Limites
  • Só vale pra ferramentas que o próprio SDK executa. Ferramentas executadas pelo provedor passam por fora.
  • A API mudou de nome entre versões (a forma anterior era a flag needsApproval na ferramenta). Confira a versão instalada antes de citar a assinatura numa entrevista.

Frase de entrevista: “Aprovação humana entra onde a ação é irreversível ou cara, e de preferência por regra dinâmica. Se você pede confirmação pra tudo, ninguém lê a confirmação.”
