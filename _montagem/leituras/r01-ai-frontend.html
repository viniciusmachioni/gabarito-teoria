Em uma frase: o useChat é o hook React mais usado para telas de chat com IA. Ele guarda as mensagens, recebe a resposta em pedaços, informa em que fase a conversa está e oferece os botões de parar e de gerar de novo. Mesmo sem usar o SDK, é esse o vocabulário que o entrevistador vai usar.

No mundo realNo ChatGPT, no Claude e no Gemini, o botão de enviar vira um quadrado de “parar” enquanto a resposta chega, e volta a ser “enviar” quando ela termina. São exatamente os estados desta página. O template oficial de chatbot da Vercel é construído sobre o useChat.

As duas pontas
  • No servidor, um Route Handler recebe as mensagens, chama o modelo com streamText() e devolve a resposta em pedaços. A chave da API do modelo nunca sai do servidor.
  • No cliente, o hook guarda a lista de mensagens e atualiza a última conforme os pedaços chegam. Você só desenha a tela.
  • Cada mensagem é uma lista de partes (parts), e não um texto único: texto, chamada de ferramenta, resultado de ferramenta, arquivo. É isso que permite desenhar cada tipo de um jeito, a base da Generative UI.
As quatro fases
  • submitted: a mensagem foi enviada e nada chegou ainda. Mostre “pensando…” e desabilite o envio.
  • streaming: os pedaços estão chegando. Mostre o texto crescendo e o botão parar.
  • ready: a resposta terminou. Libere um novo envio.
  • error: o pedido falhou. Mostre uma mensagem genérica e “tentar de novo”. Não mostre detalhes internos do servidor, que podem vazar informação.
As ações
  • sendMessage() envia, stop() cancela a resposta em andamento e regenerate() pede outra versão da última resposta.
  • Os eventos onFinish e onError servem para registrar uso, custo e erros.
Desempenho: não redesenhar a cada pedaço
  • Cada pedaço que chega atualiza o estado e faz o React redesenhar a tela. Com 50 pedaços por segundo, o gargalo vira o React, e não a rede.
  • A opção throttle (em milissegundos) junta as atualizações: os pedaços continuam chegando na hora, mas a tela é redesenhada com menos frequência.

Frase de entrevista: “Uma tela de IA tem pelo menos quatro fases (enviado, chegando, pronto, erro) e uma ação que o usuário sempre precisa ter: parar. Eu desenho as quatro antes de escrever o caminho feliz.”

Em uma frase: todo SDK de streaming faz, por baixo, a mesma coisa. A resposta do fetch é um fluxo de bytes (response.body), e você lê um pedaço de cada vez num laço até acabar. Saber fazer isso à mão é o que te salva quando o SDK não ajuda.

No mundo realAs APIs da OpenAI e da Anthropic, com stream: true, mandam a resposta como uma sequência de eventos (Server-Sent Events) pela mesma conexão HTTP. Quem consome sem SDK escreve exatamente o laço desta página. O exercício 1 do R8 treina isso.

Ler a resposta aos pedaços
const reader = response.body.getReader();
const decoder = new TextDecoder();
while (true) {
  const { done, value } = await reader.read();
  if (done) break;
  const texto = decoder.decode(value, { stream: true }); // bytes viram texto
  // acrescente o texto na tela
}
  • getReader() cria um leitor. Só existe um leitor por vez para cada fluxo.
  • reader.read() devolve { done, value }. O value vem em bytes, e o TextDecoder transforma em texto.
  • O { stream: true } importa: um caractere como “ç” ocupa dois bytes e pode chegar partido entre dois pedaços. Com essa opção, o decodificador espera o resto antes de entregar.
  • A forma mais curta é for await (const pedaco of response.body).
Cancelar de verdade
  • Crie um AbortController, passe o signal para o fetch e chame abort() no botão “parar”.
  • Isso fecha a conexão. O servidor percebe e pode parar de gerar, e de cobrar tokens. Esconder o texto sem cancelar continua gastando.
Criar um fluxo no servidor
  • new ReadableStream({ start(controller) { ... } }) cria um fluxo próprio: você empurra pedaços com controller.enqueue() e fecha com controller.close(). É o que um Route Handler faz para repassar a resposta do modelo ao navegador.
  • tee() divide um fluxo em dois iguais, por exemplo para mostrar ao usuário e gravar no banco ao mesmo tempo.

Frase de entrevista: “Por baixo do SDK é um ReadableStream: leitor, laço de read(), TextDecoder e um AbortController no botão de parar, porque parar também precisa parar o custo.”

Em uma frase: structured output é pedir que o modelo responda em JSON seguindo um formato que você descreveu (um schema). Mesmo assim, a própria documentação manda validar a resposta no seu código: o schema garante a forma, não a verdade.

No mundo realA OpenAI lançou o modo Structured Outputs em 2024 justamente porque empresas usavam o modelo para extrair dados de notas fiscais, contratos e e-mails, e o JSON vinha quebrado de vez em quando. Com o schema obrigatório, a forma fica garantida. O valor ainda pode estar errado: o total da nota pode vir trocado. No Gabarita, uma explicação com o JSON perfeito e a alternativa errada é recusada e refeita.

Como pedir
  • Você diz que quer JSON e envia o schema junto com o pedido. No SDK @google/genai, que o Ally AI usa, isso fica em config.responseMimeType e config.responseJsonSchema.
  • Em JavaScript, o schema pode sair do Zod, convertido para JSON Schema. Assim existe uma definição só do formato, em vez de duas que precisam ser mantidas iguais à mão.
O que o schema consegue dizer
  • Os tipos de cada campo (texto, número, inteiro, booleano, objeto, lista) e quais são obrigatórios.
  • Uma lista fechada de valores (enum), mínimo e máximo de número, e tamanho mínimo e máximo de lista.
  • Uma descrição por campo, que orienta o modelo.
  • O que ele não consegue dizer fica no seu código: “exatamente uma alternativa correta”, “a correta tem de ser a do gabarito”, “este id existe no banco”.
Boas práticas
  • Prefira tipos específicos a texto livre. O Ally AI usa priority: enum ["baixa","media","alta"] em vez de deixar o modelo escrever a prioridade como quiser.
  • Use descrições nos campos e um prompt claro.
  • Valide os valores na aplicação e trate a resposta que tem a forma certa e o conteúdo errado.
  • Em streaming, cada pedaço é um JSON pela metade. Dá para mostrar progresso, mas o objeto só é válido no fim.
Structured output ou function calling?
  • Structured output define o formato da resposta final.
  • Function calling é o modelo pedindo uma ação antes de responder.

Frase de entrevista: “O schema é contrato de forma. O significado eu confiro no código, porque um JSON perfeito ainda pode trazer a resposta errada.”

Em uma frase: com function calling, o modelo pede uma ação. Ele devolve o nome de uma função e os argumentos, o seu código executa e devolve o resultado, e só então o modelo responde. O modelo nunca executa nada sozinho.

No mundo realQuando você pergunta ao ChatGPT o placar de um jogo de ontem, ele decide sozinho usar a ferramenta de busca na web antes de responder. Um assistente de companhia aérea faz o mesmo para consultar o status de um voo: o modelo pede consultarVoo({ numero: "LA3040" }), e o sistema da empresa é quem consulta.

O ciclo em quatro passos
  1. Declarar as funções: nome, descrição e argumentos, descritos em JSON Schema.
  2. Chamar o modelo com a mensagem do usuário e a lista de funções.
  3. Se o modelo decidir usar uma, ele devolve o nome e os argumentos. O seu código executa.
  4. Devolver o resultado ao modelo, que escreve a resposta final.
Variações
  • Em paralelo: várias funções independentes no mesmo turno, como o clima de três cidades.
  • Em sequência: o resultado de uma alimenta a próxima, como descobrir onde o usuário está e depois buscar o clima de lá. É o começo de um agente (veja o B2).
  • Modos: auto (o modelo decide se chama), any (sempre chama alguma) e none (nunca chama).
Segurança
  • As descrições são o que o modelo lê para decidir. Escreva com clareza quando usar cada função.
  • Valide os argumentos antes de executar. O modelo pode errar o tipo, inventar um valor ou ser induzido por um texto malicioso escondido no conteúdo que ele leu (prompt injection).
  • Confira a autorização: o usuário pode ver aquele pedido? A função só deve ter o acesso de que precisa.
  • Se a função falhar, devolva ao modelo uma mensagem útil, em vez de quebrar a conversa.

Frase de entrevista: “Tool calling é o modelo preenchendo um formulário que o meu código executa. Então eu trato os argumentos como qualquer entrada de usuário: schema, autorização e o menor acesso possível.”

Em uma frase: Generative UI é a IA respondendo com um componente, e não só com texto. O modelo chama uma ferramenta, a ferramenta devolve dados com formato fixo, e a tela desenha um componente React com esses dados.

No mundo realQuando a busca do ChatGPT responde sobre o tempo, uma ação na bolsa ou um jogo, ela mostra um cartão com o dado, e não um parágrafo descrevendo o número. Na busca de compras, aparecem cartões de produto com foto e preço. Cada cartão é um componente escolhido a partir do resultado de uma ferramenta.

O fluxo
  1. O modelo recebe o pedido e uma lista de ferramentas, cada uma com descrição, formato de entrada (em Zod) e uma função que executa.
  2. Pelo contexto, ele decide chamar uma. “Como está o tempo em São Paulo?” vira displayWeather.
  3. A ferramenta roda no servidor e devolve dados: { temperatura, condicao, cidade }.
  4. Os dados chegam ao navegador como uma parte da mensagem, e um componente <Clima /> desenha o cartão.
Desenhar por tipo e por fase
  • Cada parte de ferramenta tem o nome dela (tool-displayWeather). Você percorre as partes da mensagem e escolhe o componente pelo nome.
  • Cada parte também tem uma fase: rodando (mostre um esqueleto do cartão), pronta (mostre o cartão com os dados) e com erro (mostre o erro só naquele bloco, sem derrubar a conversa).
O que muda no desenho
  • A ferramenta vira um contrato entre o modelo e o design system: o formato de saída da ferramenta é a lista de props do componente. Mudar um obriga a mudar o outro.
  • Cada componente gerado precisa dos mesmos cuidados de qualquer componente: acessível, responsivo, com estado de carregando e de erro. É aqui que Design Engineering (R2) encontra IA.
  • O modelo escolhe de uma lista fechada de componentes. Ele nunca gera HTML para a página executar.

Frase de entrevista: “Generative UI é o modelo escolhendo qual componente do meu design system mostrar, e com quais dados. O formato da ferramenta é a interface de props.”

Em uma frase: antes de executar uma ação sensível, como rodar um comando ou fazer um pagamento, o agente para e a tela pede aprovação. Se a pessoa nega, a ação não acontece, e o modelo continua sabendo disso. É o human-in-the-loop no nível de cada ferramenta.

No mundo realO Claude Code pede permissão antes de rodar um comando no terminal ou editar um arquivo, e a pessoa pode liberar sempre, só desta vez ou negar. O agente de código do GitHub Copilot trabalha sozinho, mas entrega o resultado como um pull request que espera revisão humana antes do merge.

Os desfechos de uma chamada
  • Sem aprovação: executa direto. É o padrão, bom para ações de leitura.
  • Aprovada ou negada automaticamente: uma regra decide e fica registrado.
  • Pede ao usuário: o agente para e espera a resposta.
Regra fixa ou regra pelo valor
  • Fixa: uma regra por ferramenta, como “runCommand sempre pede aprovação”.
  • Pelo valor: uma função olha o argumento. Pagamento acima de R$ 1.000 pede aprovação, abaixo passa direto.
  • A regra pelo valor costuma ser a melhor. Pedir aprovação para tudo ensina a pessoa a clicar “sim” sem ler.
Na tela
  • O pedido chega como uma parte de ferramenta na fase “aguardando aprovação”. A tela mostra o que vai ser feito, com os argumentos legíveis, e dois botões.
  • A resposta volta pelo useChat. Na negação, a ferramenta não roda e o modelo recebe a negação. Instrua o modelo a não tentar de novo o que foi negado.
  • A API mudou de nome entre versões do SDK. Confira a versão antes de citar a assinatura numa entrevista.

Frase de entrevista: “Aprovação humana entra onde a ação é irreversível ou cara, de preferência por regra que olha o valor. Se você pede confirmação para tudo, ninguém lê a confirmação.”
