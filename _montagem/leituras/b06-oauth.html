O cheat sheet é a lista de tudo que costuma dar errado em OAuth. Três pontos concentram a maioria dos ataques reais: PKCE, validação exata de redirect_uri e o parâmetro state. Se você souber explicar esses três, cobriu a pergunta de segurança de OAuth.

Os quatro papéis, pra não trocar os nomes
  • Resource owner: a pessoa. Client: a sua aplicação. Authorization server: quem autentica e emite token (Google, GitHub). Resource server: a API que aceita o token.
  • Cliente confidencial (backend, guarda segredo) vs. público (SPA, app mobile — não consegue guardar segredo nenhum). Essa distinção determina o fluxo permitido.
PKCE — o que é e por que virou obrigatório pra todo mundo
  • O cliente gera um segredo aleatório (code_verifier), manda o hash dele (code_challenge) na ida, e o code_verifier original na troca do código por token.
  • Assim, um atacante que intercepte o authorization code não consegue trocá-lo por token: falta o verifier, que nunca trafegou na primeira etapa.
  • Nasceu pra app mobile (onde o redirect por esquema de URL podia ser sequestrado por outro app), mas o OAuth 2.1 o exige pra todos os clientes — inclusive backend. Custa quase nada e fecha uma classe inteira de ataque.
redirect_uri — validação exata, sempre
  • O servidor de autorização deve comparar a URI string por string contra uma lista pré-registrada. Nada de wildcard, nada de "começa com", nada de aceitar subdomínio.
  • O ataque: um open redirect em qualquer página do seu domínio permite fazer o código de autorização ser entregue ao atacante, mantendo a URL “legítima” aos olhos de uma validação frouxa.
state e nonce
  • state: valor aleatório, imprevisível, guardado na sessão e conferido na volta. Sem ele existe CSRF de login — o atacante te faz concluir o fluxo dele, e você fica logado na conta do atacante, entregando dados a ela sem perceber.
  • nonce (OIDC): vai no pedido e volta dentro do ID token, provando que aquele token foi emitido pra esta requisição. Defesa contra replay de ID token.
O resto da lista, em uma linha cada
  • Nunca use implicit flow nem resource owner password — os dois estão obsoletos no OAuth 2.1.
  • Token de acesso curto; refresh token com rotação e detecção de reuso (se um antigo reaparecer, revogue a família inteira).
  • Escopo mínimo, e o resource server deve validar audience, emissor, expiração e assinatura — nunca só decodificar o JWT.

Frase de entrevista: “PKCE protege o código interceptado, redirect_uri exato protege contra o código ir pro lugar errado, e state protege contra CSRF de login. São três ataques diferentes, e cada um tem a sua defesa.”

Releia só os conceitos, não os guias de instalação. Três decisões do Auth.js viram pergunta de entrevista: estratégia de sessão (JWT vs. banco), os callbacks (onde você enxerta autorização) e account linking (o mesmo humano com dois provedores).

Os callbacks, e o que fazer em cada um
  • signIn: autorização de entrada — bloquear e-mail não verificado, restringir a um domínio corporativo, recusar conta banida. Devolver false barra o login.
  • jwt: roda quando o token é criado ou atualizado. É onde você enfia dados extras (papel, id interno, accessToken do provedor). Cuidado: tudo que entrar aqui vai no cookie.
  • session: molda o que o cliente enxerga. O token pode ter campos que a sessão não deve expor — separar os dois é higiene.
  • Regra de ouro: autorização de verdade se checa no servidor, a cada requisição. O papel dentro da sessão serve pra UI; o servidor confere de novo antes de qualquer ação.
Account linking
  • Mesma pessoa entra com Google e depois com GitHub, mesmo e-mail: são duas Account apontando pro mesmo User.
  • O ponto de segurança: só ligar automaticamente quando o provedor verifica o e-mail. Ligar por e-mail não verificado permite tomada de conta — o atacante cria uma conta num provedor frouxo com o seu e-mail e herda o seu usuário.

Frase de entrevista: “Escolhi sessão em JWT porque não preciso revogar na hora; se aparecesse banimento ou ‘sair de todos os dispositivos’, eu migraria pra sessão em banco — a diferença é exatamente essa.”

Três capítulos bastam: Authorization Code Flow com PKCE, Access Tokens e Refresh Tokens. Pule tudo sobre construir servidor de autorização — no seu caso você é o cliente, e a entrevista vai perguntar do lado do cliente.

O fluxo, em oito passos
  1. O cliente gera state e code_verifier, calcula o code_challenge (SHA-256) e guarda ambos na sessão.
  2. Redireciona pro /authorize com client_id, redirect_uri, scope, response_type=code, state, code_challenge.
  3. O usuário autentica no servidor de autorização — a sua aplicação nunca vê a senha. Esse é o ponto inteiro do OAuth.
  4. O usuário consente com os escopos pedidos.
  5. Volta pro redirect_uri com code e state.
  6. O cliente confere o state contra o que guardou. Se não bater, aborta.
  7. POST /token com o code, o code_verifier e (se confidencial) o segredo do cliente. Essa chamada é servidor-a-servidor.
  8. Recebe access_token, expires_in, geralmente refresh_token e, com OIDC, id_token.

Por que o código intermediário existe: o token nunca aparece na URL, no histórico do navegador, nem no header Referer. Esse era exatamente o defeito do implicit flow.

Access tokens
  • Pro cliente, o token é opaco — não é pra você decodificar nem depender do formato; ele pode mudar.
  • Dois formatos do lado do servidor: JWT (auto-contido, valida offline pela assinatura, não dá pra revogar antes de expirar) e referência (uma chave que o resource server consulta via introspection — revogável, ao custo de uma chamada).
  • Vida curta (minutos a uma hora) é o que limita o estrago de um vazamento.
Refresh tokens
  • Servem pra obter novo access token sem incomodar o usuário. São de vida longa — e por isso o alvo mais valioso.
  • Rotação: cada uso emite um refresh novo e invalida o anterior. Se o antigo reaparecer, é sinal de roubo: revogue a família inteira e force novo login. É a resposta esperada em entrevista.
  • Em cliente público, guarde em cookie HttpOnly + Secure + SameSite, nunca em localStorage.
  • Duas condições de corrida clássicas: duas abas renovando ao mesmo tempo (resolve com single-flight, uma renova e as outras esperam), e requisições em voo quando o token expira (fila e repete depois da renovação).

Frase de entrevista: “O code existe pra o token nunca passar pelo navegador; o PKCE existe pra o code sozinho não valer nada. Access token curto, refresh com rotação e detecção de reuso.”

A primeira metade responde a pergunta que mais cai: OAuth não é autenticação, é autorização delegada. Quem faz autenticação é o OpenID Connect, uma camada fina em cima. A segunda metade do guia é produto e pode pular.

Por que OAuth sozinho não autentica
  • Um access token diz “o portador pode acessar estes recursos”. Não diz quem é o portador, nem se essa pessoa acabou de se autenticar aqui, nem pra qual aplicação o token foi emitido.
  • Daí o ataque clássico: usar /userinfo com um token obtido em outro app pra “logar” alguém. O token é válido, a pessoa existe — e ainda assim é uma tomada de conta, porque nada amarra o token à sua aplicação.
  • Foi isso que o OIDC veio padronizar, depois de cada provedor inventar um jeito próprio de responder "quem é você".
O que o OIDC acrescenta
  • scope=openid: o gatilho. Sem ele, não é OIDC, é só OAuth.
  • ID token: um JWT (aqui o formato é garantido) com claims sobre a autenticação — iss (emissor), sub (id estável do usuário), aud (a sua client_id), exp, iat, nonce, e opcionalmente email, name, picture.
  • /userinfo: endpoint padronizado pra buscar o perfil com o access token.
  • Discovery (/.well-known/openid-configuration) e JWKS: o cliente descobre endpoints e chaves públicas sozinho, e a rotação de chave do provedor não quebra você.
Validar o ID token — o que não pode faltar
  • Assinatura contra a chave do JWKS; iss igual ao esperado; aud igual à sua client_id (é isso que barra o token emitido pra outro app); exp não vencido; nonce igual ao que você enviou.
  • Identifique o usuário por sub, nunca por e-mail: e-mail muda, e e-mail não verificado permite personificação.

Frase de entrevista: “Access token é autorização — diz o que pode, não quem é. Autenticação vem do ID token do OIDC, e validar o aud é o que impede usar um token emitido pra outra aplicação.”
