O handbook, na trilha The Basics → Everyday Types → Narrowing → More on Functions → Object Types. O que ele te dá além de sintaxe: o entendimento de que o TypeScript é estrutural (compatibilidade por formato, não por nome) e que tudo é apagado em tempo de execução.

The Basics — o que o compilador faz e não faz
  • Todo o sistema de tipos some na compilação. Não existe checagem de tipo em runtime — daí a necessidade de validar a fronteira (resposta de API, formulário, variável de ambiente) com algo como Zod.
  • strict não é preferência, é o modo em que o TypeScript entrega valor. Sem strictNullChecks, null e undefined entram em qualquer tipo e a maior classe de bug real fica invisível.
  • Erro de tipo não impede a emissão do JavaScript por padrão. O que barra é o CI rodando tsc --noEmit.
Everyday Types — as decisões que aparecem em code review
  • any desliga a checagem e contamina o que toca. unknown é o par seguro: aceita tudo na entrada e obriga a estreitar antes de usar. Em fronteira, use unknown.
  • interface vs. type: praticamente intercambiáveis pra formato de objeto. interface permite declaration merging e costuma dar mensagem de erro melhor; type é o único que faz união, tupla e tipo condicional. Regra prática: interface pra objeto público, type pro resto.
  • Union literal ('ativo' | 'pausado' | 'cancelado') substitui enum na maioria dos casos, sem gerar código em runtime e com narrowing melhor.
Tipagem estrutural — o que confunde quem vem de Java/C#
  • Dois tipos são compatíveis se o formato bate; o nome não importa. Um objeto com as propriedades certas satisfaz a interface sem declarar que a implementa.
  • O excess property check só vale pra objeto literal atribuído diretamente — passando por variável intermediária, a propriedade extra passa. Saber disso explica metade dos "por que não deu erro?".
  • Quando você quer impedir a troca acidental de dois tipos de mesmo formato (UserId e PostId, ambos string), usa-se branded type: string & { __brand: 'UserId' }.
Functions e Object Types — o essencial
  • Sobrecarga só quando a assinatura muda de verdade conforme o argumento; na dúvida, união de parâmetros é mais simples de manter.
  • readonly e as const travam mutação em nível de tipo — as const transforma o literal em tipo literal, e é o que faz uma tupla de strings virar união exata.
  • Parâmetro opcional (x?: T) e T | undefined não são a mesma coisa: o segundo obriga a passar o argumento, ainda que como undefined.

O que pular no primeiro passe: conditional types, mapped types e template literal types. São poderosos, aparecem em biblioteca, e não valem o tempo antes de Narrowing e Generics estarem sólidos.

Generic serve pra preservar a relação entre entrada e saída. Se o parâmetro de tipo aparece uma vez só na assinatura, provavelmente ele não deveria existir. E 90% do erro real de generics está em constraint, não na sintaxe.

Por que generic, e não any
  • function primeiro(a: any[]): any aceita tudo e devolve nada de útil. function primeiro<T>(a: T[]): T devolve exatamente o tipo que entrou — a informação atravessa a função.
  • O compilador infere T na chamada; escrever primeiro<string>(...) quase sempre é desnecessário e às vezes atrapalha.
Generic constraints — onde mora o aprendizado
  • <T extends { length: number }> significa "qualquer T que tenha length". Sem a constraint, o corpo da função não pode acessar propriedade nenhuma de T, porque T pode ser qualquer coisa.
  • A armadilha clássica: com <T extends Forma>, você não pode devolver um Forma qualquer — quem chamou espera exatamente o T dele, que pode ter mais propriedades. O compilador está certo; a assinatura é que estava errada.
“Using type parameters in generic constraints”
  • O padrão que resolve acesso seguro a propriedade: function pegar<T, K extends keyof T>(obj: T, chave: K): T[K]. A chave é obrigada a existir no objeto, e o retorno é o tipo daquela propriedade.
  • Esse é o mecanismo por trás de Pick, Omit, e de praticamente toda API tipada de formulário ou ORM. Reconhecer keyof + indexed access (T[K]) é o pulo de qualidade real.
Dois avisos práticos
  • Default de parâmetro de tipo (<T = unknown>) facilita a adoção, mas = any como default silencia tudo sem avisar.
  • Em .tsx, <T>(x: T) => x é lido como JSX. Escreve-se <T,> (com vírgula) ou usa-se function.

Frase de entrevista: “Generic só se justifica quando o parâmetro de tipo aparece em mais de um lugar — é ele que carrega a relação entre entrada e saída. Um T que aparece só no retorno geralmente é um any disfarçado.”

A página mais útil do handbook inteiro. Narrowing é o compilador acompanhando o fluxo de controle pra saber que, dentro daquele if, o valor já não pode ser null. Três coisas daqui caem em entrevista: type predicates, discriminated unions e exaustividade com never.

As formas de estreitar
  • typeof — cuidado com a pegadinha histórica: typeof null === 'object'.
  • Truthiness — if (valor) descarta null e undefined, mas também descarta 0 e ''. Pra número e string, prefira comparação explícita.
  • in pra checar propriedade, instanceof pra classe, e igualdade (===) que estreita os dois lados de uma vez.
  • Atribuição também estreita, e o compilador rastreia isso ao longo do bloco.
Type predicates — x is Foo
  • function ehGato(a: Animal): a is Gato { return 'miar' in a; }. Depois disso, o compilador estreita dentro do if (ehGato(a)), coisa que uma função devolvendo boolean comum não faz.
  • É uma promessa não verificada: se o corpo da função mentir, o compilador acredita. Predicate é um as com melhor aparência — use com a mesma desconfiança.
  • Uso mais comum e mais útil: filtrar nulos com tipo correto — lista.filter((x): x is Item => x !== null).
Discriminated unions — o padrão que resolve estado
  • Uma propriedade literal comum (tipo, status, kind) discrimina os membros da união. Dentro de if (r.status === 'erro'), o compilador libera exatamente os campos daquele caso.
  • Substitui o objeto com tudo opcional ({ carregando?, dado?, erro? }), que permite estados impossíveis como "carregando e com erro ao mesmo tempo". A união torna esses estados irrepresentáveis.
  • É o mesmo padrão de Result<T, E>: { ok: true, dado: T } | { ok: false, erro: E }.
Exaustividade com never
  • No default do switch: const _exaustivo: never = valor;. Se um dia alguém adicionar um membro novo à união e esquecer de tratar, isso vira erro de compilação — o compilador vira o teste.
  • É a resposta certa pra "como você garante que não esqueceu um caso?" — e o argumento mais convincente a favor de união literal em vez de string solta.

Frase de entrevista: “Eu modelo estado com união discriminada em vez de campos opcionais, e fecho o switch com um never. Assim estado impossível não compila e caso novo não passa esquecido.”

É dicionário. Seis entradas cobrem quase todo uso real; o resto você procura no dia em que precisar. A ideia por trás de todas: derivar tipo em vez de duplicar — tipo copiado à mão sai de sincronia, tipo derivado não.

Detalhes que mordem
  • Omit não valida a chave: Omit<User, 'nmae'> compila e não remove nada. Pick valida. Por isso Pick é mais seguro em refatoração.
  • Partial em validação de entrada é perigoso: torna tudo opcional, inclusive o que é obrigatório. Bom pra update, ruim pra criação.
  • Required, Readonly, NonNullable, Parameters e Exclude/Extract completam a lista — passe o olho pra reconhecer quando aparecerem em código alheio.

Frase de entrevista: “Eu derivo tipo da fonte da verdade: Omit da entidade pro tipo de criação, ReturnType em vez de redeclarar retorno, e z.infer do schema quando o dado vem de fora. Tipo duplicado à mão sempre sai de sincronia.”

Zod resolve o buraco central do TypeScript: o tipo some em runtime. Toda fronteira — resposta de API, corpo de requisição, formulário, variável de ambiente, JSON.parse — entrega any ou uma mentira. Zod valida de verdade e, do mesmo schema, deriva o tipo estático.

A ideia central: uma fonte, dois usos
  • Você escreve o schema uma vez; ele serve pra validar em runtime e, via z.infer<typeof schema>, pra tipar em tempo de compilação. Sem duplicação, sem chance de divergir.
  • Esse é o argumento decisivo contra as Resposta depois de um fetch: a asserção não checa nada, só cala o compilador. Se a API mudar um campo, você descobre com undefined is not a function em produção.
parse vs. safeParse
  • parse() lança ZodError — bom no boot da aplicação (variável de ambiente faltando deve derrubar o processo na hora).
  • safeParse() devolve { success: true, data } ou { success: false, error } — uma união discriminada, que estreita sozinha no if. É o certo pra entrada de usuário, onde erro é fluxo normal, não exceção.
  • error.issues traz caminho (path) e mensagem por campo — é o que vira erro por campo no formulário.
O que mais aparece no dia a dia
  • Coerção (z.coerce.number()) pra query string e FormData, onde tudo chega como texto.
  • .refine() pra regra que não é de formato ("senha e confirmação iguais"), e .transform() pra normalizar (trim, minúsculas) já na validação.
  • Por padrão, propriedade desconhecida é removida da saída; .strict() faz virar erro. Isso importa quando o objeto validado vai direto pro banco.
  • Tipo de entrada e saída podem diferir quando há transform — daí existirem z.input e z.output.

Frase de entrevista: “Tipo do TypeScript é apagado em runtime, então toda fronteira precisa de validação de verdade. Eu valido com Zod e derivo o tipo do schema com z.infer — uma fonte só, em vez de um as que só cala o compilador.”
