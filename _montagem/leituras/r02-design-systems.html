Em uma frase: um design token é um nome ligado a um valor (color-text-primary: #000000). Esta especificação padroniza o arquivo que guarda esses pares, para o Figma, as ferramentas de conversão e o seu código trocarem decisões de design sem conversor feito à mão.

No mundo realO termo “design token” nasceu no Salesforce Lightning Design System, por volta de 2014, para manter iguais as cores e os espaços de vários produtos. O Material Design 3, do Google, usa exatamente as três camadas desta página: tokens de referência (a paleta crua, md.ref.palette.primary40), de sistema (o uso, md.sys.color.primary) e de componente (md.comp.filled-button.container.color). É isso que deixa o Android gerar um tema inteiro a partir da cor do papel de parede.

O arquivo
  • É um JSON. Cada token tem $value (o valor) e $type (o tipo: cor, dimensão, fonte, duração…). Pode ter também $description.
  • O $ no começo separa o que é do formato do que é nome de token.
  • A versão 2025.10 é um relatório final e estável de um grupo da comunidade W3C. Não é um padrão oficial do W3C, mas foi feito para ser implementado.
Grupos
  • Um grupo é um objeto sem $value, que só organiza (color.accent.light).
  • Um token sem $type herda o tipo do grupo. Declare "$type": "color" uma vez no grupo color, e todos os filhos são cor.
Aliases: a parte que importa para tema
  • Um token pode apontar para outro: "$value": "{colors.orange.560}". Esse apontamento se chama alias.
  • É assim que o token semântico (color.brand) aponta para o primitivo (colors.orange.560). Para o tema escuro, você muda só o alvo do alias.
  • Um token não pode apontar para si mesmo, direta ou indiretamente. Isso deve dar erro.
Tipos
  • Simples: cor, dimensão ({ value: 16, unit: "px" }), família e peso de fonte, duração, curva de animação e número.
  • Compostos: borda, sombra, transição, gradiente e tipografia (família, tamanho, peso e entrelinha juntos).
  • A cor deixou de ser um hex solto: virou um objeto com espaço de cor, o que combina com quem já usa OKLCH.

Frase de entrevista: “Token é decisão de design com nome. Eu separo primitivo de semântico por alias, e o componente só conhece o semântico. É isso que deixa trocar tema ou marca sem tocar em componente.”

Em uma frase: o cva transforma “quais classes este botão usa em cada combinação?” numa tabela com tipos. Você descreve as variantes uma vez, e ele devolve uma função que recebe as props e devolve as classes certas.

No mundo realO <Button> do shadcn/ui, uma das coleções de componentes React mais copiadas hoje, é escrito com cva: variant (default, destructive, outline, ghost, link) e size (default, sm, lg, icon). Quando você roda npx shadcn add button, é esse arquivo que entra no seu projeto.

As quatro partes
const button = cva(["font-semibold", "border", "rounded"], {
  variants: {
    intent: { primary: ["bg-blue-500", "text-white"], secondary: ["bg-white", "text-gray-800"] },
    size:   { small: ["text-sm", "py-1", "px-2"], medium: ["text-base", "py-2", "px-4"] },
  },
  compoundVariants: [{ intent: "primary", size: "medium", class: "uppercase" }],
  defaultVariants: { intent: "primary", size: "medium" },
});
  • Base (o primeiro argumento): as classes que toda instância recebe.
  • variants: cada chave é uma dimensão (intent, size), e cada valor é uma opção.
  • compoundVariants: classes que só entram quando várias condições valem juntas, como “maiúsculas só no primário médio”. Substitui um CSS do tipo .btn-primary.btn-medium.
  • defaultVariants: o que vale quando a prop não é passada.
Por que existe
  • Sem ele, você liga classe e prop à mão e escreve os tipos à mão, e os dois se desencontram.
  • Com VariantProps<typeof button>, o tipo das props sai da própria tabela. Acrescente size: "large" e ele aparece no autocomplete. Passe um valor inválido e o TypeScript reclama.
  • É pequeno (cerca de 600 bytes) e funciona com Tailwind ou com qualquer classe.

Frase de entrevista: “Variante de componente é uma tabela, não um if espalhado. Com cva, a tabela vira o tipo das props, então uma combinação que o design não prevê nem compila.”

Em uma frase: uma story é um estado de um componente, desenhado sozinho fora do app: o botão primário, o botão desabilitado, o botão carregando. A mesma story serve de documentação e de caso de teste.

No mundo realO site de componentes React do Carbon, o design system da IBM, é um Storybook: cada componente tem as suas stories, com controles para mudar as props ao vivo. O Primer, do GitHub, publica um Storybook do mesmo jeito. É ali que designers e devs de outros times conferem como um componente se comporta antes de usar.

Como se escreve
import type { Meta, StoryObj } from '@storybook/react-vite';
import { Button } from './Button';

const meta = { component: Button } satisfies Meta<typeof Button>;
export default meta;
type Story = StoryObj<typeof meta>;

export const Primary: Story = { args: { label: 'Salvar', intent: 'primary' } };
export const Disabled: Story = { args: { label: 'Salvar', disabled: true } };
  • O export default diz qual componente o arquivo documenta.
  • Cada export com nome é uma story, com as props que ela usa.
Os quatro conceitos
  • args: as props da story, que dá para editar ao vivo no painel. Uma story por variante.
  • decorators: o que envolve a story, como o tema escuro ou um provider de contexto.
  • parameters: configurações dos addons, como as regras do teste de acessibilidade.
  • play: código que roda depois de desenhar a story e simula o usuário: clicar, digitar e conferir o resultado. A story vira um teste de interação.
Por que é mais que um catálogo
  • A mesma story alimenta a documentação, o teste de interação, o teste de acessibilidade e o print do teste visual. Um lugar só para manter.
  • Estados difíceis de alcançar no app (erro, lista vazia, texto enorme) viram uma story cada. É onde o design system prova que cobriu todos os casos.

Frase de entrevista: “Cada estado que o design exige vira uma story. A partir daí ela é documentação viva e o caso que o teste visual e o de acessibilidade usam.”

Em uma frase: o addon de acessibilidade do Storybook roda o axe-core em cada story e aponta problemas como contraste baixo ou botão sem nome. Segundo a documentação, isso pega até cerca de 57% dos problemas de WCAG. Uma configuração decide se o problema é só um aviso ou se reprova o build.

No mundo realO axe-core, da empresa Deque, é o motor de acessibilidade mais usado da web. As auditorias de acessibilidade do Lighthouse, no Chrome, rodam axe-core por baixo, e o Accessibility Insights, da Microsoft, também. O Ally AI usa o mesmo motor para auditar sites.

O que aparece
  • Um painel com três abas: violações, aprovados e incompletos. A última lista o que o axe não conseguiu decidir sozinho, e você precisa conferir à mão.
  • Botões que simulam deficiências de visão, como daltonismo, sobre a story.
A configuração que importa
// .storybook/preview.ts
parameters: {
  a11y: { test: 'error' }, // 'error' | 'todo' | 'off'
}
  • 'error': a violação reprova o teste, no Storybook e no CI.
  • 'todo': a violação aparece como aviso. Serve para um problema conhecido que você ainda vai corrigir.
  • 'off': desliga a checagem automática.
  • Dá para deixar 'error' no projeto todo e baixar para 'todo' só numa story com problema conhecido, sem afrouxar o resto.
O limite

O teste automático pega o que dá para medir no código. Ele não sabe se a ordem do Tab faz sentido nem se o texto alternativo descreve bem a imagem. Não substitui teste manual nem teste com quem usa leitor de tela.

Frase de entrevista: “Eu ponho o axe no componente, em modo error, para a regressão de acessibilidade quebrar o build cedo. O que sobra, como ordem de foco e leitor de tela, eu testo à mão, sem chamar isso de conformidade.”

Em uma frase: o Code Connect liga um componente do Figma ao seu componente React. Quando alguém inspeciona o botão no Dev Mode, aparece o seu <Button intent="danger">, com as props certas, e não um CSS gerado.

No mundo realSem isso, o Dev Mode mostra o que o Figma consegue deduzir do desenho: position, padding: 12px, uma cor em hex. Num time com design system, ninguém deveria copiar esse CSS, porque o certo é usar o componente que já existe. O Code Connect fecha essa distância: o designer escolhe a variante “Danger” no Figma, e o dev vê o código exato que precisa escrever.

Como se liga
figma.connect(Button, 'https://figma.com/design/...', {
  props: {
    label: figma.string('Label'),
    disabled: figma.boolean('Disabled'),
    intent: figma.enum('Variant', { Primary: 'primary', Danger: 'danger' }),
  },
  example: ({ label, disabled, intent }) => (
    <Button intent={intent} disabled={disabled}>{label}</Button>
  ),
});
  • figma.string lê um texto do Figma (o rótulo), figma.boolean lê um sim ou não, e figma.enum traduz cada variante do Figma para o valor da prop.
  • figma.instance lê um componente dentro de outro, como o ícone dentro do botão.
  • Se um componente do Figma corresponde a vários no código (um “Button” que no código é PrimaryButton e SecondaryButton), você cria uma ligação para cada variante.
Um detalhe importante
  • O arquivo não é executado: o exemplo é tratado como texto. Condicionais e lógica dentro do example não funcionam como em React de verdade. Escreva o exemplo como o dev deveria escrever o uso.
  • O ganho é de contrato: o nome da prop no Figma e no código passam a ter um mapa explícito, e uma diferença entre os dois fica visível.

Frase de entrevista: “Handoff bom é quando o designer e eu usamos o mesmo nome de prop. O Code Connect torna esse mapa explícito: o Dev Mode mostra o meu componente com a variante certa, e não um CSS que ninguém vai usar.”

Em uma frase: await expect(page).toHaveScreenshot() é teste visual numa linha. Na primeira vez, ele salva um print de referência. Nas seguintes, compara pixel a pixel. O difícil não é escrever o teste, é manter o print de referência confiável.

No mundo realO Chromatic, serviço criado pelos mantenedores do Storybook, existe para resolver exatamente o problema desta página: ele tira o print de cada story sempre no mesmo ambiente, na nuvem, e quando algo muda pede que uma pessoa aprove ou recuse a diferença no pull request. O Percy, da BrowserStack, faz o mesmo. O Playwright, que tem essa função de graça, é mantido pela Microsoft.

O print de referência
  • O print de referência (a baseline) fica numa pasta ao lado do teste e vai para o Git, como código.
  • O nome do arquivo leva o navegador e o sistema: landing-chromium-linux.png.
  • Mudou o visual de propósito? npx playwright test --update-snapshots grava os prints novos, e a revisão do pull request passa a incluir as imagens.
O aviso que separa teste útil de teste instável

A renderização muda com o sistema operacional, a versão do navegador, as fontes instaladas e até o hardware. Um print gerado no seu Windows e comparado no Linux do CI falha em todas as telas. A regra é gerar e comparar no mesmo ambiente, na prática o container do CI.

Controlando o ruído
  • maxDiffPixels: 100 tolera uma diferença pequena de pixels, como o serrilhado de uma fonte.
  • stylePath aplica um CSS só no print para esconder o que muda sozinho: data, avatar, animação.
  • Componente isolado (uma story, ou uma página de referência como o /admin/design do Gabarita) dá print estável. Página inteira com dados reais dá print instável.

Frase de entrevista: “Teste visual só vale com print de referência estável: mesmo container no CI, conteúdo dinâmico escondido e tolerância pequena só para ruído de fonte.”
