A base pra tudo nesta seção. O caminho crítico é a sequência que o navegador percorre entre receber o HTML e pintar o primeiro pixel: HTML → DOM, CSS → CSSOM, os dois → render tree, layout, paint, composite. Otimizar carregamento é encurtar essa sequência; otimizar interação é evitar refazê-la.

As seis etapas
  1. DOM: o parser lê o HTML incrementalmente e já pode pintar o que chegou.
  2. CSSOM: o CSS é bloqueante de renderização. Sem ele completo, o navegador não pinta — pintar sem estilo e repintar seria pior.
  3. Render tree: DOM + CSSOM, só com o que é visível (display: none fica de fora; visibility: hidden entra, ocupando espaço).
  4. Layout (reflow): calcula geometria — posição e tamanho de cada caixa. Custo proporcional ao número de nós.
  5. Paint: preenche pixels em camadas.
  6. Composite: junta as camadas, muitas vezes na GPU.
O que bloqueia o quê
  • CSS bloqueia renderização (e, por tabela, a execução de script que vem depois, porque o script pode consultar estilo).
  • Script sem defer/async bloqueia o parser: ele para de construir o DOM, baixa e executa. O motivo histórico é document.write.
  • Fonte via @font-face só é baixada quando o CSS diz que ela é usada — daí a demora, e daí o preload.
As alavancas, em ordem de impacto
  • Reduzir o número de recursos bloqueantes (CSS crítico inline, o resto adiado; defer em todo script).
  • Reduzir bytes (compressão Brotli, minificação, dividir o bundle).
  • Reduzir viagens (CDN próximo, preconnect pro domínio de origem crítico, preload do recurso que só é descoberto tarde).

Frase de entrevista: “CSS bloqueia pintura, script sem defer bloqueia o parser. A primeira coisa que eu olho num carregamento lento é quantos recursos bloqueantes existem antes do primeiro paint — quase sempre é um script síncrono no head ou uma folha de estilo gigante.”

O foco aqui é a diferença entre nenhum atributo, defer e async — quando cada um baixa e quando executa em relação ao parse do HTML. É a pergunta de front-end mais previsível que existe.

Como escolher
  • defer é o padrão certo pra script da aplicação: ordem preservada e DOM pronto quando roda.
  • async só pra script totalmente independente, que não depende do DOM nem de outro script — analytics é o exemplo canônico.
  • Nenhum atributo só quando o script precisa rodar antes da pintura de propósito (o trecho anti-flash que decide o tema, por exemplo).
  • type="module" já é defer por padrão.
As outras causas comuns de FCP ruim
  • CSS não usado: extrair o crítico e carregar o resto de forma não bloqueante (media="print" trocado no onload, ou rel="preload" + troca pra stylesheet).
  • Fonte: font-display: swap evita texto invisível; preload da fonte usada no topo evita a espera em cascata.
  • Cadeia de requisições: HTML → CSS → @import → fonte é uma sequência serial. Cada elo custa um RTT — @import dentro de CSS é o pior padrão dessa lista.
  • Servidor lento (TTFB): nenhuma otimização de front-end compensa 800ms de espera pelo primeiro byte.

Tabela de consulta: para cada propriedade CSS, quais fases ela dispara ao mudar — layout, paint, composite. A conclusão prática cabe numa linha: anime só transform e opacity.

As três fases, em custo
  • Layout (o mais caro): recalcula geometria, e pode afetar irmãos e filhos. Disparado por width, height, top, left, margin, padding, font-size, display.
  • Paint (médio): repinta pixels sem recalcular posição. Disparado por color, background, box-shadow, border-radius, visibility.
  • Composite (barato): só reposiciona camadas já pintadas, tipicamente na GPU. É o que transform e opacity fazem.
Por que isso decide se a animação roda a 60fps
  • A 60fps, cada quadro tem 16,7 ms para tudo. Animar left significa layout + paint + composite a cada quadro; animar transform: translateX() significa só composite.
  • Layout thrashing: ler uma propriedade geométrica (offsetWidth, getBoundingClientRect) logo depois de escrever força o navegador a recalcular o layout naquele instante. Num laço, isso multiplica reflows. A correção é agrupar todas as leituras e só então todas as escritas.
  • will-change: transform avisa o navegador pra promover a camada antes — mas usar em excesso consome memória de GPU e piora. Aplique pouco antes da animação, remova depois.
Como migrar animação comum
  • Posição: left/top → transform: translate().
  • Tamanho: width/height → transform: scale() (com a ressalva de que escala distorce o conteúdo).
  • Aparecer/sumir: display → opacity + visibility, ou as transições de @starting-style e transition-behavior: allow-discrete, mais novas.

JavaScript é o recurso mais caro da página: além de baixar, precisa ser parseado, compilado e executado na thread principal. Code splitting adia o que não é necessário agora — e em celular modesto isso vale mais do que qualquer compressão.

Os três cortes, em ordem de retorno
  1. Por rota: cada página baixa só o seu código. É o corte de maior retorno, e frameworks modernos fazem automaticamente.
  2. Por componente pesado: editor de texto rico, biblioteca de gráfico, mapa, leitor de PDF. import() dinâmico (ou React.lazy) carrega quando o componente aparece ou quando o usuário aciona.
  3. Por interação: modal, menu complexo, fluxo de checkout — só quando o usuário clicar.
Como funciona
  • import('./editor') devolve promessa; o bundler cria um chunk separado no ponto do import(). Em React: const Editor = lazy(() => import('./Editor')) dentro de um <Suspense> com fallback.
  • Sempre trate a falha de carregamento do chunk: rede instável e deploy novo (hash de arquivo mudou) fazem o import dinâmico rejeitar. Sem tratamento, a tela fica branca.
  • Precarregue na intenção: no mouseenter/focus do botão, dispare o import(). O download acontece durante os ~200ms até o clique e a espera percebida vira zero.
Os erros que anulam o ganho
  • Granularidade demais: dezenas de chunks minúsculos custam mais em requisições do que economizam em bytes.
  • Cascata: chunk que importa chunk que importa chunk — cada nível é mais um RTT.
  • Dependência duplicada em vários chunks porque não foi extraída num chunk comum.
  • Não medir: rode o analisador de bundle antes de dividir. Muitas vezes o problema é uma biblioteca de datas ou de ícones importada inteira, e a correção é trocar o import, não dividir.

Imagem costuma ser a maior fatia de bytes de uma página e o elemento LCP mais comum. Dois módulos bastam: formato e imagens responsivas. Compressão avançada e vídeo podem ficar de fora.

Formato
  • AVIF comprime melhor; WebP tem suporte universal hoje; JPEG é o fallback. <picture> com vários <source type> deixa o navegador escolher o primeiro que ele entende.
  • SVG pra ícone, logo e ilustração vetorial — escala sem perder e costuma ser minúsculo.
  • PNG só quando transparência com bordas nítidas for necessária e o WebP não servir.
  • Foto grande em PNG é o erro de peso mais comum em produção.
Imagens responsivas
  • srcset + sizes: você oferece várias larguras e declara o espaço que a imagem vai ocupar no layout; o navegador escolhe considerando também a densidade da tela.
  • sizes errado é o erro clássico — sem ele, o navegador assume 100% da largura da janela e baixa maior do que precisa.
  • <picture> com media serve pra art direction: recorte diferente no celular, não só tamanho diferente.
Layout e prioridade
  • Sempre declare width e height (ou aspect-ratio): o navegador reserva o espaço e o conteúdo não pula quando a imagem chega. É a principal causa de CLS.
  • loading="lazy" pro que está abaixo da dobra — e nunca na imagem do topo, que é justamente a que precisa vir primeiro.
  • Pra imagem LCP: fetchpriority="high" e, se ela for descoberta tarde (via CSS ou JS), preload.
  • decoding="async" evita bloquear a thread principal na decodificação.

Frase de entrevista: “Imagem do topo: sem lazy, com fetchpriority="high", dimensão declarada e formato moderno via <picture>. Abaixo da dobra: lazy. Isso resolve LCP e CLS ao mesmo tempo.”
