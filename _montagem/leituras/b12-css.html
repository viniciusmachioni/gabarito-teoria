A cascata é o algoritmo que decide qual declaração vence quando várias miram o mesmo elemento. Especificidade é só um dos critérios, e nem o primeiro — entender a ordem completa é o que resolve “por que meu CSS não aplica”.

A ordem de desempate, de cima pra baixo
  1. Origem e importância. A ordem completa: normal do navegador → normal do usuário → normal do autor → animação → !important do autor → !important do usuário → !important do navegador. Repare que !important inverte a hierarquia — por isso o do usuário ganha do seu, e é assim que folha de estilo de acessibilidade funciona.
  2. Camadas (@layer), na ordem em que foram declaradas.
  3. Especificidade, como (inline, id, classe/atributo/pseudo-classe, elemento/pseudo-elemento).
  4. Ordem de aparição: em tudo igual, a última declaração vence.
Especificidade — os detalhes que mordem
  • Não é um número: (0,1,0) é infinitamente maior que (0,0,99). Noventa e nove classes não vencem um id.
  • :is() e :not() assumem a especificidade do argumento mais específico; :where() vale zero — a ferramenta certa pra estilo base sobrescrevível.
  • Seletor universal (*) e combinadores (>, +) não somam nada.
  • Estilo style="" só perde pra !important. Por isso guerra de !important começa quando alguém resolve “só desta vez”.
Herança e os valores especiais
  • Nem toda propriedade herda: cor, fonte e line-height herdam; border, padding e display não.
  • inherit força herdar, initial volta ao padrão da especificação (não ao do navegador), unset = herda se herdável, senão initial, e revert volta ao estilo do navegador. revert costuma ser o que você realmente queria ao “resetar”.

Frase de entrevista: “A cascata resolve por origem, depois camada, depois especificidade, depois ordem. Como !important inverte a ordem de origem, ele deixa de ser truque e vira dívida — prefiro resolver com camada.”

@layer resolve o problema que a especificidade criou: entre camadas diferentes, a ordem de declaração decide, e a especificidade não entra na conta. Um seletor de uma classe numa camada posterior vence um #id de uma camada anterior.

Como funciona
  • Declare a ordem uma vez, no topo: @layer reset, base, componentes, utilidades;. A ordem das declarações é o que vale, não a ordem em que você preenche cada camada.
  • Dentro da mesma camada, a especificidade tradicional volta a valer normalmente.
  • Estilo sem camada vence todas as camadas. Isso é contraintuitivo e proposital: código legado fora de camadas continua ganhando, o que permite adotar @layer aos poucos.
  • @import url(…) layer(vendor) coloca uma folha de terceiro inteira numa camada — jeito limpo de garantir que o CSS de uma biblioteca nunca ganhe do seu.
O que isso resolve na prática
  • Fim do !important defensivo e das cadeias de seletor inflacionadas só pra ganhar de uma biblioteca.
  • Ordem de importação deixa de importar pro resultado — a camada declara a intenção, não o acaso do bundler.
  • Design system sobrescrevível de verdade: base em camada baixa, aplicação em camada alta, sem guerra.

A combinação vencedora: @layer pra hierarquia entre grupos + :where() pra zerar especificidade dentro do estilo base. Juntos, eliminam praticamente toda a necessidade de !important em CSS novo.

É consulta, não leitura linear. Agora, passe o olho na estrutura: propriedades do contêiner de um lado, do item do outro. Depois volte pra propriedade específica no dia em que precisar.

A distinção que organiza tudo: grid vs. flex
  • Grid é bidimensional — você define linhas e colunas, e o contêiner manda no layout. Use pra estrutura de página e para qualquer arranjo em que o alinhamento entre linhas importe.
  • Flex é unidimensional — uma direção por vez, e o conteúdo influencia o tamanho. Use pra barra, lista de botões, alinhamento de um grupo.
  • Regra prática: layout em grid, componente em flex. E eles se combinam — itens de grid podem ser contêineres flex.
Do contêiner — o que mais se usa
  • grid-template-columns com fr (fração do espaço livre) e repeat().
  • minmax() pra faixa (mínimo e máximo) e auto-fit / auto-fill pra quantidade variável de colunas.
  • A linha que resolve grade responsiva sem media query nenhuma: grid-template-columns: repeat(auto-fit, minmax(250px, 1fr)). Vale memorizar — é pedida clássica em entrevista de CSS.
  • gap, grid-template-areas (layout legível por nome), place-items pra alinhar nos dois eixos.
  • Diferença de auto-fit e auto-fill: com poucos itens, auto-fit estica as colunas existentes; auto-fill mantém colunas vazias.
Do item
  • grid-column: span 2 / grid-row pra ocupar mais de uma célula; grid-area pra nomear.
  • justify-self / align-self pra alinhar um item específico dentro da célula.
Detalhes que evitam bug
  • O valor padrão minimum size de um item de grid/flex é auto, e ele se recusa a encolher abaixo do conteúdo — a causa clássica de estouro horizontal com texto longo ou <pre>. A correção é min-width: 0 (ou min-height: 0) no item.
  • Propriedades lógicas (margin-inline, padding-block, inset) em vez de left/right facilitam suporte a idioma da direita pra esquerda.

Media query pergunta o tamanho da janela; container query pergunta o tamanho do espaço disponível pro componente. É a diferença entre um componente que só funciona onde foi projetado e um que funciona em qualquer lugar.

Por que media query não bastava
  • O mesmo card aparece numa sidebar estreita e numa área de conteúdo larga, na mesma tela. A largura do viewport não distingue os dois casos — a media query decide errado num deles necessariamente.
  • A gambiarra antiga era passar uma prop (variant="compacto") e obrigar quem usa a saber em que contexto está. Container query devolve essa responsabilidade ao CSS.
Como escrever
  • No pai: container-type: inline-size (o mais comum — observa só a largura) e, opcionalmente, container-name.
  • No filho: @container (min-width: 400px) { … }, ou com nome pra mirar um contêiner específico.
  • Só funciona com um ancestral declarado como contêiner — o erro número um é esquecer o container-type no pai.
  • container-type: size (as duas dimensões) exige altura definida e quebra layout com frequência; prefira inline-size.
Unidades de contêiner e o efeito no design system
  • cqw, cqh, cqi, cqb — relativas ao contêiner, não ao viewport. Úteis pra tipografia que acompanha o espaço do componente.
  • O ganho arquitetural: o componente vira de verdade autocontido. Você pode movê-lo pra qualquer região do layout e ele se adapta sozinho, sem prop e sem media query no consumidor.

Frase de entrevista: “Media query é para o layout da página; container query é para o componente. Com container query eu consigo um card que se adapta ao espaço que recebeu, o que media query não resolve porque ela só conhece o viewport.”

Resolve de vez o “meu z-index: 9999 não funciona”. z-index só compete dentro do mesmo contexto de empilhamento — e vários ancestrais criam contexto novo sem que você perceba.

O que cria um contexto de empilhamento
  • Elemento posicionado (relative, absolute, sticky) com z-index diferente de auto.
  • position: fixed ou sticky — sempre, mesmo sem z-index.
  • opacity menor que 1. Este é o culpado mais frequente e o menos suspeito.
  • transform, filter, backdrop-filter, perspective, clip-path, mask, mix-blend-mode diferente de normal.
  • will-change com qualquer dessas propriedades, isolation: isolate, contain: paint e filho de flex/grid com z-index.
A regra que explica o bug
  • O contexto funciona como uma caixa selada: o filho, por maior que seja o z-index, nunca escapa da posição do pai na pilha. Um filho com z-index: 9999 dentro de um pai com z-index: 1 continua atrás de um irmão do pai com z-index: 2.
  • Dentro de um contexto, a ordem de pintura é: fundo do contexto → z-index negativo → blocos no fluxo → flutuantes → inline → z-index: 0/auto → z-index positivo.
Como consertar de verdade
  • Tire o elemento de dentro do contexto: renderize modal, tooltip e menu em portal no fim do body. É por isso que toda biblioteca de UI faz isso.
  • Melhor ainda: use a top layer do navegador — <dialog> com showModal() e a Popover API ficam acima de tudo, imunes a z-index e a contexto de empilhamento.
  • Padronize a escala de z-index em variáveis (--z-dropdown: 100; --z-modal: 400) em vez de números mágicos crescentes.
  • isolation: isolate serve pra criar contexto de propósito, contendo o z-index de um subárvore.
