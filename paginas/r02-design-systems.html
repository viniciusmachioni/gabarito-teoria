Design Systems & Design Engineering

~8h · a frente que justifica o título “Design Engineer” na headline

Uma vaga de Design Engineer não pergunta se você sabe Tailwind — pergunta como você transforma uma decisão de design em algo que não precisa ser decidido de novo: um token, uma variante, um componente documentado, um teste que reprova o build quando alguém quebra o contraste. O roadmap pede quatro coisas: evoluir o design system que você já tem pra tokens/variantes/composição/documentação, ter uma biblioteca no Storybook ligada ao Figma, regressão visual e acessibilidade testadas automaticamente, e componentes responsivos e acessíveis pela WCAG 2.1. A boa notícia: o Gabarita já tem metade da fundação, e o Ally AI é um motor de teste automatizado de acessibilidade. Base teórica de apoio em B11 · Acessibilidade, B12 · CSS moderno e B10 · Testes.

  • Design Tokens Format Module 2025.10
    O formato de arquivo de tokens do W3C Design Tokens Community Group, publicado como relatório final estável em outubro de 2025. É a língua comum entre Figma, Style Dictionary, Tokens Studio e o seu código.
    Ler trechos · ~30 minLeia a introdução, a definição de token, grupos, aliases e a lista de tipos (color, dimension, typography, shadow). Pule as seções de conformidade e as regras de parsing.
    designtokens.org · W3C Community Group
    Resumo aqui na página

    Um design token é, no mínimo, um nome legível ligado a um valor (color-text-primary: #000000). A especificação do Design Tokens Community Group padroniza o arquivo que guarda esses pares, pra Figma, ferramentas de tradução e o seu código trocarem decisões de design sem conversor feito à mão. A versão 2025.10 é um relatório final, marcado como estável e “intended for implementation” — não é um padrão W3C oficial, é um relatório de Community Group.

    O arquivo
    • É JSON, com extensão recomendada .tokens ou .tokens.json e MIME application/design-tokens+json.
    • Todo token tem $value (obrigatório, o dado) e $type (obrigatório ou herdado). Opcionais: $description, $deprecated e $extensions (metadado de fornecedor, em notação de domínio reverso).
    • O prefixo $ é reservado: é o que separa propriedade do formato de nome de token ou grupo.
    Grupos e herança de tipo
    • Grupo é qualquer objeto sem $value. Serve pra organizar (color.accent.light), não implica tipo nem propósito.
    • Um token sem $type herda o tipo do grupo-pai mais próximo que declara $type — declare "$type": "color" uma vez no grupo color e todos os filhos são cor.
    • $root dá ao grupo um valor-base (o “accent” sem sufixo), e $extends permite um grupo herdar de outro, com as propriedades locais sobrescrevendo.
    Aliases: a parte que importa pra tema
    • Chaves: "$value": "{colors.blue}" resolve pro valor inteiro de outro token. É assim que um token semântico (semantic.primary) aponta pra um primitivo (colors.blue).
    • JSON Pointer ({"$ref": "#/colors/blue/$value/components/0"}) acessa uma propriedade específica, como só o matiz de uma cor.
    • Referência circular é proibida e deve gerar erro.
    Tipos
    CategoriaTipos
    Básicoscolor (com colorSpace e components), dimension ({ value, unit: "px" | "rem" }), fontFamily, fontWeight, duration, cubicBezier, number
    CompostosstrokeStyle, border, transition, shadow (um ou vários), gradient, typography (família + tamanho + peso + entrelinha)

    Repare que cor não é mais uma string hex solta: é um objeto com espaço de cor — o que casa com quem já escreve token em OKLCH.

    Frase de entrevista: “Token é decisão de design com nome. Eu separo primitivo de semântico por alias, e o componente só conhece o semântico — é isso que deixa trocar tema ou marca sem tocar em componente. O formato do DTCG é o que faz essa camada viajar entre Figma e código.”

  • cva — Variants
    A API de variantes que o shadcn/ui popularizou: base, variants, compoundVariants e defaultVariants, com tipo derivado das variantes.
    Ler inteiro · ~10 minPágina curta, um exemplo de botão que cobre tudo. Leia junto a página de TypeScript (VariantProps).
    cva.style · oficial
    Resumo aqui na página

    O cva (class-variance-authority) transforma “qual combinação de classes este botão usa?” numa tabela declarativa e tipada. Você descreve base, variantes, combinações e defaults; ele devolve uma função que recebe props e devolve a string de classes certa. É a peça por trás dos componentes do shadcn/ui.

    As quatro partes
    const button = cva(["font-semibold", "border", "rounded"], {
  variants: {
    intent: { primary: ["bg-blue-500", "text-white"], secondary: ["bg-white", "text-gray-800"] },
    size:   { small: ["text-sm", "py-1", "px-2"], medium: ["text-base", "py-2", "px-4"] },
    disabled: { false: null, true: ["opacity-50", "cursor-not-allowed"] },
  },
  compoundVariants: [{ intent: "primary", disabled: false, class: "hover:bg-blue-600" }],
  defaultVariants: { intent: "primary", size: "medium", disabled: false },
});
    • Base (primeiro argumento): classes aplicadas em toda instância.
    • variants: cada chave é uma dimensão (intent, size) e cada valor é uma opção. null numa opção significa “não aplica nada” — é o truque do disabled: false.
    • compoundVariants: classes que só entram quando várias condições batem juntas (hover só no primário habilitado; uppercase só no primário médio). É o que substitui o CSS de “.btn-primary.btn-small:not(:disabled)”.
    • defaultVariants: o que vale quando a prop não é passada.
    • class e className funcionam igual; use o do seu framework.
    Por que existe
    • A documentação cita a dor original: com CSS tradicional você casa classe e prop na mão e escreve os tipos na mão. Bibliotecas CSS-in-TS (Stitches) tinham variantes tipadas, mas não servem pra todo projeto.
    • Com o helper VariantProps<typeof button>, as props do componente derivam da tabela de variantes: adicionar size: "large" já aparece no autocomplete e um valor inválido reprova no TypeScript.
    • É pequeno (~600 bytes comprimido) e agnóstico: funciona com Tailwind ou com qualquer classe.

    Frase de entrevista: “Variante de componente é uma tabela, não um if espalhado. Com cva a tabela vira o tipo das props, então uma combinação que o design não prevê nem compila.”

  • Storybook — How to write stories
    O que é uma story, o Component Story Format (CSF), args, decorators, parameters e play functions.
    Ler inteiro · ~20 minÉ a página-base. Os subtópicos (args, decorators, play) têm páginas próprias — abra só quando for implementar.
    storybook.js.org · oficial
    Resumo aqui na página

    Uma story captura o estado renderizado de um componente sob condições específicas: um objeto com anotações que descrevem comportamento e aparência dados certos argumentos. O formato padrão é o CSF (Component Story Format), que é só um módulo ES — e a mesma story serve de documentação e de caso de teste.

    A anatomia do CSF
    import type { Meta, StoryObj } from '@storybook/your-framework';
import { Button } from './Button';

const meta = { component: Button } satisfies Meta<typeof Button>;
export default meta;
type Story = StoryObj<typeof meta>;

export const Primary: Story = { args: { label: 'Button', primary: true } };
    • Export default (meta): metadados que dizem como o Storybook lista as stories e o que os addons recebem. Precisa de title ou de component (que gera o título).
    • Exports nomeados: cada um é uma story, em UpperCamelCase. Cada story é um objeto dizendo com que argumentos renderizar.
    Os quatro conceitos
    ConceitoO que éUso típico
    argsas props do componente, editáveis ao vivo no painel Controlsuma story por variante: Primary, Danger, Disabled
    decoratorswrappers em volta da story, em nível global, de componente ou de storytema claro/escuro, layout, provider de contexto
    parametersmetadado estático que configura addonsfundos disponíveis, regras do addon de acessibilidade
    playcódigo que roda depois da renderização, simulando interação e afirmando resultado“clicar no botão abre o menu” como teste
    Por que isso é mais que um catálogo
    • A story centraliza a definição dos estados de um componente: o mesmo objeto alimenta a página de documentação, o teste de interação (play), o teste de acessibilidade e o snapshot visual. Menos lugares pra manter.
    • Estados difíceis de alcançar no app real (erro, vazio, carregando, texto muito longo) viram uma story cada — é onde o design system prova que cobriu os “estados obrigatórios”.

    Frase de entrevista: “Pra mim cada estado que o design exige vira uma story. A partir daí ela é ao mesmo tempo documentação viva e o caso que o teste visual e o de acessibilidade usam.”

  • Storybook — Accessibility tests
    @storybook/addon-a11y: axe-core rodando em cada story, com parameters.a11y.test decidindo se a violação reprova o CI.
    Ler inteiro · ~15 minPreste atenção nos três valores de test (error/todo/off) e na aba “incomplete”.
    storybook.js.org · oficial
    Resumo aqui na página

    O @storybook/addon-a11y roda o axe-core da Deque em cada story, avaliando o DOM renderizado contra as regras WCAG 2.0/2.1 A/AA e boas práticas. Segundo a própria documentação, isso pega até ~57% dos problemas de WCAG — e a configuração decide se a violação é aviso ou build vermelho.

    Instalação e o que aparece
    • npx storybook add @storybook/addon-a11y.
    • Um painel com três abas: violations, passes e incomplete. A última lista o que o axe não conseguiu decidir e você precisa conferir na mão.
    • Botões na toolbar pra simular deficiências de visão sobre a story.
    parameters.a11y: a chave que importa
    // .storybook/preview.ts
parameters: {
  a11y: {
    context: 'body',
    config: { rules: [{ id: 'region', enabled: false }] },
    test: 'error', // 'error' | 'todo' | 'off'
  },
}
    testEfeito
    'error'violação reprova o teste na UI do Storybook e no CI
    'todo'violação aparece como aviso — pra dívida conhecida que você está pagando
    'off'desliga a checagem automática (o painel manual continua)
    • Pode ser global (em preview.ts) e sobrescrito por story: uma story com problema conhecido vai pra 'todo' sem afrouxar o resto.
    • Com @storybook/addon-vitest, as checagens rodam como teste de componente e aparecem como status ao lado de cada story; no CI, as stories com 'error' reprovam o build.
    O limite, dito pela própria doc

    Teste automatizado pega o óbvio; não substitui auditoria manual nem teste com usuário de tecnologia assistiva. A aba incomplete existe exatamente pra lembrar disso.

    Frase de entrevista: “Eu ponho o axe no nível do componente, em modo error, pra regressão de acessibilidade quebrar o build cedo — e trato o que sobra (ordem de foco, leitor de tela) como teste manual, sem chamar isso de conformidade.”

  • Figma Code Connect — React
    Como ligar o componente do Figma ao componente React, pra o Dev Mode mostrar o snippet real com as props mapeadas.
    Ler trechos · ~20 minLeia figma.connect(), a tabela de helpers de propriedade e “variant restrictions”. A configuração do CLI é consulta.
    developers.figma.com · oficial
    Resumo aqui na página

    Code Connect liga um componente do Figma ao seu componente React, pra o Dev Mode mostrar o snippet do seu código, com as props certas, em vez de CSS gerado. Funciona sozinho ou integrado a arquivos do Storybook. Detalhe que muda tudo: os arquivos não são executados — o CLI trata o exemplo como string.

    As duas formas de figma.connect()
    • figma.connect(Button, "https://figma.com/...") — liga um componente do seu código ao nó do Figma.
    • figma.connect("https://figma.com/...") — liga direto a um elemento HTML, sem importar componente.
    • O example devolve o JSX que aparece no Dev Mode, recebendo as props já mapeadas.
    Mapeamento de propriedades
    HelperMapeia
    figma.string('Label')propriedade de texto (rótulo, título)
    figma.boolean('Disabled')estado binário; normaliza Yes/No, True/False, On/Off
    figma.enum('Variant', {...})variante com várias opções → valor da prop (não normaliza sozinho)
    figma.instance('Icon')instância aninhada (ícone dentro do botão)
    figma.children('Layer')filhos, com curinga *
    figma.slot, figma.nestedProps, figma.textContent, figma.classNameslots compostos, props de instância aninhada, texto de camada, concatenação de classes
    Variant restrictions

    Quando um componente do Figma representa vários do código (um “Button” com Type = Primary/Secondary que no código são PrimaryButton e SecondaryButton), você cria uma ligação por variante: figma.connect(PrimaryButton, url, { variant: { Type: 'Primary' }, example: () => <PrimaryButton /> }). Aceita combinação de variantes.

    A consequência de “não é executado”
    • Condicional e construção dinâmica dentro do exemplo não funcionam como em React de verdade: escreva o exemplo como o desenvolvedor deveria escrever o uso.
    • O ganho é de contrato: o nome da prop no Figma e no código passam a ter um mapa explícito, e divergência vira algo que se vê.

    Frase de entrevista: “Handoff bom é quando o designer e eu falamos o mesmo nome de prop. Code Connect torna esse mapa explícito: o Dev Mode mostra o meu componente com a variante certa, não um CSS que ninguém vai usar.”

    Resumo em português do recorte indicado · original em developers.figma.com
  • Playwright — Visual comparisons
    toHaveScreenshot(): baseline no primeiro run, comparação nos seguintes, --update-snapshots e o aviso sobre SO/hardware.
    Ler inteiro · ~10 minPágina curta. O parágrafo sobre variação de renderização entre ambientes é o que mais cai em entrevista.
    playwright.dev · oficial
    Resumo aqui na página

    await expect(page).toHaveScreenshot() é regressão visual em uma linha: no primeiro run gera a imagem de referência, nos seguintes compara pixel a pixel. O problema não é escrever o teste — é manter a baseline confiável, porque a renderização muda de máquina pra máquina.

    Como a baseline nasce e se chama
    • Fica numa pasta com o nome do arquivo de teste (example.spec.ts-snapshots/) e deve ir pro controle de versão.
    • O nome leva o identificador de navegador e plataforma: example-test-1-chromium-darwin.png. Dá pra nomear: toHaveScreenshot('landing.png').
    • Mudou de propósito? npx playwright test --update-snapshots regrava as referências — e a revisão do PR passa a incluir as imagens.
    O aviso que separa suíte útil de suíte flaky

    A documentação é direta: a renderização do navegador varia com SO, versão, configurações, hardware, fonte de energia (bateria ou tomada), modo headless e outros fatores. Baseline gerada no seu Windows e comparada num runner Linux vai falhar em tudo. Regra: gere e compare no mesmo ambiente — na prática, o container do CI.

    Controlando o ruído
    OpçãoPra quê
    maxDiffPixels: 100tolera uma quantidade pequena de pixels diferentes (comparação via pixelmatch)
    stylePathaplica um CSS só no screenshot pra esconder o que muda sozinho (data, avatar, animação)
    toMatchSnapshot()o mesmo princípio pra texto ou binário: expect(await page.textContent('.hero__title')).toMatchSnapshot('hero.txt')
    Onde aplicar
    • Componente isolado (uma página de stories ou de referência, como o /admin/design do Gabarita) dá screenshot estável e barato.
    • Página inteira com dado real dá screenshot instável: esconda o dinâmico ou não faça.

    Frase de entrevista: “Regressão visual só vale se a baseline for determinística: mesmo container no CI, conteúdo dinâmico escondido, e tolerância pequena só pra ruído de antialiasing.”

Composição, documentação e responsivo em componente

Composição em vez de prop pra tudo

Um <Card title icon actions footer ...> ganha uma prop nova a cada pedido de design. A alternativa é expor partes que se encaixam: <Card><Card.Header/><Card.Body/></Card>, com o estado compartilhado por contexto (é como Tabs, Accordion e Select funcionam). Quem usa decide a ordem e o conteúdo; o componente continua dono do que não pode errar: ids, aria-*, gerenciamento de foco e teclado. O padrão asChild (o Slot do Radix) deixa trocar o elemento renderizado, um <a> no lugar de um <button>, sem perder o comportamento. Quando não usar: componente pequeno e fechado, onde as partes só adicionam cerimônia. Variantes visuais continuam em cva; composição resolve estrutura, variante resolve aparência.

Documentação que não desatualiza

O que documentar: quando usar e quando não usar, anatomia, variantes e estados, comportamento de teclado e ARIA, e exemplos que se copiam. Gerada do próprio código (as stories e os tipos das props) pra mudar junto com ele, e com as decisões que não aparecem no código escritas à parte, num registro curto de decisões.

Responsivo dentro do componente

  • Container queries (@container) fazem o componente se adaptar ao espaço onde está, e não à largura da janela. Num design system é o que importa: o mesmo card aparece numa coluna estreita e numa grade larga.
  • Unidades relativas e clamp() pra tipografia e espaçamento fluidos; rem respeita a fonte que a pessoa escolheu no navegador.
  • Alvo de toque de 44 × 44 px é a recomendação das plataformas e o critério AAA 2.5.5 da WCAG 2.1; o mínimo de AA (WCAG 2.2) é 24 px.
  • Reflow (1.4.10): sem rolagem horizontal a 320 px de largura, o equivalente a 400% de zoom numa tela de 1280 px. E nunca bloquear o zoom (user-scalable=no reprova).
  • Testar: o Playwright troca o viewport por teste, e a story de cada componente em larguras estreita e larga pega o que a leitura do código não pega.

Acabamento visual: movimento, foco e hover

A diferença entre um componente que “funciona” e um que parece pronto está nos detalhes de estado e de movimento, e é o que o título Design Engineer promete. Movimento não é enfeite: ele mostra causa e efeito, de onde algo veio e o que mudou.

Duração e easing

  • Feedback imediato (hover, pressionar): 100 a 150 ms. Entrada e saída de elementos (menu, toast, diálogo): 150 a 300 ms. Acima de 500 ms só em transição grande, e a saída é sempre mais rápida que a entrada.
  • Easing: ease-out pra entrada (começa rápido e assenta, parece responder ao usuário), ease-in pra saída, ease-in-out pra mover algo dentro da tela. linear parece mecânico, exceto em barra de progresso e rotação contínua.
  • Anime só transform e opacity: rodam no compositor, sem recalcular layout. Animar width, height, top ou left força layout a cada quadro. E evite transition: all, que anima o que você não pensou e custa caro.

Spring versus easing

O easing tem duração fixa e curva fixa. O spring é descrito por rigidez e amortecimento e preserva a velocidade quando é interrompido: se o usuário solta e pega de novo um elemento no meio do movimento, ele continua de onde está, sem pulo. Por isso o spring vale pra arrastar, gestos e qualquer coisa que se interrompe; o easing basta pra estado que vai de A a B e pronto. Em CSS puro, a função linear() aproxima um spring com várias paradas; spring de verdade vem de bibliotecas como a Motion.

prefers-reduced-motion

Não significa “sem animação”, significa sem movimento que enjoa: tire deslocamento, zoom, parallax e vídeo em loop, e mantenha a mudança de cor e de opacidade, que ainda comunica o estado. Há também a WCAG 2.2.2 (nível A): conteúdo que se move sozinho por mais de 5 s precisa de um jeito de pausar.

.btn {
  transition: background-color 150ms ease-out, transform 100ms ease-out;
}
/* hover só onde existe ponteiro de verdade: no toque ele "gruda" depois do toque */
@media (hover: hover) {
  .btn:hover { background-color: var(--btn-hover); }
}
.btn:active { transform: scale(0.98); }
/* outline, e não box-shadow: sobrevive ao modo de alto contraste (forced-colors) */
.btn:focus-visible { outline: 2px solid var(--focus); outline-offset: 2px; }
.btn[aria-disabled="true"] { opacity: .5; cursor: not-allowed; }

@media (prefers-reduced-motion: reduce) {
  .btn { transition: background-color 150ms ease-out; } /* mantém a cor, tira o movimento */
  .btn:active { transform: none; }
}

View Transitions

document.startViewTransition(callback) tira uma foto do estado atual, executa a atualização do DOM e anima da foto antiga pra nova com pseudo-elementos (::view-transition-old e ::view-transition-new). view-transition-name num elemento faz ele “viajar” entre os dois estados (a miniatura que vira a imagem grande). Duas regras: sempre tenha o fallback (nem todo navegador suporta) e respeite o reduce. No React, a atualização precisa estar concluída quando o callback devolve, por isso o flushSync.

import { flushSync } from 'react-dom';

function comTransicao(atualiza: () => void) {
  const semMovimento = matchMedia('(prefers-reduced-motion: reduce)').matches;
  if (!document.startViewTransition || semMovimento) return atualiza();
  document.startViewTransition(() => flushSync(atualiza));
}

comTransicao(() => setAberto(true));

Padrão, hover, :focus-visible, pressionado, desabilitado e carregando — e o anel de foco com contraste de pelo menos 3:1 contra o fundo ao lado (WCAG 1.4.11). Munição da sua entrevista · a GradeNumerada do Gabarita

O componente-assinatura do produto mostra o estado de cada questão de uma prova. A decisão de design foi que nenhum estado depende só de cor (WCAG 1.4.1): acerto é borda sólida, erro é borda pontilhada, em branco é tracejada, anulada é riscada — legível em escala de cinza e por quem tem daltonismo — e toda grade tem legenda textual. O mesmo componente roda em quatro escalas tipadas (trilha, mini, completa, mobile), e vira <button> com aria-label só quando é navegável. E a regra está travada por teste: “todo estado tem legenda textual, não só cor” é literalmente o nome de um caso em grade-numerada.test.tsx.

Por que isso importa: é a história completa de Design Engineering em um componente — decisão de design documentada (DESIGN.md), implementação com variantes tipadas, critério WCAG nomeado e um teste que impede regressão. Quando perguntarem “o que é um design system pra você?”, responda com ela.

Responda em voz alta · só depois abra o gabarito
  1. Qual a diferença entre um token primitivo e um token semântico, e por que o componente deveria usar só o segundo?
    ver resposta

    Primitivo nomeia o valor (orange-560); semântico nomeia a intenção (color-brand, color-ink-soft) e aponta pra um primitivo. Se o botão usa color-brand, trocar a marca ou ligar o dark mode é trocar o alias num lugar só — é exatamente o que o :root[data-theme="dark"] do Gabarita faz sem tocar em componente nenhum. Componente que usa o primitivo direto precisa ser editado em toda mudança de tema.

  2. O Gabarita tem .btn-primary e .btn-danger como classes em @layer components. O que você ganharia migrando pra um <Button> com cva? E o que perderia?
    ver resposta

    Ganha: variante tipada (o TypeScript reprova intent="danjer"), combinações explícitas por compoundVariants em vez de duas classes conflitando no mesmo elemento, defaults num lugar só, e um ponto único pra semântica (o <button type="button">, o foco, o estado disabled). Perde: uma dependência e uma camada de JS pra algo que hoje é CSS puro, e as classes deixam de servir em markup que não é React. A resposta sênior é dizer quando vale: a partir do momento em que há variantes combináveis ou mais de uma pessoa criando tela.

  3. Seu teste de regressão visual passa na sua máquina e falha no CI em todas as telas, com diferença de poucos pixels no texto. O que aconteceu e como resolver?
    ver resposta

    A baseline foi gerada num ambiente diferente do CI: a renderização de fonte e antialiasing muda com SO, versão do navegador, hardware e até modo headless (a própria doc do Playwright avisa). Por isso o nome do snapshot leva navegador e plataforma (-chromium-linux). Solução: gerar e atualizar a baseline no mesmo ambiente do CI (um container fixo), e usar tolerância (maxDiffPixels) só pra ruído, nunca pra esconder mudança real.

  4. O Ally AI audita acessibilidade dos sites dos clientes com axe-core. Como você explicaria a divisão de trabalho entre o axe-core e o LLM nesse motor?
    ver resposta

    O axe-core detecta: é um motor de regras determinístico (contraste calculado, ARIA inválido, nome acessível ausente) e roda no DOM real do Chromium depois que a SPA montou. Detecção precisa dar o mesmo resultado hoje e daqui a três meses, ou ninguém confia nela num CI. O LLM só escreve a correção de cada violação — o aria-label certo pra aquele botão é onde regra não chega e modelo chega. E o resultado preserva o critério WCAG, o seletor e os nós afetados, então a sugestão da IA sempre aponta pra um fato verificável.

  5. Se o axe-core não acusa nenhuma violação, o componente está conforme a WCAG 2.1 AA?
    ver resposta

    Não. Teste automatizado pega só uma parte dos critérios (a doc do Storybook fala em até ~57% dos problemas): contraste calculável, nome acessível ausente, ARIA inválido. Ordem de foco que faz sentido, texto alternativo que descreve o que importa, foco que não se perde num fluxo, leitor de tela anunciando a coisa certa — isso é teclado e NVDA/VoiceOver na mão. Por isso o Ally AI tem como regra “nunca afirmar conformidade”, e a aba incomplete do addon-a11y existe.

  6. Como o Storybook e o Figma se encaixam num fluxo de design system? O que cada um resolve?
    ver resposta

    O Figma é a fonte do design: componentes, variantes e variables (cores, espaçamentos). O Storybook é a fonte do componente de código: estados reais, documentação e testes (acessibilidade, interação, regressão visual). Cada um sozinho desatualiza o outro.

    A ligação é feita em três pontos: os tokens (as variables do Figma e as CSS variables dizem a mesma coisa, de preferência geradas de um tokens.json), o Code Connect (liga cada componente do Figma ao componente de código, e o modo Dev mostra o snippet real) e a convenção de nomes (a variante destructive do Figma é a mesma do cva). O risco é ter duas fontes de verdade que divergem; a regra é um dono por token, e a mudança passando por um lado só.
