E2

Live coding de front em React

~10h, um componente por sessão de 45 min · 8 clássicos de entrevista, com solução testada

Em uma frase: em vaga de front, o código ao vivo mais comum é construir um componente React pequeno, e o que se avalia é o estado bem pensado, os casos de erro e a acessibilidade, não a quantidade de recurso. Os oito exercícios abaixo são os temas que mais aparecem: lista com estado, dados de uma API, busca enquanto digita, formulário, abas, tabela, cronômetro e modal. Todas as soluções foram rodadas com testes (React 19 + Testing Library). Faça o E1 até o nível 2 antes de começar.

1. Como é a etapa

FormatoDe 45 a 60 minutos, num editor online (CodeSandbox, StackBlitz) ou no seu, com a tela compartilhada. Às vezes há uma API pronta; às vezes, um mock com dados.

O que pedem“Faça uma lista de tarefas com filtro”, “busque e mostre os usuários desta API”, “faça um campo de busca que não chame a API a cada tecla”.

O que avaliamSe você pergunta antes de supor, se o estado é o mínimo necessário, se trata carregando, erro e vazio, se o HTML é semântico, e se explica o que faz.

Na entrevista“Primeiro faço o caminho feliz funcionar; depois trato carregando, erro e lista vazia; no fim, teclado e leitor de tela.”

2. Como treinar

Projetonpm create vite@latest treino -- --template react-ts, e um arquivo por exercício. Ou abra um projeto React no StackBlitz.

Cronômetro45 minutos. Passou do tempo? Pare, leia a solução, feche e refaça do zero dois dias depois.

Em voz altaExplique cada decisão enquanto escreve. Grave um dos exercícios e assista: os silêncios longos são o que mais pesa contra.

Teste rápidoNo fim, use o componente só com o teclado (Tab, Enter, setas). É o teste de acessibilidade mais barato que existe.

3. O esqueleto de todo componente

Estado mínimoGuarde só o que não dá para calcular. A lista filtrada, o total e a página atual derivam do estado; não precisam de useState próprio.

Nunca mude o estadoCrie objetos e listas novos ([...list, item], map, filter). Mudar no lugar não avisa o React, e a tela não atualiza.

Efeito é para o mundo de forauseEffect sincroniza com algo externo (API, timer, evento). E todo efeito que começa algo devolve uma função que limpa.

Os quatro estadosCarregando, erro (com “tentar de novo”), vazio e pronto. O vazio é o mais esquecido.

Na entrevista“Isto não precisa ser estado, eu calculo a partir da lista.” Essa frase mostra mais maturidade em React do que qualquer hook avançado.

Checklist

LC 1

Lista de tarefas com filtro

30 min · useState, listas, formulário

Faça uma lista de tarefas: adicionar, marcar como feita, remover e filtrar entre todas, ativas e feitas. Mostre quantas faltam.

Requisitos

  • Enter no campo adiciona. Texto vazio ou só com espaços não entra.
  • Mostre “1 tarefa restante” ou “N tarefas restantes”, e “Nada por aqui.” quando o filtro não tiver itens.
  • Tudo funciona pelo teclado e tem nome para o leitor de tela.

Pode consultarReact: atualizando listas no estado · React: renderizando listas

dica

O estado é a lista de tarefas, o texto do campo e o filtro. A lista visível e o número de restantes não são estado: calcule-os a partir da lista. Use um <form> com onSubmit, que já dá o Enter de graça.

solução comentada
type Todo = { id: string; text: string; done: boolean };
type Filter = 'all' | 'active' | 'done';
const FILTER_LABELS: Record<Filter, string> = { all: 'todas', active: 'ativas', done: 'feitas' };

export function TodoList() {
  const [todos, setTodos] = useState<Todo[]>([]);
  const [text, setText] = useState('');
  const [filter, setFilter] = useState<Filter>('all');

  function add(e: FormEvent) {
    e.preventDefault(); // without this, the form reloads the page
    const trimmed = text.trim();
    if (!trimmed) return;
    setTodos((ts) => [...ts, { id: crypto.randomUUID(), text: trimmed, done: false }]);
    setText('');
  }
  function toggle(id: string) {
    setTodos((ts) => ts.map((t) => (t.id === id ? { ...t, done: !t.done } : t)));
  }
  function remove(id: string) {
    setTodos((ts) => ts.filter((t) => t.id !== id));
  }

  // derived from state: no useState needed
  const visible = todos.filter((t) => filter === 'all' || (filter === 'done' ? t.done : !t.done));
  const remaining = todos.filter((t) => !t.done).length;

  return (
    <div>
      <form onSubmit={add}>
        <label htmlFor="new-todo">Nova tarefa</label>
        <input id="new-todo" value={text} onChange={(e) => setText(e.target.value)} />
        <button type="submit">Adicionar</button>
      </form>
      <div role="group" aria-label="Filtro">
        {(['all', 'active', 'done'] as const).map((f) => (
          <button key={f} type="button" aria-pressed={filter === f} onClick={() => setFilter(f)}>
            {FILTER_LABELS[f]}
          </button>
        ))}
      </div>
      {visible.length === 0 ? (
        <p>Nada por aqui.</p>
      ) : (
        <ul>
          {visible.map((t) => (
            <li key={t.id}>
              <label>
                <input type="checkbox" checked={t.done} onChange={() => toggle(t.id)} />
                {t.text}
              </label>
              <button type="button" aria-label={`Remover ${t.text}`} onClick={() => remove(t.id)}>×</button>
            </li>
          ))}
        </ul>
      )}
      <p>{remaining === 1 ? '1 tarefa restante' : `${remaining} tarefas restantes`}</p>
    </div>
  );
}

O que mostrar ao entrevistador: a key é o id, não o índice; toda atualização cria uma lista nova; o filtro é derivado; o botão “×” tem aria-label, senão o leitor de tela diria só “vezes”; e o aria-pressed diz qual filtro está ligado.

Revisar

Caça ao bug

Um colega escreveu assim. A tela não atualiza ao marcar uma tarefa, e às vezes o item errado fica marcado depois de remover. Por quê?

function toggle(id: string) {
  const t = todos.find((t) => t.id === id)!;
  t.done = !t.done;
  setTodos(todos);
}
// ...
{visible.map((t, i) => <li key={i}>...</li>)}
os erros
  1. Muda o objeto no lugar e passa a mesma lista. O React compara a lista nova com a antiga pela referência. Como é o mesmo array, ele conclui que nada mudou e não redesenha.
  2. key pelo índice. Ao remover o item 0, o item que era 1 passa a ter a chave 0, e o React reaproveita o elemento do vizinho. Tudo o que vive no elemento (um input não controlado, o foco, uma animação) vai parar no item errado.
Mude um requisito

As tarefas precisam sobreviver ao recarregar a página. Onde você mexe?

o que muda

Leia o localStorage no valor inicial (useState(() => load()), a forma com função, que só roda uma vez) e grave num useEffect que depende de todos. Envolva a leitura em try/catch: o dado salvo pode estar corrompido ou o navegador pode bloquear o acesso. Num app com Next, a leitura precisa esperar o navegador, porque o servidor não tem localStorage.

LC 2

Dados de uma API, com todos os estados

30 min · useEffect, fetch, AbortController

Busque os usuários em https://jsonplaceholder.typicode.com/users e mostre nome e e-mail. Trate carregando, erro (com “Tentar de novo”) e lista vazia. Se o componente sair da tela antes da resposta, o pedido é cancelado.

Pode consultarReact: buscar dados com efeitos · MDN: AbortController

dica

Um estado com três formas (carregando, erro, pronto), como no reducer do R1. O efeito busca e devolve uma limpeza que aborta. Para “tentar de novo”, um contador nas dependências do efeito faz ele rodar outra vez.

solução comentada
type User = { id: number; name: string; email: string };
type State = { status: 'loading' } | { status: 'error' } | { status: 'ready'; users: User[] };

export function UserList() {
  const [state, setState] = useState<State>({ status: 'loading' });
  const [attempt, setAttempt] = useState(0); // changing the number re-runs the effect

  useEffect(() => {
    const controller = new AbortController();
    fetch('https://jsonplaceholder.typicode.com/users', { signal: controller.signal })
      .then((res) => {
        if (!res.ok) throw new Error(`HTTP ${res.status}`); // fetch does not reject on 404 or 500
        return res.json() as Promise<User[]>;
      })
      .then((users) => setState({ status: 'ready', users }))
      .catch(() => {
        if (!controller.signal.aborted) setState({ status: 'error' }); // cancelled is not an error
      });
    return () => controller.abort(); // left the screen, or fetching again: cancel this one
  }, [attempt]);

  function retry() {
    setState({ status: 'loading' });
    setAttempt((n) => n + 1);
  }

  if (state.status === 'loading') return <p role="status">Carregando usuários…</p>;
  if (state.status === 'error') {
    return (
      <div role="alert">
        <p>Não foi possível carregar os usuários.</p>
        <button type="button" onClick={retry}>Tentar de novo</button>
      </div>
    );
  }
  if (state.users.length === 0) return <p>Nenhum usuário encontrado.</p>;
  return (
    <ul>
      {state.users.map((u) => <li key={u.id}>{u.name} ({u.email})</li>)}
    </ul>
  );
}

O que mostrar ao entrevistador: o fetch só rejeita em falha de rede; 404 e 500 chegam como resposta normal, por isso o res.ok. Em desenvolvimento, o StrictMode do React monta o componente duas vezes de propósito: com o abort na limpeza, o primeiro pedido é cancelado e nada quebra.

Na vida real: num app grande, você usaria TanStack Query ou SWR, que já trazem cache, nova tentativa e cancelamento. Vale dizer isso, e mostrar que sabe o que eles fazem por baixo.

Revisar

Caça ao bug

Esta versão funciona quando tudo dá certo. Ache três problemas.

useEffect(() => {
  fetch(URL)
    .then((r) => r.json())
    .then((users) => setState({ status: 'ready', users }));
}, []);
os erros
  1. Sem catch. Se a rede cai, a tela fica em “Carregando” para sempre.
  2. Sem res.ok. Um 500 com página HTML faz o json() lançar erro, que também não é tratado.
  3. Sem limpeza. Saindo da tela antes da resposta, o pedido continua e ainda tenta mudar o estado de um componente que não existe mais. Em desenvolvimento, saem dois pedidos.
Mude um requisito

A lista ganha um seletor de página (?_page=2). O que muda no efeito?

o que muda

A página vira estado e entra nas dependências do efeito. Ao trocar de página, a limpeza aborta o pedido da página anterior, então uma resposta lenta da página 1 não sobrescreve a página 2. É o mesmo problema de corrida do LC 3, resolvido pelo mesmo abort.

LC 3

Busca enquanto digita

40 min · debounce, corrida entre pedidos

Um campo de busca de países chama GET /api/countries?q=term. Só busque 300 ms depois que a pessoa parar de digitar. Mostre “Buscando…”, os resultados, “Nenhum país com X” e o erro. Uma resposta atrasada de um termo antigo nunca pode aparecer na tela.

Pode consultarReact: você talvez não precise de um efeito · o exercício 13 do E1

dica

Separe em duas partes: um hook useDebounce(value, ms) que devolve o valor atrasado, e um efeito que busca quando o termo atrasado muda. Para a corrida, aborte o pedido anterior na limpeza e guarde junto da resposta o termo a que ela pertence.

solução comentada
export function useDebounce<T>(value: T, ms: number): T {
  const [delayed, setDelayed] = useState(value);
  useEffect(() => {
    const t = setTimeout(() => setDelayed(value), ms);
    return () => clearTimeout(t); // typed again before the delay: cancel
  }, [value, ms]);
  return delayed;
}

async function fetchCountries(query: string, signal: AbortSignal): Promise<string[]> {
  const res = await fetch(`/api/countries?q=${encodeURIComponent(query)}`, { signal });
  if (!res.ok) throw new Error(`HTTP ${res.status}`);
  return res.json();
}

type SearchResult = { query: string; items: string[] } | { query: string; error: true };

export function CountrySearch() {
  const [text, setText] = useState('');
  const query = useDebounce(text.trim(), 300);
  const [result, setResult] = useState<SearchResult | null>(null);

  useEffect(() => {
    if (!query) return;
    const controller = new AbortController();
    fetchCountries(query, controller.signal)
      .then((items) => setResult({ query, items }))
      .catch(() => {
        if (!controller.signal.aborted) setResult({ query, error: true });
      });
    return () => controller.abort(); // query changed: the old response no longer matters
  }, [query]);

  // only the result for the current query counts
  const current = result && result.query === query ? result : null;
  const loading = query !== '' && current === null;

  return (
    <div>
      <label htmlFor="search">Buscar país</label>
      <input id="search" type="search" value={text} onChange={(e) => setText(e.target.value)} />
      <div role="status">
        {loading && 'Buscando…'}
        {current && 'error' in current && 'Não foi possível buscar agora.'}
        {current && 'items' in current && current.items.length === 0 && `Nenhum país com “${query}”.`}
      </div>
      {current && 'items' in current && current.items.length > 0 && (
        <ul>
          {current.items.map((c) => <li key={c}>{c}</li>)}
        </ul>
      )}
    </div>
  );
}

O que mostrar ao entrevistador: são duas proteções contra a corrida. O abort cancela o pedido velho, e a comparação result.query === query garante que, mesmo se ele chegar, não aparece. O “carregando” não é estado: é “tenho termo e ainda não tenho a resposta dele”. O role="status" faz o leitor de tela anunciar o resultado.

O teste que pegaria o bug: o termo “br” responde em 500 ms e “bra” em 10 ms. Sem as proteções, “br” chega por último e substitui o resultado certo.

Revisar

Explique em voz alta

Por que encodeURIComponent? E por que o debounce fica num hook separado?

respostas

Sem ele, um termo como “a&b” quebraria a URL (o & começaria outro parâmetro). O hook separado pode ser reaproveitado e testado sozinho, e deixa o componente lendo como uma frase: “o termo é o texto atrasado em 300 ms”.

Mude um requisito

Buscar com 1 letra traz resultado demais. Só busque a partir de 2 letras, e mostre “Digite pelo menos 2 letras”.

o que muda

No efeito, troque if (!query) por if (query.length < 2). O “carregando” também usa essa regra, e a mensagem nova é mais uma linha derivada: query.length === 1. Repare que nenhum estado novo foi preciso.

LC 4

Formulário de cadastro

40 min · validação, acessibilidade, envio

Faça um cadastro com e-mail, senha e confirmação. Ao enviar, valide; se houver erro, mostre a mensagem junto do campo e leve o foco ao primeiro campo com erro. Durante o envio, o botão fica desabilitado. Se o envio falhar, avise e deixe tentar de novo.

Regras

  • E-mail com formato válido. Senha com pelo menos 8 caracteres e um número. Confirmação igual à senha.
  • O leitor de tela precisa ouvir o erro ao chegar no campo.

Pode consultarMDN: aria-invalid · MDN: aria-describedby · React: input

dica

Uma função pura validate(fields) que devolve um objeto de erros é fácil de testar e de explicar. No campo, aria-invalid marca o erro e aria-describedby aponta para o id da mensagem. Um componente Field evita repetir isso três vezes.

solução comentada
type Fields = { email: string; password: string; confirm: string };
type Errors = Partial<Record<keyof Fields, string>>;

export function validate(f: Fields): Errors {
  const errors: Errors = {};
  if (!/^[^\s@]+@[^\s@]+\.[^\s@]+$/.test(f.email)) errors.email = 'Digite um e-mail válido.';
  if (f.password.length < 8) errors.password = 'A senha precisa de pelo menos 8 caracteres.';
  else if (!/\d/.test(f.password)) errors.password = 'A senha precisa de pelo menos um número.';
  if (f.confirm !== f.password) errors.confirm = 'As senhas não são iguais.';
  return errors;
}

function Field(props: {
  name: keyof Fields; label: string; type: string; value: string; error?: string;
  onChange: (e: ChangeEvent<HTMLInputElement>) => void;
}) {
  const errorId = `${props.name}-error`;
  return (
    <div>
      <label htmlFor={props.name}>{props.label}</label>
      <input
        id={props.name} name={props.name} type={props.type} value={props.value} onChange={props.onChange}
        aria-invalid={props.error ? true : undefined}
        aria-describedby={props.error ? errorId : undefined} // the screen reader reads the message with the field
      />
      {props.error && <p id={errorId}>{props.error}</p>}
    </div>
  );
}

export function SignUpForm({ submit }: { submit: (f: Fields) => Promise<void> }) {
  const [fields, setFields] = useState<Fields>({ email: '', password: '', confirm: '' });
  const [errors, setErrors] = useState<Errors>({});
  const [status, setStatus] = useState<'editing' | 'submitting' | 'done' | 'failed'>('editing');

  function handleChange(e: ChangeEvent<HTMLInputElement>) {
    const { name, value } = e.target;
    setFields((f) => ({ ...f, [name]: value }));
  }

  async function handleSubmit(e: FormEvent) {
    e.preventDefault();
    const found = validate(fields);
    setErrors(found);
    const first = Object.keys(found)[0];
    if (first) {
      document.getElementById(first)?.focus(); // take the user to the first error
      return;
    }
    setStatus('submitting');
    try {
      await submit(fields);
      setStatus('done');
    } catch {
      setStatus('failed');
    }
  }

  if (status === 'done') return <p role="status">Conta criada. Confira o seu e-mail.</p>;
  return (
    <form onSubmit={handleSubmit} noValidate>
      <Field name="email" label="E-mail" type="email" value={fields.email} error={errors.email} onChange={handleChange} />
      <Field name="password" label="Senha" type="password" value={fields.password} error={errors.password} onChange={handleChange} />
      <Field name="confirm" label="Confirmar senha" type="password" value={fields.confirm} error={errors.confirm} onChange={handleChange} />
      {status === 'failed' && <p role="alert">Não foi possível criar a conta. Tente de novo.</p>}
      <button type="submit" disabled={status === 'submitting'}>
        {status === 'submitting' ? 'Criando…' : 'Criar conta'}
      </button>
    </form>
  );
}

O que mostrar ao entrevistador: a validação é uma função pura, testável sem tela; o noValidate desliga os balões do navegador para as mensagens serem as suas; o botão desabilitado evita envio duplo; e a validação do front é conforto, a de verdade fica no servidor.

Revisar

Explique em voz alta

Por que validar ao enviar, e não a cada tecla? Quando faria sentido validar ao sair do campo?

respostas

Validar a cada tecla grita “e-mail inválido” enquanto a pessoa ainda está digitando o e-mail. Ao sair do campo (onBlur) é um meio-termo bom para formulários longos: o aviso chega cedo, mas só depois de a pessoa terminar aquele campo. Depois que o erro apareceu, revalidar a cada tecla é bom, porque o aviso some assim que o campo fica certo.

Mude um requisito

O servidor responde que o e-mail já está em uso. Onde essa mensagem aparece?

o que muda

No próprio campo de e-mail, como os outros erros. O submit passa a devolver os erros do servidor (ou a lançar um erro com eles), e o catch faz setErrors({ email: 'Este e-mail já tem conta.' }) e foca o campo. Um aviso genérico no topo obrigaria a pessoa a adivinhar qual campo corrigir.

LC 5

Abas acessíveis

30 min · ARIA, teclado, refs

Faça um componente Tabs que recebe uma lista { id, title, content }. Clicar troca a aba. No teclado: Tab entra na aba ativa, setas trocam de aba, Home e End vão para a primeira e a última, e o próximo Tab vai para o conteúdo.

Pode consultarW3C: padrão de abas · React: refs e o DOM

dica

Papéis: tablist no grupo, tab em cada botão, tabpanel no conteúdo. Só a aba ativa tem tabIndex={0}; as outras, -1. Assim o Tab entra numa aba só, e as setas fazem o resto. Para mover o foco, guarde os botões num useRef.

solução comentada
type Tab = { id: string; title: string; content: ReactNode };

export function Tabs({ tabs }: { tabs: Tab[] }) {
  const [active, setActive] = useState(0);
  const buttons = useRef<(HTMLButtonElement | null)[]>([]);

  function handleKeyDown(e: KeyboardEvent<HTMLDivElement>) {
    let next: number;
    if (e.key === 'ArrowRight') next = (active + 1) % tabs.length;               // after the last, wrap to the first
    else if (e.key === 'ArrowLeft') next = (active - 1 + tabs.length) % tabs.length;
    else if (e.key === 'Home') next = 0;
    else if (e.key === 'End') next = tabs.length - 1;
    else return; // other keys behave as usual
    e.preventDefault();
    setActive(next);
    buttons.current[next]?.focus();
  }

  return (
    <div>
      <div role="tablist" aria-label="Seções" onKeyDown={handleKeyDown}>
        {tabs.map((tab, i) => (
          <button
            key={tab.id}
            ref={(el) => { buttons.current[i] = el; }}
            type="button"
            role="tab"
            id={`tab-${tab.id}`}
            aria-selected={i === active}
            aria-controls={`panel-${tab.id}`}
            tabIndex={i === active ? 0 : -1} // only the active tab is in the Tab order
            onClick={() => setActive(i)}
          >
            {tab.title}
          </button>
        ))}
      </div>
      {tabs.map((tab, i) => (
        <div key={tab.id} role="tabpanel" id={`panel-${tab.id}`} aria-labelledby={`tab-${tab.id}`} hidden={i !== active} tabIndex={0}>
          {tab.content}
        </div>
      ))}
    </div>
  );
}

O que mostrar ao entrevistador: o % faz a seta “dar a volta”; o + tabs.length evita índice negativo; e os painéis escondidos continuam no DOM com hidden, então trocar de aba não perde o que foi digitado dentro deles.

Revisar

Explique em voz alta

Por que não deixar todas as abas com tabIndex={0}?

resposta

Com dez abas, a pessoa no teclado precisaria de dez Tabs para chegar ao conteúdo. O padrão do W3C trata o grupo de abas como um controle só: um Tab para entrar, setas para escolher, um Tab para sair. É o mesmo comportamento de um grupo de rádio.

Mude um requisito

Cada aba agora carrega dados de uma API, e só deve buscar quando for aberta pela primeira vez.

o que muda

Guarde um Set com as abas já abertas e renderize o conteúdo só delas (as nunca abertas ficam vazias). Cada conteúdo é um componente com o seu próprio efeito de busca, como o LC 2. Como os painéis já abertos continuam montados (com hidden), voltar a uma aba não busca de novo.

LC 6

Tabela com ordenação e paginação

40 min · estado derivado, useMemo

Mostre uma lista de pessoas ({ id, name, age, city }) numa tabela de 5 linhas por página. Clicar no cabeçalho ordena pela coluna; clicar de novo inverte. Ao mudar a ordem, volte para a página 1. Os botões Anterior e Próxima ficam desabilitados nas pontas.

Pode consultarReact: useMemo · MDN: aria-sort · o exercício 8 do E1

dica

O estado é só a ordem (coluna e direção) e o número da página. A lista ordenada, a fatia da página e o total de páginas são calculados. Ordene uma cópia, e use localeCompare para texto com acento.

solução comentada
type Person = { id: number; name: string; age: number; city: string };
type Column = 'name' | 'age' | 'city';
const PAGE_SIZE = 5;
const LABELS: Record<Column, string> = { name: 'Nome', age: 'Idade', city: 'Cidade' };

export function PeopleTable({ people }: { people: Person[] }) {
  const [sort, setSort] = useState<{ column: Column; direction: 'asc' | 'desc' }>({ column: 'name', direction: 'asc' });
  const [page, setPage] = useState(1);

  const sorted = useMemo(() => {
    const sign = sort.direction === 'asc' ? 1 : -1;
    return [...people].sort((a, b) => {
      const x = a[sort.column];
      const y = b[sort.column];
      const cmp = typeof x === 'number' && typeof y === 'number' ? x - y : String(x).localeCompare(String(y), 'pt-BR');
      return cmp * sign;
    });
  }, [people, sort]);

  const totalPages = Math.max(1, Math.ceil(sorted.length / PAGE_SIZE));
  const currentPage = Math.min(page, totalPages); // the list may have shrunk
  const visible = sorted.slice((currentPage - 1) * PAGE_SIZE, currentPage * PAGE_SIZE);

  function sortByColumn(column: Column) {
    setSort((s) => ({ column, direction: s.column === column && s.direction === 'asc' ? 'desc' : 'asc' }));
    setPage(1); // new order: back to the start
  }

  return (
    <div>
      <table>
        <thead>
          <tr>
            {(Object.keys(LABELS) as Column[]).map((c) => (
              <th key={c} aria-sort={sort.column === c ? (sort.direction === 'asc' ? 'ascending' : 'descending') : 'none'}>
                <button type="button" onClick={() => sortByColumn(c)}>{LABELS[c]}</button>
              </th>
            ))}
          </tr>
        </thead>
        <tbody>
          {visible.map((p) => (
            <tr key={p.id}><td>{p.name}</td><td>{p.age}</td><td>{p.city}</td></tr>
          ))}
        </tbody>
      </table>
      <nav aria-label="Paginação">
        <button type="button" onClick={() => setPage(currentPage - 1)} disabled={currentPage === 1}>Anterior</button>
        <span>Página {currentPage} de {totalPages}</span>
        <button type="button" onClick={() => setPage(currentPage + 1)} disabled={currentPage === totalPages}>Próxima</button>
      </nav>
    </div>
  );
}

O que mostrar ao entrevistador: o cabeçalho é um <button> dentro do <th> (clicável pelo teclado), e o aria-sort diz ao leitor de tela qual coluna está ordenada. O Math.min da página atual cobre a lista que encolheu: sem ele, a tela mostraria “Página 3 de 2”.

Sobre o useMemo: ordenar 50 itens é rápido, e o useMemo poderia sair. Ele passa a valer com milhares de linhas. Dizer isso mostra que você sabe quando a otimização se paga.

Revisar

Caça ao bug

Um colega guardou a lista ordenada no estado, assim. O que dá errado quando a prop people muda?

const [sorted, setSorted] = useState(people);
function sortByColumn(column: Column) {
  setSorted([...sorted].sort(/* ... */));
}
o erro

O useState(people) só usa o valor na primeira renderização. Se o pai mandar uma lista nova (uma pessoa cadastrada), a tabela continua mostrando a antiga. É o erro de estado duplicado: a mesma informação em dois lugares, que deixam de concordar. A solução é derivar a lista ordenada da prop, como na solução.

Mude um requisito

Os dados passam a vir paginados do servidor (?page=2&sort=age), porque são 100 mil pessoas.

o que muda

Ordenar e fatiar saem do componente e vão para o servidor (o banco faz ORDER BY e LIMIT/OFFSET). A ordem e a página continuam sendo estado, mas agora entram nas dependências de um efeito de busca, como no LC 2. Pôr os dois na URL (?page=2) permite compartilhar o link e usar o botão voltar.

LC 7

Cronômetro

30 min · setInterval, cleanup, useRef

Faça um cronômetro mm:ss.d com Iniciar/Continuar, Pausar e Zerar. O tempo mostrado não pode atrasar, mesmo depois de vários minutos ou com a aba em segundo plano. Ao sair da tela, nenhum timer fica rodando.

Pode consultarReact: useRef · MDN: setInterval

dica

Não some 100 a cada tick: o navegador não garante o intervalo exato. Guarde o horário em que a contagem começou e calcule Date.now() - startedAt a cada tick. Valores que não aparecem na tela (o início, o acumulado) ficam num useRef.

solução comentada
function format(ms: number) {
  const totalSec = Math.floor(ms / 1000);
  const min = String(Math.floor(totalSec / 60)).padStart(2, '0');
  const sec = String(totalSec % 60).padStart(2, '0');
  const tenth = Math.floor((ms % 1000) / 100);
  return `${min}:${sec}.${tenth}`;
}

export function Stopwatch() {
  const [elapsed, setElapsed] = useState(0); // what the screen shows
  const [running, setRunning] = useState(false);
  const accumulated = useRef(0); // time added up until the last pause
  const startedAt = useRef(0);   // when the current run started

  useEffect(() => {
    if (!running) return;
    const id = setInterval(() => setElapsed(accumulated.current + Date.now() - startedAt.current), 100);
    return () => clearInterval(id); // paused or left the screen: stop the interval
  }, [running]);

  function start() {
    startedAt.current = Date.now();
    setRunning(true);
  }
  function pause() {
    accumulated.current += Date.now() - startedAt.current;
    setElapsed(accumulated.current);
    setRunning(false);
  }
  function reset() {
    accumulated.current = 0;
    setElapsed(0);
    setRunning(false);
  }

  return (
    <div>
      <p>{format(elapsed)}</p>
      {running
        ? <button type="button" onClick={pause}>Pausar</button>
        : <button type="button" onClick={start}>{elapsed === 0 ? 'Iniciar' : 'Continuar'}</button>}
      <button type="button" onClick={reset} disabled={elapsed === 0 && !running}>Zerar</button>
    </div>
  );
}

O que mostrar ao entrevistador: useState é para o que aparece na tela; useRef é para o que só o código precisa lembrar (mudar uma ref não redesenha). E o tempo vem do relógio, não da contagem de ticks.

Revisar

Caça ao bug

Esta é a versão que quase todo mundo escreve primeiro. Ache os três problemas.

useEffect(() => {
  if (!running) return;
  setInterval(() => setElapsed(elapsed + 100), 100);
}, [running]);
os erros
  1. Closure velha (stale closure). A função do intervalo lembra o elapsed do momento em que foi criada (0). Ela calcula 0 + 100 para sempre, e a tela trava em 00:00.1. Com setElapsed((e) => e + 100), esse problema some.
  2. Sem limpeza. Pausar não para o intervalo, e cada Iniciar cria mais um. Depois de três pausas, são três intervalos rodando juntos.
  3. Somar 100 a cada tick atrasa. O intervalo não é exato, e navegadores como o Chrome reduzem os timers de abas em segundo plano para no máximo um por segundo. Contando ticks, o cronômetro mostra menos tempo do que passou.
Mude um requisito

O cronômetro ganha um botão “Volta”, que registra o tempo atual numa lista, como no app de relógio do celular.

o que muda

Um estado novo, laps: number[]. O botão calcula o tempo atual do mesmo jeito que o intervalo (accumulated.current + Date.now() - startedAt.current) e acrescenta à lista. O tempo de cada volta (a diferença para a anterior) é derivado na hora de mostrar, e o Zerar também limpa as voltas.

LC 8

Modal de confirmação

25 min · <dialog>, foco, teclado

Um botão “Excluir item” abre um modal de confirmação. Enquanto ele está aberto, o resto da página não recebe clique nem foco. Esc e Cancelar fecham sem excluir. Ao fechar, o foco volta para o botão que abriu.

Pode consultarMDN: <dialog> · W3C: padrão de diálogo modal

dica

Antes de montar tudo à mão, lembre que o HTML já tem um elemento para isto. O <dialog> aberto com showModal() já bloqueia o fundo, fecha com Esc e devolve o foco. Um <form method="dialog"> dentro dele fecha o modal ao enviar.

solução comentada
export function ConfirmDelete({ name, onConfirm }: { name: string; onConfirm: () => void }) {
  const dialogRef = useRef<HTMLDialogElement>(null);
  return (
    <>
      <button type="button" onClick={() => dialogRef.current?.showModal()}>
        Excluir {name}
      </button>
      <dialog ref={dialogRef} aria-labelledby="delete-title">
        <h2 id="delete-title">Excluir “{name}”?</h2>
        <p>Essa ação não pode ser desfeita.</p>
        {/* method="dialog": submitting this form closes the dialog, no reload */}
        <form method="dialog">
          <button value="cancel">Cancelar</button>
          <button value="delete" onClick={onConfirm}>Excluir</button>
        </form>
      </dialog>
    </>
  );
}

O que mostrar ao entrevistador: o showModal() entrega de graça o que levaria uma tarde para fazer à mão: o resto da página fica inerte, o Esc fecha e o foco volta para quem abriu. O foco começa no primeiro botão, o Cancelar, que é o mais seguro numa ação destrutiva. Saber que o HTML já resolve, em vez de escrever 80 linhas de JavaScript, é um sinal forte de senioridade.

Revisar

Explique em voz alta

Se você fizesse o modal com uma <div> e CSS, o que precisaria implementar à mão?

resposta

Prender o foco dentro do modal (o Tab não pode sair para a página atrás), fechar com Esc, devolver o foco ao botão que abriu, impedir clique e rolagem no fundo, e os atributos role="dialog" e aria-modal="true". Bibliotecas como Radix e Headless UI existem justamente para isso; o <dialog> nativo cobre a maior parte.

Mude um requisito

A exclusão agora chama a API e pode falhar. O modal só fecha se der certo.

o que muda

O botão Excluir sai do form method="dialog" (que fecha na hora) e vira um botão comum que chama a API. Enquanto espera, ele fica desabilitado com “Excluindo…”; se der certo, dialogRef.current?.close(); se falhar, uma mensagem com role="alert" aparece dentro do modal, que continua aberto.
