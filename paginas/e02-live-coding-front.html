E2

Live coding de front em React

~10h, um componente por sessão de 45 min · 8 clássicos de entrevista, com solução testada

Em uma frase: em vaga de front, o código ao vivo mais comum é construir um componente React pequeno, e o que se avalia é o estado bem pensado, os casos de erro e a acessibilidade, não a quantidade de recurso. Os oito exercícios abaixo são os temas que mais aparecem: lista com estado, dados de uma API, busca enquanto digita, formulário, abas, tabela, cronômetro e modal. Todas as soluções foram rodadas com testes (React 19 + Testing Library). Faça o E1 até o nível 2 antes de começar.

1. Como é a etapa

FormatoDe 45 a 60 minutos, num editor online (CodeSandbox, StackBlitz) ou no seu, com a tela compartilhada. Às vezes há uma API pronta; às vezes, um mock com dados.

O que pedem“Faça uma lista de tarefas com filtro”, “busque e mostre os usuários desta API”, “faça um campo de busca que não chame a API a cada tecla”.

O que avaliamSe você pergunta antes de supor, se o estado é o mínimo necessário, se trata carregando, erro e vazio, se o HTML é semântico, e se explica o que faz.

Na entrevista“Primeiro faço o caminho feliz funcionar; depois trato carregando, erro e lista vazia; no fim, teclado e leitor de tela.”

2. Como treinar

Projetonpm create vite@latest treino -- --template react-ts, e um arquivo por exercício. Ou abra um projeto React no StackBlitz.

Cronômetro45 minutos. Passou do tempo? Pare, leia a solução, feche e refaça do zero dois dias depois.

Em voz altaExplique cada decisão enquanto escreve. Grave um dos exercícios e assista: os silêncios longos são o que mais pesa contra.

Teste rápidoNo fim, use o componente só com o teclado (Tab, Enter, setas). É o teste de acessibilidade mais barato que existe.

3. O esqueleto de todo componente

Estado mínimoGuarde só o que não dá para calcular. A lista filtrada, o total e a página atual derivam do estado; não precisam de useState próprio.

Nunca mude o estadoCrie objetos e listas novos ([...lista, item], map, filter). Mudar no lugar não avisa o React, e a tela não atualiza.

Efeito é para o mundo de forauseEffect sincroniza com algo externo (API, timer, evento). E todo efeito que começa algo devolve uma função que limpa.

Os quatro estadosCarregando, erro (com “tentar de novo”), vazio e pronto. O vazio é o mais esquecido.

Na entrevista“Isto não precisa ser estado, eu calculo a partir da lista.” Essa frase mostra mais maturidade em React do que qualquer hook avançado.

Checklist

LC 1

Lista de tarefas com filtro

30 min · useState, listas, formulário

Faça uma lista de tarefas: adicionar, marcar como feita, remover e filtrar entre todas, ativas e feitas. Mostre quantas faltam.

Requisitos

  • Enter no campo adiciona. Texto vazio ou só com espaços não entra.
  • Mostre “1 tarefa restante” ou “N tarefas restantes”, e “Nada por aqui.” quando o filtro não tiver itens.
  • Tudo funciona pelo teclado e tem nome para o leitor de tela.

Pode consultarReact: atualizando listas no estado · React: renderizando listas

dica

O estado é a lista de tarefas, o texto do campo e o filtro. A lista visível e o número de restantes não são estado: calcule-os a partir da lista. Use um <form> com onSubmit, que já dá o Enter de graça.

solução comentada
type Tarefa = { id: string; texto: string; feita: boolean };
type Filtro = 'todas' | 'ativas' | 'feitas';

export function ListaDeTarefas() {
  const [tarefas, setTarefas] = useState<Tarefa[]>([]);
  const [texto, setTexto] = useState('');
  const [filtro, setFiltro] = useState<Filtro>('todas');

  function adicionar(e: FormEvent) {
    e.preventDefault(); // sem isto, o form recarrega a página
    const limpo = texto.trim();
    if (!limpo) return;
    setTarefas((ts) => [...ts, { id: crypto.randomUUID(), texto: limpo, feita: false }]);
    setTexto('');
  }
  function alternar(id: string) {
    setTarefas((ts) => ts.map((t) => (t.id === id ? { ...t, feita: !t.feita } : t)));
  }
  function remover(id: string) {
    setTarefas((ts) => ts.filter((t) => t.id !== id));
  }

  // derivados do estado: não precisam de useState
  const visiveis = tarefas.filter((t) => filtro === 'todas' || (filtro === 'feitas' ? t.feita : !t.feita));
  const restantes = tarefas.filter((t) => !t.feita).length;

  return (
    <div>
      <form onSubmit={adicionar}>
        <label htmlFor="nova-tarefa">Nova tarefa</label>
        <input id="nova-tarefa" value={texto} onChange={(e) => setTexto(e.target.value)} />
        <button type="submit">Adicionar</button>
      </form>
      <div role="group" aria-label="Filtro">
        {(['todas', 'ativas', 'feitas'] as const).map((f) => (
          <button key={f} type="button" aria-pressed={filtro === f} onClick={() => setFiltro(f)}>
            {f}
          </button>
        ))}
      </div>
      {visiveis.length === 0 ? (
        <p>Nada por aqui.</p>
      ) : (
        <ul>
          {visiveis.map((t) => (
            <li key={t.id}>
              <label>
                <input type="checkbox" checked={t.feita} onChange={() => alternar(t.id)} />
                {t.texto}
              </label>
              <button type="button" aria-label={`Remover ${t.texto}`} onClick={() => remover(t.id)}>×</button>
            </li>
          ))}
        </ul>
      )}
      <p>{restantes === 1 ? '1 tarefa restante' : `${restantes} tarefas restantes`}</p>
    </div>
  );
}

O que mostrar ao entrevistador: a key é o id, não o índice; toda atualização cria uma lista nova; o filtro é derivado; o botão “×” tem aria-label, senão o leitor de tela diria só “vezes”; e o aria-pressed diz qual filtro está ligado.

Revisar

Caça ao bug

Um colega escreveu assim. A tela não atualiza ao marcar uma tarefa, e às vezes o item errado fica marcado depois de remover. Por quê?

function alternar(id: string) {
  const t = tarefas.find((t) => t.id === id)!;
  t.feita = !t.feita;
  setTarefas(tarefas);
}
// ...
{visiveis.map((t, i) => <li key={i}>...</li>)}
os erros
  1. Muda o objeto no lugar e passa a mesma lista. O React compara a lista nova com a antiga pela referência. Como é o mesmo array, ele conclui que nada mudou e não redesenha.
  2. key pelo índice. Ao remover o item 0, o item que era 1 passa a ter a chave 0, e o React reaproveita o elemento do vizinho. Tudo o que vive no elemento (um input não controlado, o foco, uma animação) vai parar no item errado.
Mude um requisito

As tarefas precisam sobreviver ao recarregar a página. Onde você mexe?

o que muda

Leia o localStorage no valor inicial (useState(() => carregar()), a forma com função, que só roda uma vez) e grave num useEffect que depende de tarefas. Envolva a leitura em try/catch: o dado salvo pode estar corrompido ou o navegador pode bloquear o acesso. Num app com Next, a leitura precisa esperar o navegador, porque o servidor não tem localStorage.

LC 2

Dados de uma API, com todos os estados

30 min · useEffect, fetch, AbortController

Busque os usuários em https://jsonplaceholder.typicode.com/users e mostre nome e e-mail. Trate carregando, erro (com “Tentar de novo”) e lista vazia. Se o componente sair da tela antes da resposta, o pedido é cancelado.

Pode consultarReact: buscar dados com efeitos · MDN: AbortController

dica

Um estado com três formas (carregando, erro, pronto), como no reducer do R1. O efeito busca e devolve uma limpeza que aborta. Para “tentar de novo”, um contador nas dependências do efeito faz ele rodar outra vez.

solução comentada
type Usuario = { id: number; name: string; email: string };
type Estado = { tipo: 'carregando' } | { tipo: 'erro' } | { tipo: 'pronto'; usuarios: Usuario[] };

export function ListaDeUsuarios() {
  const [estado, setEstado] = useState<Estado>({ tipo: 'carregando' });
  const [tentativa, setTentativa] = useState(0); // mudar o número refaz o efeito

  useEffect(() => {
    const controle = new AbortController();
    fetch('https://jsonplaceholder.typicode.com/users', { signal: controle.signal })
      .then((res) => {
        if (!res.ok) throw new Error(`HTTP ${res.status}`); // fetch não falha sozinho em 404 ou 500
        return res.json() as Promise<Usuario[]>;
      })
      .then((usuarios) => setEstado({ tipo: 'pronto', usuarios }))
      .catch(() => {
        if (!controle.signal.aborted) setEstado({ tipo: 'erro' }); // cancelado não é erro
      });
    return () => controle.abort(); // saiu da tela, ou vai buscar de novo: cancela este
  }, [tentativa]);

  function tentarDeNovo() {
    setEstado({ tipo: 'carregando' });
    setTentativa((n) => n + 1);
  }

  if (estado.tipo === 'carregando') return <p role="status">Carregando usuários…</p>;
  if (estado.tipo === 'erro') {
    return (
      <div role="alert">
        <p>Não foi possível carregar os usuários.</p>
        <button type="button" onClick={tentarDeNovo}>Tentar de novo</button>
      </div>
    );
  }
  if (estado.usuarios.length === 0) return <p>Nenhum usuário encontrado.</p>;
  return (
    <ul>
      {estado.usuarios.map((u) => <li key={u.id}>{u.name} ({u.email})</li>)}
    </ul>
  );
}

O que mostrar ao entrevistador: o fetch só rejeita em falha de rede; 404 e 500 chegam como resposta normal, por isso o res.ok. Em desenvolvimento, o StrictMode do React monta o componente duas vezes de propósito: com o abort na limpeza, o primeiro pedido é cancelado e nada quebra.

Na vida real: num app grande, você usaria TanStack Query ou SWR, que já trazem cache, nova tentativa e cancelamento. Vale dizer isso, e mostrar que sabe o que eles fazem por baixo.

Revisar

Caça ao bug

Esta versão funciona quando tudo dá certo. Ache três problemas.

useEffect(() => {
  fetch(URL)
    .then((r) => r.json())
    .then((usuarios) => setEstado({ tipo: 'pronto', usuarios }));
}, []);
os erros
  1. Sem catch. Se a rede cai, a tela fica em “Carregando” para sempre.
  2. Sem res.ok. Um 500 com página HTML faz o json() lançar erro, que também não é tratado.
  3. Sem limpeza. Saindo da tela antes da resposta, o pedido continua e ainda tenta mudar o estado de um componente que não existe mais. Em desenvolvimento, saem dois pedidos.
Mude um requisito

A lista ganha um seletor de página (?_page=2). O que muda no efeito?

o que muda

A página vira estado e entra nas dependências do efeito. Ao trocar de página, a limpeza aborta o pedido da página anterior, então uma resposta lenta da página 1 não sobrescreve a página 2. É o mesmo problema de corrida do LC 3, resolvido pelo mesmo abort.

LC 3

Busca enquanto digita

40 min · debounce, corrida entre pedidos

Um campo de busca de países chama GET /api/paises?q=termo. Só busque 300 ms depois que a pessoa parar de digitar. Mostre “Buscando…”, os resultados, “Nenhum país com X” e o erro. Uma resposta atrasada de um termo antigo nunca pode aparecer na tela.

Pode consultarReact: você talvez não precise de um efeito · o exercício 13 do E1

dica

Separe em duas partes: um hook useDebounce(valor, ms) que devolve o valor atrasado, e um efeito que busca quando o termo atrasado muda. Para a corrida, aborte o pedido anterior na limpeza e guarde junto da resposta o termo a que ela pertence.

solução comentada
export function useDebounce<T>(valor: T, ms: number): T {
  const [atrasado, setAtrasado] = useState(valor);
  useEffect(() => {
    const t = setTimeout(() => setAtrasado(valor), ms);
    return () => clearTimeout(t); // digitou de novo antes do prazo: cancela
  }, [valor, ms]);
  return atrasado;
}

async function buscarPaises(termo: string, signal: AbortSignal): Promise<string[]> {
  const res = await fetch(`/api/paises?q=${encodeURIComponent(termo)}`, { signal });
  if (!res.ok) throw new Error(`HTTP ${res.status}`);
  return res.json();
}

type Resposta = { termo: string; itens: string[] } | { termo: string; erro: true };

export function BuscaDePaises() {
  const [texto, setTexto] = useState('');
  const termo = useDebounce(texto.trim(), 300);
  const [resposta, setResposta] = useState<Resposta | null>(null);

  useEffect(() => {
    if (!termo) return;
    const controle = new AbortController();
    buscarPaises(termo, controle.signal)
      .then((itens) => setResposta({ termo, itens }))
      .catch(() => {
        if (!controle.signal.aborted) setResposta({ termo, erro: true });
      });
    return () => controle.abort(); // termo mudou: a resposta antiga não interessa mais
  }, [termo]);

  // só vale a resposta do termo atual
  const atual = resposta && resposta.termo === termo ? resposta : null;
  const carregando = termo !== '' && atual === null;

  return (
    <div>
      <label htmlFor="busca">Buscar país</label>
      <input id="busca" type="search" value={texto} onChange={(e) => setTexto(e.target.value)} />
      <div role="status">
        {carregando && 'Buscando…'}
        {atual && 'erro' in atual && 'Não foi possível buscar agora.'}
        {atual && 'itens' in atual && atual.itens.length === 0 && `Nenhum país com “${termo}”.`}
      </div>
      {atual && 'itens' in atual && atual.itens.length > 0 && (
        <ul>
          {atual.itens.map((p) => <li key={p}>{p}</li>)}
        </ul>
      )}
    </div>
  );
}

O que mostrar ao entrevistador: são duas proteções contra a corrida. O abort cancela o pedido velho, e a comparação resposta.termo === termo garante que, mesmo se ele chegar, não aparece. O “carregando” não é estado: é “tenho termo e ainda não tenho a resposta dele”. O role="status" faz o leitor de tela anunciar o resultado.

O teste que pegaria o bug: o termo “br” responde em 500 ms e “bra” em 10 ms. Sem as proteções, “br” chega por último e substitui o resultado certo.

Revisar

Explique em voz alta

Por que encodeURIComponent? E por que o debounce fica num hook separado?

respostas

Sem ele, um termo como “a&b” quebraria a URL (o & começaria outro parâmetro). O hook separado pode ser reaproveitado e testado sozinho, e deixa o componente lendo como uma frase: “o termo é o texto atrasado em 300 ms”.

Mude um requisito

Buscar com 1 letra traz resultado demais. Só busque a partir de 2 letras, e mostre “Digite pelo menos 2 letras”.

o que muda

No efeito, troque if (!termo) por if (termo.length < 2). O “carregando” também usa essa regra, e a mensagem nova é mais uma linha derivada: termo.length === 1. Repare que nenhum estado novo foi preciso.

LC 4

Formulário de cadastro

40 min · validação, acessibilidade, envio

Faça um cadastro com e-mail, senha e confirmação. Ao enviar, valide; se houver erro, mostre a mensagem junto do campo e leve o foco ao primeiro campo com erro. Durante o envio, o botão fica desabilitado. Se o envio falhar, avise e deixe tentar de novo.

Regras

  • E-mail com formato válido. Senha com pelo menos 8 caracteres e um número. Confirmação igual à senha.
  • O leitor de tela precisa ouvir o erro ao chegar no campo.

Pode consultarMDN: aria-invalid · MDN: aria-describedby · React: input

dica

Uma função pura validar(campos) que devolve um objeto de erros é fácil de testar e de explicar. No campo, aria-invalid marca o erro e aria-describedby aponta para o id da mensagem. Um componente Campo evita repetir isso três vezes.

solução comentada
type Campos = { email: string; senha: string; confirmar: string };
type Erros = Partial<Record<keyof Campos, string>>;

export function validar(c: Campos): Erros {
  const erros: Erros = {};
  if (!/^[^\s@]+@[^\s@]+\.[^\s@]+$/.test(c.email)) erros.email = 'Digite um e-mail válido.';
  if (c.senha.length < 8) erros.senha = 'A senha precisa de pelo menos 8 caracteres.';
  else if (!/\d/.test(c.senha)) erros.senha = 'A senha precisa de pelo menos um número.';
  if (c.confirmar !== c.senha) erros.confirmar = 'As senhas não são iguais.';
  return erros;
}

function Campo(props: {
  nome: keyof Campos; rotulo: string; tipo: string; valor: string; erro?: string;
  onChange: (e: ChangeEvent<HTMLInputElement>) => void;
}) {
  const idErro = `${props.nome}-erro`;
  return (
    <div>
      <label htmlFor={props.nome}>{props.rotulo}</label>
      <input
        id={props.nome} name={props.nome} type={props.tipo} value={props.valor} onChange={props.onChange}
        aria-invalid={props.erro ? true : undefined}
        aria-describedby={props.erro ? idErro : undefined} // o leitor lê a mensagem junto do campo
      />
      {props.erro && <p id={idErro}>{props.erro}</p>}
    </div>
  );
}

export function Cadastro({ enviar }: { enviar: (c: Campos) => Promise<void> }) {
  const [campos, setCampos] = useState<Campos>({ email: '', senha: '', confirmar: '' });
  const [erros, setErros] = useState<Erros>({});
  const [status, setStatus] = useState<'editando' | 'enviando' | 'enviado' | 'falhou'>('editando');

  function mudar(e: ChangeEvent<HTMLInputElement>) {
    const { name, value } = e.target;
    setCampos((c) => ({ ...c, [name]: value }));
  }

  async function aoEnviar(e: FormEvent) {
    e.preventDefault();
    const novos = validar(campos);
    setErros(novos);
    const primeiro = Object.keys(novos)[0];
    if (primeiro) {
      document.getElementById(primeiro)?.focus(); // leva a pessoa ao primeiro erro
      return;
    }
    setStatus('enviando');
    try {
      await enviar(campos);
      setStatus('enviado');
    } catch {
      setStatus('falhou');
    }
  }

  if (status === 'enviado') return <p role="status">Conta criada. Confira o seu e-mail.</p>;
  return (
    <form onSubmit={aoEnviar} noValidate>
      <Campo nome="email" rotulo="E-mail" tipo="email" valor={campos.email} erro={erros.email} onChange={mudar} />
      <Campo nome="senha" rotulo="Senha" tipo="password" valor={campos.senha} erro={erros.senha} onChange={mudar} />
      <Campo nome="confirmar" rotulo="Confirmar senha" tipo="password" valor={campos.confirmar} erro={erros.confirmar} onChange={mudar} />
      {status === 'falhou' && <p role="alert">Não foi possível criar a conta. Tente de novo.</p>}
      <button type="submit" disabled={status === 'enviando'}>
        {status === 'enviando' ? 'Criando…' : 'Criar conta'}
      </button>
    </form>
  );
}

O que mostrar ao entrevistador: a validação é uma função pura, testável sem tela; o noValidate desliga os balões do navegador para as mensagens serem as suas; o botão desabilitado evita envio duplo; e a validação do front é conforto, a de verdade fica no servidor.

Revisar

Explique em voz alta

Por que validar ao enviar, e não a cada tecla? Quando faria sentido validar ao sair do campo?

respostas

Validar a cada tecla grita “e-mail inválido” enquanto a pessoa ainda está digitando o e-mail. Ao sair do campo (onBlur) é um meio-termo bom para formulários longos: o aviso chega cedo, mas só depois de a pessoa terminar aquele campo. Depois que o erro apareceu, revalidar a cada tecla é bom, porque o aviso some assim que o campo fica certo.

Mude um requisito

O servidor responde que o e-mail já está em uso. Onde essa mensagem aparece?

o que muda

No próprio campo de e-mail, como os outros erros. O enviar passa a devolver os erros do servidor (ou a lançar um erro com eles), e o catch faz setErros({ email: 'Este e-mail já tem conta.' }) e foca o campo. Um aviso genérico no topo obrigaria a pessoa a adivinhar qual campo corrigir.

LC 5

Abas acessíveis

30 min · ARIA, teclado, refs

Faça um componente Abas que recebe uma lista { id, titulo, conteudo }. Clicar troca a aba. No teclado: Tab entra na aba ativa, setas trocam de aba, Home e End vão para a primeira e a última, e o próximo Tab vai para o conteúdo.

Pode consultarW3C: padrão de abas · React: refs e o DOM

dica

Papéis: tablist no grupo, tab em cada botão, tabpanel no conteúdo. Só a aba ativa tem tabIndex={0}; as outras, -1. Assim o Tab entra numa aba só, e as setas fazem o resto. Para mover o foco, guarde os botões num useRef.

solução comentada
type Aba = { id: string; titulo: string; conteudo: ReactNode };

export function Abas({ abas }: { abas: Aba[] }) {
  const [ativa, setAtiva] = useState(0);
  const botoes = useRef<(HTMLButtonElement | null)[]>([]);

  function teclado(e: KeyboardEvent<HTMLDivElement>) {
    let nova: number;
    if (e.key === 'ArrowRight') nova = (ativa + 1) % abas.length;               // depois da última, volta à primeira
    else if (e.key === 'ArrowLeft') nova = (ativa - 1 + abas.length) % abas.length;
    else if (e.key === 'Home') nova = 0;
    else if (e.key === 'End') nova = abas.length - 1;
    else return; // outras teclas seguem normais
    e.preventDefault();
    setAtiva(nova);
    botoes.current[nova]?.focus();
  }

  return (
    <div>
      <div role="tablist" aria-label="Seções" onKeyDown={teclado}>
        {abas.map((aba, i) => (
          <button
            key={aba.id}
            ref={(el) => { botoes.current[i] = el; }}
            type="button"
            role="tab"
            id={`aba-${aba.id}`}
            aria-selected={i === ativa}
            aria-controls={`painel-${aba.id}`}
            tabIndex={i === ativa ? 0 : -1} // só a ativa entra na ordem do Tab
            onClick={() => setAtiva(i)}
          >
            {aba.titulo}
          </button>
        ))}
      </div>
      {abas.map((aba, i) => (
        <div key={aba.id} role="tabpanel" id={`painel-${aba.id}`} aria-labelledby={`aba-${aba.id}`} hidden={i !== ativa} tabIndex={0}>
          {aba.conteudo}
        </div>
      ))}
    </div>
  );
}

O que mostrar ao entrevistador: o % faz a seta “dar a volta”; o + abas.length evita índice negativo; e os painéis escondidos continuam no DOM com hidden, então trocar de aba não perde o que foi digitado dentro deles.

Revisar

Explique em voz alta

Por que não deixar todas as abas com tabIndex={0}?

resposta

Com dez abas, a pessoa no teclado precisaria de dez Tabs para chegar ao conteúdo. O padrão do W3C trata o grupo de abas como um controle só: um Tab para entrar, setas para escolher, um Tab para sair. É o mesmo comportamento de um grupo de rádio.

Mude um requisito

Cada aba agora carrega dados de uma API, e só deve buscar quando for aberta pela primeira vez.

o que muda

Guarde um Set com as abas já abertas e renderize o conteúdo só delas (as nunca abertas ficam vazias). Cada conteúdo é um componente com o seu próprio efeito de busca, como o LC 2. Como os painéis já abertos continuam montados (com hidden), voltar a uma aba não busca de novo.

LC 6

Tabela com ordenação e paginação

40 min · estado derivado, useMemo

Mostre uma lista de pessoas ({ id, nome, idade, cidade }) numa tabela de 5 linhas por página. Clicar no cabeçalho ordena pela coluna; clicar de novo inverte. Ao mudar a ordem, volte para a página 1. Os botões Anterior e Próxima ficam desabilitados nas pontas.

Pode consultarReact: useMemo · MDN: aria-sort · o exercício 8 do E1

dica

O estado é só a ordem (coluna e direção) e o número da página. A lista ordenada, a fatia da página e o total de páginas são calculados. Ordene uma cópia, e use localeCompare para texto com acento.

solução comentada
type Pessoa = { id: number; nome: string; idade: number; cidade: string };
type Coluna = 'nome' | 'idade' | 'cidade';
const POR_PAGINA = 5;
const ROTULOS: Record<Coluna, string> = { nome: 'Nome', idade: 'Idade', cidade: 'Cidade' };

export function TabelaDePessoas({ pessoas }: { pessoas: Pessoa[] }) {
  const [ordem, setOrdem] = useState<{ coluna: Coluna; direcao: 'asc' | 'desc' }>({ coluna: 'nome', direcao: 'asc' });
  const [pagina, setPagina] = useState(1);

  const ordenadas = useMemo(() => {
    const sinal = ordem.direcao === 'asc' ? 1 : -1;
    return [...pessoas].sort((a, b) => {
      const x = a[ordem.coluna];
      const y = b[ordem.coluna];
      const cmp = typeof x === 'number' && typeof y === 'number' ? x - y : String(x).localeCompare(String(y), 'pt-BR');
      return cmp * sinal;
    });
  }, [pessoas, ordem]);

  const totalPaginas = Math.max(1, Math.ceil(ordenadas.length / POR_PAGINA));
  const paginaAtual = Math.min(pagina, totalPaginas); // a lista pode ter encolhido
  const visiveis = ordenadas.slice((paginaAtual - 1) * POR_PAGINA, paginaAtual * POR_PAGINA);

  function ordenarPor(coluna: Coluna) {
    setOrdem((o) => ({ coluna, direcao: o.coluna === coluna && o.direcao === 'asc' ? 'desc' : 'asc' }));
    setPagina(1); // nova ordem: volta ao começo
  }

  return (
    <div>
      <table>
        <thead>
          <tr>
            {(Object.keys(ROTULOS) as Coluna[]).map((c) => (
              <th key={c} aria-sort={ordem.coluna === c ? (ordem.direcao === 'asc' ? 'ascending' : 'descending') : 'none'}>
                <button type="button" onClick={() => ordenarPor(c)}>{ROTULOS[c]}</button>
              </th>
            ))}
          </tr>
        </thead>
        <tbody>
          {visiveis.map((p) => (
            <tr key={p.id}><td>{p.nome}</td><td>{p.idade}</td><td>{p.cidade}</td></tr>
          ))}
        </tbody>
      </table>
      <nav aria-label="Paginação">
        <button type="button" onClick={() => setPagina(paginaAtual - 1)} disabled={paginaAtual === 1}>Anterior</button>
        <span>Página {paginaAtual} de {totalPaginas}</span>
        <button type="button" onClick={() => setPagina(paginaAtual + 1)} disabled={paginaAtual === totalPaginas}>Próxima</button>
      </nav>
    </div>
  );
}

O que mostrar ao entrevistador: o cabeçalho é um <button> dentro do <th> (clicável pelo teclado), e o aria-sort diz ao leitor de tela qual coluna está ordenada. O Math.min da página atual cobre a lista que encolheu: sem ele, a tela mostraria “Página 3 de 2”.

Sobre o useMemo: ordenar 50 itens é rápido, e o useMemo poderia sair. Ele passa a valer com milhares de linhas. Dizer isso mostra que você sabe quando a otimização se paga.

Revisar

Caça ao bug

Um colega guardou a lista ordenada no estado, assim. O que dá errado quando a prop pessoas muda?

const [ordenadas, setOrdenadas] = useState(pessoas);
function ordenarPor(coluna: Coluna) {
  setOrdenadas([...ordenadas].sort(/* ... */));
}
o erro

O useState(pessoas) só usa o valor na primeira renderização. Se o pai mandar uma lista nova (uma pessoa cadastrada), a tabela continua mostrando a antiga. É o erro de estado duplicado: a mesma informação em dois lugares, que deixam de concordar. A solução é derivar a lista ordenada da prop, como na solução.

Mude um requisito

Os dados passam a vir paginados do servidor (?pagina=2&ordem=idade), porque são 100 mil pessoas.

o que muda

Ordenar e fatiar saem do componente e vão para o servidor (o banco faz ORDER BY e LIMIT/OFFSET). A ordem e a página continuam sendo estado, mas agora entram nas dependências de um efeito de busca, como no LC 2. Pôr os dois na URL (?pagina=2) permite compartilhar o link e usar o botão voltar.

LC 7

Cronômetro

30 min · setInterval, cleanup, useRef

Faça um cronômetro mm:ss.d com Iniciar/Continuar, Pausar e Zerar. O tempo mostrado não pode atrasar, mesmo depois de vários minutos ou com a aba em segundo plano. Ao sair da tela, nenhum timer fica rodando.

Pode consultarReact: useRef · MDN: setInterval

dica

Não some 100 a cada tick: o navegador não garante o intervalo exato. Guarde o horário em que a contagem começou e calcule Date.now() - inicio a cada tick. Valores que não aparecem na tela (o início, o acumulado) ficam num useRef.

solução comentada
function formatar(ms: number) {
  const totalSeg = Math.floor(ms / 1000);
  const min = String(Math.floor(totalSeg / 60)).padStart(2, '0');
  const seg = String(totalSeg % 60).padStart(2, '0');
  const decimo = Math.floor((ms % 1000) / 100);
  return `${min}:${seg}.${decimo}`;
}

export function Cronometro() {
  const [decorrido, setDecorrido] = useState(0); // o que a tela mostra
  const [rodando, setRodando] = useState(false);
  const acumulado = useRef(0); // tempo somado até a última pausa
  const inicio = useRef(0);    // quando começou a rodada atual

  useEffect(() => {
    if (!rodando) return;
    const id = setInterval(() => setDecorrido(acumulado.current + Date.now() - inicio.current), 100);
    return () => clearInterval(id); // pausou ou saiu da tela: para o intervalo
  }, [rodando]);

  function iniciar() {
    inicio.current = Date.now();
    setRodando(true);
  }
  function pausar() {
    acumulado.current += Date.now() - inicio.current;
    setDecorrido(acumulado.current);
    setRodando(false);
  }
  function zerar() {
    acumulado.current = 0;
    setDecorrido(0);
    setRodando(false);
  }

  return (
    <div>
      <p>{formatar(decorrido)}</p>
      {rodando
        ? <button type="button" onClick={pausar}>Pausar</button>
        : <button type="button" onClick={iniciar}>{decorrido === 0 ? 'Iniciar' : 'Continuar'}</button>}
      <button type="button" onClick={zerar} disabled={decorrido === 0 && !rodando}>Zerar</button>
    </div>
  );
}

O que mostrar ao entrevistador: useState é para o que aparece na tela; useRef é para o que só o código precisa lembrar (mudar uma ref não redesenha). E o tempo vem do relógio, não da contagem de ticks.

Revisar

Caça ao bug

Esta é a versão que quase todo mundo escreve primeiro. Ache os três problemas.

useEffect(() => {
  if (!rodando) return;
  setInterval(() => setDecorrido(decorrido + 100), 100);
}, [rodando]);
os erros
  1. Closure velha (stale closure). A função do intervalo lembra o decorrido do momento em que foi criada (0). Ela calcula 0 + 100 para sempre, e a tela trava em 00:00.1. Com setDecorrido((d) => d + 100), esse problema some.
  2. Sem limpeza. Pausar não para o intervalo, e cada Iniciar cria mais um. Depois de três pausas, são três intervalos rodando juntos.
  3. Somar 100 a cada tick atrasa. O intervalo não é exato, e navegadores como o Chrome reduzem os timers de abas em segundo plano para no máximo um por segundo. Contando ticks, o cronômetro mostra menos tempo do que passou.
Mude um requisito

O cronômetro ganha um botão “Volta”, que registra o tempo atual numa lista, como no app de relógio do celular.

o que muda

Um estado novo, voltas: number[]. O botão calcula o tempo atual do mesmo jeito que o intervalo (acumulado.current + Date.now() - inicio.current) e acrescenta à lista. O tempo de cada volta (a diferença para a anterior) é derivado na hora de mostrar, e o Zerar também limpa as voltas.

LC 8

Modal de confirmação

25 min · <dialog>, foco, teclado

Um botão “Excluir item” abre um modal de confirmação. Enquanto ele está aberto, o resto da página não recebe clique nem foco. Esc e Cancelar fecham sem excluir. Ao fechar, o foco volta para o botão que abriu.

Pode consultarMDN: <dialog> · W3C: padrão de diálogo modal

dica

Antes de montar tudo à mão, lembre que o HTML já tem um elemento para isto. O <dialog> aberto com showModal() já bloqueia o fundo, fecha com Esc e devolve o foco. Um <form method="dialog"> dentro dele fecha o modal ao enviar.

solução comentada
export function ConfirmarExclusao({ nome, onConfirmar }: { nome: string; onConfirmar: () => void }) {
  const dialogo = useRef<HTMLDialogElement>(null);
  return (
    <>
      <button type="button" onClick={() => dialogo.current?.showModal()}>
        Excluir {nome}
      </button>
      <dialog ref={dialogo} aria-labelledby="titulo-excluir">
        <h2 id="titulo-excluir">Excluir “{nome}”?</h2>
        <p>Essa ação não pode ser desfeita.</p>
        {/* method="dialog": enviar este form fecha o diálogo, sem recarregar nada */}
        <form method="dialog">
          <button value="cancelar">Cancelar</button>
          <button value="excluir" onClick={onConfirmar}>Excluir</button>
        </form>
      </dialog>
    </>
  );
}

O que mostrar ao entrevistador: o showModal() entrega de graça o que levaria uma tarde para fazer à mão: o resto da página fica inerte, o Esc fecha e o foco volta para quem abriu. O foco começa no primeiro botão, o Cancelar, que é o mais seguro numa ação destrutiva. Saber que o HTML já resolve, em vez de escrever 80 linhas de JavaScript, é um sinal forte de senioridade.

Revisar

Explique em voz alta

Se você fizesse o modal com uma <div> e CSS, o que precisaria implementar à mão?

resposta

Prender o foco dentro do modal (o Tab não pode sair para a página atrás), fechar com Esc, devolver o foco ao botão que abriu, impedir clique e rolagem no fundo, e os atributos role="dialog" e aria-modal="true". Bibliotecas como Radix e Headless UI existem justamente para isso; o <dialog> nativo cobre a maior parte.

Mude um requisito

A exclusão agora chama a API e pode falhar. O modal só fecha se der certo.

o que muda

O botão Excluir sai do form method="dialog" (que fecha na hora) e vira um botão comum que chama a API. Enquanto espera, ele fica desabilitado com “Excluindo…”; se der certo, dialogo.current?.close(); se falhar, uma mensagem com role="alert" aparece dentro do modal, que continua aberto.
