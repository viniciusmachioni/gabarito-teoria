Frontend Architecture

~8h · onde o código mora, onde ele roda e quanto ele custa pro usuário

“Arquitetura de front” aqui não é diagrama de caixinha. São quatro decisões: o que vira pacote compartilhado, onde um módulo termina, qual página é estática e qual é dinâmica, e quanto JavaScript chega ao celular. Uma tela de IA piora as quatro, porque a resposta é lenta, o payload é grande e o componente é pesado. O Ver explica cada decisão em linguagem simples. A base de renderização está na Semana 2, e a de performance de navegador no B13.

Para júnior avançado e pleno

Arquitetura de front, para pleno, é decidir bem dentro de uma página: como renderizar e como buscar dados. Monorepo e microfrontends são decisões de time.

baseDomine: estático, dinâmico ou ISR por rota; cascata de requisições e Promise.all; quando buscar no Server Component, no useEffect ou com TanStack Query.

diferencialSaiba explicar: monorepo com Turborepo, o cache do Next e os Web Vitals (LCP, INP, CLS).

sêniorDeixe para depois: tipos de pacote interno, fronteiras entre pacotes e as formas de integrar microfrontends. Basta saber dizer quando não usar microfrontend.

1 · VerO básico, em linguagem simples

Leia isto antes do resto. Cada cartão responde a três perguntas: qual é o problema, como se resolve e o que você diz na entrevista.

1. Monorepo: vários apps num repositório só

O problemaO site, o painel e a biblioteca de componentes vivem em três repositórios. Mudar um botão exige publicar uma versão da biblioteca e atualizar os outros dois. As versões se desencontram.

Como funcionaTudo fica num repositório: os apps em apps/ e o código compartilhado em packages/. O pnpm workspaces liga os pacotes entre si sem publicar nada. O Turborepo roda as tarefas na ordem certa (primeiro o build da biblioteca, depois o do app) e guarda o resultado: se nada mudou, ele reaproveita em vez de rodar de novo.

PegadinhaSe uma variável de ambiente muda o resultado do build, ela precisa estar declarada no turbo.json. Senão o Turborepo reaproveita um build velho.

Na entrevista“Monorepo me dá uma mudança atômica: o botão e todas as telas que usam ele mudam no mesmo pull request.”

2. O que vai para packages/, e o que não vai

VaiComponentes de UI sem regra de negócio, tipos compartilhados, configuração de lint e de TypeScript.

Não vaiRegra de negócio de um app. Se o pacote de UI sabe o que é “assinatura vencida”, ele deixou de ser compartilhável.

Como imporO campo exports do package.json define o que o pacote mostra para fora. O que não está ali não pode ser importado, então a fronteira não depende de disciplina.

Na entrevista“Pacote compartilhado é UI burra e tipos. A fronteira eu imponho com exports, não com combinado.”

3. Microfrontends: só quando houver necessidade real

O que éO front é dividido em partes que times diferentes desenvolvem e publicam de forma independente. Por exemplo, o time de checkout publica o checkout sem esperar o time do catálogo.

Quando valeMuitos times autônomos que se atrapalham no mesmo deploy, ou um sistema antigo sendo migrado aos pedaços.

O que custaBibliotecas baixadas em dobro, telas com visual diferente, mais infraestrutura e mais combinados entre times.

Na entrevista“Microfrontend resolve um problema de organização, não de código. Com um time só, eu começo por um monorepo bem dividido.”

4. Página estática ou dinâmica

EstáticaO HTML é gerado uma vez, no build, e servido pela CDN para todo mundo. É rápida e barata. Serve para o que é igual para todos: página de preços, post de blog.

DinâmicaO HTML é gerado a cada pedido. É necessária quando a página depende de quem pede. No Next, ler cookies() ou headers() já torna a rota dinâmica.

Meio-termoO ISR gera a página estática e a refaz de tempos em tempos ou quando o dado muda. O streaming com loading.tsx manda a casca da página na hora e o resto quando ficar pronto.

Na entrevista“Eu decido rota por rota: se é igual para todos, é estática. Se depende de quem pede, é dinâmica, com streaming para não travar a tela.”

5. Cache no Next, sem mistério

Dentro de um pedidoO cache() do React evita buscar a mesma coisa duas vezes enquanto uma página é montada.

Entre pedidosO 'use cache' (Next 16) guarda o resultado de uma função para os próximos visitantes.

Depois de mudar o dadoO revalidateTag() ou o revalidatePath() avisa que aquele cache ficou velho.

A regra de ouroCache compartilhado só para dado que é igual para todos. Dado de um usuário num cache compartilhado vaza para os outros.

Na entrevista“Eu ponho em cache o que é público e invalido por tag quando o dado muda. Nada que dependa do usuário vai para cache compartilhado.”

6. Buscar dados sem cascata

O problemaTrês await seguidos, de buscas independentes, somam os tempos: 300 + 200 + 250 ms = 750 ms. Isso é uma cascata (waterfall).

Como resolveComece as buscas independentes juntas com Promise.all. O tempo cai para o da mais lenta. Só espere em sequência quando uma busca precisa do resultado da outra.

Onde buscarNum Server Component, a busca roda no servidor, perto do banco, e o HTML já chega pronto. Com useEffect no cliente, a página carrega, depois busca, e só depois mostra: uma ida e volta a mais.

Na entrevista“Busca independente começa junto. Só fica em sequência o que depende de outro resultado.”

7. Web Vitals: as três notas do Google

LCPQuanto demora para o maior elemento visível aparecer (a imagem principal ou o título). Bom: até 2,5 s.

INPQuanto a tela demora para reagir a um clique ou a uma tecla. Bom: até 200 ms.

CLSQuanto o layout pula enquanto carrega, como um botão que desce quando uma imagem aparece. Bom: até 0,1.

Como medirCom usuários reais (dados de campo), olhando o percentil 75: a nota que 75% das visitas alcançam ou superam. Para melhorar, mande menos JavaScript ao cliente, reserve espaço para imagens e carregue a imagem principal primeiro.

Na entrevista“Eu meço LCP, INP e CLS com usuários reais, no p75, e ataco primeiro o JavaScript que não precisava ir para o cliente.”

Workspace
recurso do pnpm (e do npm/yarn) que liga pacotes do mesmo repositório sem publicar.
ISR

  • Turborepo — Internal Packages
    As três estratégias de pacote interno e o que cada uma custa. É exatamente a decisão que o @ally-ai/types tomou sem dizer o nome.
    Ler inteiro · ~15 minPágina curta. Preste atenção na lista de limitações do Just-in-Time — é a pergunta de entrevista.
    turborepo.dev · oficial
    Resumo aqui na página

    Em uma frase: um pacote interno é código compartilhado entre os apps do mesmo repositório, como uma biblioteca de botões ou um arquivo de tipos. A decisão que importa é quem transforma o TypeScript dele em JavaScript, e há três respostas.

    No mundo realO Google guarda quase todo o seu código num único repositório, com bilhões de linhas, para que uma mudança numa biblioteca e em todos os sistemas que a usam saia junto. Numa escala bem menor, o próprio repositório do Next.js é um monorepo com pnpm e Turborepo. No Ally AI, o pacote @ally-ai/types é um pacote interno do tipo “Just-in-Time”, explicado abaixo.

    As três estratégias
    • Just-in-Time: o pacote não tem build. O package.json aponta direto para os arquivos .ts, e o app que importa compila junto. Quase não tem configuração. Em troca, só funciona se todo app que usa o pacote souber compilar TypeScript, o Turborepo não tem build para guardar em cache, e um erro de tipo do pacote aparece no app que o importa.
    • Compiled: o próprio pacote compila (normalmente com tsc) para uma pasta dist/. O Turborepo guarda esse resultado em cache, e qualquer app consegue usar. Em troca, exige mais configuração.
    • Publishable: como o Compiled, mas preparado para ir ao npm e ser usado fora do repositório. Exige controle de versão e publicação. A documentação recomenda o changesets.
    Como saber qual você tem
    • O package.json aponta para ./src/index.ts e não existe script de build? É Just-in-Time.
    • Aponta para ./dist/index.js e existe um build que gera esse arquivo? É Compiled.
    • No turbo.json, o dependsOn: ["^build"] garante que o pacote seja compilado antes do app que depende dele.
    Boas práticas
    • Declare o campo exports no package.json. Ele define o que o pacote mostra para fora. O que não está ali não pode ser importado, e é assim que a fronteira do pacote fica garantida sem depender de disciplina.
    • Use os mesmos scripts (lint, typecheck) em todos os pacotes, para o Turborepo rodar a mesma tarefa no repositório inteiro.

    Frase de entrevista: “Comecei o pacote de tipos como Just-in-Time porque é só contrato e os dois apps compilam TypeScript. Se virasse uma biblioteca de UI usada por vários apps, eu passaria para Compiled, pelo cache do build e para o erro de tipo não vazar para quem usa.”

  • Micro Frontends (Cam Jackson, no site do Martin Fowler)
    O texto de referência: definição, benefícios, as cinco formas de integrar e, principalmente, os custos. É de onde vem o “quando houver necessidade real” do roadmap.
    Ler trechos · ~35 minLeia Benefits, Integration approaches e Downsides. O exemplo completo com código pode ser pulado.
    martinfowler.com
    Resumo aqui na página

    Em uma frase: microfrontends dividem o front de um produto em partes que times diferentes desenvolvem e publicam de forma independente, e que juntas formam uma aplicação só. O artigo, de Cam Jackson no site do Martin Fowler, é a favor do estilo, mas honesto sobre o preço, e o preço é o que se cobra na entrevista.

    No mundo realA Zalando, maior varejista de moda online da Europa, criou o Project Mosaic para montar cada página no servidor a partir de fragmentos de vários times, cada um com o seu deploy. O app desktop do Spotify foi, por anos, montado com iframes, um por área do app, cada uma de um time. Mais tarde, a empresa unificou o cliente. É o padrão: microfrontend aparece onde há dezenas de times, e é revisto quando o custo de manter tudo consistente pesa.

    Os quatro benefícios
    • Troca aos pedaços: substituir um sistema antigo parte por parte, em vez de reescrever tudo, e testar uma tecnologia nova num pedaço só.
    • Bases de código menores: menos dependência acidental entre partes.
    • Deploy independente: cada parte tem o seu pipeline, e o time decide quando publicar.
    • Times autônomos: organizados por funcionalidade que o usuário vê (checkout, catálogo), e não por camada técnica.
    As cinco formas de juntar as partes
    • No servidor: o servidor monta a página com fragmentos de HTML de cada time. É simples e é o que a Zalando faz.
    • No build, como pacote npm: o artigo desaconselha. Cada parte vira dependência do app principal, e publicar uma exige republicar o app inteiro, o que traz de volta o acoplamento que se queria evitar.
    • Com iframe: isola estilo e script, mas sofre com rotas, links diretos, layout responsivo e comunicação entre as partes.
    • Com JavaScript no navegador: cada parte expõe uma função de entrada, e o app principal decide quando e onde desenhar. É a mais flexível e a mais usada.
    • Com Web Components: a mesma ideia, usando elementos HTML próprios como ponto de entrada.
    Os problemas que aparecem em todas
    • CSS é global: é preciso uma convenção (CSS Modules, prefixos) para um time não quebrar o estilo do outro.
    • Biblioteca compartilhada: comece só por peças visuais simples (botão, ícone), nunca com regra de negócio, e com alguém responsável por ela.
    • Comunicação entre partes: o mínimo possível, por eventos, props ou pela URL.
    Os custos
    • Peso: cada parte empacota as próprias dependências, e o usuário pode baixar o React duas vezes.
    • Ambientes diferentes: desenvolver cada parte isolada esconde problemas que só aparecem com tudo junto.
    • Operação: mais repositórios, pipelines e combinados entre times. Exige automação madura.

    Frase de entrevista: “Microfrontend resolve um problema de organização, não de código. Com um time só, eu pagaria peso duplicado e coordenação sem ganhar deploy independente de ninguém.”

    Resumo em português do recorte indicado · original em martinfowler.com
  • Next.js — Multi-Zones
    O microfrontend que o próprio Next oferece: várias apps Next no mesmo domínio, cada uma dona de um conjunto de rotas.
    Ler inteiro · ~15 minGuia curto com toda a configuração. O detalhe que mais cai: <a> em vez de <Link> entre zonas.
    nextjs.org · oficial
    Resumo aqui na página

    Em uma frase: multi-zones é o jeito do Next de fazer microfrontend por rota. Várias aplicações Next ficam no mesmo domínio, cada uma dona de um conjunto de caminhos. Para o usuário parece um site só. Para os times, são builds e deploys separados.

    No mundo realO próprio site da Vercel é dividido assim: o site de marketing, a documentação e o painel são aplicações separadas, servidas no mesmo domínio vercel.com por caminho. Cada time publica a sua parte sem esperar os outros.

    A ideia
    • O exemplo da documentação: /blog/*, /dashboard/* e o resto (/*) viram três apps. Cada um fica menor, faz build mais rápido e não carrega código que só o outro usa.
    • Navegar dentro de uma zona é rápido, sem recarregar a página. Navegar entre zonas recarrega a página inteira. Regra prática: páginas que a pessoa visita em sequência ficam na mesma zona.
    Como se monta
    • Cada zona é um app Next normal com um assetPrefix próprio ('/blog-static'), para o JavaScript e o CSS dela não colidirem com os da outra.
    • O roteamento pode ser feito pelo app principal, com rewrites que mandam /blog e /blog/... para o endereço da outra zona. Cada caminho pertence a uma zona só.
    • Os links entre zonas usam <a>, e não <Link>. O Link tenta pré-carregar e navegar sem recarregar, e isso não funciona entre apps diferentes.
    • As zonas podem morar em repositórios diferentes, mas um monorepo facilita compartilhar código. Para ligar uma funcionalidade em todas ao mesmo tempo, use uma feature flag.

    Frase de entrevista: “Se eu precisasse separar uma área com time próprio, começaria por multi-zones por rota. É o microfrontend mais barato: nada é compartilhado no navegador, e o custo é só a recarga na fronteira.”

    Resumo em português do recorte indicado · original em nextjs.org
  • Next.js — Content Security Policy
    Lido aqui pelo lado de arquitetura, não de segurança: a seção “Static vs Dynamic Rendering with CSP” explica por que o Gabarita inteiro é dinâmico.
    Ler trechos · ~15 minLeia “How nonces work”, “Static vs Dynamic Rendering with CSP” e “Subresource Integrity”. A configuração em si você já tem (Semana 5).
    nextjs.org · oficial
    Resumo aqui na página

    Em uma frase: a Content Security Policy (CSP) diz ao navegador quais scripts ele pode executar, o que bloqueia scripts injetados por um atacante. O jeito mais seguro usa um nonce, um código aleatório novo a cada pedido. O efeito colateral é grande: com nonce, toda página vira dinâmica, porque o código só existe quando existe um pedido.

    No mundo realO GitHub adotou uma CSP rígida há anos e escreveu publicamente sobre o caminho: ela é uma das camadas que impedem um script malicioso, colado num comentário ou num README, de rodar na página de quem está logado. No Gabarita, a CSP com nonce foi uma escolha consciente, aceitando o custo de perder o cache de páginas estáticas.

    Como o Next aplica o nonce
    1. O proxy (o antigo middleware) gera o nonce a cada pedido e o coloca no cabeçalho Content-Security-Policy.
    2. Ao montar a página no servidor, o Next lê esse cabeçalho e marca com o nonce os scripts do próprio framework e os da página.
    3. Para um script de terceiro, você lê o nonce com headers() num Server Component e passa para ele.

    Uma página estática é gerada no build, quando não existe pedido nem cabeçalho. Por isso não há como pôr o nonce nela.

    O que se perde
    • Páginas estáticas e ISR ficam desligados: cada pedido gera a página de novo.
    • A CDN não consegue guardar a página sem configuração extra.
    • O Partial Prerendering não funciona, porque a casca estática não tem o nonce.
    • Resultado: primeira carga mais lenta, mais trabalho no servidor e hospedagem mais cara.
    • Vale a pena quando há dado sensível, uma exigência de segurança que proíbe scripts inline ou compliance.
    As alternativas
    • CSP fixa, sem nonce: configurada no next.config. Mantém o estático, mas precisa liberar scripts inline ('unsafe-inline'), o que enfraquece a proteção.
    • Subresource Integrity (experimental): o build calcula um código de cada arquivo de script, e o navegador confere antes de executar. Mantém o estático e o cache, mas não cobre scripts gerados na hora.

    Frase de entrevista: “Nonce é uma decisão de arquitetura, não só de segurança: ele troca o cache da CDN por uma CSP sem scripts inline. Eu aceitei esse custo num app com dado de usuário, e sei que a integridade por hash é a saída se precisar de páginas estáticas.”

    Resumo em português do recorte indicado · original em nextjs.org
  • Next.js — Optimizing package bundling
    As duas ferramentas de análise de bundle e os três remédios mais comuns — a base do script analyze que o Ally AI já tem.
    Ler inteiro · ~15 minGuia direto. Note qual analisador serve pra Turbopack e qual só pra webpack.
    nextjs.org · oficial
    Resumo aqui na página

    Em uma frase: quanto menos JavaScript o navegador baixa, mais rápido a página carrega e responde. O Next já divide o código por página e descarta o que não é usado. Este guia é para quando você precisa medir e agir.

    No mundo realO Moment.js, biblioteca de datas muito usada, passa de 200 KB quando vem com todos os idiomas, e milhares de sites o carregavam para formatar uma data. A própria equipe do Moment hoje recomenda alternativas menores. É o tipo de achado que um analisador de pacote mostra em minutos: uma dependência grande trazida por um único import.

    As ferramentas de análise
    • Com Turbopack (Next 16.1 ou mais novo): next experimental-analyze abre um mapa interativo do código, filtrável por rota e por lado (cliente ou servidor). Clicar num módulo mostra o tamanho e quem o importou.
    • Com webpack: o plugin @next/bundle-analyzer, ligado com ANALYZE=true, abre os relatórios no navegador.
    Os três remédios mais comuns
    • Pacote com centenas de exports (ícones, utilitários): optimizePackageImports faz carregar só o que foi usado. Vários pacotes já vêm otimizados por padrão, como lucide-react, date-fns e lodash-es.
    • Trabalho pesado no navegador: uma biblioteca que só transforma dado em tela (realce de código, gráfico, markdown) dentro de um Client Component vai inteira para o navegador. Se ela não precisa de clique nem de API do navegador, rode num Server Component e mande só o HTML. O exemplo da documentação troca o Prism no cliente pelo Shiki no servidor.
    • Pacote que não deve ser empacotado no servidor: serverExternalPackages deixa de fora pacotes específicos.

    Frase de entrevista: “Antes de otimizar, eu meço: rodo o analisador, acho o módulo grande e quem o trouxe, e só então escolho entre carregar só o necessário, mover para um Server Component ou carregar depois.”

  • web.dev — Optimize Interaction to Next Paint
    A métrica de Core Web Vitals que mais pega interface rica: o tempo do clique até a tela mudar. As três fases e o remédio de cada uma.
    Ler trechos · ~25 minLeia a definição das três fases e as seções de otimização. A parte de ferramentas de diagnóstico é consulta.
    web.dev · Google
    Resumo aqui na página

    Em uma frase: o INP (Interaction to Next Paint) mede quanto a tela demora para reagir a um clique, toque ou tecla. Ele observa todas as interações da visita e reporta a mais lenta. A meta é até 200 ms para 75% das visitas. Acima de 500 ms é ruim.

    No mundo realO INP substituiu o FID como métrica oficial de resposta do Google em março de 2024, porque o FID só media a primeira interação. Num estudo de caso publicado no web.dev, a redBus, plataforma de passagens de ônibus da Índia, melhorou o INP do site e registrou cerca de 7% a mais de vendas.

    As três fases de uma interação
    • Espera para começar (input delay): do clique até o código do clique começar. Acontece quando o navegador está ocupado com outra coisa, como carregar scripts. Remédio: menos trabalho na inicialização.
    • Processamento: o código do clique rodando. Remédio: fazer primeiro só o que muda a tela e adiar o resto, por exemplo com setTimeout, para devolver o controle ao navegador.
    • Desenho (presentation delay): do fim do código até a tela ser redesenhada. Acontece quando a mudança é grande. Remédio: menos elementos na página, content-visibility para o que está fora da tela e menos HTML montado por JavaScript no navegador.

    A soma das três é o tempo da interação. HTML que chega pronto do servidor, aos pedaços, deixa o navegador livre entre um pedaço e outro. HTML montado por JavaScript prende o navegador até terminar.

    Como achar a interação lenta
    • Comece pelos usuários reais: uma ferramenta de monitoramento (RUM) ou os dados do Chrome no PageSpeed Insights dizem qual interação e qual página.
    • Depois reproduza: repita o fluxo e teste as interações durante o carregamento, quando o navegador está mais ocupado.

    Frase de entrevista: “Quando o INP piora, eu não saio colocando useMemo. Separo a interação nas três fases e ataco a que a medição apontou.”

FAZER 1

Estática, dinâmica ou ISR?

15 min · decisão, sem código

Para cada rota de um app de estudos, diga como ela deve ser renderizada e por quê, em uma frase.

  1. /precos: muda duas vezes por ano.
  2. /painel: mostra o nome e o desempenho de quem está logado.
  3. /questoes/[id]: pública, igual para todos, mas o admin corrige um erro de vez em quando.
  4. /busca?q=...: resultado depende do texto digitado.
  5. /blog/[slug]: posts novos toda semana, os antigos quase nunca mudam.

Pode consultaros cartões do Ver · Next.js: caching e revalidação

dica

Faça duas perguntas para cada rota: o conteúdo depende de quem pede ou do que vem no pedido? E quando o dado muda, eu sei o momento exato?

solução comentada
  1. Estática. É igual para todos e quase não muda. Um deploy novo resolve quando mudar.
  2. Dinâmica. Depende do cookie de sessão. Use streaming (loading.tsx ou Suspense) para mostrar a casca enquanto os números carregam.
  3. Estática com revalidação sob demanda. Igual para todos. Quando o admin salva a correção, a ação chama revalidateTag('questao-' + id) e só aquela página é refeita.
  4. Dinâmica. Depende do searchParams. Dá para pôr em cache o resultado de buscas comuns, mas a página em si é gerada no pedido.
  5. Estática com ISR. Gere os posts no build e use generateStaticParams com revalidação por tempo ou por tag para os novos.

O que mostrar ao entrevistador: a decisão é por rota, e o critério é “depende de quem pede?”. Quando você sabe o momento em que o dado muda, revalidar sob demanda é melhor que revalidar por tempo.

Tire a cascata desta página

15 min · Next.js + TS

Esta página demora 750 ms para começar a responder. getUsuario leva 300 ms, getEstatisticas leva 200 ms e getRecomendadas leva 250 ms. As recomendações dependem do nível do usuário. Reescreva para que a página fique o mais rápida possível.

export default async function Painel({ params }: { params: Promise<{ id: string }> }) {
  const { id } = await params;
  const usuario = await getUsuario(id);
  const stats = await getEstatisticas(id);
  const recomendadas = await getRecomendadas(usuario.nivel);
  return <Tela usuario={usuario} stats={stats} recomendadas={recomendadas} />;
}

Pode consultarMDN: Promise.all

dica

Desenhe as dependências: stats não depende de ninguém, e recomendadas depende de usuario. Qual é o caminho mais longo?

solução comentada
export default async function Painel({ params }: { params: Promise<{ id: string }> }) {
  const { id } = await params;
  const [usuario, stats] = await Promise.all([
    getUsuario(id),        // 300 ms
    getEstatisticas(id),   // 200 ms, ao mesmo tempo
  ]);
  const recomendadas = await getRecomendadas(usuario.nivel); // + 250 ms: precisa do nível
  return <Tela usuario={usuario} stats={stats} recomendadas={recomendadas} />;
}

O tempo cai de 750 ms para 550 ms. O caminho mais longo é usuario e depois recomendadas (300 + 250). stats roda em paralelo e não entra na conta.

Próximo passo: se as recomendações são a parte lenta e menos importante, mova-as para um componente próprio dentro de <Suspense>. A página aparece em 300 ms e as recomendações chegam depois, por streaming.

Revisar · depois da solução

1 · Explique em voz alta
  1. Por que o tempo cai para 550 ms, e não para 300 ms?
  2. Por que dois await seguidos esperam um de cada vez, mas o Promise.all não?
  3. O que acontece com a página se getEstatisticas falhar?
respostas
  1. Porque recomendadas precisa do nível do usuário, então só começa depois que getUsuario termina: 300 + 250. Paralelizar só ajuda o que não depende de nada.
  2. A busca começa quando a função é chamada, e o await só pausa até ela terminar. Com dois await seguidos, a segunda chamada só acontece depois da primeira terminar. No Promise.all, as duas chamadas acontecem antes de qualquer pausa.
  3. A página inteira falha. O Promise.all rejeita assim que uma das promessas rejeita. Se as estatísticas forem opcionais, é preciso tratar isso (veja o passo 3).
2 · Caça ao bug

Três colegas mandaram versões diferentes. Calcule o tempo de cada uma e diga qual tem problema.

os erros

Rendering: por que toda rota do Gabarita é dinâmica decisão tomada (D111)

Em uma frase: Toda página é montada a cada acesso porque a proteção contra script injetado usa um código novo por acesso, e uma página gerada no build não tem esse código.

Escolha
Renderizar todas as rotas no servidor a cada requisição, com CSP de script-src sem 'unsafe-inline' e um nonce novo por requisição, gerado no middleware.
O que compra
Um <script> injetado por um atacante não carrega o nonce da resposta, então o navegador não o executa. O nonce só protege porque ninguém consegue adivinhá-lo.
O que custa
Saem o estático, o ISR, o cache de CDN e o PPR: toda página é montada a cada acesso. Isso conflita com a ideia de milhares de páginas públicas pré-geradas para busca.
Restrição que forçou
O nonce só existe durante a renderização de uma requisição. O HTML gerado no build leva o nonce de antes, que não bate com o do cabeçalho da requisição: o navegador bloqueia os scripts e a tela fica branca. Gerar a política por hash também não serve, porque ela é montada no middleware (edge), onde o node:crypto não existe.
Quando eu faria diferente
Sua vez.Pista: a “Munição” abaixo cita uma saída que preservaria o estático. Em que situação ela valeria a pena?

No mundo realO GitHub, que guarda o código e os segredos de milhões de desenvolvedores, usa uma CSP rígida nas páginas logadas. Um portal de notícias com milhões de visitas anônimas faz a escolha oposta: precisa do cache da CDN para aguentar picos de tráfego, e por isso protege as páginas públicas de outro jeito. A decisão segue o que a página guarda e quanta gente a visita.

Escolha

O que compra
O contrato AIAnalysis/AuditResponse é um só nos dois lados: mudar o tipo quebra o build dos dois juntos, em vez de divergir sem aviso. O Turborepo ainda cacheia as tasks pelo hash das entradas.

  3. Por que o Gabarita não usa ISR, unstable_cache nem "use cache"?
    ver resposta

    Porque a CSP usa nonce por request, e o Next só consegue injetar o nonce durante a renderização no servidor — página gerada no build não tem request, logo não tem nonce. Com nonce, toda rota é dinâmica: estático, ISR, cache de CDN e PPR saem do jogo. Sobra o que funciona por request: cache() do React pra deduplicar consultas, revalidatePath depois de mutação, streaming com loading.tsx, e tirar trabalho lento do render (after()). A alternativa que preservaria estático é SRI (hash dos scripts no build), ainda experimental.

  4. No Ally AI, as páginas buscam dados no cliente, com axios, numa API Express em outro domínio. Por que essa escolha faz sentido, e qual seria o próximo passo?
    ver resposta

    A API é um Express em outro domínio e o cookie de sessão é dela; quem tem esse cookie é o navegador, então buscar no cliente com withCredentials é o caminho direto. O próximo passo natural é TanStack Query no cliente (cache por chave, deduplicação, refetch ao voltar à aba) ou um BFF — Route Handlers no próprio Next, mesmo domínio, que repassam pra API — e aí Server Components buscando no servidor. A resposta sênior nomeia a restrição antes da solução.

  5. Usuários reclamam que “o botão de responder demora” numa página de questão. Como você investiga?
    ver resposta

    É sintoma de INP. Primeiro dado de campo (RUM — no Gabarita, o tracing do Sentry; ou CrUX), pra saber se é geral ou de um tipo de aparelho, e qual o p75. Depois reproduzir em laboratório (DevTools, CPU com throttling) e quebrar a interação nas três fases: input delay (thread principal ocupada — script carregando, hidratação), processing (o handler faz trabalho demais — quebrar e ceder a thread) e presentation delay (re-render grande, DOM enorme). Só então otimizar o que a medição apontou.

  6. Uma página de listagem busca os dados no cliente (useEffect + fetch) e pisca em “carregando” a cada visita. Como você refatora no App Router?
    ver resposta

    Passo a passo: (1) a página vira Server Component async e busca direto no servidor, sem useEffect; (2) consultas independentes viram Promise.all, pra não formar cascata; (3) o que demora fica atrás de uma fronteira Suspense (ou loading.tsx), e a casca da página já aparece; (4) se o dado é compartilhado entre usuários, a função ganha 'use cache' com cacheLife e cacheTag, e a Server Action que muda o dado invalida a tag; dado do usuário não vai pra cache compartilhado; (5) o cliente fica só com a ilha que precisa de estado, como filtro e ordenação, recebendo os dados por props.

    Ganhos mensuráveis: menos JavaScript enviado, uma ida a menos à rede no caminho crítico e LCP melhor. O trade-off: o servidor passa a renderizar a cada visita (ou a depender do cache), e a interatividade fina continua no cliente.

  7. O que são LCP, INP e CLS, quais os limites de “bom” e o que você faz pra melhorar cada um?
    ver resposta

    LCP (Largest Contentful Paint) é quando o maior elemento visível aparece; bom é até 2,5 s. Melhora com a imagem principal carregada com prioridade (e nunca com loading="lazy"), HTML renderizado no servidor, fontes por next/font e menos TTFB. INP (Interaction to Next Paint) é a latência das interações ao longo da visita; bom é até 200 ms. Melhora quebrando tarefas longas, adiando trabalho não urgente (useTransition), mandando menos JavaScript e evitando re-render pesado. CLS (Cumulative Layout Shift) é o quanto o layout pula; bom é até 0,1. Melhora reservando espaço (dimensões ou aspect-ratio nas imagens, skeletons com a mesma altura) e evitando inserir conteúdo acima do que a pessoa está lendo.

    O número que vale é o p75 de dado de campo, de usuários reais; o Lighthouse é laboratório e serve pra achar a causa.
