AI + Full Stack Integration

~8h · a chamada ao modelo é a parte fácil; o difícil é tudo em volta dela

Uma vaga de Frontend/Design Engineer com foco em IA não te pede pra treinar modelo — pede pra entregar o produto em volta dele: quem pode chamar (auth), como a resposta chega na tela (streaming), onde mora o arquivo que o usuário mandou (upload e storage), o que acontece quando o trabalho demora mais que um request (fila), onde a saída fica guardada (Postgres) e como provar que tudo isso funciona sem gastar cota de API em cada teste. A boa notícia: o Gabarita e o Ally AI já fazem boa parte disso. Esta página dá nome ao que você fez e aponta o arquivo de cada exemplo — e indica o próximo passo do roadmap em cada projeto: streaming, embeddings/pgvector e Playwright.

  • Next.js — route.js (Route Handlers)
    A referência do arquivo que vira endpoint no App Router: métodos, params como promessa, cookies, webhooks e a seção de Streaming com ReadableStream puro.
    Ler trechos · ~20 minLeia Parameters, Streaming, Request Body FormData, Webhooks e Segment Config. Pule Cookies/Headers se já usa.
    nextjs.org · oficial
    Resumo aqui na página

    Um route.ts dentro de app/ vira endpoint HTTP usando as APIs padrão da web — Request e Response. Isso inclui devolver um ReadableStream: streaming de LLM no Next não exige biblioteca nenhuma, só a Web Streams API.

    O básico que cai em entrevista
    • Métodos suportados: GET, POST, PUT, PATCH, DELETE, HEAD e OPTIONS. Se você não define OPTIONS, o Next implementa sozinho e preenche o header Allow.
    • O primeiro argumento é um NextRequest (extensão do Request, com cookies e nextUrl já parseados). O segundo traz params — que desde o Next 15 é uma promessa: const { id } = await params.
    • Também desde o 15, GET deixou de ser estático por padrão e passou a ser dinâmico. Cache em route handler agora é opt-in (export const revalidate = 60, ou Cache Components).
    • Route handlers usam a mesma configuração de segmento que páginas: dynamic, revalidate, runtime ('nodejs' ou edge) etc.
    Streaming: as duas formas mostradas
    • Com o AI SDK: o handler recebe as mensagens, chama streamText e devolve a resposta já em formato de stream. A doc mostra o exemplo com OpenAI; o modelo é trocável.
    • Com Web APIs puras: um gerador assíncrono produz pedaços (TextEncoder transforma string em bytes), e uma função converte o iterador em ReadableStream — o pull(controller) pede o próximo valor, faz enqueue ou close. O handler só faz return new Response(stream).
    return new ReadableStream({
  async pull(controller) {
    const { value, done } = await iterator.next()
    if (done) controller.close()
    else controller.enqueue(value)
  },
})

    O ponto conceitual: “essas abstrações usam as Web APIs pra criar o stream”. Trocar o iterador por um iterador sobre os chunks do provider de LLM é o caso real.

    Outros recortes úteis pro roadmap
    • FormData: await request.formData() lê upload multipart; como tudo chega string, a doc sugere validar com zod-form-data.
    • Webhooks: leia o corpo com request.text() (cru, pra verificar assinatura). Diferente do Pages Router, não precisa desligar bodyParser.
    • CORS: headers na própria Response pra um handler; pra vários, use Proxy (o antigo middleware) ou next.config.
    • Respostas não-UI: RSS, XML, qualquer Content-Type — sitemap, robots e imagens OG já têm convenção própria.

    Frase de entrevista: “No App Router, um endpoint de streaming é só um Route Handler que devolve um ReadableStream. Eu sei fazer com o SDK e sem ele — o que muda é quem converte os chunks do modelo em bytes.”

  • Gemini API — Embeddings
    Os dois projetos já usam @google/genai; este é o mesmo SDK gerando vetores com embedContent — o primeiro passo de qualquer RAG ou busca semântica.
    Ler trechos · ~20 minLeia o exemplo em JavaScript, task types, controle de dimensão e casos de uso. Pule a parte de multimodal se o seu caso é só texto.
    ai.google.dev · oficial
    Resumo aqui na página

    Embedding é o texto (ou imagem, PDF, áudio) convertido num vetor de números em que coisas parecidas ficam perto. É a matéria-prima de RAG, busca semântica, classificação e clustering — e sai do mesmo SDK @google/genai que o Gabarita e o Ally AI já usam.

    Modelos e chamada
    • gemini-embedding-2: multimodal (texto, imagem, vídeo, áudio, PDF), até 8.192 tokens de entrada.
    • gemini-embedding-001: só texto, até 2.048 tokens — o legado.
    • A chamada é ai.models.embedContent({ model, contents }) e a resposta traz embeddings.
    • Os espaços vetoriais dos dois modelos são incompatíveis: trocar de modelo obriga a re-gerar todos os vetores guardados. Guarde qual modelo gerou cada vetor.
    Task type: o mesmo texto, vetores diferentes conforme o uso
    Task typePra quê
    RETRIEVAL_DOCUMENT / RETRIEVAL_QUERYbusca: um pro que é guardado, outro pra pergunta do usuário
    SEMANTIC_SIMILARITYrecomendação, detecção de duplicata
    CLASSIFICATIONcategorizar por rótulos pré-definidos
    CLUSTERINGagrupar por semelhança, achar anomalia
    QUESTION_ANSWERING, FACT_VERIFICATION, CODE_RETRIEVAL_QUERYcasos específicos de recuperação

    No 001 isso é o parâmetro taskType; no 2, a instrução vai no próprio texto (ex.: "task: search result | query: ..."). Documento e pergunta embutidos com o mesmo propósito de busca casam melhor.

    Dimensão: o trade-off de armazenamento
    • Padrão de 3.072 dimensões; configurável de 128 a 3.072 com outputDimensionality. Recomendados: 768, 1.536 ou 3.072.
    • O embedding-2 normaliza sozinho quando você trunca; no 001 você normaliza na mão (divide o vetor pela norma).
    • Pro pgvector, 768 dimensões dá 4 × 768 + 8 ≈ 3 KB por linha — conta que você deve saber fazer antes de escolher.
    Custo e armazenamento
    • A Batch API custa 50% do preço normal — bom pra indexar o acervo inteiro de uma vez, onde latência não importa (um job no worker, por exemplo).
    • Pra guardar, a doc cita serviços do Google Cloud (AlloyDB, Cloud SQL, BigQuery, Vector Search) e bancos vetoriais de terceiros. O Postgres com pgvector entra na mesma categoria.

    Frase de entrevista: “Antes de escolher a dimensão do embedding eu faço a conta de armazenamento, e guardo o nome do modelo junto do vetor — trocar de modelo significa re-indexar tudo.”

  • pgvector — README
    A extensão que transforma o Postgres que você já tem num banco vetorial: tipo vector, operadores de distância, HNSW/IVFFlat, filtro com índice aproximado.
    Ler trechos · ~30 minLeia Getting Started, Querying, Indexing (HNSW e IVFFlat) e Filtering. Half-precision, binary e sparse são consulta pra quando escala virar problema.
    github.com · oficial
    Resumo aqui na página

    pgvector põe busca por similaridade dentro do Postgres, ao lado dos seus dados relacionais, com transação, backup e replicação de graça. Busca exata por padrão; índices aproximados (HNSW, IVFFlat) trocam um pouco de precisão por muita velocidade.

    O mínimo pra começar
    CREATE EXTENSION vector;
CREATE TABLE items (id bigserial PRIMARY KEY, embedding vector(3));
SELECT * FROM items ORDER BY embedding <-> '[3,1,2]' LIMIT 5;
    • A coluna vector guarda até 16.000 dimensões, mas o índice (HNSW ou IVFFlat) só aceita até 2.000; halfvec indexa até 4.000. O Gemini devolve 3.072 por padrão, então sem tratar isso o índice nem é criado. Saídas: pedir menos dimensões (outputDimensionality), indexar a coluna como halfvec (cast na expressão do índice) ou deixar sem índice se a tabela for pequena. Cada vetor ocupa 4 × dimensões + 8 bytes.
    • Operadores: <-> L2 (euclidiana), <#> produto interno negativo (multiplique por -1), <=> distância de cosseno, <+> L1, e <~>/<%> pra vetores binários.
    • Pra embeddings de texto, cosseno é o mais comum; com vetor normalizado, produto interno dá o mesmo ranking e é mais rápido.
    Exata vs. aproximada
    • Sem índice: varre a tabela inteira, recall perfeito, lento em tabela grande (dá pra paralelizar com max_parallel_workers_per_gather).
    • Com índice aproximado: rápido, mas pode devolver resultados diferentes da busca exata. Só é usado com ORDER BY ... LIMIT.
    HNSWIVFFlat
    Estruturagrafo em camadasvetores divididos em listas
    Consultamelhor relação velocidade/recallmais lenta
    Buildmais lento, mais memória; sem fase de treinorápido, pouca memória; crie depois de ter dados
    Ajustem (16), ef_construction (64); na consulta hnsw.ef_search (40)lists ≈ linhas/1000 até 1M; na consulta ivfflat.probes (1)
    A pegadinha: filtro + índice aproximado
    • O filtro (WHERE categoria = ...) é aplicado depois do scan do índice. Se 10% das linhas casam e ef_search é 40, sobram em média ~4 resultados — você pediu 10 e recebe 4.
    • Saídas: iterative index scan (SET hnsw.iterative_scan = strict_order ou relaxed_order, com teto em hnsw.max_scan_tuples), índice parcial por categoria (CREATE INDEX ... WHERE category_id = 123), ou particionar a tabela.
    Quando escalar virar problema
    • halfvec (meia precisão) corta o armazenamento pela metade; binary_quantize encolhe mais ainda, com re-ranking pelo vetor original pra recuperar recall.
    • Carga em massa com COPY, índice criado depois da carga, maintenance_work_mem suficiente pro grafo caber em memória.

    Frase de entrevista: “Antes de adicionar um banco vetorial, eu adicionaria uma extensão. pgvector no Postgres que já existe mantém o embedding na mesma transação e no mesmo backup que o dado — e eu sei que filtro com HNSW pode devolver menos linhas do que o LIMIT.”

  • Amazon S3 — Uploading objects with presigned URLs
    Como deixar o navegador mandar o arquivo direto pro bucket, sem credencial AWS e sem passar o corpo pelo seu servidor. O mesmo vale pro R2, que fala a API do S3.
    Ler trechos · ~15 minLeia a introdução, a parte de SDK (o exemplo é Python, mas o conceito é o mesmo no @aws-sdk) e o troubleshooting de SignatureDoesNotMatch. Pule o Visual Studio.
    docs.aws.amazon.com · oficial
    Resumo aqui na página

    Uma URL pré-assinada é uma permissão de uso único no tempo: o servidor, que tem credencial, assina uma URL que autoriza exatamente um PUT numa key, por um prazo. O navegador manda o arquivo direto pro bucket — sem credencial AWS e sem o corpo passar pelo seu servidor.

    O que a URL carrega (e o que não carrega)
    • Ela está limitada às permissões de quem a criou: se o usuário/role que assinou não pode gravar naquele bucket, a URL também não pode.
    • Se já existe objeto com a mesma key, o upload substitui o anterior. Depois do upload, o dono do bucket é o dono do objeto.
    • Prazo: pelo CLI ou SDK, até 7 dias. Na prática, pra upload de navegador, minutos bastam — quanto menor, menor a janela se a URL vazar.
    O fluxo
    1. O cliente pede uma URL ao seu back-end (que autentica o usuário e decide a key).
    2. O back-end gera a URL com o SDK pra operação put_object/PutObjectCommand, com bucket, key, ContentType e expiração.
    3. O cliente faz PUT do arquivo nessa URL, com o mesmo Content-Type usado na assinatura.
    4. O cliente avisa o back-end que terminou; o back-end registra a key (e, num app como o Gabarita, enfileira o processamento).
    SignatureDoesNotMatch: as causas listadas
    • Relógio da máquina dessincronizado.
    • URL modificada (ou não colocada entre aspas no curl, quebrando caracteres especiais).
    • URL expirada.
    • Content-Type do upload diferente do assinado — a mais comum.
    • Região errada do bucket.
    O que isso muda no seu desenho
    • O limite de corpo da função (o bodySizeLimit de Server Action, o limite de payload de serverless) deixa de importar pro arquivo.
    • A validação muda de lugar: o servidor não viu os bytes, então tipo e tamanho precisam estar amarrados na assinatura e ser conferidos depois do upload, antes de processar.
    • O exemplo da doc é em Python, mas o conceito é idêntico no @aws-sdk/s3-request-presigner — e serve pro Cloudflare R2, que implementa a API do S3.

    Frase de entrevista: “Arquivo grande não passa pela minha função: eu assino uma URL curta pra uma key específica, o navegador sobe direto pro bucket, e eu valido o objeto antes de processar.”

  • AI SDK — Testing
    Modelos falsos (MockLanguageModel) e simulateReadableStream: a referência de como testar streaming e saída estruturada sem chamar o modelo de verdade.
    Ler inteiro · ~15 minPágina curta, quase só código. Mesmo sem usar o AI SDK, o exemplo de Route Handler que devolve SSE simulado serve pra qualquer front que consome stream.
    ai-sdk.dev · oficial
    Resumo aqui na página

    Testar código que chama LLM é difícil por três motivos que a doc nomeia: o modelo é não determinístico, é lento e é caro. A resposta é a mesma de qualquer dependência externa: um modelo falso que devolve exatamente o que o teste mandou.

    As peças (de ai/test e ai)
    • MockLanguageModelV4 — implementa a especificação de modelo de linguagem; você fornece doGenerate (resposta inteira) ou doStream (resposta em pedaços).
    • MockEmbeddingModelV4 — o mesmo pra embeddings.
    • simulateReadableStream — cria um stream a partir de uma lista de chunks, com atraso configurável (initialDelayInMs, chunkDelayInMs).
    • mockId (id incremental) e mockValues (devolve um valor diferente a cada chamada — útil pra simular retry).
    Os cenários cobertos
    • Texto inteiro e texto em stream: o stream simulado é uma sequência explícita — text-start, vários text-delta, text-end e um finish com motivo e uso de tokens. O teste controla cada pedaço.
    • Saída estruturada: o mock devolve o JSON e o schema Zod valida — inclusive em stream, montando o objeto aos poucos.
    • Agente com ferramenta: uma lista de respostas, a primeira pedindo uma tool call e a segunda dando a resposta final — testa o loop multi-turno.
    O exemplo mais útil pro front: SSE simulado num Route Handler

    Um POST do Next devolve simulateReadableStream com linhas data: {...}\n\n, passado por TextEncoderStream, com Content-Type: text/event-stream e Cache-Control: no-cache. Serve pra desenvolver e testar a UI de streaming (loading, texto chegando, fim, erro) sem gastar um token — e com atraso controlado, pra ver os estados intermediários.

    O que levar mesmo sem usar o AI SDK
    • O Gabarita faz o equivalente com createFakeAIProvider atrás da interface AIProvider; o Ally AI com vi.mock("@google/genai"). A ideia é a mesma: fixar a saída do modelo e testar o que o seu código faz com ela.
    • O que falta nos dois é o lado do stream: um teste que entrega chunks com atraso e verifica a UI no meio do caminho.

    Frase de entrevista: “O modelo é uma dependência não determinística e cara, então nos testes ele é um fake que eu controlo — inclusive o stream, chunk por chunk, pra testar os estados intermediários da UI.”

  • Playwright — Mock APIs
    page.route + route.fulfill, editar resposta real, gravar/reproduzir HAR e mockar WebSocket — tudo o que um E2E de fluxo de IA precisa pra ser rápido e reprodutível.
    Ler inteiro · ~15 minPágina curta. A seção de WebSocket é exatamente o caso do saldo de créditos do Ally AI.
    playwright.dev · oficial
    Resumo aqui na página

    O Playwright intercepta, observa, modifica e falsifica tráfego de rede (HTTP, HTTPS, fetch, XHR e WebSocket) do navegador. Pra fluxo de IA, isso significa E2E de verdade na sua UI com a resposta do back-end fixada — rápido, grátis e reprodutível.

    Falsificar a resposta: page.route + route.fulfill
    await page.route('*/**/api/v1/fruits', async route => {
  const json = [{ name: 'Strawberry', id: 21 }];
  await route.fulfill({ json });
});

    Toda chamada que casa o padrão é interceptada e não chega ao servidor. Troque fruits por /api/audit e o JSON por um relatório de auditoria e você tem o E2E do Ally AI sem Puppeteer nem Gemini rodando.

    Corrigir a resposta real: route.fetch

    Quando você quer o servidor de verdade mas precisa ajustar um campo: const response = await route.fetch(), altera o JSON e devolve com route.fulfill({ response, json }). Útil pra forçar um caso raro (lista vazia, item com erro) em cima de dado real.

    Gravar e reproduzir: HAR
    • page.routeFromHAR('./hars/x.har', { url, update: true }) grava o tráfego real num arquivo HAR.
    • Com update: false, o teste passa a ser servido pelo arquivo. A correspondência é estrita por URL e método, e entre candidatos ganha o que casar mais headers.
    • Dá pra editar o conteúdo gravado e versionar no repositório — uma resposta real do modelo, congelada como fixture.
    WebSocket
    • page.routeWebSocket(url, ws => ...) mocka a conexão inteira: você responde mensagens com ws.send.
    • Ou intercepta no meio: ws.connectToServer() liga ao servidor real e você filtra/altera mensagens nos dois sentidos.
    • No Ally AI, é o caminho pra testar o saldo atualizando quando chega credits_updated — sem Stripe, sem webhook.

    Frase de entrevista: “No E2E eu não chamo o modelo: intercepto a rota com page.route e sirvo uma resposta real gravada. O teste fica determinístico e cobre o que é meu — a UI, os estados e a navegação.”

    Resumo em português do recorte indicado · original em playwright.dev

Eu faria assim: uma coluna embedding vector(768) (o Gemini aceita outputDimensionality), um job no worker que já existe gerando o embedding quando a questão é criada, um índice HNSW com vector_cosine_ops e a consulta com <=> junto dos filtros SQL de sempre. Guardo o nome do modelo ao lado do vetor, porque trocar de modelo obriga a reindexar tudo. Cuidado de entrevista: o índice só aceita até 2.000 dimensões em vector, e o padrão do Gemini é 3.072.

In English: “Not in production. I'd add a vector(768) column using the Gemini outputDimensionality option, embed in a background job, index with HNSW and cosine ops, and query with <=> plus the usual SQL filters, storing the model name beside the vector because switching models means reindexing. The index limit for vector is 2,000 dimensions.”

Pra treinar: exercício 9 (RAG com pgvector).

Você já testou um fluxo de IA com Playwright? não usei em produção

Em voz alta: Não: nos dois projetos uso Testing Library e Vitest com a IA trocada por um provedor falso, o que deixa o teste determinístico. Eu faria o end-to-end assim: page.route devolvendo um corpo SSE gravado (a resposta do modelo vira um arquivo), asserções nos estados da tela (pensando, escrevendo, pronto, erro), e o @axe-core/playwright no final. Nunca chamo o modelo de verdade no CI. Por quê: o modelo é lento, caro e não determinístico, e o que quero testar é a interface, não o modelo.

In English: “Not yet; I use a fake provider with Testing Library and Vitest. For end-to-end I'd intercept the request with page.route and return a recorded SSE body, assert on each UI state, add axe at the end, and never call the real model in CI, because I'm testing the interface, not the model.”

Pra treinar: exercício 6 (Playwright com SSE gravado).

Munição da sua entrevista · a explicação que fica pronta enquanto o aluno lê (Gabarita)

“Tirei a IA do caminho crítico do render: a página agenda a geração da explicação com after() assim que a questão abre, então ela fica pronta enquanto o aluno lê (explain-prefetch.ts). Uma trava atômica no Postgres — updateMany condicional, não select seguido de update — garante que duas abas resultem numa chamada só (explain.ts L66–74). No cliente, polling escalonado e um estado final explícito, testado com fake timers. O próximo passo é streaming.”

Por que isso importa: é uma história de full stack de IA inteira — latência percebida, custo de cota, concorrência no banco, estado da UI e teste determinístico — num fluxo só.

Responda em voz alta · só depois abra o gabarito
  1. Semáforo em memória (como no Ally AI) e fila durável com worker (como o pg-boss no Gabarita): o que cada um resolve?
    ver resposta

    O semáforo controla quantas tarefas rodam ao mesmo tempo dentro de um processo — simples, sem infraestrutura, ótimo pra proteger CPU e memória de um recurso pesado como o Chromium. A fila durável decide onde e quando o trabalho roda: o request só enfileira e responde, o worker processa, e o job sobrevive a um restart porque mora no banco. Os dois se combinam: fila pra durabilidade, limite de concorrência no worker pra proteger o recurso.

  2. Streaming de tokens deixa a resposta do LLM mais rápida?
    ver resposta

    Não a latência total — o modelo gera os mesmos tokens no mesmo tempo. Muda o tempo até o primeiro conteúdo útil: em vez de 10 segundos de spinner, o texto começa em meio segundo. É uma melhoria de latência percebida. A validação estruturada (Zod) roda sobre o texto completo, então a UI precisa saber mostrar texto parcial e tratar um stream que termina inválido ou é cortado no meio.

  3. Quando vale a pena usar URL pré-assinada pra upload em vez de mandar o arquivo pela sua Server Action?
    ver resposta

    Quando o arquivo é grande ou a função é serverless: o corpo inteiro passando pelo seu servidor ocupa memória, conta no limite de corpo (o Gabarita configura bodySizeLimit: "25mb") e na duração da função. Com URL pré-assinada, o servidor só assina uma permissão curta e limitada (uma key, um método, um prazo); o navegador manda direto pro bucket. A validação de tipo e tamanho vai pra assinatura (content-type amarrado) e pra um passo de confirmação depois do upload.

  4. O Gabarita não usa pgvector. Ele faz RAG?
    ver resposta

    Faz grounding, não RAG vetorial. fetchStyleReferences recupera questões reais por filtro relacional (especialidade e tema) e as põe no prompt; o resumo de diretriz é ancorado no texto completo da fonte e só sai se a citação existir literalmente nele. Quando o critério de recuperação é exato e conhecido, SQL comum é a ferramenta certa. Embedding passa a valer quando a pergunta é “o que é parecido com isto?” — questões semelhantes à que o aluno errou, por exemplo.

  5. Como você testaria, sem chamar o Gemini, o fluxo “responder questão → ver explicação” de ponta a ponta?
    ver resposta

    Em dois níveis. Integração (o que o Gabarita já faz): RTL com a action mockada e fake timers, cobrindo os estados “escrevendo”, “pronto” e o fallback. E2E: Playwright contra o app real com o AIProvider fake selecionado por variável de ambiente, ou interceptando a chamada com page.route quando ela parte do navegador. O princípio é o mesmo nos dois: o modelo é uma dependência não determinística e cara, então o teste fixa a saída dele e verifica o que o seu código faz com ela.

  6. Como você protege um endpoint de IA e uma rota de upload?
    ver resposta

    Quem é a pessoa: sessão em cookie httpOnly, Secure e SameSite, verificada no servidor (Server Component, Server Action e Route Handler), e não só no proxy, que é uma primeira barreira. O que ela pode: autorização por recurso (o id pedido é dela?). Quanto pode gastar: o custo do LLM é superfície de abuso, então rate limit por usuário e IP, e um orçamento de tokens ou créditos reservado de forma atômica e devolvido se a chamada falhar (o Ally AI faz isso).

    Upload: validar o tipo pelo conteúdo (os primeiros bytes), não pelo nome nem pelo Content-Type; limite de tamanho; nome gerado por você; armazenamento fora da raiz do site (S3 ou R2), de preferência com URL pré-assinada de curta duração, pro arquivo não passar pela função serverless; processamento assíncrono em fila. E o texto de um arquivo enviado é dado não confiável pro modelo: pode conter instrução (prompt injection), então a saída dele passa pelas mesmas validações de sempre.
