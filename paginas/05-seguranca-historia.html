05

Segurança, performance & a história do projeto

~8h · a semana de fechar com força

Você já implementou defesa contra IDOR, invalidação de sessão e uma CSP real — a maioria dos plenos nunca chegou perto disso. Esta semana é sobre dar nome OWASP pro que você já fez, e depois transformar as decisões documentadas do seu projeto em respostas de entrevista prontas.

Tópicos

Onde estudar (grátis)

  • OWASP Top 10 — A01 Broken Access Control
    A categoria que inclui IDOR, explicada pela fonte que toda empresa séria de segurança cita.
    Ler inteiro · ~10 minPágina curta. Foque na lista de exemplos de ataque e no bloco How to Prevent — são oito bullets que viram resposta pronta.
    owasp.org · oficial, gratuito
    Resumo aqui na página

    Broken Access Control é a categoria nº1 do OWASP Top 10 — não por ser exótica, mas por ser fácil de introduzir sem perceber: a autenticação funciona, e a checagem de quem pode ver o quê é que falta ou está incompleta.

    O que conta como quebra de controle de acesso
    • Violar o princípio do menor privilégio: acesso liberado além do necessário pra função.
    • Contornar checagem editando a URL, o estado interno da aplicação, ou o próprio HTML (esconder botão na interface não é controle de acesso).
    • IDOR — permitir ver/editar registro de outro usuário só trocando um ID.
    • Elevar privilégio: agir como admin estando logado como usuário comum, ou agir como usuário estando deslogado.
    • CORS mal configurado permitindo acesso de origem não confiável.
    • Forçar navegação pra páginas autenticadas sem estar logado.
    Como prevenir (os oito da doc)
    1. Negar por padrão, exceto recursos públicos explícitos.
    2. Implementar controle de acesso uma vez e reusar em toda a aplicação, minimizando CORS.
    3. Modelar controle de acesso como dono do registro, não achar que o papel do usuário decide sozinho quem vê qual linha.
    4. Regras de negócio de domínio (limites de taxa, cota) aplicadas no servidor, não confiáveis vindas do cliente.
    5. Desativar listagem de diretório e não deixar metadado (.git, backup) acessível.
    6. Logar falhas de controle de acesso e alertar em repetição.
    7. Rate limit em APIs pra reduzir dano de automação/scripts.
    8. Invalidar token de sessão no servidor no logout — sessão sem estado dificulta isso (Semana 5, JWT).

    O bloco de exemplos de ataque da própria página é a resposta pronta pra "me dá um exemplo real": trocar acct=104 por acct=105 numa URL sem checagem de posse é o exemplo mais citado — e é literalmente o padrão que o Gabarita corrige nas D109.

  • IDOR Prevention Cheat Sheet
    O padrão “prove posse na mesma query” que você já usa em posse-de-sessao.test.ts está descrito aqui como prática recomendada — ótima confirmação pra citar.
    Ler inteiro · ~8 minCheat sheet, leitura direta. O que importa: por que “esconder o ID” não é defesa, e por que a checagem de posse precisa estar dentro da query, não num if antes dela.
    cheatsheetseries.owasp.org · oficial, gratuito
    Resumo aqui na página

    IDOR não se resolve escondendo o ID — se resolve provando posse dentro da mesma consulta que busca o recurso.

    • Por que UUID não é a correção: dificulta adivinhar (segurança por obscuridade), mas se o ID vazar em qualquer lugar (log, URL compartilhada, resposta de outra API), o acesso continua liberado pra quem não é dono.
    • A correção certa: toda consulta que busca um recurso por ID inclui o dono na mesma cláusula — WHERE id = ? AND userId = ?, nunca WHERE id = ? seguido de um if separado checando posse depois. Separar em duas etapas cria uma janela pra a próxima função esquecer a segunda.
    • Mapear ID pra sessão é a alternativa mais forte quando dá: em vez do cliente mandar o ID de um item de carrinho, o servidor resolve a partir da sessão autenticada — o cliente não tem como nem tentar outro ID.
    • Testes de autorização deveriam existir por função, não só por tela: uma tela pode chamar três Server Actions, e testar só a tela não garante que as três provam posse.
    • Log de tentativa de acesso a recurso de outro dono é sinal de ataque em andamento, não só bug.

  • Session Management Cheat Sheet
    Cobre invalidação de sessão e rotação de token — o mesmo problema que seu carimbo credenciaisAlteradasEm resolve.
    Ler trechos · ~20 minÉ longa. Leia Session ID Properties, Session Management Implementation (atributos de cookie: HttpOnly, Secure, SameSite) e Session Expiration & Renewal. Pule as seções específicas de frameworks Java.
    cheatsheetseries.owasp.org · oficial, gratuito
    Resumo aqui na página

    Sessão é o estado que liga um usuário autenticado às requisições seguintes. O que decide se ela é segura são os atributos do cookie, o tamanho e a fonte do ID, e quando ela expira.

    Session ID Properties
    • O ID precisa ter entropia suficiente (gerado por um CSPRNG, não sequencial nem previsível) — sequencial vira IDOR de sessão.
    • Não deve carregar significado (nem nome, nem role, nem timestamp legível) — é só uma chave opaca pro servidor.
    Session Management Implementation — atributos do cookie
    AtributoO que evita
    HttpOnlyJavaScript não lê o cookie — mitiga roubo de sessão via XSS
    Secureo cookie só viaja em HTTPS — mitiga interceptação em rede
    SameSite=Lax/Stricto cookie não vai em requisição cross-site — mitiga CSRF
    Path/Domain estreitosreduz onde o cookie é enviado automaticamente

    Regenerar o ID de sessão no login (não reaproveitar um ID pré-autenticação) evita session fixation — um atacante que force a vítima a usar um ID conhecido antes do login não ganha nada, porque o ID muda ao autenticar.

    Session Expiration & Renewal
    • Idle timeout (expira por inatividade) e timeout absoluto (expira depois de X horas, mesmo em uso) são complementares — um sozinho não cobre os dois riscos.
    • Logout precisa invalidar no servidor, não só apagar o cookie no cliente — com JWT sem estado isso exige denylist ou um carimbo tipo credenciaisAlteradasEm (a saída que a Semana 5 já cobre).
    • Trocar senha, e-mail ou papel deveria encerrar as outras sessões — é exatamente a D107 do Gabarita.

  • Learn Core Web Vitals
    Curso gratuito do Google sobre LCP, INP e CLS — com o porquê técnico de cada métrica, não só o número.
    Ler trechos · ~1hSão 10+ módulos. Faça só LCP, INP e CLS, nessa ordem, e pare. Os módulos de otimização só valem quando você for otimizar de verdade — não pra entrevista.
    web.dev · oficial, Google
    Resumo aqui na página

    Core Web Vitals são três métricas que tentam capturar "a página parece rápida" do jeito que o usuário sente, não do jeito que o servidor mede.

    LCP — Largest Contentful Paint

    Tempo até o maior elemento visível (geralmente imagem hero ou bloco de texto) terminar de renderizar. Bom: ≤2.5s. As causas mais comuns de LCP ruim: servidor lento pra responder, CSS/JS bloqueando o render, imagem não otimizada ou carregada tarde demais (falta fetchpriority="high" ou pré-carga).

    INP — Interaction to Next Paint

    Substituiu o antigo FID em 2024: mede o atraso entre qualquer interação (clique, toque, tecla) e o próximo frame pintado na tela — olhando a pior interação da visita inteira, não só a primeira. Bom: ≤200ms. A causa raiz quase sempre é trabalho síncrono longo na thread principal — handler pesado, re-render caro, terceiro script bloqueando. Conecta direto com o event loop (Semana 1): uma tarefa que não devolve o controle trava a resposta ao clique.

    CLS — Cumulative Layout Shift

    Soma quanto o layout "pula" sem o usuário ter feito nada — imagem sem width/height que empurra o texto quando carrega, fonte que troca de largura, banner que injeta acima do conteúdo. Bom: ≤0.1. Correção: reservar o espaço final antes de o conteúdo chegar (dimensões explícitas, font-display: optional ou pré-carregar fonte, aspect-ratio em mídia).

    O que isso significa pra você

    Nenhuma das três métricas é sobre "quão rápido o servidor responde" isoladamente — são sobre a experiência percebida. Um TTFB ótimo com LCP ruim é comum quando o servidor responde rápido mas o navegador ainda precisa baixar CSS bloqueante antes de pintar. As três juntas formam a régua que o Google usa (Lighthouse, PageSpeed Insights) e que aparece em ranking de busca.

  • MDN — Content Security Policy
    Referência de cada diretiva CSP — leia lado a lado com o seu próprio csp.ts.
    Ler trechos · ~25 minLeia o guia conceitual até a seção de nonce e hash (que é o seu caso) e a de unsafe-inline / strict-dynamic. A tabela com todas as diretivas é referência — não leia de ponta a ponta.
    developer.mozilla.org · oficial
    Resumo aqui na página

    Content Security Policy é uma lista de origens permitidas por tipo de recurso, entregue por header. Ela existe pra conter o dano depois que uma injeção de HTML/JS já aconteceu — é defesa em profundidade, não a única defesa contra XSS.

    O básico
    • Header Content-Security-Policy com diretivas tipo script-src 'self' (só scripts do próprio domínio), img-src, connect-src etc. default-src é o fallback pras diretivas não especificadas.
    • Sem CSP, um <script> injetado por um campo mal sanitizado roda com os mesmos privilégios do site inteiro. Com script-src restrito, o navegador recusa executar qualquer script que não bata com a política — inclusive um injetado.
    Nonce e hash — as duas formas de permitir script inline
    • Hash (script-src 'sha256-...'): só funciona pra script com texto exatamente conhecido de antemão — calculado uma vez, fixo em config. Serve bem pra sites estáticos.
    • Nonce (script-src 'nonce-abc123'): um valor aleatório gerado a cada resposta, colocado no header e repetido no atributo nonce do script. Serve quando o conteúdo do script muda por request — como o payload inline que o Next.js injeta pra hidratar Server Components, que é diferente toda vez.
    strict-dynamic

    Propaga a confiança: um script com nonce válido pode carregar outros scripts (via <script src> dinâmico) e esses herdam a confiança, sem precisar estar cada um na allowlist. Isso é o que permite que os chunks JS que o Next carrega depois do payload inicial também rodem — e, como efeito colateral, o navegador passa a ignorar allowlist de domínio (script-src https://cdn.x.com), que é a parte de uma CSP mais fácil de contornar (um domínio confiável pode hospedar um script vulnerável a JSONP, por exemplo).

    unsafe-inline — por que evitar

    Libera qualquer script inline, inclusive o injetado por um atacante — anula praticamente toda a proteção contra XSS que a CSP daria. Quando um navegador entende nonce/hash, ele já ignora unsafe-inline automaticamente (fica só como fallback pra navegador antigo).

    Report-only e outras diretivas úteis
    • Content-Security-Policy-Report-Only: só reporta violação (via report-uri/report-to), não bloqueia — o jeito de testar uma política nova em produção sem quebrar nada.
    • frame-ancestors 'none': substitui o antigo X-Frame-Options, evita clickjacking (o site não pode ser embutido num <iframe> de outra origem).
    • object-src 'none': bloqueia plugins antigos (Flash) que ignoravam outras diretivas.

    Frase de entrevista: "nonce por request resolve o caso do Next porque hash exige texto estável e o payload RSC muda toda resposta; strict-dynamic propaga a confiança pros chunks carregados por esse script; e nada disso substitui sanitizar entrada — CSP é a segunda camada, pra quando a primeira falhar."

Munição da sua entrevista · src/lib/auth/sessao-valida.ts

O trecho mais denso do seu próprio código, e um ótimo exemplo de trade-off explicado:

/**
 * A sessão é JWT de 30 dias sem rotação. Trocar a senha não tinha
 * efeito sobre quem já estava dentro — um cookie vazado continuava
 * válido por até um mês.
 *
 * O mecanismo é um CARIMBO, não uma comparação de tempo:
 * `credenciaisAlteradasEm` entra no token no login e é reconferido
 * contra o banco em cada guarda.
 *
 * Por que carimbo e não `iat`: o Auth.js reemite o cookie
 * periodicamente, renovando o `iat` — uma sessão comprometida
 * escaparia da checagem temporal.
 */

Por que isso importa: isso é uma resposta pronta e correta pra “como você invalidaria uma sessão JWT sem manter estado no servidor?” — pergunta clássica de entrevista de segurança, e você não só sabe a resposta teórica, sabe por que a solução óbvia (comparar timestamps) não funciona.

Responda em voz alta · só depois abra o gabarito
  1. Por que JWT “sem estado” dificulta revogar uma sessão antes da expiração?
    ver resposta

    Porque a validação é feita só pela assinatura, sem consultar nada — que é justamente a propriedade que torna o JWT atraente. Revogar exigiria o estado que o design eliminou. Na prática: um cookie vazado vale até expirar, e você não tem botão de desligar.

    Saídas conhecidas: TTL curto + refresh token rotativo (com detecção de reuso); uma denylist consultada a cada request, que reintroduz estado e desfaz metade do argumento; ou o caminho do Gabarita (D107) — um carimbo credenciaisAlteradasEm que já viaja no mesmo select que lê papel e plano, então a checagem sai de graça, sem consulta extra.

    Detalhe que impressiona: não dá pra usar o iat do próprio token, porque o Auth.js reemite o cookie periodicamente e renova o iat — a sessão comprometida escaparia da comparação.

  2. O que é IDOR, e qual o padrão de código que evita — não de UI, de query?
    ver resposta

    IDOR (Insecure Direct Object Reference) é usar um identificador vindo do cliente pra buscar um recurso sem provar que ele pertence a quem pediu: trocar /prova/123 por /prova/124 e ver a prova de outra pessoa.

    O padrão que evita não é esconder o ID (UUID só dificulta, não protege) nem checar na UI. É colocar o dono na cláusula WHERE da mesma consulta que busca o dado: where: { id: sessionId, session: { userId } }. Nunca em duas etapas — buscar e depois comparar em código é o padrão que a próxima função esquece de repetir.

    É literalmente a D109 do seu projeto, e o teste certo é por função, não por tela: guarda de página confirma quem é a pessoa, nunca de quem é o recurso.

  3. CSP com nonce: o que impede um script injetado de rodar mesmo que ele consiga se inserir no HTML?
    ver resposta

    O navegador só executa um <script> cujo atributo nonce bate com o valor declarado em script-src naquele response — e o valor é aleatório a cada request. O atacante que consegue injetar HTML não sabe o nonce: ele não está no HTML anterior, não é previsível e não sobrevive de uma resposta pra outra. O script entra no DOM e simplesmente não roda.

    O que fecha a resposta em nível sênior: strict-dynamic. Ele propaga a confiança de um script com nonce para os chunks que ele carrega — necessário porque o Next importa JS dinamicamente — e faz o navegador ignorar allowlists de domínio, que são exatamente a parte da CSP que costuma ser contornável por um endpoint JSONP esquecido num CDN permitido.

  4. Cite uma métrica de Core Web Vitals e uma causa comum dela ficar ruim numa Server Component-heavy app.
    ver resposta

    LCP (Largest Contentful Paint): a causa clássica num app com Server Components pesadas é a página inteira esperar uma query lenta antes de emitir qualquer HTML. Correção: streaming com Suspense, pra casca sair na hora e o conteúdo caro chegar depois; next/image com priority no herói; fonte com display: swap e preload.

    INP (Interaction to Next Paint — substituiu o FID em março de 2024): mede a resposta a interações. Piora quando você marcou "use client" alto demais na árvore e o navegador hidrata JavaScript demais.

    CLS: layout pulando quando o conteúdo assíncrono chega — imagem sem width/height, banner injetado, ou um Suspense cujo fallback tem altura diferente do conteúdo real.
