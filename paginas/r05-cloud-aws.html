Cloud & Delivery na AWS

~8h · sair do “a Vercel faz isso sozinha” e saber o que ela fazia

O Gabarita roda na Vercel e a API do Ally AI vai pro Google Cloud Run. Nenhum dos dois está na AWS, e é a AWS que aparece na maioria das vagas de Frontend Engineer com foco em IA lá fora. Ninguém espera que um front-end vire especialista em infra. Espera-se que você saiba o que muda quando o Next.js sai da Vercel: streaming atrás de proxy, cache por instância, NEXT_PUBLIC_ embutido no build, CDN que guarda o que não devia. E que o pipeline faça deploy sem uma chave de acesso esquecida num secret. Esta página liga essas peças ao que os seus dois projetos já fazem. Pra base de observabilidade e deploy, veja o B17; pra cache em camadas, o B1; pra cache do App Router, a semana 2.

  • Next.js — How to self-host your Next.js application
    A lista oficial do que a Vercel resolvia por você: proxy reverso, variáveis de ambiente, cache por instância, encryption key de Server Actions, version skew, streaming atrás de proxy e after().
    Ler inteiro · ~30 minA página que mais rende nesta frente. Se só der pra ler uma, é esta: cada seção é uma pergunta de entrevista.
    nextjs.org · oficial
    Resumo aqui na página

    A Vercel resolve em silêncio uma lista de problemas que, num servidor seu, viram responsabilidade sua. Esta página é essa lista: proxy na frente, variável de ambiente em runtime, cache por instância, mesma chave de criptografia em todas as instâncias, version skew, streaming sem buffer e desligamento gracioso pro after().

    Proxy reverso e otimização de imagem
    • A recomendação é não expor o next start direto. Um proxy (nginx, ou o load balancer da nuvem) cuida de request malformado, conexão lenta, limite de payload e rate limit, e o Next gasta CPU só renderizando.
    • next/image funciona sem configuração com next start. Dá pra trocar por um serviço externo com um loader. Em Linux com glibc, o Sharp pode precisar de ajuste de alocador pra não estourar memória.
    Variáveis de ambiente: build vs. runtime
    • Por padrão, variável só existe no servidor. Com prefixo NEXT_PUBLIC_ ela vai pro navegador, mas embutida no bundle durante o next build. Trocar o valor depois não muda nada até o próximo build.
    • No servidor, numa renderização dinâmica (depois de await connection(), cookies() ou headers()), process.env.X é lido em runtime. É isso que permite uma única imagem Docker promovida entre ambientes com valores diferentes.
    Cache e ISR
    • Páginas em cache e ISR usam o mesmo cache do servidor, que por padrão fica no disco de cada instância (mais 50 MB em memória). Com uma instância e disco persistente, isso basta.
    • Com várias instâncias, ou em computação efêmera, cada pod tem a própria cópia e pode servir dado velho. A saída é um cacheHandler próprio (Redis, S3) com cacheMaxMemorySize: 0.
    • revalidateTag() numa instância só invalida aquela instância. Coordenar exige implementar refreshTags() no handler.
    • Os cabeçalhos automáticos importam pra CDN. Arquivo com hash no nome sai com public, max-age=31536000, immutable, ISR sai com s-maxage + stale-while-revalidate, e página dinâmica sai com private, no-cache, no-store.
    Várias instâncias e deploy gradual
    ProblemaSintomaConserto
    Chave das Server Actions diferente por build“Failed to find Server Action”NEXT_SERVER_ACTIONS_ENCRYPTION_KEY igual em todas
    Version skew (cliente velho, servidor novo)asset 404, navegação quebradadeploymentId: o Next detecta e força recarga completa
    Build refeito por ambienteIDs de build diferentes entre containersgenerateBuildId fixo (ex.: hash do git)
    Streaming e after()
    • Streaming (loading.tsx, Suspense) funciona self-hosted, mas todo salto do caminho tem que repassar a resposta em pedaços. No nginx, isso é X-Accel-Buffering: no. A página cita o ALB com integração Lambda como exemplo de algo que pode fazer buffer por padrão.
    • after() é suportado com next start. No desligamento (SIGINT/SIGTERM), o servidor termina os requests em andamento e os callbacks pendentes do after(), e a plataforma precisa dar um intervalo de drenagem (10–30 s é o recomendado).

    Frase de entrevista: “Sair da Vercel não é só trocar onde o container roda. É assumir o cache compartilhado, a chave das Server Actions, o version skew e o streaming sem buffer, que antes a plataforma resolvia por mim.”

  • OpenNext for AWS
    Adaptador open source que transforma a saída do next build em peças de AWS: Lambda pro servidor, S3 pro estático, CloudFront na frente, fila de revalidação e cache de tags.
    Ler trechos · ~20 minLeia a visão geral e a página de arquitetura (“Inner workings → Architecture”). Pule as páginas de configuração avançada.
    opennext.js.org · projeto open source
    Resumo aqui na página

    OpenNext é um adaptador open source que pega a saída do next build e a transforma em peças de AWS que você mesmo implanta: Lambda pro servidor, S3 pro estático, CloudFront na frente, Lambda de imagem, fila de revalidação e DynamoDB pro cache de tags. É o que plataformas como o SST usam por baixo.

    O que ele suporta
    • Next.js 15 com App Router e Pages Router, API routes e rotas dinâmicas.
    • SSG, SSR e ISR, middleware e otimização de imagem.
    • Integração com NextAuth, opção de rodar em Lambda@Edge, e cache componível com 'use cache'.
    • Implantação seletiva: dá pra mandar as rotas de API pra ECS, ISR/SSG pra Lambda e outras partes pra outro destino, conforme a necessidade.
    A arquitetura, peça por peça
    PeçaPapel
    CloudFrontCDN e roteador: /_next/static vai pro S3 (com public,max-age=31536000,immutable), imagem vai pra função de imagem, o resto vai pra função do servidor
    Lambda do servidoro Next em modo standalone (a classe NextServer + node_modules), atendendo SSR, ISR, SSG e API
    S3assets estáticos e o cache de rotas e de fetch
    Fila de revalidaçãomensagens de ISR; uma função consome e faz um HEAD na rota pra regenerar
    DynamoDBcache de tags, pra revalidateTag funcionar entre execuções
    Lambda de imagemotimização com Sharp
    Warmerinvoca as funções periodicamente pra reduzir partida a frio
    O que ele não faz
    • Não cria a infraestrutura. Você descreve as peças com SST, CDK ou Terraform. A troca em relação ao Amplify é mais controle e mais recurso suportado, em troca de mais coisa pra manter.
    • Suporte limitado a Windows por causa do tooling do Next. A recomendação é buildar em WSL, VM ou CI Linux.

    Frase de entrevista: “O OpenNext mostra o que a Vercel faz por baixo: CDN roteando estático e dinâmico, função do servidor, fila de revalidação e cache de tags compartilhado. Saber isso é o que me deixa depurar ISR em qualquer nuvem.”

  • GitHub Actions — Configuring OpenID Connect in AWS
    Como o workflow troca um token de curta duração por credencial temporária da AWS, sem AWS_SECRET_ACCESS_KEY guardada em lugar nenhum.
    Ler inteiro · ~15 minCurta e prática: identity provider, trust policy com sub, permissions e o passo do configure-aws-credentials.
    docs.github.com · oficial
    Resumo aqui na página

    O workflow não guarda credencial da AWS. Ele pede ao GitHub um token OIDC de curta duração, e a AWS troca esse token por credencial temporária de uma role, se a trust policy permitir aquele repositório e aquela branch ou environment. Não há segredo de longa duração pra vazar.

    Os quatro passos
    1. Identity provider no IAM: URL https://token.actions.githubusercontent.com, audience sts.amazonaws.com.
    2. Role com trust policy: condicione aud e principalmente sub, que identifica de onde o workflow roda.
    3. Permissões do workflow: id-token: write pra poder emitir o token, e contents: read pro checkout.
    4. Action oficial: aws-actions/configure-aws-credentials com role-to-assume e aws-region.
    "Condition": {
  "StringEquals": {
    "token.actions.githubusercontent.com:aud": "sts.amazonaws.com",
    "token.actions.githubusercontent.com:sub": "repo:octo-org/octo-repo:environment:prod"
  }
}
    Onde mora a segurança
    • A condição sub é o controle. Com repo:org/repo:ref:refs/heads/main, só a main assume a role. Com repo:org/repo:environment:prod, só jobs no environment prod, que pode exigir aprovação manual.
    • Sem a condição sub (ou com curinga largo demais), qualquer repositório do GitHub com o mesmo provider poderia tentar assumir a role. É o erro clássico de configuração.
    • A credencial expira sozinha: não tem rotação pra lembrar, e um log vazado não serve pra nada amanhã.
    permissions:
  id-token: write
  contents: read
steps:
  - uses: aws-actions/configure-aws-credentials@<sha>
    with:
      role-to-assume: arn:aws:iam::123456789012:role/deploy-web
      aws-region: eu-west-1
    Um ci.yml comentado: do pull request ao deploy

    É o arquivo que a entrevista pede pra você escrever no quadro. Cada linha comentada é uma decisão que dá pra defender. As versões das actions são ilustrativas: use as atuais e, em produção, fixe por SHA.

    name: ci
on:
  pull_request:              # roda em todo PR
  push:
    branches: [main]         # e quando algo entra na main

# um push novo no mesmo PR cancela a execução anterior: não paga minuto de código velho
concurrency:
  group: ci-${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true

permissions:
  contents: read             # o mínimo pra todo job; quem precisar de mais pede no próprio job

jobs:
  qualidade:
    runs-on: ubuntu-latest
    timeout-minutes: 15      # job travado não pode consumir a cota inteira
    services:
      postgres:              # banco descartável pra suíte que usa banco de teste
        image: postgres:16
        env:
          POSTGRES_PASSWORD: postgres
          POSTGRES_DB: app_test
        ports: ['5432:5432']
        options: >-
          --health-cmd "pg_isready -U postgres"
          --health-interval 5s --health-timeout 5s --health-retries 10
    env:
      DATABASE_URL: postgresql://postgres:postgres@localhost:5432/app_test
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v4        # lê a versão do campo "packageManager"
      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: pnpm                     # guarda o store do pnpm entre execuções
      - run: pnpm install --frozen-lockfile   # falha se o lockfile estiver fora de sincronia
      - run: pnpm turbo lint typecheck test build   # o Turborepo pula o que não mudou

  deploy:
    needs: qualidade                      # só depois que o CI passou
    if: github.event_name == 'push' && github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    permissions:
      id-token: write                     # deixa o job pedir o token OIDC
      contents: read
    steps:
      - uses: actions/checkout@v4
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::123456789012:role/deploy-web
          aws-region: eu-west-1
      - run: ./scripts/deploy.sh          # build da imagem, push pro ECR, atualiza o serviço
    • Dois jobs, uma porta: o deploy só roda na main, depois do CI, e só ele recebe id-token: write. O job que roda código de PR não tem poder de assumir role nenhuma.
    • concurrency com cancel-in-progress poupa minutos nos PRs. Não use no deploy de produção sem pensar: cancelar um deploy no meio pode deixar o ambiente pela metade.
    • A trust policy da role precisa casar com o gatilho: com environment: prod no job, o sub vira repo:org/repo:environment:prod; sem environment, repo:org/repo:ref:refs/heads/main.
    • Check obrigatório: o CI só protege se a branch protection exigir o job qualidade pra mesclar.

    Frase de entrevista: “Meu pipeline não tem chave da AWS. Ele assume uma role por OIDC, e a trust policy só aceita o environment de produção do meu repositório.”

  • Sentry — Next.js guide
    O guia que o Gabarita já seguiu: os quatro arquivos por runtime, withSentryConfig, source maps, túnel e amostragem.
    Ler trechos · ~15 minLeia a configuração manual e a parte de amostragem. Compare com o seu src/instrumentation*.ts: o exercício é explicar cada linha.
    docs.sentry.io · oficial
    Resumo aqui na página

    O Next roda o seu código em até três runtimes (navegador, Node, edge), e o Sentry precisa de um ponto de entrada em cada um. O guia cobre esses arquivos, o withSentryConfig (source map e túnel) e a amostragem, que é a decisão de custo da observabilidade.

    Os arquivos e o que cada um faz
    ArquivoPapel
    instrumentation-client.tsinit no navegador; é onde entram replay e opções do cliente
    sentry.server.config.tsinit no runtime Node (Server Actions, Route Handlers, RSC)
    sentry.edge.config.tsinit no runtime edge (middleware)
    instrumentation.tsregister() importa a config certa conforme NEXT_RUNTIME, e exporta onRequestError pra erro de servidor

    O wizard (npx @sentry/wizard@latest -i nextjs) gera tudo isso. Saber montar à mão é o que permite explicar cada linha.

    withSentryConfig
    • Source maps: com SENTRY_AUTH_TOKEN no build, os maps sobem pro Sentry e o stack trace de produção aparece com o código original, não minificado.
    • Túnel: tunnelRoute (o exemplo do guia é /sentry-tunnel) faz o navegador mandar os eventos pela sua própria origem, o que contorna bloqueador de anúncio. Efeito colateral bom: a CSP não precisa liberar o host do Sentry em connect-src.
    O que ele captura
    • Erro com stack completa, traces de carregamento e interação, replay de sessão em vídeo, logs estruturados via Sentry.logger e métricas próprias (contagem, gauge, distribuição).
    • dataCollection desliga categorias de dado. A verificação é feita na página /sentry-example-page, que tem um botão que lança erro.
    Amostragem
    • O guia sugere tracesSampleRate 1.0 em desenvolvimento e 0.1 em produção, ajustando pelo volume. 100% de tracing com tráfego alto vira fatura, e 1% com tráfego baixo vira ponto cego.

    Frase de entrevista: “Instrumentei os três runtimes do Next, mandei os eventos por um túnel same-origin pra não abrir a CSP, e deixei a amostragem em 100% por enquanto, com o motivo escrito: tráfego baixo, cabe no plano grátis.”

  • CloudFront — Understand cache policies
    Cache key, TTLs contra Cache-Control, compressão. A página onde está a regra que vaza página privada se você não souber dela.
    Ler trechos · ~20 minLeia “Time to live (TTL) settings” e “Cache key settings”. A parte longa de compressão é consulta.
    docs.aws.amazon.com · oficial
    Resumo aqui na página

    A cache policy do CloudFront decide duas coisas: quanto tempo um objeto fica na borda (TTLs, em conjunto com o Cache-Control da origem) e o que diferencia um objeto do outro (a cache key). Cada valor a mais na chave derruba a taxa de acerto. E um TTL mínimo errado guarda o que a origem pediu pra não guardar.

    TTLs contra o Cache-Control da origem
    TTLQuando vale
    Mínimopiso. Se for maior que 0, o CloudFront guarda mesmo com no-cache, no-store ou private na origem
    Máximoteto, aplicado quando a origem manda Cache-Control ou Expires
    Padrãousado só quando a origem não manda Cache-Control nem Expires

    Os três em 0 desligam o cache. A linha do TTL mínimo é a que vaza dado: página dinâmica de usuário logado sai do Next com private, no-store, e um piso de um dia faz a borda entregar a página de um usuário pra outro.

    Cache key: headers, cookies e query strings
    • Pra cada tipo, as opções são: nada, uma lista específica, todos, ou “todos exceto”. Você nomeia a chave, mas o valor inteiro entra na cache key.
    • Tudo o que entra na cache key também é repassado à origem automaticamente. Pra repassar algo à origem sem fragmentar o cache, existe a origin request policy, separada.
    • O * é tratado como texto literal, não curinga.
    • Exemplo do custo: Accept-Language na chave multiplica as cópias por idioma, o que pode ser certo pra i18n. Um cookie de sessão na chave torna cada usuário uma cópia, e aí não há cache.
    Compressão
    • Liga cache de objetos Gzip e/ou Brotli. O CloudFront normaliza o Accept-Encoding (por exemplo, pra br,gzip) antes de pôr na chave, pra não criar uma cópia por variação de navegador.
    • Chrome e Firefox só aceitam Brotli em HTTPS. Com a compressão de cache ligada, não ponha Accept-Encoding na origin request policy, porque não tem efeito.

    Frase de entrevista: “Na borda eu separo por comportamento: estático com hash no nome tem cache longo, e o dinâmico respeita o Cache-Control da origem com TTL mínimo zero. A cache key leva só o que muda a resposta.”

  • Segredos fora do repositório e da imagem: apps/api/.env.example lista as chaves, .dockerignore e .gcloudignore excluem todo .env* (mantendo só o .env.example), e as variáveis de produção ficam num arquivo fora do repo, passado com --env-vars-file (docs/DEPLOY-CLOUD-RUN.md:93-125).
  • Build-time vs. runtime: o runbook registra que NEXT_PUBLIC_API_URL é embutido no build do front e que trocá-lo pede um novo deploy (:195-196) — o tópico 7 desta página, já documentado no projeto.
  • Escala e custo como configuração: --max-instances 1 como teto real de gasto, --min-instances 0 pra desligar quando ocioso, --cpu-boost e --timeout 600, cada um explicado no runbook (:129-166).
  • Escolha de infraestrutura por medição: a decisão D06 (docs/DECISOES.md:39-55) mediu a mesma imagem Docker com quatro limites de CPU (0,1 CPU dá timeout; 1 vCPU audita em 6,5 s) e escolheu o Cloud Run comparando com Koyeb, Fly.io, Railway e Oracle.

Regra prática: configuração e segredo que não gira, no SSM; segredo que precisa de rotação (a senha do banco), no Secrets Manager. Nos dois casos o valor é entregue em runtime: no ECS, a task definition tem o campo secrets com valueFrom apontando pro ARN, e o valor vira variável de ambiente do container sem passar pelo repositório nem pela imagem. A exceção que prende é o NEXT_PUBLIC_*, que é embutido no build.

i18n: subcaminho ou domínio?

  • Subcaminho (/pt-BR/, /en/): um domínio, um certificado, um deploy, e a autoridade de SEO concentrada. É o padrão: no App Router vira o segmento [locale], com generateStaticParams pros idiomas e o proxy escolhendo o idioma na primeira visita pelo Accept-Language (e lembrando num cookie).
  • Domínio por país (.ie, .co.uk): sinal geográfico forte pro buscador e confiança local, ao custo de N domínios, certificados e configurações.
  • Em qualquer um: hreflang e canonical por idioma, formatação de data, número e moeda com Intl, e espaço pra texto que cresce (o alemão costuma ficar uns 30% mais longo que o inglês).
  • Residência de dado (LGPD, GDPR) é restrição que escolhe a região antes da latência: a pergunta “onde ficam os dados dessa pessoa?” vem primeiro.

Munição da sua entrevista · D42, a função em Washington e o banco em São Paulo

Os cliques do Gabarita em produção estavam levando segundos, e você foi medir antes de mexer. O header X-Vercel-Id: gru1::iad1::… mostrou que o request entrava pela borda de São Paulo mas a função executava em Washington, enquanto o Neon estava em sa-east. Duas rotas isolaram o custo: /api/auth/session (JWT, sem banco) levava ~280 ms e /api/health (um SELECT 1) levava ~830 ms, ou seja, ~550 ms por ida ao banco.

A solução combinou três frentes: "regions": ["gru1"] no vercel.json, connection_limit de 1 pra 5, e relationJoins do Prisma (7 queries → 1 na página da questão). E um teste conta as queries do answerItem e falha acima de 5, pra o ganho ficar garantido (docs/DECISOES.md:64).

Por que isso importa: é a resposta pronta pra “como você pensa região e latência numa aplicação internacional?”. A regra que você aprendeu medindo, a função fica onde o dado está, vale igual pra Lambda, Fargate ou Cloud Run. E “mediu, isolou, resolveu e pôs teste de orçamento” é o roteiro que um painel sênior quer ouvir.

Responda em voz alta · só depois abra o gabarito
  1. Te pedem pra migrar o Gabarita da Vercel pra AWS “pelo caminho mais simples, o Amplify”. O que você checa antes de aceitar?
    ver resposta

    A lista de recursos não suportados do Amplify Hosting contra o que o app usa. O Gabarita depende de after() pra gerar a explicação da IA fora do caminho do render, e de streaming de RSC pelos loading.tsx. Os dois estão fora do suporte. Sem o after(), a explicação some ou passa a bloquear a resposta.

    A alternativa é a imagem que já existe (Dockerfile.web com output: "standalone") em ECS Fargate ou App Runner, com desligamento gracioso (SIGTERM e um intervalo de drenagem) pra os after() pendentes terminarem. Outra opção é o OpenNext. Também é preciso decidir o cron diário e o worker do pg-boss, que viram EventBridge e um segundo serviço.

  2. Por que configurar OIDC entre GitHub Actions e AWS, em vez de guardar AWS_ACCESS_KEY_ID e AWS_SECRET_ACCESS_KEY nos secrets do repositório?
    ver resposta

    Com OIDC não existe chave de longa duração pra vazar, girar ou esquecer. O workflow pede um token assinado pelo GitHub (permissions: id-token: write) e troca por credencial temporária da role. A trust policy decide quem pode fazer essa troca: a condição token.actions.githubusercontent.com:sub restringe ao repositório e à branch ou ao environment (por exemplo, repo:org/ally-ai:environment:prod). Assim, um fork, outra branch ou outro repositório não assume a role de deploy de produção, mesmo rodando o mesmo YAML.

  3. Você troca NEXT_PUBLIC_API_URL no painel da hospedagem e o front continua chamando a API antiga. Por quê? E como ter uma imagem que serve staging e produção?
    ver resposta

    Variável NEXT_PUBLIC_* é embutida no JavaScript durante o next build. O valor do painel só vale no próximo build — o runbook de deploy do Ally AI já documenta exatamente esse passo. Pra promover a mesma imagem entre ambientes, o valor que muda por ambiente tem que ser lido no servidor em runtime: numa rota dinâmica (depois de connection()/headers()), ou entregue ao cliente por um endpoint de configuração ou por uma prop de Server Component. A outra saída, mais simples e mais lenta, é aceitar um build por ambiente.

  4. Você põe o CloudFront na frente do Gabarita com um cache policy de TTL mínimo de 1 dia, “pra acelerar”. O que pode dar errado?
    ver resposta

    Com TTL mínimo maior que zero, o CloudFront guarda o objeto mesmo com Cache-Control: private, no-cache ou no-store vindos da origem. As páginas dinâmicas do Next (que saem com private, no-store) e as rotas de imagem privadas do Gabarita passariam a ser servidas da borda. Como a cache key padrão não leva o cookie de sessão, a página logada de uma aluna pode ser entregue a outra, ou o gabarito aparecer antes da resposta, enquanto o objeto estiver dentro do TTL (passado o prazo, o CloudFront revalida na origem, mas até lá o private não vale).

    A forma certa é ter comportamentos separados. /_next/static/* fica com cache longo, porque o arquivo tem hash no nome. O resto respeita o Cache-Control da origem (TTL mínimo 0), e a cache key leva só o que muda a resposta. Cookie de sessão na cache key derruba a taxa de acerto a quase zero, e ficar sem ele nas páginas dinâmicas é exatamente o motivo de não cachear essas páginas na borda.

  5. Dois containers do mesmo Next atrás de um load balancer, e de vez em quando aparece “Failed to find Server Action” logo depois de um deploy. Qual a causa provável e o conserto?
    ver resposta

    Há duas causas que se somam. Primeira: o Next cifra as variáveis capturadas das Server Actions com uma chave gerada por build. Se as instâncias vieram de builds diferentes, uma não decifra o que a outra cifrou, e o conserto é fixar NEXT_SERVER_ACTIONS_ENCRYPTION_KEY. Segunda: durante o deploy gradual, o navegador com o JavaScript antigo chama uma action que o servidor novo não conhece (version skew). O conserto é configurar deploymentId: o Next detecta a diferença e faz navegação completa em vez de quebrar. Com várias instâncias, também vale lembrar que revalidateTag só invalida o cache local se não houver um cache handler compartilhado.

  6. Além de erro e lentidão, como você mede se um recurso de IA está sendo bem usado?
    ver resposta

    Métricas de produto, que o monitor de erro não vê: TTFT (tempo até o primeiro token, o que o usuário sente), tempo total, tokens e custo por conversa e por usuário, a taxa de parar a resposta no meio e a de regenerar (as duas são sinais de insatisfação), polegar pra cima ou pra baixo, taxa de retry e de erro por tipo (429 e 5xx são problemas diferentes) e conversas abandonadas.

    Como coletar: OpenTelemetry com um span por chamada ao modelo (atributos como modelo, tokens de entrada e saída, resultado) exportado pra CloudWatch e X-Ray, pelo coletor da AWS, ou pro Sentry; e eventos de produto à parte das métricas de infraestrutura. Cuidado com privacidade: não registre o prompt inteiro quando houver dado pessoal.
