Fundamentos: a conversa técnica

~8h · 38 perguntas com gabarito, em seis temas · responda em voz alta antes de abrir

Em uma frase: além do código ao vivo, quase toda entrevista de júnior avançado e pleno tem uma conversa técnica, e as perguntas se repetem. Elas não querem a definição de livro. Querem ver se você entende o porquê e se já viu aquilo na prática. As respostas abaixo são curtas de propósito: é o tamanho certo para falar em um ou dois minutos. Para cada tema, o aprofundamento está numa página do guia (indicada no título).

Como usar esta página

Em voz altaLeia a pergunta, responda falando, e só depois abra o gabarito. Reconhecer a resposta lendo é muito mais fácil do que produzi-la sob pressão, e só a segunda é avaliada.

O formatoDefinição em uma frase, um exemplo e, se tiver, onde você usou. “Closure é…; por exemplo, o debounce…; no Gabarita, eu…”.

Não sabe?Diga o que sabe e como descobriria. “Não lembro a diferença exata, mas sei que um deles…; eu confirmaria na documentação.” Inventar é pior que admitir.

Na entrevistaUma resposta com exemplo próprio vale mais que uma definição perfeita decorada.

Checklist

JavaScript · aprofunde em 01 e 04

Responda em voz alta · só depois abra o gabarito
  1. Qual a diferença entre var, let e const?
    ver resposta

    var vale para a função inteira e pode ser usada antes da linha em que foi declarada (vale undefined). let e const valem só dentro do bloco { } e dão erro se usadas antes da declaração. const não deixa reatribuir a variável, mas o objeto dentro dela pode mudar: const list = []; list.push(1) funciona.

    Na prática: const por padrão, let quando o valor muda, e var nunca em código novo.

  2. O que é closure? Dê um exemplo.
    ver resposta

    É uma função que lembra as variáveis do lugar onde foi criada, mesmo depois que aquele lugar terminou de rodar. Exemplo: no debounce, a função devolvida lembra a variável timer entre as chamadas. Os hooks do React também dependem disso, e é por isso que existe o bug da “closure velha” num setInterval (veja o LC 7).

  3. Em que ordem isto imprime? console.log(1); setTimeout(() => console.log(2), 0); Promise.resolve().then(() => console.log(3)); console.log(4);
    ver resposta

    1, 4, 3, 2. Primeiro roda todo o código síncrono (1 e 4). Quando a pilha esvazia, o event loop roda todas as microtarefas (os then das Promises: 3) e só depois a próxima tarefa (o setTimeout: 2). O 0 do setTimeout quer dizer “assim que der”, não “agora”.

    Por isso um laço pesado trava a página: enquanto ele roda, nada mais roda, nem o clique, nem a pintura da tela.

  4. Qual a diferença entre == e ===?
    ver resposta

    === compara valor e tipo. == converte os tipos antes de comparar, com regras difíceis de lembrar: 0 == '' é true, e null == undefined também. Use sempre ===. A exceção aceita por muitos times é x == null, que pega null e undefined de uma vez.

  5. Como o valor de this é definido? E na arrow function?
    ver resposta

    Numa função comum, o this depende de como ela é chamada: em obj.method(), é obj; passada como callback solta, ele se perde (fica undefined no modo estrito). A arrow function não tem this próprio: usa o do lugar onde foi escrita. Por isso arrow functions são a escolha natural para callbacks.

  6. Qual a diferença entre Promise.all, allSettled, race e any?
    ver resposta

    all: espera todas e falha se uma falhar (buscar dados que a página inteira precisa). allSettled: espera todas e diz o resultado de cada uma, sem falhar (enviar 10 fotos e mostrar quais deram erro). race: devolve a primeira que terminar, com sucesso ou erro (um prazo, como o withTimeout). any: devolve a primeira que der certo (tentar dois servidores).

  7. O que é cópia rasa e cópia profunda?
    ver resposta

    A cópia rasa ({ ...obj }, [...lista]) cria um objeto novo, mas os objetos de dentro continuam sendo os mesmos. Mudar copy.address.city muda o original também. A cópia profunda copia tudo, em todos os níveis: structuredClone(obj) faz isso.

    No React, isso explica por que atualizar estado aninhado exige espalhar cada nível: { ...user, address: { ...user.address, city } }.

  8. O que é hoisting?
    ver resposta

    Antes de rodar, o JavaScript registra as declarações do escopo. Funções declaradas com function name() podem ser chamadas antes da linha onde estão. var existe antes da linha, mas vale undefined. let e const também são registradas, mas usá-las antes da linha dá erro: o trecho até a declaração se chama temporal dead zone.

  9. O que é propagação de eventos (bubbling) e delegação?
    ver resposta

    Um clique num botão dispara o evento no botão e depois em cada elemento pai, até o documento: o evento “sobe”. Delegação aproveita isso: em vez de um ouvinte em cada um dos 500 itens da lista, um ouvinte só, na lista, que olha event.target para saber qual item foi clicado. event.stopPropagation() interrompe a subida. O próprio React usa delegação: ele põe os ouvintes na raiz da aplicação.

React · aprofunde em 01 e B15

Responda em voz alta · só depois abra o gabarito
  1. Para que serve a key numa lista? Por que não usar o índice?
    ver resposta

    A key diz ao React qual item é qual entre uma renderização e outra, para ele reaproveitar o elemento certo. Com o índice, remover ou reordenar itens faz um item herdar a chave do vizinho, e o estado interno (um input, o foco) vai parar no item errado. Use um id estável do dado. O índice só é aceitável numa lista que nunca muda de ordem nem de tamanho.

  2. Qual a diferença entre props e estado? Como você decide se algo deve ser estado?
    ver resposta

    Props chegam do pai e o componente não as muda. Estado pertence ao componente e muda com setState, o que redesenha a tela. Antes de criar um estado, pergunte: dá para calcular a partir de props ou de outro estado? Se dá (a lista filtrada, o total do carrinho), não é estado: é uma variável calculada na renderização. Estado duplicado é a fonte de bug mais comum em React.

  3. Quando o useEffect roda, e para que serve a função que ele devolve?
    ver resposta

    Ele roda depois que a tela é atualizada: na primeira vez e sempre que uma dependência do array mudar. A função devolvida é a limpeza: roda antes do efeito rodar de novo e quando o componente sai da tela. Serve para cancelar o fetch, limpar o setInterval ou remover o ouvinte de evento.

    E o principal: efeito é para sincronizar com algo de fora do React. Calcular um valor a partir do estado não precisa de efeito.

  4. O que faz um componente renderizar de novo? Quando usar React.memo, useMemo e useCallback?
    ver resposta

    Ele renderiza de novo quando o próprio estado muda, quando o pai renderiza ou quando um contexto que ele usa muda. Renderizar não é ruim: na maioria das vezes, é barato. React.memo pula a renderização se as props não mudaram. useMemo guarda um cálculo caro. useCallback guarda a mesma função entre renderizações, o que só importa se ela vai para um componente com memo ou para as dependências de um efeito.

    A regra: meça primeiro (React DevTools Profiler), otimize depois. O React Compiler já faz boa parte disso sozinho.

  5. O que é input controlado e não controlado?
    ver resposta

    Controlado: o valor vem do estado (value={text} mais onChange), e o React é a fonte da verdade. Bom quando você precisa reagir a cada tecla (validar, formatar, habilitar um botão). Não controlado: o próprio DOM guarda o valor, e você lê quando precisa (com ref, ou com FormData no envio). Mais simples e com menos renderizações, bom para formulários grandes. Bibliotecas como React Hook Form usam essa ideia.

  6. Quando usar Context? E quando usar uma biblioteca de estado?
    ver resposta

    Context serve para passar um valor a muitos componentes sem repassar prop por prop: tema, idioma, usuário logado. O cuidado: quando o valor muda, todos os componentes que o usam renderizam de novo. Para estado que muda muito e é usado em muitos lugares, Zustand ou Redux deixam cada componente assinar só o pedaço que usa. E dado que vem do servidor fica melhor em TanStack Query ou SWR, que cuidam de cache e de nova busca.

  7. Qual a diferença entre Server Component e Client Component no Next.js?
    ver resposta

    O Server Component roda só no servidor: pode buscar no banco direto e não manda o seu JavaScript ao navegador. Não pode ter estado, efeito nem evento de clique. O Client Component (com 'use client' no topo do arquivo) roda também no navegador e pode ser interativo. A regra prática: tudo é servidor por padrão, e só as “folhas” interativas (o botão, o formulário) viram cliente.

  8. Por que o meu efeito roda duas vezes em desenvolvimento?
    ver resposta

    É o StrictMode. Em desenvolvimento, o React monta, desmonta e monta de novo cada componente, de propósito, para revelar efeitos sem limpeza. Se rodar duas vezes quebra algo (dois pedidos, dois ouvintes), falta a função de limpeza. Em produção, roda uma vez só. A resposta errada é tirar o StrictMode.

  9. Uma lista com 10 mil itens está lenta. O que você faria?
    ver resposta

    Primeiro, medir com o Profiler para ver se o custo é renderizar ou outra coisa. As saídas mais comuns: virtualização (desenhar só os itens visíveis na tela, com TanStack Virtual ou react-window), paginação ou “carregar mais”, e React.memo no item para ele não renderizar de novo quando outro item muda. Em busca sobre a lista, useDeferredValue mantém o campo de texto rápido enquanto a lista atualiza.

TypeScript · aprofunde em B4

Responda em voz alta · só depois abra o gabarito
  1. Qual a diferença entre type e interface?
    ver resposta

    Para descrever o formato de um objeto, os dois servem quase igual. type também descreve uniões ('a' | 'b') e outros tipos compostos, que a interface não consegue. A interface pode ser declarada de novo e as declarações se juntam, o que é útil para estender tipos de bibliotecas. O mais importante é o time escolher um padrão e seguir.

  2. Qual a diferença entre any e unknown?
    ver resposta

    any desliga a checagem: você pode fazer qualquer coisa com o valor, e os erros passam. unknown diz “não sei o que é”, e o TypeScript obriga a conferir antes de usar. Para dado de fora (resposta de API, JSON.parse), use unknown e valide (com Zod, por exemplo).

  3. O que é uma união discriminada?
    ver resposta

    Uma união de objetos em que todos têm um campo com valor fixo diferente, como status: 'loading' | 'error' | 'ready'. Ao conferir esse campo, o TypeScript sabe quais outros campos existem: dentro de if (s.status === 'ready'), ele deixa ler s.data. Isso impede estados impossíveis, como “carregando com mensagem de erro”. É a base do reducer do R1.

  4. O que são generics? Dê um exemplo.
    ver resposta

    São tipos com parâmetro, para uma função servir a vários tipos sem perder a informação. function first<T>(list: T[]): T | undefined: com uma lista de números devolve número; com uma de usuários, usuário. Sem generic, você teria de escolher entre repetir a função ou usar any. O useState<Todo[]> que você usa todo dia é um generic.

  5. Para que servem Partial, Pick, Omit e Record?
    ver resposta

    Criam tipos novos a partir de um existente, sem repetir campos. Partial<User>: todos os campos opcionais (bom para um formulário de edição). Pick<User, 'id' | 'name'>: só esses campos. Omit<User, 'password'>: todos menos esse (o que vai para o cliente). Record<string, number>: um objeto usado como dicionário.

Navegador, HTTP e segurança · aprofunde em B5, B13 e 05

Responda em voz alta · só depois abra o gabarito
  1. O que acontece quando você digita uma URL e aperta Enter?
    ver resposta

    Em ordem: o DNS traduz o domínio em um endereço IP; o navegador abre a conexão (TCP e, em HTTPS, a negociação TLS); manda o pedido HTTP; recebe o HTML e começa a ler. Ao achar CSS e JavaScript, busca esses arquivos; monta a árvore do DOM e a do CSS, calcula o layout e pinta a tela. Na entrevista, o bom é dizer onde cada etapa pode ficar lenta: DNS, servidor longe, JavaScript que bloqueia a leitura do HTML, imagem grande.

  2. Qual a diferença entre GET e POST? E entre 401 e 403?
    ver resposta

    GET lê e não deve mudar nada no servidor; pode ser guardado em cache e repetido. POST cria ou executa algo; repetir pode duplicar (dois pedidos, duas cobranças). PUT e DELETE devem ser idempotentes: repetir dá o mesmo resultado. 401: “não sei quem você é” (falta login). 403: “sei quem você é e você não pode”. A família 4xx é erro de quem pediu; a 5xx, erro do servidor.

  3. O que é CORS?
    ver resposta

    É a regra do navegador que impede uma página de um site ler a resposta de outro site, a não ser que o outro autorize, com o cabeçalho Access-Control-Allow-Origin. Quem bloqueia é o navegador, não o servidor: por isso a mesma chamada funciona no Postman e falha na página. A correção é no servidor da API (liberar a origem) ou passar a chamada pelo seu próprio back-end.

  4. Cookie, localStorage ou sessionStorage: onde guardar o token de login?
    ver resposta

    O mais seguro é um cookie httpOnly, Secure e SameSite. Com httpOnly, o JavaScript da página não consegue ler o cookie, então um ataque XSS não rouba o token. No localStorage, qualquer script na página lê. localStorage fica até ser apagado; sessionStorage some quando a aba fecha. Os dois servem para preferência (tema, rascunho), não para segredo.

  5. Qual a diferença entre CSR, SSR e geração estática?
    ver resposta

    CSR: o servidor manda um HTML quase vazio, e o JavaScript monta a página no navegador (primeira tela mais lenta, ruim para SEO). SSR: o servidor monta o HTML a cada pedido (dado sempre atual, custo a cada visita). Estática: o HTML é gerado no build e servido pela CDN (o mais rápido, para conteúdo que muda pouco); com ISR, ele é refeito de tempos em tempos ou quando o dado muda. O exercício de decisão do R3 treina essa escolha.

  6. O que são os Core Web Vitals e como você melhoraria cada um?
    ver resposta

    LCP: quanto demora o maior elemento visível (em geral, a imagem principal). Melhora com imagem otimizada e carregada com prioridade, e servidor mais rápido. INP: quanto a página demora para responder a um clique ou tecla. Melhora com menos JavaScript rodando no clique e quebrando tarefas longas. CLS: o quanto o layout pula enquanto carrega. Melhora reservando espaço para imagens e anúncios (width e height).

  7. O que é XSS e o que é CSRF?
    ver resposta

    XSS: o atacante consegue rodar o script dele na sua página, por exemplo com um comentário que contém <script>. O React escapa o texto por padrão; o risco volta com dangerouslySetInnerHTML. A CSP é a segunda linha de defesa. CSRF: outro site faz o navegador da vítima mandar um pedido ao seu, levando o cookie junto. Defesa: cookie SameSite, token anti-CSRF e nunca mudar dado com GET.

CSS · aprofunde em B12

Responda em voz alta · só depois abra o gabarito
  1. O que é o box model? Para que serve box-sizing: border-box?
    ver resposta

    Todo elemento é uma caixa com conteúdo, padding, borda e margin. No padrão antigo, a width vale só para o conteúdo: uma caixa de 200px com 20px de padding ocupa 240px. Com border-box, a width inclui padding e borda, e 200px são 200px. Quase todo projeto aplica border-box em tudo logo no começo.

  2. Quando usar Flexbox e quando usar Grid?
    ver resposta

    Flexbox organiza numa direção (uma linha ou uma coluna): uma barra de navegação, botões lado a lado, centralizar algo. Grid organiza em duas direções ao mesmo tempo: o layout da página, uma galeria de cartões alinhados em linhas e colunas. Eles se combinam: Grid para a página, Flexbox dentro de cada cartão.

  3. Como o navegador decide qual regra CSS vale quando duas se aplicam ao mesmo elemento?
    ver resposta

    Pela cascata. Primeiro a origem e o !important; depois a especificidade do seletor (id vale mais que classe, que vale mais que tag); por último, a ordem: a regra que vem depois ganha. Hoje, @layer deixa organizar camadas inteiras (reset, componentes, utilitários) sem brigar por especificidade. O !important é sinal de que a briga já começou.

  4. Qual a diferença entre position relative, absolute, fixed e sticky?
    ver resposta

    relative: fica no lugar normal e pode ser deslocado; também serve de referência para filhos com absolute. absolute: sai do fluxo e se posiciona em relação ao ancestral posicionado mais próximo (um selo no canto de um cartão). fixed: preso à janela, não rola (um botão de chat). sticky: rola normalmente até um ponto e então gruda (um cabeçalho de tabela).

Testes, acessibilidade, Git e code review · aprofunde em B10 e B11

Responda em voz alta · só depois abra o gabarito
  1. Teste unitário, de integração e e2e: o que você testa em cada um no front?
    ver resposta

    Unitário: uma função pura (validar um formulário, formatar um preço). Integração: um componente com seus filhos, como a pessoa usa (digitar, clicar, ver o resultado), com a rede simulada; com Testing Library, é onde fica a maior parte dos testes de front. E2E: o fluxo inteiro num navegador de verdade, com Playwright (cadastro, compra), em poucos casos, porque é mais lento e mais frágil.

  2. Qual o mínimo de acessibilidade que todo componente precisa?
    ver resposta

    Usar o elemento certo (<button> para ação, <a> para navegação); tudo funcionar pelo teclado, com foco visível; todo campo com <label>; imagem com alt; informação que não dependa só de cor; contraste suficiente. E testar: navegar só com o teclado e passar o axe (a extensão do navegador) leva cinco minutos.

  3. Qual a diferença entre merge e rebase? O que você faz quando dá conflito?
    ver resposta

    merge junta dois ramos e cria um commit de junção, mantendo a história como aconteceu. rebase reaplica os seus commits em cima do ramo atualizado, deixando a história em linha reta. Regra: não faça rebase de um ramo que outras pessoas já usam. No conflito: abrir os arquivos marcados, entender as duas mudanças (e perguntar a quem fez a outra, se precisar), juntar, rodar os testes e só então concluir.

  4. O que você olha quando revisa o PR de um colega?
    ver resposta

    Primeiro, se o PR faz o que promete (li a descrição, rodei, se for o caso). Depois: os casos de erro e de borda, se há teste para o comportamento novo, nomes claros, código duplicado, e segurança (dado de fora sendo confiado). Escrevo o comentário como pergunta ou sugestão, com o porquê, e separo o que bloqueia do que é preferência. Essa pergunta mede maturidade: pleno revisa código, não só escreve.
