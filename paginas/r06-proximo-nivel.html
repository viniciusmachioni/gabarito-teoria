Aprofundamento: MCP, AI UX, frontend distribuído & multi-cloud

~6h · a frente amarela: o vocabulário que separa “usa IA” de “desenha produto com IA”

As frentes R1–R5 são o que você precisa fazer. Esta é o que você precisa saber discutir numa vaga de Design Engineer ou Frontend Engineer com foco em IA: como uma interface de IA se conecta a ferramentas externas (MCP), como ela ganha ou perde a confiança de quem usa (AI UX), quando faz sentido quebrar o front em pedaços independentes (microfrontends) e o que “multi-cloud” significa de verdade. Nenhum dos quatro é obrigatório no dia 1 de uma vaga, mas todos aparecem na conversa de arquitetura, e o seu Gabarita já tem um dos melhores exemplos de AI UX que dá pra levar pra uma entrevista: citação verificada pelo código, não pela IA.

  • MCP — Architecture overview
    A página oficial que define host/client/server, as duas camadas (dados e transporte), as primitivas e um exemplo passo a passo em JSON-RPC.
    Ler trechos · ~30 minLeia “Participants”, “Layers” e “Primitives” inteiros; no exemplo, foque em tools/list e tools/call. Os blocos de JSON de notificação são consulta.
    modelcontextprotocol.io · oficial
    Resumo aqui na página

    MCP é um protocolo de troca de contexto: ele não diz como a aplicação usa o LLM, só como ela descobre e chama ferramentas e dados de fora. A arquitetura é host → um client por servidor → servidor, sobre JSON-RPC 2.0, com duas camadas separadas: dados e transporte.

    Participantes
    • Host — a aplicação de IA que coordena tudo (Claude Code, Claude Desktop, VS Code).
    • Client — um componente dentro do host que mantém a conexão com um servidor. O host cria um client por servidor: conectar ao Sentry e ao sistema de arquivos são dois clients.
    • Server — o programa que fornece contexto. “Local” quando roda na máquina via stdio (normalmente serve um client só); “remoto” quando roda numa plataforma via Streamable HTTP (serve muitos).
    As duas camadas
    CamadaO que define
    Dados (interna)O protocolo JSON-RPC: descoberta de versão e capacidades, primitivas (tools, resources, prompts), notificações, progresso
    Transporte (externa)Canal, enquadramento de mensagem e autorização. stdio: processos locais, sem rede. Streamable HTTP: POST do cliente pro servidor + Server-Sent Events opcional; autenticação HTTP padrão, com OAuth recomendado

    O mesmo formato de mensagem vale nos dois transportes: trocar stdio por HTTP não muda a lógica do servidor.

    Primitivas
    • Do servidor: tools (funções executáveis: consultar banco, chamar API), resources (dado de contexto: conteúdo de arquivo, schema do banco) e prompts (templates reutilizáveis, few-shot). Cada uma tem */list pra descobrir, e as tools têm tools/call pra executar.
    • Do cliente: elicitation, que permite ao servidor pedir mais informação ou confirmação ao usuário. Na versão 2026-07-28 do protocolo, sampling (o servidor pedir completion ao LLM do host) e logging foram marcados como obsoletos.
    O ciclo de uma ferramenta
    1. Descoberta: na versão atual o protocolo é stateless. Cada request leva versão e capacidades no _meta, e o cliente pode chamar server/discover pra saber o que o servidor suporta.
    2. tools/list: o servidor devolve cada tool com name (identificador único, ex. weather_current), title, description e inputSchema em JSON Schema. O host junta as tools de todos os servidores num registro único que entrega ao modelo.
    3. tools/call: quando o modelo decide usar uma tool, o host intercepta, roteia pro servidor certo, executa e devolve o resultado (um array content com texto, imagem etc.) pra conversa.
    4. Notificações: opt-in. O cliente abre um stream (subscriptions/listen) e recebe, por exemplo, notifications/tools/list_changed quando as tools mudam. São best effort: o cliente também deve fazer polling.

    Frase de entrevista: “MCP não substitui tool calling, ele distribui as ferramentas. O modelo continua chamando função por JSON Schema; o MCP padroniza como o host descobre essas funções em qualquer servidor.”

  • MCP — Security Best Practices
    Os ataques específicos de MCP com mitigação: confused deputy, token passthrough, SSRF, sequestro de state handle, mix-up, impersonação de redirect em localhost, servidor local comprometido, escopo mínimo.
    Ler trechos · ~30 minLeia a descrição e a mitigação de cada ataque; pule os diagramas de sequência na primeira passada. A seção de SSRF conversa direto com o urlGuard do Ally AI.
    modelcontextprotocol.io · especificação
    Resumo aqui na página

    Ligar um LLM a ferramentas reais cria superfícies de ataque novas. A spec nomeia cada uma com mitigação obrigatória. As que mais caem em conversa: token passthrough é proibido, servidor local exige consentimento explícito antes de rodar comando, e todo escopo começa mínimo.

    Os ataques e as defesas
    AtaqueComo aconteceMitigação
    Confused deputyServidor MCP que faz proxy pra API de terceiro com um client ID estático: um cookie de consentimento antigo deixa um client malicioso registrado dinamicamente pular a tela de consentimento e receber o código de autorizaçãoConsentimento por client no próprio servidor MCP, antes de redirecionar; redirect_uri com comparação exata; state aleatório, de uso único, gravado só depois do consentimento
    Token passthroughServidor aceita token que não foi emitido pra ele e repassa pra API de baixo: fura rate limit e auditoria, e vira proxy de exfiltraçãoO servidor MUST NOT aceitar token que não tenha sido explicitamente emitido pra ele
    SSRFServidor malicioso põe URLs internas (169.254.169.254, localhost, IP privado) nos metadados de OAuth que o cliente segueHTTPS obrigatório, bloquear faixas privadas e link-local, validar cada redirect, proxy de saída; cuidado com DNS rebinding (TOCTOU)
    State handle hijackingO MCP novo é sem estado e não tem sessão no protocolo; o servidor que precisa lembrar algo (carrinho, workflow) entrega um handle que volta como argumento. Atacante que obtém ou adivinha o handle opera no estado de outro usuárioPosse do handle nunca é autenticação; handle aleatório e com expiração; chave <user_id>:<handle> com o usuário vindo do token verificado
    Mix-up attackO cliente fala com vários servidores de autorização; um deles, controlado pelo atacante, faz o cliente mandar a ele um código emitido por outro, honestoValidar a resposta de autorização contra o servidor registrado antes do redirect (iss).     Localhost redirect URI impersonationCliente nativo usa redirect_uri em localhost; o atacante apresenta o client_id legítimo, escuta numa porta qualquer e recebe o código quando o usuário aprovaO servidor de autorização mostra aviso extra pra redirect só em localhost e exibe o host do redirect na tela de consentimento
    Servidor local comprometidoConfiguração “um clique” com comando de inicialização malicioso, que roda com os privilégios do clienteMostrar o comando exato, sem truncar, e exigir aprovação; sandbox; preferir stdio ou exigir token em HTTP local
    URL de autorização maliciosajavascript: aberto com window.open (XSS) ou URL passada pra shell (RCE)Aceitar só https:// (ou http:// em loopback), nunca abrir URL via shell, CSP no cliente web
    Escopo amplo demaisToken roubado com files:*/admin:* abre tudo de uma vezEscopo inicial mínimo e elevação progressiva por desafio WWW-Authenticate
    A ligação com o que você já fez
    • A seção de SSRF descreve o mesmo problema que o urlGuard do Ally AI resolve: bloquear faixas IANA, validar redirect, e a ressalva de DNS rebinding, que o seu código já documenta como limite conhecido.
    • A recomendação de CSP com nonce pra clientes web é a mesma do Gabarita.

    Frase de entrevista: “Num servidor MCP eu trato a ferramenta como API pública: autorização em toda request, token emitido pra mim e não repassado, escopo mínimo, e qualquer URL que vem de fora passa pelo mesmo filtro de SSRF.”

  • People + AI Guidebook — Explainability + Trust
    O capítulo do Google PAIR sobre calibrar confiança: fontes de dado, explicação ligada à ação, e como (e quando não) mostrar a confiança do modelo.
    Ler inteiro · ~30 minCapítulo único. A seção “Manage influence on user decisions” é a que mais rende em entrevista de AI UX.
    pair.withgoogle.com · Google
    Resumo aqui na página

    O objetivo não é fazer o usuário confiar na IA, é fazer ele confiar na medida certa: nem aceitar tudo às cegas, nem descartar tudo. O capítulo dá quatro alavancas: explicar a fonte, explicar no momento certo, explicar só o que ajuda a decidir, e escolher com cuidado se e como mostrar a confiança do modelo.

    1. Ajudar a calibrar a confiança
    • Articule as fontes de dado: o que está sendo usado, se é pessoal ou agregado, como remover. Isso evita surpresa de privacidade e mostra ao usuário quando ele deve passar por cima do sistema.
    • Ligue a explicação à ação do usuário: “só aparecem restaurantes italianos porque o raio é de uma quadra”. A relação de causa e efeito ensina rápido.
    • Considere o que está em jogo: o trajeto de todo dia não precisa de explicação; o trajeto pro aeroporto precisa avisar que o trânsito só atualiza de hora em hora.
    2. Confiança ao longo do produto

    Estabelecer (deixar claros capacidades e limites desde o onboarding), crescer (privacidade explícita, poder testar sem risco), manter (aumentar a automação aos poucos) e recuperar (plano pra quando errar, e ensinar o usuário a corrigir).

    3. Otimizar pra entendimento
    • Explicação parcial que serve à decisão, não o algoritmo inteiro.
    • Tipos: explicação geral do sistema, explicação de uma saída específica, contrafactual (“não é um bordo porque não tem 5 pontas”), exemplos parecidos, e explicação por interação (“e se eu mudar isso?”).
    4. Mostrar (ou não) a confiança do modelo
    FormatoQuando serve
    Categórico (alta/média/baixa)Cada faixa tem uma ação clara pro usuário
    N-best (“pode ser A, B ou C”)Confiança baixa: convida o usuário a julgar
    Numérico (%)Arriscado: o usuário não sabe o que 80% quer dizer e espera 100% no óbvio
    Visualização (barra de erro)Público especialista

    A primeira pergunta é se mostrar a confiança muda a decisão. Se não muda, ou pode enganar quem não é técnico, não mostre. E teste com usuários reais antes de implementar.

    Frase de entrevista: “Eu não mostro porcentagem de confiança. Mostro a fonte. No Gabarita, o resumo da IA vem com o trecho literal do documento, e o que não dá pra verificar não é exibido.”

    Dezoito diretrizes de design pra produtos com IA, da Microsoft Research (CHI 2019, validadas com 49 designers em 20 produtos). Elas se organizam por quando a interação acontece: no início, durante, quando a IA erra, e ao longo do tempo. Servem de checklist de revisão de tela.

    As 18, por fase
    FaseDiretrizes
    No inícioG1 Deixar claro o que o sistema faz · G2 Deixar claro quão bem ele faz
    Durante a interaçãoG3 Agir no momento certo pelo contexto · G4 Mostrar informação relevante ao contexto · G5 Respeitar normas sociais · G6 Mitigar vieses sociais
    Quando a IA erraG7 Invocação eficiente · G8 Descarte eficiente · G9 Correção eficiente · G10 Limitar o escopo na dúvida · G11 Explicar por que fez o que fez
    Ao longo do tempoG12 Lembrar interações recentes · G13 Aprender com o comportamento · G14 Atualizar e adaptar com cautela · G15 Incentivar feedback granular · G16 Mostrar a consequência das ações do usuário · G17 Controles globais · G18 Avisar sobre mudanças
    As que mais rendem numa revisão de produto
    • G2: a maioria das telas de IA diz o que faz e esquece o quão bem. O Ally AI deveria dizer que o teste automático cobre só parte do WCAG, como o próprio CLAUDE.md exige.
    • G9 + G8: quando a IA erra, corrigir ou dispensar tem de custar um clique. No Gabarita, editar a frase-chave do caderno e reportar a questão fazem esse papel.
    • G10: na dúvida, faça menos. É o que o Gabarita faz quando a citação não confere: publica a diretriz sem resumo.
    • G11: explicar o porquê. A citação literal é uma forma de G11.
    • G15: feedback granular (por item, não “avalie o app”). O report por categoria do Gabarita é G15; o Ally AI ainda não tem.

    Cada diretriz na biblioteca tem padrões de design associados, com exemplos. Use como consulta quando for desenhar uma tela específica.

  • Micro Frontends (Cam Jackson, martinfowler.com)
    O artigo de referência: definição, benefícios, as cinco formas de integração, estilo, biblioteca compartilhada, comunicação entre apps e as desvantagens.
    Ler trechos · ~40 minLeia “Benefits”, “Integration approaches”, “Shared component libraries” e “Downsides”. O exemplo completo de código é opcional.
    martinfowler.com
    Resumo aqui na página

    Microfrontend é “aplicações de front entregáveis de forma independente, compostas num todo maior”. O ganho é organizacional: times autônomos, deploy independente, migração aos poucos. O preço é payload, ambiente e governança. Não é ferramenta de performance nem de time pequeno.

    Benefícios
    • Upgrade incremental: trocar o legado pedaço a pedaço (strangler), decidindo a tecnologia caso a caso.
    • Bases simples e desacopladas: fronteira por domínio de negócio dificulta acoplamento acidental.
    • Deploy independente: cada parte com seu pipeline, sem coordenar release.
    • Times autônomos: organizados por funcionalidade vertical, não por camada técnica.
    As cinco formas de integrar
    AbordagemComoTrade-off
    Template no servidorFragmentos HTML compostos no servidor (SSI)Simples; cada pipeline cuida do seu fragmento
    Build-timeCada micro é um pacote npm do containerRelease em lockstep: perde o deploy independente, que é o ponto todo
    Iframe em runtimeCada app num iframeIsolamento grátis; roteamento, deep link e responsividade ficam difíceis
    JavaScript em runtimeCada bundle expõe uma função global que o container chamaA mais flexível e a mais usada
    Web Components em runtimeCada micro define um custom elementMesma flexibilidade, dentro do padrão da plataforma
    Estilo, biblioteca compartilhada e comunicação
    • CSS é global: precisa de convenção (BEM), CSS Modules, CSS-in-JS ou shadow DOM.
    • Biblioteca de componentes compartilhada: só UI, sem lógica de domínio, e só depois que o padrão emergiu (criar cedo demais gera churn). Funciona melhor com um time guardião que aceita contribuição.
    • Comunicação mínima entre micros: custom events, callbacks do container pra baixo, ou a própria URL. Cada micro tem seu estado, sem store global.
    • Backend: um BFF por micro; autenticação no container, com token injetado nos micros.
    Desvantagens
    • Payload: dependências duplicadas. Extrair as comuns reintroduz acoplamento de build.
    • Diferença de ambiente: desenvolver isolado e quebrar quando integrado.
    • Complexidade operacional e de governança: mais repositórios, pipelines e decisões descentralizadas. Exige maturidade de automação antes de adotar.

    Frase de entrevista: “Microfrontend resolve um problema de times, não de tráfego. Antes dele eu iria de monorepo com fronteiras de módulo e uma biblioteca de componentes.”

MCP Apps: a interface dentro da conversa

Resposta de texto só vai até certo ponto. Quando a pessoa precisa explorar dado, preencher um formulário com muitas opções ou aprovar vários itens, o MCP Apps (extensão oficial do protocolo) deixa o servidor devolver uma interface HTML interativa que o host mostra na própria conversa.

  1. A descrição da ferramenta traz _meta.ui.resourceUri, apontando pra um recurso ui:// do servidor.
  2. O host busca esse HTML (pode até pré-carregar antes da chamada) e o renderiza num iframe isolado.
  3. O app e o host trocam mensagens JSON-RPC por postMessage: o app pode chamar ferramentas do servidor, e o host empurra resultados novos pro app.
  4. A segurança vem do isolamento: o app não alcança o DOM, os cookies nem o armazenamento do host, e as origens externas que ele pode carregar são declaradas em _meta.ui.csp.

Quando vale: dado complexo pra explorar (mapa, gráfico com filtro), configuração com muitas opções interdependentes, mídia rica, monitoramento em tempo real e fluxo de várias etapas (aprovar itens um a um). Quando não: se uma resposta em texto resolve, ou se a pessoa vai precisar do app fora da conversa. Ligação com o R1: na Generative UI o front é seu e escolhe componentes seus; no MCP Apps o host é de outra empresa e o servidor entrega a interface, por isso o isolamento do iframe é a parte central do desenho.

I'd build with the official TypeScript SDK, a tool with a Zod inputSchema and a description of when to use it, stdio locally and HTTP remotely with proper authorization, tokens issued to my server and never passed through, minimal scopes, and confirmation for write actions.”

Munição da sua entrevista · src/lib/diretrizes/citacao.ts

O Gabarita resume diretrizes clínicas novas com IA, num domínio em que uma frase inventada pode ensinar conduta errada a um futuro médico. A saída fácil seria pôr um revisor humano em cada resumo. A escolhida foi outra: a IA tem de devolver, junto do resumo, o trecho do documento que o sustenta, e o código confere que esse trecho existe palavra por palavra no texto que ela leu, já truncado (pra que “citar” não vire adivinhar o resto do documento). Se não confere, o resumo é descartado e a diretriz entra só com título e link. Na tela, a citação aparece embaixo do resumo: é ela, e não a síntese, que carrega a autoridade.

Por que isso importa: é o padrão “a IA propõe, o código verifica” aplicado a AI UX. Responde de uma vez três perguntas que toda vaga de IA faz: como você lida com alucinação, como mostra fonte, e quando dispensa humano no circuito (quando dá pra ter uma verificação determinística no lugar dele).

Responda em voz alta · só depois abra o gabarito
  1. Qual a diferença entre tool calling e MCP? Se a API do modelo já faz tool calling, pra que MCP?
    ver resposta

    Tool calling é o mecanismo do modelo: você descreve funções com JSON Schema e a API responde “quero chamar x com estes argumentos”; executar é problema da sua aplicação. MCP é o protocolo que padroniza de onde vêm essas ferramentas: um servidor publica tools/resources/prompts uma vez, e qualquer host (Claude Code, VS Code, seu app) descobre com tools/list e executa com tools/call.

    O ganho é de distribuição: sem padrão, cada app integra cada serviço (N×M); com MCP, cada serviço escreve um servidor e cada app escreve um cliente (N+M). Os dois convivem: o host converte as tools MCP em definições de tool calling pro modelo.

  2. Você vai publicar um servidor MCP. Quando usar stdio e quando usar Streamable HTTP?
    ver resposta

    stdio quando o servidor roda na máquina do usuário, como processo filho do host: um cliente só, sem rede, e acesso restrito a quem iniciou o processo. É o certo pra ferramenta local (sistema de arquivos, git, um CLI seu). Streamable HTTP quando o servidor é remoto e atende muitos clientes: POST do cliente pro servidor, SSE opcional pra streaming, e autenticação HTTP. A spec recomenda OAuth e proíbe token passthrough (aceitar e repassar token que não foi emitido pro próprio servidor).

  3. Como mostrar ao usuário o quanto confiar numa resposta de IA, sem jogar uma porcentagem na tela?
    ver resposta

    O PAIR desaconselha porcentagem crua: o usuário não sabe o que “80%” significa e espera 100% no óbvio. As alternativas: categorias (alta/média/baixa) com uma ação clara pra cada uma, N-best (“pode ser A, B ou C”, que convida o julgamento quando a confiança é baixa) e, acima de tudo, mostrar a fonte.

    No Gabarita, a confiança é comunicada pela citação literal verificada, embaixo do resumo. E quando não dá pra verificar, a resposta não é exibida: às vezes a melhor indicação de confiança é não mostrar o que não passou.

  4. Um time de 4 pessoas propõe migrar o front pra microfrontends “pra escalar”. O que você pergunta antes?
    ver resposta

    Microfrontend resolve problema de organização, não de tráfego: vários times autônomos que precisam fazer deploy sem coordenar, ou uma migração incremental (strangler) de um front legado. Com 4 pessoas num time só, você paga os custos (dependências duplicadas no payload, ambientes que divergem, pipelines e governança multiplicados) sem colher o benefício.

    As perguntas: quantos times vão ser donos de partes diferentes? O deploy conjunto é um gargalo hoje? Um monorepo com fronteiras de módulo e uma biblioteca de componentes resolveria? Quase sempre resolve, e é o passo que vem antes de microfrontends de qualquer forma.

  5. “Seu sistema é multi-cloud?” Como responder com o que você tem, sem inflar?
    ver resposta

    “Não, e de propósito. Multi-cloud de verdade, a mesma carga rodando em duas nuvens, custa IAM duplicado, egress entre provedores e ficar preso ao menor denominador comum dos serviços. Faz sentido por exigência regulatória ou de cliente, ou por resiliência num nível que um produto do meu tamanho não tem. O que eu fiz foi portabilidade: no Gabarita, o storage é uma interface que escolhe R2, Vercel Blob ou disco por variável de ambiente, falando o protocolo do S3. No Ally AI, a API é um container que rodou no Render e vai pro Cloud Run, e a escolha foi por benchmark de CPU.” Depois disso, a tabela de equivalência (Cloud Run ↔ App Runner/Fargate ↔ Container Apps) mostra que você sabe para onde iria.

  6. O que são MCP Apps e quando valem mais que uma resposta em texto ou um link pra um web app?
    ver resposta

    É uma extensão do MCP em que a ferramenta declara uma interface (_meta.ui.resourceUri apontando pra um recurso ui://) e o host a renderiza num iframe isolado, dentro da conversa; a comunicação com o host é por postMessage, em JSON-RPC, e o app pode chamar ferramentas do servidor.

    Contra o texto, ganha em exploração, formulário e aprovação em lote. Contra o link pra um web app, ganha em contexto (a pessoa não troca de aba nem perde a conversa), em fluxo de dados nos dois sentidos sem construir API e autenticação próprias, e em segurança, porque o iframe isolado deixa o host renderizar app de terceiro sem confiar totalmente no autor. Se nada disso se aplica, o web app comum é mais simples.
