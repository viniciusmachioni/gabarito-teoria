1 · VerO básico, em linguagem simples

Leia isto antes do resto. Cada cartão responde a três perguntas: qual é o problema, como se resolve e o que você diz na entrevista.

1. MCP em uma frase

O que éO Model Context Protocol é um padrão para um app de IA (o host, como o Claude Code ou o VS Code) plugar ferramentas de qualquer fornecedor. Pense numa tomada universal: quem faz a ferramenta escreve um servidor MCP uma vez, e ela funciona em qualquer app que fale MCP.

Por que existeSem um padrão, cada app precisa de uma integração própria para cada ferramenta: 3 apps × 3 ferramentas = 9 integrações. Com MCP, cada app implementa o protocolo uma vez e cada ferramenta também: 3 + 3 = 6.

Na entrevista“MCP transforma N vezes M integrações em N mais M.”

2. As peças do MCP

Host, client, serverO host é o app de IA. Dentro dele há um client para cada servidor conectado. O server é quem oferece as ferramentas.

O que o servidor ofereceTools são ações que o modelo pode pedir (buscar questões, abrir um ticket). Resources são dados para dar contexto (um arquivo, um registro). Prompts são modelos de pedido prontos.

O cicloO client pergunta “quais ferramentas você tem?” (tools/list). O modelo escolhe uma, e o client a chama (tools/call) com os argumentos.

Na entrevista“O servidor publica tools, resources e prompts. O host lista as tools e chama a que o modelo escolher.”

3. Segurança no MCP

O riscoUm servidor MCP roda com permissões de verdade: lê arquivos, chama APIs, grava no banco. Um servidor local é um programa rodando na sua máquina.

As regrasServidor remoto usa OAuth. Nunca repasse o token que recebeu do usuário direto para outra API (token passthrough): peça um token emitido para você. Confira toda URL que o modelo mandar antes de acessá-la, para ninguém usar o seu servidor para alcançar a rede interna (SSRF). Peça só as permissões necessárias.

Na entrevista“Ferramenta MCP é código com permissão real. Valido argumento, não repasso token e peço o mínimo de escopo.”

4. Tool calling ou MCP?

Tool callingÉ como o modelo pede uma ação: a API devolve “quero chamar x com estes argumentos” (veja o R1).

MCPÉ como as ferramentas são distribuídas entre apps. Por baixo, o host continua usando tool calling para o modelo escolher qual ferramenta MCP chamar.

Na entrevista“Tool calling é o mecanismo do modelo. MCP é o protocolo que leva as ferramentas para qualquer app.”

5. AI UX: confiança na medida certa

O objetivoNão é fazer a pessoa confiar sempre na IA. É fazer ela confiar quando deve e desconfiar quando deve.

ComoMostre a fonte de cada afirmação (citação). Diga o que o sistema faz e o quanto ele acerta. Torne fácil corrigir ou descartar a resposta. Peça feedback específico (“este trecho está errado”), não só um polegar. Em vez de “87% de confiança”, prefira categorias ligadas a uma ação: “confiança baixa, confira a fonte”.

Na entrevista“Boa AI UX calibra a confiança: mostra a fonte, deixa corrigir e diz quando a resposta é fraca.”

6. AI UX de agente

Progresso por etapa“Lendo o contrato… Comparando com o modelo… Escrevendo o resumo” diz mais que um spinner.

Aprovação antes de agirAção com efeito real (enviar, apagar, pagar) espera confirmação, de preferência mostrando o que vai mudar.

Marcar o que é IAA pessoa precisa saber o que foi gerado por IA.

Falhar com avisoQuando a IA falha, a tela diz isso e oferece um caminho. Nunca some com a resposta em silêncio.

Na entrevista“Num agente, eu mostro cada etapa, peço aprovação antes de agir e aviso quando algo dá errado.”

7. Microfrontends e multi-cloud em um minuto

MicrofrontendsComo no R3: valem quando há vários times autônomos ou uma migração aos pedaços. Com um time só, um monorepo bem dividido costuma ser melhor.

Multi-cloudRodar a mesma aplicação em duas nuvens ao mesmo tempo. É caro e raro.

PortabilidadeUsar interfaces que deixam trocar uma peça de fornecedor. Exemplo: o Gabarita grava arquivos pela API do S3, então trocar o S3 pelo Cloudflare R2 é mudar configuração, não código. É o que quase todo mundo deveria querer.

Na entrevista“Raramente preciso de multi-cloud. Quero portabilidade: poder trocar uma peça sem reescrever o app.”

Host
o app de IA que a pessoa usa (Claude Code, VS Code, um chat próprio).
JSON-RPC
formato simples de mensagem para pedir que outro programa execute um método e devolva o resultado. É o que o MCP usa.
stdio
entrada e saída padrão de um processo: o jeito de falar com um servidor MCP local.
SSRF
Server-Side Request Forgery: enganar um servidor para que ele acesse um endereço que não deveria.
HAX
as 18 diretrizes de interação humano-IA publicadas pela Microsoft.

  • MCP — Architecture overview
    A página oficial que define host/client/server, as duas camadas (dados e transporte), as primitivas e um exemplo passo a passo em JSON-RPC.
    Ler trechos · ~30 minLeia “Participants”, “Layers” e “Primitives” inteiros; no exemplo, foque em tools/list e tools/call. Os blocos de JSON de notificação são consulta.
    modelcontextprotocol.io · oficial
    Resumo aqui na página

    Em uma frase: o MCP é um protocolo para um app de IA descobrir e usar ferramentas e dados de fora. Ele não diz como o app usa o modelo, só como encontra e chama as ferramentas. A estrutura é: o app (host) cria um client para cada servidor conectado, e eles conversam por mensagens JSON-RPC.

    No mundo realA Anthropic lançou o MCP em novembro de 2024. Em poucos meses, a OpenAI, o Google e a Microsoft anunciaram suporte, e ele chegou ao ChatGPT, ao Gemini, ao VS Code e ao Copilot. O GitHub mantém um servidor MCP oficial: com ele, um assistente consegue ler issues e abrir pull requests em qualquer app compatível, sem uma integração própria para cada app.

    Quem é quem
    • Host: o app de IA que a pessoa usa (Claude Code, VS Code, ChatGPT).
    • Client: uma conexão dentro do host com um servidor. Conectar ao GitHub e ao sistema de arquivos são dois clients.
    • Servidor: o programa que oferece ferramentas e dados. É local quando roda na sua máquina, conversando pela entrada e saída do processo (stdio). É remoto quando roda na internet, por HTTP, e atende muita gente.
    As duas camadas
    • Dados: as mensagens em si, como listar ferramentas, chamar uma ferramenta e receber avisos.
    • Transporte: por onde elas passam. stdio para processos locais, sem rede. Streamable HTTP para servidores remotos, com login por OAuth recomendado.
    • As mensagens são as mesmas nos dois transportes. Trocar um pelo outro não muda a lógica do servidor.
    O que um servidor oferece
    • Tools: ações que o modelo pode pedir, como consultar um banco ou chamar uma API.
    • Resources: dados para dar contexto, como o conteúdo de um arquivo.
    • Prompts: modelos de pedido prontos.
    • Do lado do cliente existe a elicitation: o servidor pode pedir ao usuário mais uma informação ou uma confirmação.
    O ciclo de uma ferramenta
    1. tools/list: o servidor devolve cada ferramenta com nome, descrição e formato dos argumentos (em JSON Schema). O host junta as ferramentas de todos os servidores e entrega a lista ao modelo.
    2. tools/call: quando o modelo decide usar uma, o host manda o pedido ao servidor certo e devolve o resultado para a conversa.
    3. Na versão atual do protocolo (2026-07-28), não há sessão: cada pedido leva a versão e as capacidades. Se as ferramentas mudam, o servidor pode avisar, mas o cliente também deve conferir de tempos em tempos.

    Frase de entrevista: “MCP não substitui tool calling, ele distribui as ferramentas. O modelo continua pedindo funções descritas em JSON Schema; o MCP padroniza como o app encontra essas funções em qualquer servidor.”

  • MCP — Security Best Practices
    Os ataques específicos de MCP com mitigação: confused deputy, token passthrough, SSRF, sequestro de state handle, mix-up, impersonação de redirect em localhost, servidor local comprometido, escopo mínimo.
    Ler trechos · ~30 minLeia a descrição e a mitigação de cada ataque; pule os diagramas de sequência na primeira passada. A seção de SSRF conversa direto com o urlGuard do Ally AI.
    modelcontextprotocol.io · especificação
    Resumo aqui na página

    Em uma frase: ligar um modelo a ferramentas reais abre caminhos novos de ataque, e a especificação do MCP nomeia cada um com a defesa obrigatória. As três que mais caem em conversa: não repassar token, pedir consentimento explícito antes de rodar um servidor local e começar com o mínimo de permissão.

    No mundo realEm 2025, pesquisadores da Invariant Labs mostraram um ataque com o servidor MCP do GitHub: uma issue pública com instruções escondidas fazia o agente de quem a lia vazar dados de repositórios privados dessa pessoa. O servidor não tinha bug. O problema era um agente com acesso amplo demais, obedecendo a um texto de terceiro. É por isso que permissão mínima e aprovação humana aparecem em toda conversa sobre agentes.

    Os ataques, em linguagem simples
    • Token repassado (token passthrough): o servidor recebe um token emitido para outra API e o repassa direto. Isso fura os limites e a auditoria da API de baixo. Regra: o servidor não pode aceitar token que não foi emitido para ele.
    • Representante confuso (confused deputy): um servidor que faz a ponte com uma API de terceiro usa uma identidade única para todos. Um app malicioso aproveita um consentimento antigo e recebe acesso sem a pessoa ver a tela de permissão. Defesa: pedir consentimento para cada app, no próprio servidor.
    • SSRF: um servidor malicioso põe endereços internos (localhost, IPs privados, o endereço de metadados da nuvem) num lugar que o cliente vai acessar. Defesa: exigir HTTPS, bloquear endereços privados e conferir cada redirecionamento. O urlGuard do Ally AI resolve exatamente isso.
    • Roubo de identificador de estado (state handle hijacking): sem sessão no protocolo, um servidor que precisa lembrar algo (um carrinho) devolve um identificador. Quem consegue o identificador de outra pessoa opera no carrinho dela. Defesa: ter o identificador nunca prova quem você é. Guarde o estado ligado ao usuário do token verificado.
    • Troca de servidor de login (mix-up): o cliente fala com vários servidores de autorização, e um deles, do atacante, recebe um código emitido por outro. Defesa: conferir de qual servidor veio a resposta (o campo iss). O PKCE sozinho não resolve, porque o segredo dele também iria para o atacante.
    • Servidor local malicioso: uma instalação “em um clique” esconde um comando perigoso, que roda com as suas permissões. Defesa: mostrar o comando completo e exigir aprovação.
    • Permissão ampla demais: um token roubado com acesso a tudo abre tudo de uma vez. Defesa: começar com o mínimo e pedir mais só quando precisar.

    Frase de entrevista: “Num servidor MCP eu trato a ferramenta como API pública: autorização em todo pedido, token emitido para mim e não repassado, permissão mínima, e qualquer URL que vem de fora passa pelo filtro de SSRF.”

  • People + AI Guidebook — Explainability + Trust
    O capítulo do Google PAIR sobre calibrar confiança: fontes de dado, explicação ligada à ação, e como (e quando não) mostrar a confiança do modelo.
    Ler inteiro · ~30 minCapítulo único. A seção “Manage influence on user decisions” é a que mais rende em entrevista de AI UX.
    pair.withgoogle.com · Google
    Resumo aqui na página

    Em uma frase: o objetivo não é fazer a pessoa confiar na IA, é fazer ela confiar na medida certa: nem aceitar tudo às cegas, nem descartar tudo. O guia do Google dá quatro caminhos: mostrar a fonte, explicar na hora certa, explicar só o que ajuda a decidir e pensar bem antes de mostrar uma porcentagem de confiança.

    No mundo realEm 2024, as respostas de IA da busca do Google sugeriram passar cola na pizza para o queijo grudar, a partir de uma piada antiga de fórum, e muita gente só percebeu o erro porque a resposta virou notícia. O Perplexity mostra a fonte numerada ao lado de cada frase, e a pessoa confere com um clique. E, em 2024, um tribunal do Canadá obrigou a Air Canada a honrar uma regra de reembolso que o chatbot dela tinha inventado. A empresa responde pelo que a IA diz.

    1. Ajudar a calibrar a confiança
    • Diga de onde vêm os dados: o que está sendo usado e se é pessoal. Isso evita surpresa e mostra quando a pessoa deve passar por cima do sistema.
    • Ligue a explicação à ação da pessoa: “só aparecem restaurantes italianos porque o raio é de uma quadra”. Causa e efeito ensinam rápido.
    • Pense no que está em jogo: o trajeto de todo dia não precisa de explicação. O trajeto para o aeroporto precisa avisar que o trânsito só atualiza de hora em hora.
    2. Confiança ao longo do tempo
    • Estabelecer (deixar claros o que o sistema faz e os limites dele), crescer (deixar testar sem risco), manter (aumentar a automação aos poucos) e recuperar (ter um plano para quando errar).
    3. Explicar o suficiente
    • Uma explicação parcial que ajuda a decidir vale mais que o algoritmo inteiro.
    • Formas que funcionam: exemplos parecidos, “não é X porque falta Y” e “e se eu mudar isto?”.
    4. Mostrar ou não a confiança do modelo
    • Categorias (alta, média, baixa): funcionam quando cada faixa tem uma ação clara.
    • Várias opções (“pode ser A, B ou C”): boas quando a confiança é baixa, porque convidam a pessoa a julgar.
    • Porcentagem: arriscada. A pessoa não sabe o que 80% quer dizer e espera 100% no óbvio.
    • A primeira pergunta é se mostrar a confiança muda a decisão. Se não muda, não mostre.

    Frase de entrevista: “Eu não mostro porcentagem de confiança. Mostro a fonte. No Gabarita, o resumo da IA vem com o trecho literal do documento, e o que não dá para conferir não é exibido.”

  • HAX Toolkit — Guidelines for Human-AI Interaction
    As 18 diretrizes da Microsoft Research (CHI 2019), cada uma com padrões de design e exemplos de produto real.
    Ler trechos · ~25 minLeia os 18 títulos e abra G1, G2, G9, G11 e G15. O resto é consulta pra quando for desenhar uma tela específica.
    microsoft.com · Microsoft Research
    Resumo aqui na página

    Em uma frase: são 18 diretrizes de design para produtos com IA, publicadas pela Microsoft Research em 2019 e testadas com 49 designers em 20 produtos. Elas se organizam pelo momento da interação: no começo, durante, quando a IA erra e ao longo do tempo. Servem de checklist para revisar uma tela.

    No mundo realO autocompletar do Gmail e o do GitHub Copilot mostram a sugestão em cinza: aceitar é apertar Tab, e recusar é só continuar digitando. São as diretrizes 8 e 9 (descartar e corrigir com o menor esforço possível) aplicadas a milhões de pessoas por dia. Uma sugestão que exigisse fechar uma janela para recusar seria abandonada.

    As 18, por momento
    • No começo: G1 deixar claro o que o sistema faz; G2 deixar claro quão bem ele faz.
    • Durante: G3 agir na hora certa; G4 mostrar o que é relevante ao contexto; G5 respeitar normas sociais; G6 evitar vieses.
    • Quando erra: G7 fácil de chamar; G8 fácil de descartar; G9 fácil de corrigir; G10 na dúvida, fazer menos; G11 explicar por que fez o que fez.
    • Ao longo do tempo: G12 lembrar o que aconteceu há pouco; G13 aprender com o uso; G14 mudar com cuidado; G15 pedir feedback específico; G16 mostrar a consequência das ações; G17 controles gerais; G18 avisar sobre mudanças.
    As que mais rendem numa revisão
    • G2: a maioria das telas diz o que a IA faz e esquece de dizer quão bem. O Ally AI deveria avisar que o teste automático cobre só parte da WCAG.
    • G8 e G9: descartar ou corrigir tem de custar um clique. No Gabarita, editar a frase-chave e reportar a questão fazem esse papel.
    • G10: na dúvida, faça menos. O Gabarita publica a diretriz sem resumo quando a citação não confere.
    • G15: feedback por item, e não “avalie o app”. O report por categoria do Gabarita é G15.

    Frase de entrevista: “Antes de lançar uma tela de IA, eu passo pelas 18 diretrizes do HAX como checklist. As que mais pegam são G2, dizer quão bem funciona, e G15, feedback por item.”

  • Micro Frontends (Cam Jackson, martinfowler.com)
    O artigo de referência: definição, benefícios, as cinco formas de integração, estilo, biblioteca compartilhada, comunicação entre apps e as desvantagens.
    Ler trechos · ~40 minLeia “Benefits”, “Integration approaches”, “Shared component libraries” e “Downsides”. O exemplo completo de código é opcional.
    martinfowler.com
    Resumo aqui na página

    Em uma frase: microfrontends são partes do front que times diferentes publicam de forma independente e que juntas formam um produto. O ganho é de organização: times autônomos, deploy independente, migração aos poucos. O preço é peso, ambientes diferentes e coordenação. Não é ferramenta de performance nem de time pequeno.

    No mundo realA DAZN, plataforma de streaming de esportes presente em dezenas de países, dividiu o front por área do produto, cada uma com o seu time e o seu deploy, e o arquiteto do projeto escreveu um livro sobre isso. Os exemplos da Zalando e do Spotify estão no R3. Em comum: centenas de engenheiros. Num time de cinco pessoas, o custo vem sem o benefício.

    Benefícios
    • Troca aos pedaços: substituir o sistema antigo parte por parte.
    • Bases menores: fronteiras por área de negócio dificultam o acoplamento acidental.
    • Deploy independente: cada parte com o seu pipeline, sem combinar a data de lançamento.
    • Times autônomos: organizados por funcionalidade, e não por camada técnica.
    As cinco formas de juntar
    • No servidor: fragmentos de HTML montados no servidor. Simples.
    • No build, como pacote npm: obriga a publicar tudo junto. Perde o deploy independente, que é o objetivo.
    • Com iframe: isolamento de graça, mas rotas, links diretos e layout responsivo ficam difíceis.
    • Com JavaScript no navegador: cada parte expõe uma função que o app principal chama. A mais flexível e a mais usada.
    • Com Web Components: a mesma flexibilidade, usando elementos HTML próprios.
    Desvantagens
    • Peso: dependências baixadas em dobro. Juntar as comuns traz de volta o acoplamento.
    • Ambientes diferentes: funciona isolado e quebra quando junta.
    • Coordenação: mais repositórios, pipelines e decisões espalhadas. Exige automação madura antes de adotar.

    Frase de entrevista: “Microfrontend resolve um problema de times, não de tráfego. Antes dele, eu iria de monorepo com fronteiras de módulo e uma biblioteca de componentes.”

MCP Apps: a interface dentro da conversa

Resposta de texto só vai até certo ponto. Quando a pessoa precisa explorar dado, preencher um formulário com muitas opções ou aprovar vários itens, o MCP Apps (extensão oficial do protocolo) deixa o servidor devolver uma interface HTML interativa que o host mostra na própria conversa.

  1. A descrição da ferramenta traz _meta.ui.resourceUri, apontando pra um recurso ui:// do servidor.
  2. O host busca esse HTML (pode até pré-carregar antes da chamada) e o renderiza num iframe isolado.
  3. O app e o host trocam mensagens JSON-RPC por postMessage: o app pode chamar ferramentas do servidor, e o host empurra resultados novos pro app.
  4. A segurança vem do isolamento: o app não alcança o DOM, os cookies nem o armazenamento do host, e as origens externas que ele pode carregar são declaradas em _meta.ui.csp.

Quando vale: dado complexo pra explorar (mapa, gráfico com filtro), configuração com muitas opções interdependentes, mídia rica, monitoramento em tempo real e fluxo de várias etapas (aprovar itens um a um). Quando não: se uma resposta em texto resolve, ou se a pessoa vai precisar do app fora da conversa. Ligação com o R1: na Generative UI o front é seu e escolhe componentes seus; no MCP Apps o host é de outra empresa e o servidor entrega a interface, por isso o isolamento do iframe é a parte central do desenho.

FAZER 1

Uma ferramenta MCP, no papel

15 min · JSON

Você vai expor a busca de questões do Gabarita como ferramenta MCP. Escreva em JSON: (1) como a ferramenta aparece na resposta de tools/list; (2) o pedido tools/call que o host manda quando o modelo pede 3 questões de cardiologia; (3) uma resposta de sucesso.

Regras

  • topic é texto e obrigatório. limit é inteiro de 1 a 20, com padrão 5.
  • A descrição precisa dizer ao modelo quando usar a ferramenta.

Pode consultarMCP: tools · JSON-RPC 2.0

dica

Os argumentos são descritos por um JSON Schema no campo inputSchema. As mensagens seguem o JSON-RPC 2.0: jsonrpc, id, method e params no pedido; result na resposta.

solução comentada
// (1) one item of result.tools in the tools/list response
{
  "name": "search_questions",
  "description": "Searches medical residency questions by topic. Use it when the user asks for questions to practice a subject.",
  "inputSchema": {
    "type": "object",
    "properties": {
      "topic": { "type": "string", "description": "Subject, for example cardiology or pediatrics" },
      "limit": { "type": "integer", "minimum": 1, "maximum": 20, "default": 5 }
    },
    "required": ["topic"]
  }
}

// (2) the host calls the tool
{ "jsonrpc": "2.0", "id": 7, "method": "tools/call",
  "params": { "name": "search_questions", "arguments": { "topic": "cardiology", "limit": 3 } } }

// (3) the server response
{ "jsonrpc": "2.0", "id": 7,
  "result": {
    "content": [{ "type": "text", "text": "3 cardiology questions: Q1012, Q1048, Q1101." }],
    "isError": false
  } }

O que mostrar ao entrevistador: o modelo decide usar a ferramenta lendo o name, a description e o inputSchema, então a descrição é parte do produto. O servidor valida os argumentos de novo antes de consultar o banco (o schema descreve, mas não protege). E erro da ferramenta volta como isError: true com um texto útil, para o modelo poder explicar o que houve.

Revisar · depois da solução

1 · Explique em voz alta
  1. Por que a descrição diz quando usar a ferramenta, e não só o que ela faz?
  2. Se o inputSchema já diz que limit vai de 1 a 20, por que o servidor valida de novo?
  3. Qual a diferença entre responder com isError: true e responder com um error do JSON-RPC?
respostas
  1. Porque o modelo escolhe a ferramenta lendo a descrição. “Busca questões” não diz em que situação ela serve; “use quando a pessoa pedir questões para treinar um assunto” diz.
  2. O schema descreve o que é esperado, mas não impede nada: qualquer cliente pode mandar limit: 5000. O servidor trata o argumento como um formulário vindo de fora.
  3. isError: true quer dizer “a ferramenta rodou e falhou” (o banco caiu, o tema não existe). O texto volta para o modelo, que pode explicar ou tentar outra coisa. O error do JSON-RPC é problema de protocolo: ferramenta que não existe, pedido malformado.
2 · Caça ao bug

Esta definição e este pedido foram escritos às pressas. Ache os quatro problemas.

{
  "name": "search_questions",
  "description": "Searches questions.",
  "inputSchema": {
    "type": "object",
    "properties": {
      "topic": { "type": "string" },
      "limit": { "type": "number", "maximum": 20, "default": 5 }
    }
  }
}

{ "jsonrpc": "2.0", "method": "tools/call",
  "params": { "name": "search_questions", "arguments": { "topic": "cardiology", "limit": 3 } } }
os erros
  1. A descrição não diz quando usar. O modelo tem menos informação para escolher esta ferramenta, ou escolhe na hora errada.
  2. limit é number e não tem mínimo. Aceita 2.5, 0 e -1. O certo é integer com minimum: 1.
  3. Falta "required": ["topic"]. O modelo pode chamar a ferramenta sem tema.
  4. O pedido não tem id. No JSON-RPC, uma mensagem sem id é uma notificação: quem recebe não manda resposta. O host fica esperando um resultado que nunca chega.
3 · Mude um requisito

A ferramenta passa a aceitar uma dificuldade opcional: fácil, média ou difícil. O que muda na definição? Clientes antigos quebram?

o que muda

Uma propriedade nova: "difficulty": { "type": "string", "enum": ["easy", "medium", "hard"], "description": "Use only if the user asks for a level" }. Ela não entra no required. O enum mostra ao modelo os valores válidos, e o servidor valida de novo.

Ninguém quebra: quem não manda a dificuldade continua funcionando, porque o campo é opcional. Essa é a regra para evoluir uma ferramenta (ou uma API): adicionar campo opcional é seguro; tornar obrigatório ou mudar o tipo de um campo existente quebra quem já usa.

FAZER 2

Revise esta tela de IA

15 min · crítica de produto

Um assistente resume contratos. A tela mostra o resumo com o selo “Confiança: 87%”, sem dizer de onde saiu cada frase. O botão “Aplicar sugestões” altera o contrato na hora. Quando a IA falha, o resumo simplesmente some. Proponha pelo menos quatro melhorias e diga qual problema cada uma resolve.

Pode consultaros cartões 5 e 6 do Ver · Google PAIR: People + AI Guidebook

dica

Releia os cartões 5 e 6: fonte, confiança, aprovação antes de agir, marcação do que é IA, falha com aviso e feedback específico.

solução comentada
  1. Citação por frase. Cada frase do resumo leva a um link para a cláusula de origem. A pessoa confere em vez de confiar às cegas.
  2. Confiança como categoria com ação. Troque “87%” por “confiança baixa nesta cláusula: confira o original”. Um número cru não diz o que fazer, e 87% parece mais certo do que é.
  3. Prévia e aprovação antes de aplicar. Mostre o antes e o depois de cada mudança, deixe aceitar uma por uma e ofereça desfazer. Alterar um contrato é uma ação com efeito real.
  4. Falha visível. “Não consegui resumir agora. Tente de novo ou leia o contrato completo.” Sumir em silêncio faz a pessoa achar que não havia nada a resumir.
  5. Marca de IA e feedback por trecho. Um selo “gerado por IA” e um “este trecho está errado” em cada frase. O feedback aponta exatamente o erro, e não só “não gostei”.

O que mostrar ao entrevistador: cada melhoria resolve um problema de confiança. A pessoa precisa saber de onde veio a resposta, quando desconfiar, o que vai mudar antes de mudar e o que fazer quando falha.

Revisar · depois da solução

1 · Explique em voz alta
  1. Por que “confiança baixa nesta cláusula: confira o original” é melhor que “87%”?
  2. Por que “aplicar” precisa de prévia e de desfazer, e não só de uma confirmação?
respostas
  1. O número não diz o que fazer, nem onde está a dúvida. A categoria aponta o trecho e a ação. E 87% passa uma precisão que o modelo não tem.
  2. A confirmação pergunta “tem certeza?” sem mostrar o que vai mudar, e as pessoas aprendem a clicar “sim” sem ler. A prévia mostra a mudança; o desfazer protege quando, mesmo assim, algo passa.
2 · Caça ao bug

Um colega propôs estas quatro melhorias. Cada uma tem um problema. Qual?

  1. “Melhorar o prompt para a confiança subir de 87% para 92%.”
  2. “Pôr um modal ‘Tem certeza?’ antes de Aplicar sugestões.”
  3. “Quando a IA falhar, mostrar o último resumo que deu certo.”
  4. “Pôr um 👍 e um 👎 no fim do resumo.”
os erros
  1. O problema nunca foi o valor, foi mostrar um número cru. 92% continua sem dizer o que conferir.
  2. Confirmar sem mostrar a mudança não protege (veja a pergunta 2 do passo 1). Faltam a prévia, o aceite de uma mudança por vez e o desfazer.
  3. O resumo antigo pode ser de outra versão do contrato. A pessoa lê um resumo errado achando que é o atual: é pior que a tela vazia. Se mostrar o antigo, diga claramente de quando ele é.
  4. Ajuda pouco. O 👎 não diz qual frase está errada, então ninguém consegue corrigir a partir dele. O feedback útil fica no trecho.

Todas as quatro parecem melhorias. A pergunta da revisão é a mesma do exercício: qual problema de confiança isto resolve de verdade?

3 · Mude um requisito

O assistente passa a enviar o contrato revisado por e-mail para o cliente. O que muda no desenho da tela?

o que muda

E-mail enviado não se desfaz. Então a aprovação humana fica obrigatória: a tela mostra o e-mail exato (destinatários, assunto, texto, anexo) e só envia depois de um clique explícito em “Enviar”. A IA nunca envia sozinha.

Para dar uma rede de proteção, faça como o Gmail no “desfazer envio”: segure o envio por alguns segundos depois do clique. E registre quem aprovou e quando. A regra geral: quanto menos reversível a ação, mais forte o controle humano.

Alucinação: a IA propõe, o código verifica decisão tomada

Em uma frase: O resumo da IA só é publicado se a citação que ela trouxe existir, palavra por palavra, no documento. Se não existir, a diretriz sai sem resumo.

Escolha

Restrição que forçou
O domínio é de risco (uma frase inventada ensina conduta errada a um futuro médico) e revisão humana em cada resumo não escala.

Multi-cloud: portabilidade sem rodar em duas nuvens decisão tomada

Restrição que forçou

Restrição que forçou

4 · ProvarPerguntas abertas e múltipla escolha

Responda em voz alta antes de abrir a resposta. A múltipla escolha, no fim, começa com três questões de aquecimento, só de conceito.

Responda em voz alta · só depois abra o gabarito
  1. Qual a diferença entre tool calling e MCP? Se a API do modelo já faz tool calling, pra que MCP?
    ver resposta

    Tool calling é o mecanismo do modelo: você descreve funções com JSON Schema e a API responde “quero chamar x com estes argumentos”; executar é problema da sua aplicação. MCP é o protocolo que padroniza de onde vêm essas ferramentas: um servidor publica tools/resources/prompts uma vez, e qualquer host (Claude Code, VS Code, seu app) descobre com tools/list e executa com tools/call.

    O ganho é de distribuição: sem padrão, cada app integra cada serviço (N×M); com MCP, cada serviço escreve um servidor e cada app escreve um cliente (N+M). Os dois convivem: o host converte as tools MCP em definições de tool calling pro modelo.

  2. Você vai publicar um servidor MCP. Quando usar stdio e quando usar Streamable HTTP?
    ver resposta

    stdio quando o servidor roda na máquina do usuário, como processo filho do host: um cliente só, sem rede, e acesso restrito a quem iniciou o processo. É o certo pra ferramenta local (sistema de arquivos, git, um CLI seu). Streamable HTTP quando o servidor é remoto e atende muitos clientes: POST do cliente pro servidor, SSE opcional pra streaming, e autenticação HTTP. A spec recomenda OAuth e proíbe token passthrough (aceitar e repassar token que não foi emitido pro próprio servidor).

  3. Como mostrar ao usuário o quanto confiar numa resposta de IA, sem jogar uma porcentagem na tela?
    ver resposta

    O PAIR desaconselha porcentagem crua: o usuário não sabe o que “80%” significa e espera 100% no óbvio. As alternativas: categorias (alta/média/baixa) com uma ação clara pra cada uma, N-best (“pode ser A, B ou C”, que convida o julgamento quando a confiança é baixa) e, acima de tudo, mostrar a fonte.

    No Gabarita, a confiança é comunicada pela citação literal verificada, embaixo do resumo. E quando não dá pra verificar, a resposta não é exibida: às vezes a melhor indicação de confiança é não mostrar o que não passou.

  4. Um time de 4 pessoas propõe migrar o front pra microfrontends “pra escalar”. O que você pergunta antes?
    ver resposta

    Microfrontend resolve problema de organização, não de tráfego: vários times autônomos que precisam fazer deploy sem coordenar, ou uma migração incremental (strangler) de um front legado. Com 4 pessoas num time só, você paga os custos (dependências duplicadas no payload, ambientes que divergem, pipelines e governança multiplicados) sem colher o benefício.

    As perguntas: quantos times vão ser donos de partes diferentes? O deploy conjunto é um gargalo hoje? Um monorepo com fronteiras de módulo e uma biblioteca de componentes resolveria? Quase sempre resolve, e é o passo que vem antes de microfrontends de qualquer forma.

  6. O que são MCP Apps e quando valem mais que uma resposta em texto ou um link pra um web app?
    ver resposta

    É uma extensão do MCP em que a ferramenta declara uma interface (_meta.ui.resourceUri apontando pra um recurso ui://) e o host a renderiza num iframe isolado, dentro da conversa; a comunicação com o host é por postMessage, em JSON-RPC, e o app pode chamar ferramentas do servidor.

    Contra o texto, ganha em exploração, formulário e aprovação em lote. Contra o link pra um web app, ganha em contexto (a pessoa não troca de aba nem perde a conversa), em fluxo de dados nos dois sentidos sem construir API e autenticação próprias, e em segurança, porque o iframe isolado deixa o host renderizar app de terceiro sem confiar totalmente no autor. Se nada disso se aplica, o web app comum é mais simples.
