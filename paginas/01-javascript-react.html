JavaScript & React: os modelos mentais

~8h · base pra tudo que vem depois

Você usa hooks corretamente há anos por instinto. Esta semana é sobre nomear por que eles funcionam assim — call stack, closures, e o que realmente acontece quando o React “re-renderiza”. É a pergunta mais comum de entrevista de pleno e a que mais separa quem só usa de quem entende.

    react.dev · oficial
    Resumo aqui na página

    React é UI como função do estado. Componentes são funções puras que descrevem a tela; estado é um snapshot por render; efeitos existem só pra sincronizar com o que está fora do React.

    Describing the UI — componentes, props, listas, pureza
    • Componente é uma função que devolve JSX. Nome com maiúscula (<Perfil />) é componente; minúscula (<div>) é tag do DOM.
    • JSX: um único elemento raiz (ou <>…</>), toda tag fechada, atributos em camelCase (className, onClick). Chaves {} abrem uma “janela” pra JavaScript.
    • Props descem do pai pro filho e são somente leitura. children é só uma prop com o conteúdo aninhado — é o que permite compor layouts sem acoplar.
    • Renderização condicional: cond ? a : b, cond && a ou return null. Pegadinha: {lista.length && <Lista/>} renderiza o número 0 quando a lista está vazia — use lista.length > 0 &&.
    • Listas e key: a key identifica o item entre irmãos. Precisa ser estável e única entre irmãos; não gere com Math.random() no render (remonta tudo todo render) e evite índice quando a lista reordena, insere ou remove.
    • Pureza: mesmo input → mesmo JSX, e nada de mutar variável que existia antes do render. O StrictMode renderiza duas vezes em desenvolvimento justamente pra expor impureza. Efeito colateral vai em event handler; só em último caso em useEffect.
    Managing State — como estruturar estado

    A doc propõe pensar declarativamente: liste os estados visuais possíveis (vazio, digitando, enviando, sucesso, erro), o que dispara cada transição, e só então represente isso com o mínimo de estado. Cinco regras de estrutura que caem em code review sênior:

    1. Agrupe o que sempre muda junto ({x, y} num estado só).
    2. Evite contradições: isSending + isSent permite o impossível “enviando e enviado”. Troque por status: 'typing' | 'sending' | 'sent'.
    3. Evite redundância: se dá pra calcular a partir de props/estado (nomeCompleto), calcule no render.
    4. Evite duplicação: guarde selectedId, não uma cópia do objeto selecionado (que dessincroniza quando a lista muda).
    5. Evite aninhamento profundo: normalize (objeto por id + arrays de ids), como num banco.

    Compartilhar estado = lifting state up: sobe pro ancestral comum e desce por props. Componente controlado recebe o valor por prop; não controlado guarda o próprio.

    Preservar e resetar: o estado mora na posição da árvore, não no componente. Mesmo tipo na mesma posição preserva o estado; tipo diferente destrói; mudar a key força reset (ex.: <Chat key={contatoId} /> zera o rascunho ao trocar de contato).

    Reducer (useReducer) concentra transições num lugar só e precisa ser puro. Context resolve prop drilling, mas antes dele tente passar props ou compor com children. Reducer + Context é o padrão de escala da própria doc.

    Synchronizing with Effects
    • Efeito serve pra sincronizar com sistema externo (conexão, API do navegador, widget não-React). Roda depois do commit na tela.
    • O array de dependências diz com quais valores sincronizar; o React recria o efeito quando algum muda.
    • O cleanup desfaz o que o efeito fez (desconectar, remover listener). Em dev, o StrictMode monta → desmonta → monta de novo pra provar que seu cleanup existe.
    • Buscar dados num efeito exige tratar corrida:
    useEffect(() => {
  let ignorar = false;
  buscar(termo).then(r => { if (!ignorar) setResultado(r); });
  return () => { ignorar = true; };   // resposta antiga chega depois? é descartada
}, [termo]);
    You Might Not Need an Effect — os casos em que NÃO usar
    SituaçãoEm vez de efeito
    Derivar dado pra exibir (filtrar, somar)Calcule no render; useMemo só se for caro
    Resetar todo o estado quando uma prop mudaPasse key
    Ajustar parte do estado quando prop mudaDerive no render (ou guarde o id, não o objeto)
    Lógica causada por um clique/submitNo event handler
    Cadeia de efeitos que se disparamCalcule tudo no handler, numa passada
    Avisar o pai de uma mudançaChame o callback do pai no mesmo handler
    Assinar store externauseSyncExternalStore

    Regra mental: se o código roda porque o usuário fez algo, é handler; se roda porque o componente apareceu na tela e precisa ficar em sincronia com algo externo, é efeito.

    Resumo aqui na página

    Cada render é uma fotografia: tem suas próprias props, estado, handlers e efeitos. useEffect não é ciclo de vida — é sincronização. E dependências mentirosas são a origem de quase todo bug.

    Cada render tem seus próprios valores

    count não é uma variável que “muda”: em cada render ele é uma constante diferente. Quando você escreve setTimeout(() => alert(count), 3000) e clica três vezes rápido, aparecem três alertas com 1, 2 e 3 — cada handler fechou (closure) sobre o count do render em que nasceu. Isso não é bug do React, é JavaScript.

    O mesmo vale pro efeito: a função passada a useEffect é outra a cada render e enxerga os valores daquele render. Se você realmente precisa do valor mais recente dentro de um callback antigo, use um useRef e leia ref.current — sabendo que está saindo do modelo de snapshot.

    Cleanup acontece depois, com valores antigos

    Sequência real ao mudar de id: 10 pra id: 20: o React renderiza a UI com 20, o navegador pinta, então roda o cleanup do efeito anterior (que ainda enxerga 10) e depois o efeito novo (com 20). Por isso o cleanup “sabe” o que desfazer.

    Sincronização, não ciclo de vida

    Pare de perguntar “quando isso roda?” (montagem, atualização). Pergunte “com quais valores este efeito precisa estar sincronizado?”. O resultado deve ser o mesmo se o componente montasse já com os valores finais ou se chegasse neles depois de dez atualizações.

    Não minta sobre dependências
    // bug: count fica congelado em 0, o contador para em 1
useEffect(() => {
  const id = setInterval(() => setCount(count + 1), 1000);
  return () => clearInterval(id);
}, []);

    Duas estratégias honestas:

    1. Incluir a dependência ([count]) — funciona, mas recria o intervalo a cada tick.
    2. Fazer o efeito precisar de menos: setCount(c => c + 1) não lê count, então [] vira verdade. Quando a próxima atualização depende de outro estado ou de props, use useReducer: o efeito só faz dispatch({type: 'tick'}) e o reducer lê o que precisar. dispatch tem identidade estável — o autor chama isso de “modo trapaça” dos hooks.
    Funções como dependência
    • Função usada só pelo efeito → declare dentro do efeito.
    • Função que não usa nada do componente → mova pra fora dele.
    • Função que precisa ser passada adiante e usada em efeitos → useCallback com dependências corretas, e ela entra no array.
    Condição de corrida em fetch

    Requisições não voltam na ordem em que saíram. A flag de cancelamento no cleanup (let didCancel = false) ou um AbortController impede que a resposta velha sobrescreva a nova. O próprio texto já apontava pra onde isso foi: buscar dados em bibliotecas e frameworks (Suspense, React Query, Server Components), não em efeitos escritos à mão.

    Frase de entrevista: “closure obsoleta é o efeito enxergando o snapshot de um render antigo porque o array de dependências mentiu; a correção não é desligar o lint, é fazer o efeito depender de menos”.

  • React as a UI Runtime
    O texto que muda como você enxerga render, reconciliação e efeitos — leitura densa, mas é a que aparece em entrevista de nível sênior.
    Ler trechos · ~40 minDenso demais pra ler linear no primeiro passe. Vá direto nas seções Reconciliation, Inversion of Control, State, Consistency e Hooks. As primeiras seções (Host Tree, Instances, Elements) são vocabulário — passe o olho e siga.
    overreacted.io · Dan Abramov
    Resumo aqui na página

    React é um runtime: você descreve a árvore, ele decide quando chamar seus componentes, compara com a árvore anterior e aplica o mínimo no host (DOM). Quase todo comportamento “estranho” sai dessa inversão de controle.

    Vocabulário (passe rápido)
    • Host tree: a árvore real que o React controla (DOM, views nativas). Host instances: os nós dela.
    • Renderer: quem sabe falar com o host (react-dom, react-native).
    • React element: objeto leve e imutável que descreve um nó ({type: 'button', props: {...}}). Você não muda um element; cria outro.
    Reconciliation

    Ao renderizar de novo, o React compara a árvore nova com a anterior. Regra central: se o tipo (e a key) é o mesmo na mesma posição, reaproveita o host instance e só atualiza props; se o tipo muda, destrói e recria (perdendo estado e foco).

    Por isso condicionais preservam posição: {mostrar ? <Aviso/> : null} deixa um “buraco” no lugar do Aviso, e o <input> seguinte continua sendo o mesmo, sem perder o que foi digitado. Em listas dinâmicas a posição não basta — a key diz que o item é o mesmo mesmo em outra posição.

    Inversion of control

    Você nunca chama Formulario(); você devolve <Formulario/> e o React decide quando chamar. Isso permite:

    • Componentes terem estado local ligado à posição na árvore.
    • O tipo do componente participar da reconciliação.
    • Adiar ou priorizar trabalho (concurrent rendering).
    • Avaliação preguiçosa: <Comentarios/> dentro de uma condição falsa nunca executa.
    Consistency — render vs. commit

    O React separa render (calcular a árvore nova — pode ser interrompido, não deve ter efeito colateral) de commit (aplicar as mudanças no host de uma vez, sem ceder no meio). Assim o usuário nunca vê uma tela meio atualizada.

    State, batching e memoização
    • Vários setState no mesmo evento viram um render (batching). Com o React 18+, isso vale também dentro de promises e timeouts.
    • O React não faz assinatura granular por campo (como sistemas de observables): ele re-renderiza o componente e deixa você otimizar com memo/useMemo. É uma troca deliberada — modelo simples por padrão, otimização onde medir.
    Hooks

    Estado vive numa lista ligada no fiber do componente, indexada pela ordem de chamada. Daí a regra de não chamar hook em condição. Context funciona como escopo dinâmico: o valor vem de quem está acima na árvore no momento do render, não de onde o código foi escrito. Efeitos rodam depois do commit, e custom hooks são só funções que compõem hooks.

    GitHub · acdlite (Andrew Clark, React core)
    Resumo aqui na página

    Fiber é a reimplementação do algoritmo de reconciliação (React 16) cujo objetivo é renderização incremental: quebrar o trabalho em pedaços, pausar, priorizar, retomar ou descartar.

    O problema

    O reconciliador antigo (“stack reconciler”) percorria a árvore recursivamente e não podia parar no meio: uma atualização grande travava a thread principal e engolia frames de animação e digitação. Nem toda atualização tem a mesma urgência — uma animação importa mais que dados que chegaram da rede.

    O que é um fiber

    Uma unidade de trabalho e, ao mesmo tempo, um frame de pilha virtual. Em vez de usar a call stack do JavaScript (que não dá pra pausar), o React mantém sua própria estrutura, que ele percorre num laço e pode interromper quando o frame acabar.

    Estrutura de um fiber
    • type e key — o mesmo papel dos elements; decidem se o fiber pode ser reaproveitado.
    • child, sibling, return — ponteiros que formam a árvore como lista ligada (return é o pai, “pra onde voltar”).
    • pendingProps e memoizedProps — se forem iguais, o trabalho daquele fiber pode ser pulado.
    • prioridade do trabalho pendente (hoje modelada como lanes).
    • alternate — cada fiber tem um par: a árvore current (o que está na tela) e a work-in-progress (o que está sendo calculado). É double buffering: quando termina, troca-se a referência.
    • output / efeitos — o que precisa ser aplicado no host.
    Duas fases
    Render (reconciliação)Commit
    Constrói a work-in-progress, compara, marca efeitosAplica mutações no DOM, roda layout effects e depois efeitos
    Interrompível, pode ser descartada e refeitaSíncrona, não para no meio
    Não pode ter efeito colateralÉ onde efeito colateral acontece
    O que isso destrava hoje

    useTransition/startTransition (marcar atualização como não urgente, que pode ser interrompida por digitação), useDeferredValue, Suspense para dados e streaming de Server Components, e hidratação seletiva. Todos dependem de o render ser pausável.

    Resposta de bolso: “Fiber transformou a renderização numa lista ligada de unidades de trabalho que o React percorre num laço próprio; como não usa a call stack, pode pausar, priorizar e descartar trabalho na fase de render, e só o commit é atômico.”

    developer.mozilla.org · oficial
    Resumo aqui na página

    Uma thread executa seu JavaScript; o trabalho chega por filas; cada tarefa roda até o fim (run-to-completion). Microtasks são drenadas inteiras entre uma tarefa e a próxima.

    As três peças
    • Stack: frames de função em execução. Chamou, empilha; retornou, desempilha.
    • Heap: onde os objetos vivem (região de memória sem ordem).
    • Queue: filas de mensagens/tarefas esperando a pilha esvaziar. (A MDN atual usa o vocabulário da especificação: cada agent tem sua pilha, heap e fila de jobs.)
    O laço
    while (fila.aguardarMensagem()) {
  fila.processarProximaMensagem();   // roda até o fim, sem ser interrompida
}
    Run-to-completion

    Uma tarefa nunca é interrompida por outra. Vantagem: dentro de uma função você não precisa de lock — nada muda seus dados no meio. Custo: uma tarefa longa trava tudo, inclusive a pintura da tela e a resposta a cliques (é daí que vem INP ruim e o aviso “a página não está respondendo”).

    Zero delay não é zero

    setTimeout(fn, 0) significa “enfileire fn assim que possível, depois que a pilha esvaziar”. O atraso é um mínimo, não uma garantia. Navegadores ainda impõem ~4 ms em timers muito aninhados e reduzem timers em abas em segundo plano.

    Microtasks

    Callbacks de Promise (then/await), queueMicrotask e MutationObserver vão pra fila de microtasks, que é esvaziada por completo ao fim de cada tarefa, antes da próxima tarefa e antes de renderizar. Uma microtask que agenda outra microtask também roda antes — dá pra travar a página assim.

    console.log('1');
setTimeout(() => console.log('4'), 0);          // tarefa
Promise.resolve().then(() => console.log('3'));  // microtask
console.log('2');
// 1, 2, 3, 4
    No navegador, entre tarefas: renderização

    Após uma tarefa e suas microtasks, o navegador pode rodar requestAnimationFrame, recalcular estilo, layout e pintar (tipicamente a cada ~16,7 ms numa tela de 60 Hz). Por isso quebrar trabalho em várias tarefas deixa a página responsiva.

    Nunca bloquear

    I/O (rede, timers, eventos) é tratado por callbacks e eventos, então esperar uma resposta não ocupa a thread. Web Workers e iframes têm seus próprios event loops e conversam com postMessage.

Munição da sua entrevista · src/lib/study/scheduler + fluxo de questão

A tela de questão do Gabarita tem um fluxo selecionar → confirmar → corrigir (D85). Isso é uma máquina de estados simples vivendo em useState: cada clique é uma transição, e o React só re-renderiza a alternativa que muda de estado — não a tela inteira. Numa entrevista, é o gancho perfeito pra falar de reconciliação sem decorar teoria solta: você já implementou.

Por que isso importa: entrevistador pergunta “me conta um componente com estado complicado que você fez” — você já tem um exemplo real, não um TodoList de tutorial.

Responda em voz alta · só depois abra o gabarito
  1. Por que console.log dentro de um setTimeout só roda depois que todo o código síncrono termina, mesmo com delay 0?
    ver resposta

    setTimeout não agenda “rode agora”, ele enfileira um macrotask. O event loop só puxa da fila de tarefas quando a call stack está vazia — então delay 0 significa “o mais cedo possível depois que todo o código síncrono terminar”, não “imediatamente”.

    O detalhe que separa a resposta boa da decorada: Promise.then e queueMicrotask vão pra fila de microtasks, que é drenada inteira ao fim de cada tarefa, antes do próximo macrotask. Por isso um .then criado depois de um setTimeout(…, 0) ainda roda primeiro.

  2. O que é uma closure obsoleta (“stale closure”) e como ela se manifesta num useEffect sem array de dependências correto?
    ver resposta

    Uma função criada durante um render captura as variáveis daquele render (escopo léxico). Se o array de dependências não lista o que ela lê, o React não recria o efeito — e ele continua rodando a versão antiga, enxergando o valor congelado no render em que nasceu.

    Caso clássico: useEffect(() => { const id = setInterval(() => setCount(count + 1), 1000); … }, []). O count ali é sempre 0, então o contador trava em 1. Saídas: incluir a dependência, usar a forma de atualização (setCount(c => c + 1)) que não precisa ler o valor, ou guardar o valor mutável num useRef.

  3. Duas listas de itens são iguais, mas você trocou a key de índice pra id. O que muda no re-render, e por quê?
    ver resposta

    A reconciliação compara os filhos posição a posição, casando por (tipo, key). Com key de índice, inserir ou remover no meio desloca todo mundo: o React acha que o item da posição 2 continua sendo “o item 2” e apenas atualiza as props dele — o DOM e o estado interno (texto digitado num input, foco, animação em curso) ficam grudados na posição, não no dado.

    Com id estável, o React reconhece que é o mesmo elemento em outro lugar: move o nó do DOM e preserva o estado do componente. Bônus: trocar a key de propósito é a forma idiomática de resetar um componente.

  4. Por que você não pode chamar um hook dentro de um if?
    ver resposta

    Porque o React não guarda hooks por nome — guarda por ordem de chamada, numa lista ligada pendurada no fiber daquele componente. O primeiro useState do render é o slot 1, o segundo é o slot 2, e assim por diante.

    Um if (ou um return antecipado, ou um loop de tamanho variável) muda essa ordem entre um render e outro: o valor que era do useState vai parar no slot do useEffect, e você recebe estado trocado ou um erro de “rendered fewer hooks than expected”. Não é convenção de estilo, é consequência direta da estrutura de dados.
