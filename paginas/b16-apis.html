B16

Bônus: design de APIs

~6h · o contrato entre front e back — e por que Server Actions meio que evitam ter que desenhar um

REST bem feito, GraphQL, tRPC: três respostas diferentes pra "como o cliente pede dado ao servidor". Cada uma resolve um problema real (over-fetching, tipagem ponta a ponta, cache HTTP) — e cada uma tem um custo que vale saber nomear antes de escolher.

Tópicos

Onde estudar (grátis)

  • Google API Design Guide
    Guia denso e usado como referência de mercado pra REST bem desenhado: recursos, paginação, erros padronizados.
    Ler trechos · ~40 minLeia Resource Oriented Design e Errors. O resto é referência pra quando for desenhar um endpoint específico.
    cloud.google.com · Google
    Resumo aqui na página

    Duas seções: Resource Oriented Design e Errors. A tese é que uma API bem desenhada tem poucos verbos e muitos substantivos: você modela recursos e aplica os métodos padrão sobre eles, em vez de inventar um endpoint por operação.

    Resource Oriented Design
    • Modele recursos (substantivos, no plural) com hierarquia clara: /empresas/{id}/pedidos/{id}/itens. O caminho é o nome do recurso.
    • Os métodos padrão cobrem quase tudo: List, Get, Create, Update, Delete. Só invente um método customizado (:cancelar, :arquivar) quando a ação genuinamente não couber num CRUD — e aí deixe isso explícito no nome.
    • POST /pedidos/123/cancelar é melhor que PATCH /pedidos/123 {status:"cancelado"} quando cancelar dispara efeitos (estorno, e-mail, estoque). O verbo genérico esconde a operação de negócio.
    • Nomes de campo consistentes em todo lugar (created_at sempre, nunca createdAt num endpoint e data_criacao no outro). Consistência vale mais que a escolha em si.
    • Paginação padronizada com page_size e page_token — token opaco, não offset (ver a discussão de cursor no bloco de front-end system design).
    Errors
    • Um formato único de erro pra API inteira: código, mensagem legível e detalhes estruturados. Cliente que precisa de if por endpoint pra entender erro é sintoma de API mal desenhada.
    • O status HTTP faz parte do contrato: 400 malformado, 401 não autenticado, 403 sem permissão, 404 inexistente, 409 conflito, 429 limite, 5xx culpa nossa.
    • Erro de validação precisa dizer qual campo e por quê — mensagem genérica obriga o cliente a adivinhar.
    • Nunca vaze stack trace, SQL ou caminho de arquivo na resposta. Correlacione por um request_id devolvido ao cliente e registrado no log.

    Frase de entrevista: “Eu modelo recurso, uso os métodos padrão e só crio ação customizada quando a operação tem efeito de negócio próprio. E padronizo o formato de erro na API inteira — é o que mais reduz código de tratamento do lado do cliente.”

  • GraphQL — Learn
    Os conceitos centrais: schema, resolver, query vs. mutation, e por que over-fetching/under-fetching motivaram o design.
    Ler trechos · ~30 minLeia até "Schemas and Types" e depois "Execution" (onde entra o N+1). Subscriptions e o resto da referência ficam pra quando for usar de verdade.
    graphql.org · oficial
    Resumo aqui na página

    GraphQL resolve dois problemas do REST: over-fetching (vem mais campo do que se precisa) e under-fetching (precisa de N chamadas pra montar uma tela). Cobra com um custo próprio: cache HTTP deixa de funcionar, e a performance vira responsabilidade sua.

    Schema e tipos
    • O schema é o contrato, tipado e introspectável. Ferramentas, autocompletar no editor e geração de tipos saem dele de graça — é o maior ganho prático do dia a dia.
    • Um endpoint só (POST /graphql) com três operações: query (ler), mutation (escrever, executadas em série) e subscription (tempo real).
    • Nulabilidade explícita (String!) faz parte do contrato — e a propagação de null num campo não-nulo derruba o objeto pai inteiro, coisa que surpreende quem está começando.
    • Versionamento por evolução: em vez de /v2, adiciona-se campo novo e marca-se o antigo com @deprecated. Dá pra medir o uso real de cada campo antes de remover — isso REST não tem.
    Execution — de onde vem o N+1
    • Cada campo é resolvido por uma função. Numa lista de N posts, o campo autor chama o resolver N vezes: 1 query pros posts + N queries pros autores.
    • O problema é estrutural, não um descuido: o resolver não sabe que está sendo chamado em lote. Daí o DataLoader.
    Os custos que a entrevista quer ouvir
    • Cache HTTP não funciona: tudo é POST na mesma URL. O cache migra pro cliente (Apollo, urql, Relay), que normaliza por id — mais poderoso e mais complexo.
    • Consulta maliciosa: aninhamento profundo pode derrubar o servidor. Defesas: limite de profundidade, análise de custo e persisted queries (só consultas pré-aprovadas).
    • Autorização por campo é mais trabalhosa que por rota.
    • Quando REST continua melhor: API pública simples, download de arquivo, e qualquer caso em que cache de CDN seja o que mais importa.

  • DataLoader
    Agrupa (batch) e cacheia buscas feitas no mesmo tick — a correção padrão pro N+1 de resolver GraphQL.
    Ler inteiro · ~15 minREADME curto, com o problema e a solução lado a lado.
    github.com · Facebook
    Resumo aqui na página

    README curto com o problema e a solução lado a lado. DataLoader faz duas coisas: batching (junta as chamadas feitas no mesmo tick do event loop numa consulta só) e caching por requisição (a mesma chave pedida duas vezes vira uma).

    Como o batching funciona
    • Você não passa uma função que carrega um item — passa uma que carrega uma lista de chaves: (ids) => buscarAutores(ids), que vira WHERE id IN (...).
    • O loader acumula as chamadas de .load(id) e dispara a função uma vez, no fim do tick atual do event loop. Os N resolvers viram 1 consulta.
    • A regra que quebra tudo se ignorada: a função de lote deve devolver um array do mesmo tamanho e na mesma ordem das chaves pedidas. Banco não garante ordem de IN — é preciso remapear por id antes de devolver.
    Cache por requisição, não global
    • Crie um loader novo a cada requisição HTTP. Loader compartilhado entre requisições vaza dados entre usuários (dado autorizado pra um aparecendo pra outro) e serve dado velho.
    • O cache é só pra deduplicar dentro daquela requisição. Cache de verdade entre requisições é outra camada (Redis), com invalidação própria.
    • Depois de uma mutação na mesma requisição, chame .clear(id) pra não ler o valor anterior.
    Além do GraphQL
    • O padrão vale pra qualquer lugar onde chamadas individuais possam virar lote: REST chamando um microsserviço, um BFF agregando, um worker processando fila.
    • O nome genérico do padrão é request coalescing — e ele é primo do single-flight que evita cache stampede.

  • tRPC — Concepts
    Como a tipagem viaja do procedimento do servidor pro autocomplete do cliente sem geração de código nem schema separado.
    Ler inteiro · ~15 minPágina curta, conceitual — não precisa instalar nada pra entender a ideia central.
    trpc.io · oficial
    Resumo aqui na página

    tRPC dá tipagem ponta a ponta sem geração de código e sem schema separado: o tipo do cliente é inferido diretamente do roteador do servidor. O preço é que só funciona quando cliente e servidor são TypeScript no mesmo repositório.

    A ideia central
    • Você escreve procedures no servidor (query pra ler, mutation pra escrever) e exporta apenas o tipo do roteador. O cliente importa esse tipo — nada de runtime atravessa.
    • Resultado: renomear um campo no servidor produz erro de compilação no cliente, na hora. É o tipo de erro que, em REST, só aparece em produção.
    • Validação de entrada com Zod é parte da definição da procedure — mesmo schema valida em runtime e tipa o handler.
    Comparação honesta
    tRPCGraphQLREST + OpenAPI
    Tipagem no clienteinferida, zero buildgerada do schemagerada da spec (se houver)
    Cliente não-TSnão serveserveserve
    API públicaruimokmelhor
    Cache HTTPlimitadonãonativo
    Cerimôniamínimaaltamédia
    Quando escolher cada um
    • tRPC: monorepo TypeScript, um produto, time pequeno, velocidade importa. O caso do Next.js com backend próprio.
    • GraphQL: muitos clientes diferentes com necessidades distintas de dado, ou vários times servindo um grafo comum.
    • REST: API pública, integração com terceiros, quando cache de CDN e simplicidade valem mais que tipagem.
    • Vale notar que Server Actions do Next.js ocupam quase o mesmo nicho do tRPC — função tipada chamada do cliente, sem endpoint explícito.

  • MDN — CORS
    O que dispara um preflight (OPTIONS), os headers envolvidos, e a interação entre Access-Control-Allow-Origin e credenciais.
    Ler trechos · ~20 minLeia a visão geral e "Preflighted requests". A lista completa de headers é referência.
    developer.mozilla.org · oficial
    Resumo aqui na página

    CORS é uma regra do navegador, não do servidor: a política de mesma origem impede que um script leia a resposta de outra origem, a menos que o servidor autorize por header. Entender que a requisição é enviada mesmo quando o CORS bloqueia a leitura é o que separa quem sabe de quem chuta.

    Origem, e o que conta como “outra”
    • Origem = esquema + host + porta. https://app.com e https://api.app.com são origens diferentes; http e https também.
    • A restrição vale só pra JavaScript ler a resposta. Imagem, CSS, <script> e envio de formulário sempre cruzaram origem — o que é, aliás, a razão de CSRF existir.
    Preflight — quando e por quê
    • Requisição “simples” (GET/HEAD/POST com Content-Type de formulário ou texto e sem header customizado) vai direto.
    • Qualquer outra — e Content-Type: application/json já basta — dispara um OPTIONS de preflight antes. O navegador pergunta: “posso mandar este método com estes headers?”.
    • O servidor responde com Access-Control-Allow-Origin, -Methods, -Headers, e Access-Control-Max-Age pra o navegador cachear a permissão e não repetir o preflight a cada chamada.
    Credenciais — a parte que mais confunde
    • Pra cookie atravessar: credentials: 'include' no cliente e Access-Control-Allow-Credentials: true no servidor.
    • E aí Access-Control-Allow-Origin: * deixa de ser aceito — é preciso ecoar a origem específica. Se você ecoa dinamicamente, valide contra uma allowlist, senão qualquer site passa a poder chamar sua API com o cookie do usuário.
    • Lembre que SameSite do cookie é uma trava independente: mesmo com CORS liberado, um cookie SameSite=Lax não vai numa requisição entre sites.
    Diagnóstico
    • “Erro de CORS” significa que o servidor respondeu sem o header certo — a requisição saiu e o efeito colateral pode ter acontecido. Não é firewall, não é rede.
    • Erro no preflight e erro na requisição real são causas diferentes: veja qual das duas linhas falhou na aba de rede.
    • Proxy no mesmo domínio (rota /api do seu próprio servidor) elimina CORS por construção — costuma ser a solução mais simples em produção.

  • Stripe — Webhooks
    A referência de mercado pra webhook confiável: verificação de assinatura, retry, e o motivo de idempotência ser obrigatória do lado de quem recebe.
    Ler trechos · ~20 minLeia "Verify signature" e a seção de melhores práticas de recebimento. Você já implementou boa parte disso — é a peça que dá nome ao que já fez.
    docs.stripe.com · oficial
    Resumo aqui na página

    Webhook é a inversão do modelo: em vez de você perguntar, eles avisam. Traz dois problemas que sempre caem em entrevista: como saber que a chamada é legítima e como não duplicar o efeito quando o mesmo evento chega duas vezes.

    Verificar a assinatura
    • O provedor assina o corpo com um segredo compartilhado e manda a assinatura num header, junto com um timestamp.
    • A assinatura é sobre o corpo cru. Se o seu framework já parseou o JSON e você re-serializa, a assinatura não bate — é o erro de integração número um. A rota do webhook precisa receber o body como buffer.
    • Compare com comparação de tempo constante, e rejeite timestamp antigo (defesa contra replay).
    • Sem verificação, o endpoint é uma API pública que qualquer um pode chamar dizendo “este pagamento foi aprovado”.
    Receber bem
    • Responda 2xx rápido e faça o trabalho pesado numa fila. Provedor tem timeout curto; demorar faz ele considerar falha e reenviar — criando exatamente a duplicata que você não quer.
    • Idempotência: grave o event.id com constraint UNIQUE na mesma transação do efeito. A segunda entrega esbarra na constraint e vira no-op.
    • Eventos chegam fora de ordem. Não assuma sequência: use o estado do objeto no evento, ou busque o estado atual na API antes de decidir.
    • Trate evento desconhecido com um 2xx silencioso — o provedor adiciona tipos novos, e falhar neles gera reentrega infinita.
    Operação
    • Assine só os tipos de evento que você usa. Registre tudo que chega (com o id) pra poder auditar e reprocessar.
    • Tenha um caminho de reconciliação: um job periódico que compara o seu estado com a API do provedor. Webhook perdido acontece, e reconciliação é o que impede o divergente de virar permanente.
    • Em desenvolvimento, use o CLI do provedor pra encaminhar eventos pro localhost, em vez de expor um túnel.

Munição da sua entrevista · webhook do Stripe no Gabarita

A D104 (várias assinaturas por usuário) e a fila com SKIP LOCKED (Semana 4) já formam uma resposta completa de "webhook confiável": você verifica assinatura HMAC antes de processar, aceita que o Stripe reentrega em falha (então o handler precisa ser idempotente), e resolve o estado a partir do conjunto de eventos em vez de confiar na ordem de chegada.

Por que isso importa: "desenhe uma API de webhook confiável" é pergunta comum de back-end sênior, e você tem um caso real com bug encontrado e corrigido, não uma resposta de livro-texto.

Responda em voz alta · só depois abra o gabarito
  1. Um app mobile busca uma tela que precisa de dado de 4 endpoints REST diferentes, e cada requisição tem 200ms de latência de rede. Qual padrão reduz isso pra uma chamada?
    ver resposta

    BFF: uma camada fina, específica pro cliente mobile, que já faz as 4 chamadas (ou consultas) no servidor — onde a latência entre elas é baixíssima — e devolve um único payload agregado. O cliente paga 200ms uma vez, não quatro.

  2. Por que GraphQL empurra o problema N+1 pro resolver, e não pro cliente?
    ver resposta

    Uma query pedindo uma lista de posts com o autor de cada um chama o resolver de "autor" uma vez por post por padrão — 1 query pros posts + N queries pros autores. O DataLoader resolve agrupando todas as chamadas de autor feitas no mesmo tick numa única consulta em lote (WHERE id IN (…)), e cacheia dentro daquele request pra não repetir.

  3. Uma requisição fetch de um domínio pra outro, com credentials: 'include' e método PUT, dispara uma requisição OPTIONS antes da de verdade. Por quê?
    ver resposta

    É um preflight: o navegador pergunta ao servidor, antes de mandar a requisição real, se aquele método/headers/origem são permitidos — dispara pra métodos além de GET/HEAD/POST simples, headers customizados, ou uso de credenciais. E com credenciais, Access-Control-Allow-Origin: * não é aceito pelo navegador: o servidor precisa devolver a origem exata mais Access-Control-Allow-Credentials: true.

  4. Um provedor de pagamento reenvia o mesmo webhook duas vezes (a entrega dele é at-least-once). O que garante que seu handler não duplica o efeito?
    ver resposta

    Idempotência do lado de quem recebe: gravar o id do evento com uma constraint UNIQUE na mesma transação do efeito, de forma que a segunda execução esbarre na constraint e vire no-op. Confiar que o provedor "não deveria" reenviar é a causa mais comum de cobrança duplicada em produção — mesmo raciocínio da fila com UNIQUE da Semana 4.
